ESBMC k-path 覆盖率·下篇·插桩、spanning set 评分与验证器语义

2026-05-16

本文是「ESBMC k-path 覆盖率」系列的第 2 篇（共 2 篇）。

  1. 上篇·从分支覆盖到 BMC 可达性检查
  2. 下篇·插桩、spanning set 评分与验证器语义（当前）

上篇讲清楚了 k-path 覆盖率是什么（带“路径深度”旋钮的覆盖率指标）、它在分支覆盖与完全路径覆盖之间的谱系定位，以及为什么能用 BMC 把“goal 是否被覆盖”转成一个 assert(¬witness) 的可满足性问题。本篇接着讲 ESBMC 怎么把它落地、怎么用 spanning set 打分、怎么实战跑一遍，以及最关键的——验证器算出的百分比到底该怎么读。

0.1. 贯穿例子回顾（上篇 §2）

下篇会反复引用上篇那个最小例子，先把它和相关约定原样搬过来，读本篇时手边就有：

  • 两个独立分支点 b₁（a > 0）、b₂（b > 0），共 4 条执行路径：TT、TF、FT、FF（第一位是 b₁ 真假，第二位是 b₂ 真假）。
  • 两组朴素测试 (a=1, b=1)、(a=-1, b=-1) 让分支覆盖到 100%，但只走了 TT 与 FF——TF / FT 没被覆盖。这正是上篇要量化的“分支覆盖盲点”。
  • 上篇 §3.2 已推出：N=2 下这段程序共有 8 个 raw goal（b₁ 处 2 个长度-1，b₂ 处 2 个长度-1 + 4 个长度-2）。下文从这 8 个 raw goal 接着往下讲。

1. 第 5 章 ESBMC 是怎么落地的：插桩算法

ESBMC 把 k-path 覆盖率的插桩工作放在 GOTO 中间表示 (intermediate representation) 上完成。GOTO 是 ESBMC 的所有前端（C、C++、Python、Solidity……）共同的中间语言，把高级语法都已经降到了 标号 + 跳转 的层次：所有的 if、for、while 都被翻译成 IF cond GOTO L 形式的条件跳转。这意味着插桩算法可以语言无关。

1.1. 5.1 算法

下面是核心算法的伪代码（和源码 src/goto-programs/goto_coverage.cpp 中 k_path_coverage() 函数对应）：

每次遇到一个分支点，我们在它前面插入 2^min(|prefix|+1, N) 条 assert，正好对应当前分支点之前 N-1 个决策与当前分支决策的所有组合。

侧栏：实现位置

  • 插桩主循环：src/goto-programs/goto_coverage.cpp，函数 goto_coveraget::k_path_coverage()（约第 341 行起）
  • 命令行解析：src/esbmc/esbmc_parseoptions.cpp（约第 2449 行起）
  • 报告输出：src/esbmc/bmc.cpp，函数 report_coverage()（约第 925 行起）

算法上还有几个工程细节：

  • 化简 (simplification)：witness 在插入前会经过 ESBMC 的表达式化简器。如果化简后是恒真或恒假，就直接丢弃这条 goal——它要么是 tautology（无意义）、要么是结构性矛盾（不可达）。
  • 深度阈值 --k-path-witness-depth：witness 是合取，有些情况下会变得很长。化简后的表达式深度超过阈值的，会被丢弃，避免给后端 SMT 求解器太大的负担。
  • 每函数 goal 上限 --k-path-max-goals：每个函数的 goal 数有上限（默认 10000）；超过时 ESBMC 会主动 abort 并提示用户调大上限或减小 N。

1.2. 5.2 在贯穿例子上走一遍

先讲一个实现选择：ESBMC 在每个 anchor 上只 emit 该处能 emit 的 最长那条 goal。b₁ 上发 2 条长度-1，b₂ 上发 4 条长度-2，跳过 b₂ 的 2 条长度-1。

为什么这么剪？长 goal 一旦覆盖到，短前缀 goal 自动也覆盖了——(a>0) ∧ (b>0) 让 BMC 找出反例的同时，(b>0) 也跟着满足了。spanning set 在 §6.3 评分时也会把这种短前缀 goal 开除。既然反正会被开除，那就别发——少一条 assert 就少一次 SMT 查询。

所以你接下来看到的是 6 条 assert，而不是上篇 §3.2 形式定义里的 8 个 raw goal。把它们和上篇 §3.2 全部 8 个 raw goal 里 没被实现剪枝 的那 6 个对应起来：

在源码哪个位置插入插入的语句对应的 goal
第一个 if 之前assert(¬(a>0))(a>0)
第一个 if 之前assert(a>0)¬(a>0)
第二个 if 之前assert(¬((a>0) ∧ (b>0)))(a>0) ∧ (b>0)
第二个 if 之前assert(¬((a>0) ∧ ¬(b>0)))(a>0) ∧ ¬(b>0)
第二个 if 之前assert(¬(¬(a>0) ∧ (b>0)))¬(a>0) ∧ (b>0)
第二个 if 之前assert(¬(¬(a>0) ∧ ¬(b>0)))¬(a>0) ∧ ¬(b>0)

把整个程序连同这 6 条 assert 一起送进 BMC，多 property 检测引擎会逐一汇报每条 assert 是否能被违反——能违反就表示对应 goal 被覆盖。

本节问题：每个 goal 的“被覆盖”已经能查了，但分母怎么算？是不是有些 goal 是“白送的”？下一章解决。

2. 第 6 章 怎么打分：spanning set

2.1. 6.1 朴素分数的盲点

一句话回答：朴素分数把“白送的”goal 塞进分母，分数虚高，反而把真实漏测遮住。

最直观的覆盖率公式长这样：

拿上篇 §2 程序、N=2、上篇 §3.2 全部 8 个 raw goal 试一下。两组测试：

  • (a=1, b=1)，trace 是 [(b₁, T), (b₂, T)]
  • (a=-1, b=-1)，trace 是 [(b₁, F), (b₂, F)]

逐个 goal 看：

goalwitness谁覆盖了它覆盖？
(b₁, T)a>0第一组✅
(b₁, F)¬(a>0)第二组✅
(b₂, T)b>0第一组✅
(b₂, F)¬(b>0)第二组✅
(b₂, T, T)a>0 ∧ b>0第一组✅
(b₂, T, F)a>0 ∧ ¬(b>0)—❌
(b₂, F, T)¬(a>0) ∧ b>0—❌
(b₂, F, F)¬(a>0) ∧ ¬(b>0)第二组✅

合计 6 / 8 = 75%。

75% 看着挺漂亮。但你知道这组测试对 TF、FT 完全是瞎的：分支组合一半没踩过。75% 在骗你。

骗局藏在哪？看前 4 个长度-1 goal，它们是“白送”的。举一个：

任何让 (a>0) ∧ (b>0) 为真的输入，自动让 (a>0) 也为真。(a>0) 在分母里抬高了基线，却没贡献新信息。4 个长度-1 goal 全是这种“长 goal 一旦真、自动跟着真”的搭便车角色。

这 4 个白送 goal 同时抬高分子和分母，整个比例就稀释了。TF / FT 漏测这件事，从 6/8 = 75% 这个数字里根本读不出来。

修法：把“白送”的从分母踢出去，只留真正“独立”的 goal。这就是 spanning set 干的事。下节给定义。

预告：spanning set 修完之后，同一组测试的分数会跌到 2/4 = 50%。这才是 TF / FT 漏测的诚实反映。§6.5 会把 75% 和 50% 两个数摆在一起读。

2.2. 6.2 Marré-Bertolino 的 spanning set

Marré 和 Bertolino 在 1997 年的 ICST、2003 年完整发表于 IEEE Transactions on Software Engineering 的工作 Using Spanning Sets for Coverage Testing 给出了这个问题的标准解法。核心概念是 包含关系 (subsumption order)：

我们说 goal g 包含 goal g'（写作 g' ⪯ g），当且仅当：每一个能覆盖 g 的测试，自动也能覆盖 g'。

把所有 goal 按这个关系排成一个偏序 (partial order)。它的 极大元 (maximal elements) 集合——也就是不被任何其它 goal 包含的那些 goal——叫作 spanning set。

Spanning set 有一个非常漂亮的性质：

覆盖 spanning set 中的所有 goal ⟺ 覆盖原始 goal 集合中的所有 goal。

（直观证明：spanning set 之外的每个 goal 都被 spanning set 中至少一个 goal 包含，所以覆盖了那个包含者，自动就覆盖了它。）

这意味着 spanning set 才是真正“独立”的覆盖率目标——它把“白送”的冗余去掉了，只留下信息量真正不重复的部分。把覆盖率公式改成：

2.3. 6.3 用到 k-path 上

对 k-path goal，subsumption 有一个简单的结构化近似：把每个 goal 看作它的原子多重集 (atom multiset)，subsumption 用集合包含来判断。

  • goal g' 的原子多重集是 goal g 的真子集 → g 一定 subsume g'（多一个原子就多收紧一层约束）。
  • 没有这种包含关系的 goal 之间互不 subsume，都是 spanning set 的候选极大元。

回到上篇 §2 程序，N=2 下上篇 §3.2 全部 8 个 raw goal 的多重集列出来：

goal原子多重集长度
(b₁, T){a>0}1
(b₁, F){¬(a>0)}1
(b₂, T){b>0}1
(b₂, F){¬(b>0)}1
(b₂, T, T){a>0, b>0}2
(b₂, T, F){a>0, ¬(b>0)}2
(b₂, F, T){¬(a>0), b>0}2
(b₂, F, F){¬(a>0), ¬(b>0)}2

观察：

  • 4 个长度-1 goal 都被某个长度-2 goal 真包含。{a>0} 是 {a>0, b>0} 的真子集；{b>0} 是 {a>0, b>0} 的真子集；另外两个对称。4 个长度-1 全部踢出。
  • 4 个长度-2 goal 的多重集大小都是 2、且两两元素不同，没有任何一对成真子集关系。4 个长度-2 全部保留。

结论：spanning set 大小 = 4，正好是 4 个长度-2 goal。

把整条化简链画出来，三个数字落在三个不同步骤上：

步骤描述goal 数
上篇 §3.2 raw goal形式定义全部 goal8
§5.2 实现剪枝每 anchor 只 emit 最长（本地剪枝）6
§6.3 spanning set多重集真子集判据（定义层去冗余）4

§5.2 的剪枝和 §6.3 的 spanning set 是 两次独立的去冗余：前者只看同一个 anchor 上的最长 vs 较短前缀，是工程层为了少发 SMT 查询；后者看的是定义层所有 goal 的全局偏序，目标是修朴素分数的盲点。两件事各做各的，结果是同一个 spanning set 大小 4。

如果一个测试集把 4 个长度-2 goal 都覆盖到，4 个长度-1 自然白送覆盖。按 spanning set 公式，分数 = 4 / 4 = 100%。

2.4. 6.4 ESBMC 的实现侧栏

ESBMC 的 spanning-set 评分实现在独立的模块 src/goto-programs/k_path_spanning.{h,cpp} 中：

  • 每条插桩的 assert(¬witness) 都把它的原子多重集喂进 add_goal()，并附上消息文本和源码位置。
  • finalize() 一次性计算 spanning set：先按多重集大小升序排，再 O(n²) 两两判断子集关系。为加速，使用了一个 64 位 Bloom 风格的签名做必要条件预过滤——签名不通过就直接跳过深度比较。
  • is_redundant(msg, loc) 给报告层用：JSON 报告里每个 claim 多出一个 feasibility 字段，取值 feasible 或 spanning-set-redundant。

2.5. 6.5 怎么读这个百分比？

公式给完了，数也算完了。但 ESBMC 打出 “100%” 或 “50%” 时，你心里到底该想什么？这一节用三个场景把这件事读熟。

2.5.1. 场景一：在贯穿例子上读

§6.3 算过：N=2 下 spanning set 是 4 个长度-2 goal，对应 (a 真假, b 真假) 的 4 种组合 TT、TF、FT、FF。

先把同一组测试在三种公式下的分数摆在一起。 测试集只用 (1,1) 和 (-1,-1) 两组：

公式分母（goal 数）分子（覆盖到的 goal 数）分数
朴素 + raw goal8（上篇 §3.2 全部 raw）675%
朴素 + emitted6（§5.2 实现剪枝后）467%
Spanning set4（§6.3 极大元）250%

同一个测试集，三个分数。哪个最有用？

75% 在骗你。它把 4 个长度-1 goal 当独立目标塞进分母，分母变大，4 个白送也跟着算分子，比例就被稀释成“看上去够好”。67% 一样毛病，稀释少点而已。

50% 才诚实。它直接告诉你：4 种相邻分支组合，你只测了 2 种。剩下 TF 和 FT 完全没碰。

假如程序里藏着一个 bug，要 a > 0 且 b ≤ 0（也就是 TF）才能触发。75% 让你以为没事，50% 让你立刻知道该补测试。

100% 怎么读。 把测试集补全为 (1,1) (1,-1) (-1,1) (-1,-1)，4 个 spanning goal 全跑到，分数 = 4/4 = 100%。意思是：

在 N=2 这个粒度上，每一对相邻分支的所有真假组合你都测过了。只要 bug 只需要相邻两步配合就能触发，你的测试集就不可能漏掉它。

50% 怎么读。 回到那两组测试。50% 不是某条单独的分支没走到——分支覆盖你已经 100% 了。50% 是说：相邻两步的 4 种组合，你只测了对角线那两种。漏的是 组合，不是 单边。这正好把上篇 §2 末尾埋的“分支覆盖盲点”量化了。

2.5.2. 场景二：把程序拉长到 3 个 if

加一个 if (c > 0)，变成 3 个串联分支点 A、B、C，N 仍然 2。按 §5.2 实现规则（每个 anchor 处只发该处能发的最长 goal），emit 的 goal 这样分布：

anchor该处发出的 goal数量
A（前面 0 个分支）长度-1：A 真、A 假2
B（前面 1 个分支）长度-2：A 真假 × B 真假 共 4 组4
C（前面 2 个分支）长度-2：B 真假 × C 真假 共 4 组4

合计 10 个 emitted goal。spanning set 不是 10。按 §6.3 的“原子多重集 ⊂”判据再过一遍：

  • A 的 2 个长度-1 goal，多重集 {A_T}、{A_F} 是 B 处长度-2 goal 多重集（如 {A_T, B_T}）的真子集。开除。
  • B 处 4 个长度-2 goal 的多重集互不包含。保留。
  • C 处 4 个长度-2 goal 的多重集既互不包含，也不被 B 处的包含（大小相同但元素不同）。保留。

所以 spanning set 大小 = 4 + 4 = 8。

⚠️ 一个常见的栽法：想成“C 是末端分支点、后面再没分支了，所以 C 处的 goal 一定要保留在 spanning set 里”。这条直觉错了。subsumption 看的是原子多重集是不是别人真子集，不看 anchor 在程序的什么位置。C 末端、B 中间、A 起头，对包含关系完全没影响。原子多重集是别人真子集就开除，仅此而已。

2.5.3. 场景三：3-if 程序上 100% 的“视野长度”

把 8 个 spanning goal 全跑到，分数 100%。意思是：

相邻 2 步的真假组合全覆盖了。但 A 和 C 之间隔着 B，长程关联不会被这个分数点名。

假设一条 bug 要“A 真 → B 任意 → C 假”这种跨 3 步的配合才会触发。3-if 程序上的 100% 看上去漂亮，但根本不保证 bug 被踩到。想把长程关联也强制要求，把 N 拧到 3。

2.5.4. 一句话总结：百分比有“视野长度”

k-path 覆盖率的百分比是“在 N 这个视野长度下”的覆盖率。N 多大，“路径上下文窗口”就多长，分数只对这个窗口负责。读 k-path 百分比的时候，N 永远要一起读。

4. 第 8 章 怎么解读验证器算出的 k-path 覆盖率

4.1. 8.1 一个必须先拆掉的思维定式

前面所有关于“百分比怎么读”的叙事都默认了一个 测试统计 语境：你手上有一个测试集，覆盖率 = 这个测试集 碰巧执行到 的 goal 占比。§6.5 场景一就是这么算的——测试集只喂 (1,1) 和 (-1,-1)，4 个 spanning goal 跑到 2 个，50%。这套语境里，覆盖率的全部三条推理是：

  1. 它度量的是 测试集的充分性；
  2. 低分 = 测试集弱 = 那些没被执行的子路径上的 bug 可能被你的测试集漏掉；
  3. 可行动项 = 补测试。

第 7 章你已经看到 ESBMC 跑出来的不是这个语境。ESBMC 不持有任何测试集。它把每个 goal 翻译成 assert(¬witness)（上篇 §4.2），然后让 SMT 求解器 穷举地 去找一个能违反它的输入。上面三条推理一条都不能直接搬过来。 这一章把替代的逻辑链条完整建出来。

4.2. 8.2 语义为什么换了：一步一步推

把验证器模式下每个 goal 的命运拆开看：

  • goal 被 reached = assert(¬witness) 被证伪 = SMT 求解器 构造出了一个具体输入，使这条 length-N 子路径被走到 = ESBMC 证明了这条子路径在分析 bound 内可行。
  • goal not reached = 在 bound 内 assert(¬witness) 无法被证伪 = 不存在任何输入 能让执行走到这条子路径 = ESBMC 证明了这条子路径在 bound 内不可行。

注意第二条。测试统计模式下 “没覆盖到” 是 测试集 的缺陷（换组测试就能补上）。验证器模式下 “not reached” 是 程序自身的性质：求解器已经替你穷举过整个输入空间，它说不可行，就是不存在那样的输入——不是“你还没试到”，是“试遍了，没有”。

由此推出四条 替代推理，逐条对应 §8.1 那三条被推翻的：

(1) 低分 ≠ “可能漏 bug”。 验证器在 bound 内是穷举的，它没漏任何东西。低分的意思是：你语法上枚举出来的 length-N 子路径里，大量根本语义不可行——分支之间高度相关、有互斥状态、有死代码。它度量的不再是测试集，而是 程序的路径可行性结构 / 分支相关性强度。

把 §6.5 那个场景拿来对照，逻辑链条就闭合了：§6.5 里上篇第 2 章程序（两个 独立 if）测试集模式算出 50%，是因为 那两组测试 只打了对角线。换成验证器跑同一个程序（§7.3），打印的是 100%——因为四种组合 TT/TF/FT/FF 全部语义可行，求解器把四个都各自构造出了输入。同一个程序，同一个 spanning set，测试模式 50%、验证器模式 100%，数字相反，因为度量的东西根本不是一回事。 这就是“测试统计的意义不能迁移到验证器”最直接的证据。

那验证器模式什么时候才会低于 100%？必须程序本身有不可行子路径。把上篇第 2 章程序改成分支 相关 的版本（这正是回归测试 k_path_cov_4 的程序）：

N=2 下 spanning set 仍是 4 个 length-2 极大元，但因为 taken == (a>0)，TF（a>0 真却 taken 假）和 FT（a>0 假却 taken 真）这两条子路径 没有任何输入能走到。验证器证明它们不可行，reached = 2，覆盖率 = 2/4 = 50%。这个 50% 不是“测试不够”，是“这个程序在 N=2 粒度上有一半的语法子路径是死的”。可行动项也不再是“补测试”，而是“去看这两条死路是 预期 的（taken 本就该跟 a>0 绑死）还是 意外 的（本想让它们独立、却写错了控制流）”。

(2) 它是任何测试集能达到的覆盖率天花板。 如果你打算拿这些 k-path goal 当测试生成的靶子：验证器算出的 50% 意味着另外 50% 的 maximal goal 物理上不可达，任何测试套件、任何测试生成工具永远到不了。所以验证器模式的百分比是测试充分性的 上界：100% = 理论上存在一个能全打中的测试集；50% = 任何测试套件的天花板就是 50%，分母里那一半是不可达的噪声。

(3) “not reached” 是二义的——这条必须显式声明。 “没被 reach” 真正的含义是「语义不可行 OR 可行但需要超过 --unwind / --k-path-witness-depth 的深度才见证得到」。两种情形 ESBMC 都报成 not reached，无法从百分比本身区分。推论：

  • 验证器 coverage 只有在 bound 饱和（继续加大 --unwind，reached 数不再变）时，才等于真实可行性密度；否则它是真实密度的 下界（低估）。
  • 汇报任何验证器 k-path 百分比时，必须同时声明 bound 以及 bound 是否饱和，否则这个数字不可解释。
  • 若有 solver timeout / unknown，那个 goal 既没证可行也没证不可行，ESBMC 归入 not reached，使指标进一步偏悲观。

4.3. 8.3 N 怎么定才合理：先看单调性

§6.5 已经讲过百分比有“视野长度”。这里补上 N 之间的 单调性，它直接决定 N 该怎么选。

可行性在 N 上向下封闭：一条具体执行路径的任意子段都可行 ⇒ 一条 length-(N+1) 子路径可行 ⇒ 它包含的每个 length-N 窗口都可行。取逆否：某个 length-N 窗口不可行 ⇒ 所有穿过它的 length-(N+1) 路径全部不可行。

由此得到两条 非对称 结论（这正是 N “欺骗性”的本质）：

  • N=2 已经很低 ⇒ N=3 不会更好，且这是结论性的。 N=2 的不可行窗口会“毒化”所有穿过它的更长路径，length-(N+1) 的可行性密度只会持平或更差。低 N 低分是确定的坏消息，不必再往上测就知道程序路径相关性已经很强。
  • N=2 = 100% 完全不代表够好，且这是不可结论的。 所有相邻 2 步组合可行，只说明 相邻两个 决策不互斥；三个连续决策的 联合 相关性（decision i 约束 decision i+2）只有 N=3 才暴露，N=3 可能断崖。§6.5 场景三那个“A 真 → B 任意 → C 假”的跨 3 步 bug 就是这种：3-if 程序 N=2 跑出 100%，N=3 才掉下来。

一句话：低 N 低分 = 结论性（坏定了）；低 N 高分 = 不可结论（必须往上测才敢信）。

所以“合理的 N”不是一个魔数，它绑定到 程序里你关心的最长依赖决策链：

  • 分支大体独立（典型数值计算）→ N=2 就够，再大只是指数膨胀不产新信息；
  • 多阶段校验 / 状态机 / 协议握手（decision i 约束几步之后的 decision）→ N 必须 ≥ 那个依赖跨度，否则那条相关性根本测不到；
  • 上界由资源定：goal 数 ≈ #branches × 2^N 指数爆炸；ESBMC 硬限 N≤30，外加 per-function goal cap（§7.4 --k-path-max-goals）。N 超过 bound 能见证的深度后，not reached 全部由 bound 主导而非程序主导，指标失去意义。

4.4. 8.4 要不要逐步加 N，何时停

要。单个 N 的数字不可独立解读（§8.3），必须扫一条曲线 N → coverage。但扫之前要先警惕一个分母陷阱：

我们只给 spanning set（极大元）打分，而 极大元集合本身随 N 变。所以不同 N 的裸百分比分母不是同一个东西，直接比 N=2 的 50% 和 N=3 的 40% 是误导的。扫 N 时应同时记录两条 绝对 曲线——可行 goal 数 与 maximal goal 总数——看的是“每升一档 N，新增的 maximal 里有多少落进不可行”，而不是百分比本身的升降。

停止准则（满足任一即停）：

  1. Plateau：连续几档 N，绝对可行数 / 绝对 maximal 数两条曲线的斜率稳定 → 程序没有更深的依赖决策结构，再加 N 只是重复计同一批相关性。
  2. Resource wall：goal 数 / solver 时间指数爆炸，或撞到 N≤30 / goal cap / witness-depth cap。越过这条线，指标反映的是 bound 不是程序。
  3. 新增不可行全是“已解释的”：N+1 新冒出来的每个不可行 goal 都对应一条 已知/预期 的相关性（校验通过的 guard、互斥状态），没有 意外 死路 → 再往上只是反复数同一批语义约束。
  4. bound 没跟上 N：N 的意义不能超过 --unwind / --k-path-witness-depth 能具体见证的深度。循环 bound 见证不了 length-N 路径时，加 N 只是把“超出 bound”伪装成“不可行”。要么 N 与 bound 同步抬，要么 N 停在 bound 能饱和见证的深度。

实操上：别读单个数字，读曲线形状。早期陡降 = 强局部分支相关；平缓 = 分支大体独立；在某个特定 N 出现悬崖 = 那里藏着一条 k 步协议 / 校验链——这个“拐点位置”本身就是关于程序结构最有价值的信息，比任何单一百分比都有用。

4.5. 8.5 一次真实的扫描

把上面所有抽象规律压到一个能亲手跑的程序上。它有 3 个分支：b1 测 a>0，b2 测 b>0（与 a 完全独立），b3 测 f==1。关键在 f 只在 b1 的 then 分支里被置 1、且 a 全程不再改写，所以 f==1 恒等价于 a>0——b1 与 b3 是被一个 flag 锁死的同一个决策，中间隔着无关的 b2。这正是 §6.5 场景三“A 真 → B 任意 → C 假”那种跨 3 步关联：

存成 sweep.c，N 从 2 逐档往上扫（程序无循环，--unwind 2 此处不影响结果，bound 天然饱和——§8.2(3) 那条“必须声明 bound 饱和”在这里是满足的，所以下面的百分比就是真实可行性密度，不是 bound 假象）：

三档的真实输出（节选）：

Nk-Path WitnessesSpanning SetReachedk-Path Coverage
21088100%
3148450%
4148450%

逐行读，每一行都钉一条前面的规律：

  • N=2 → 100%。 spanning set 是 8 个 length-2 极大元：(b1,b2) 与 (b2,b3) 各 4 组，相邻两两都独立、全部可行。看着满分。但按 §8.3，这是 不可结论 的高分——它只证明了 相邻 两步不互斥，对跨 3 步的关联一无所知。只扫到 N=2 就收工，你会以为这个 flag 关联不存在或已覆盖。

  • N=3 → 断崖到 50%。 b3 anchor 现在发 length-3 goal {b1,b2,b3} 共 8 组。b1 guard 是 a>0、b3 guard 是 f==1——语法不同（逃过了 §5 的“同原子相反极性”矛盾过滤，所以不会像同名 guard 那样在 emit 前被剪掉），但语义上 f==1 ⟺ a>0，于是 b1 与 b3 必须同真同假。8 组里 b1≠b3 的那 4 组 没有任何输入能走到，验证器逐一证明其不可行 → Reached = 4 → 50%。这 50% 不是“测试不够”（§8.2(1)）：它是验证器证明了“此程序在 N=3 粒度上有一半 length-3 语法子路径是死的”，可行动项是去确认这条 f 关联是 预期 的。

  • 分母陷阱的实例（§8.4）。 注意 N=2 与 N=3 的 Spanning Set 都是 8，但 绝不是同一批 goal——N=2 的 8 是 length-2 极大元，N=3 的 8 是 length-3 极大元（取代了前者）。如果只盯百分比会以为“没变到变”很突兀；盯 绝对 Reached（8 → 4）才看得清：升一档 N，新口径下一半 maximal 落进了不可行。

  • N=4 → 与 N=3 一字不差 → plateau，停。 程序只有 3 个分支，滑动窗口涨不过 3，N=4 emit 的 goal 与 N=3 完全相同。命中 §8.4 停止准则 #1：曲线已平，再加 N 不产新信息，停在 N=3 的结论上。

这条 100% → 50% → 50% 的曲线，比其中任何单独一个数字都有信息量：拐点在 N=3，说明程序里最长的那条 意外 关联跨 3 步；N=4 立刻 plateau，说明没有更深的结构。这就是 §8.4 末尾“读曲线形状、读拐点位置”的字面演示。

5. 第 9 章 小结

把整本讲义拎出一句话总结：

k-path 覆盖率 是一种带“路径深度”旋钮的覆盖率指标，介于分支覆盖（旋钮拧到最小）和完全路径覆盖（旋钮拧到最大）之间。它先把“在每个分支点上覆盖过去 N 个决策的所有组合”作为目标 (goal)，再用 spanning set 评分剔除被白送覆盖的冗余目标，得到一个真正反映路径敏感成色的百分比。

ESBMC 把这套思路自然地嵌进了 BMC 工作流：

  1. goal → witness：把每个 k-path 目标表达成分支决策原子的合取；
  2. witness → assertion：emit assert(¬witness)，让 SMT 求解器替我们生成“覆盖该 goal 的输入”；
  3. scoring：在 GOTO 中间表示上做一次结构化的 subsumption 分析，得到 spanning set 与最终评分。

但务必记住第 8 章那条分界线：ESBMC 是 验证器 不是测试集，它打印的百分比度量的是“程序里 (maximal) length-N 子路径有多少在分析 bound 内 真实可行”，不是测试集充分性。低分意味着分支高度相关 / 有死代码，而不是“测试不够”；这个数字是任何测试套件覆盖率的天花板；“not reached” 二义（不可行 OR 超出 bound），所以汇报时必须连 N 和 bound 是否饱和一起报。

适用场景：

  • 分支组合敏感的小到中型代码（驱动、协议状态机、数据校验逻辑）；
  • 安全敏感、嵌入式或形式化验证已经在路上的项目；
  • 需要在 分支覆盖之上、但又能可控地避免完全路径爆炸 的工程团队。
