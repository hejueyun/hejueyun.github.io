9.1 数据库系统与三级模式

假设银行的柜面程序直接读写磁盘文件：某天运维把客户文件从"按开户日期排序"改成"按客户号建索引"，柜面程序、报表程序、风控程序全都要改代码。数据库系统要解决的正是这件事：让应用只描述"要什么数据"，至于数据怎样存、怎样找，由一个专门的软件统一负责。

几个基本名词。 数据库（DB）是长期存储、有组织、可共享的数据集合。数据库管理系统（DBMS）是管理数据库的软件，例如 MySQL、PostgreSQL、Oracle、SQLite。数据库系统（DBS）是 DB、DBMS、应用程序和数据库管理员（DBA）合在一起的整个系统，考试常写成"DBS 包含 DB 和 DBMS"。DBMS 的基本模块有用户接口、查询处理、查询优化、存储管理，此外还有事务管理和恢复管理。[5]

数据库系统 DBS = DB + DBMS（+ 应用和 DBA）：用户只和 DBMS 打交道

数据模型：从现实到磁盘的三步抽象。 设计数据库是一个逐步抽象的过程。第一步得到概念模型，它只描述"有哪些事物、事物之间有什么联系"，和具体用哪个 DBMS 无关，最常用的表达方式是 E-R 图（9.3 节）。第二步把概念模型转成逻辑模型，也就是 DBMS 能理解的结构。逻辑模型历史上有层次模型（树）、网状模型（图）、关系模型（表）和面向对象模型，今天的主流是关系模型。第三步是物理模型，描述数据在磁盘上怎样组织，这一步由 DBMS 自动完成。

数据库设计是逐步抽象：先画 E-R 图，再转成关系表，最后由 DBMS 决定怎么存

三级模式。 关系数据库把"数据长什么样"分三层描述，每层叫一种模式（schema）。模式只描述结构（"型"），不涉及具体数据（"值"）。

层次别名描述什么一个数据库有几个例子
外模式子模式、用户模式某个用户或应用看到的局部数据多个柜面只看到客户姓名和余额的视图
模式逻辑模式、概念模式全体数据的逻辑结构：所有表、列、类型、约束1 个Student(sno, sname, dept, age)
内模式存储模式数据的物理存储：文件组织、索引、压缩1 个Student 表按 sno 建 B+ 树

两级映像与数据独立性。 三层之间有两道"翻译"：外模式/模式映像，以及模式/内模式映像。当某一层改变时，只要修改对应的映像，相邻层就可以保持原样。

一个数据库只有一个模式、一个内模式，可以有多个外模式；两层映像各自负责一种独立性

我们用两次改动走一遍：

  1. DBA 给 Student 表加一个索引，或者把数据文件搬到新磁盘：内模式变了。DBA 修改模式/内模式映像，模式不变，应用程序当然也不变。这叫物理独立性。
  2. DBA 把 Student 表拆成两张表（例如把联系方式单独成表）：模式变了。DBA 修改外模式/模式映像，让原来的视图仍然拼出同样的列，柜面程序照常运行。这叫逻辑独立性。

要点：

  • 三级模式：外模式（多个）、模式（一个）、内模式（一个）。
  • 标准答案句："模式/内模式映像保证数据的物理独立性；外模式/模式映像保证数据的逻辑独立性。"
  • 记法：物理独立性靠"贴近物理"的那道映像（模式/内模式），逻辑独立性靠"贴近用户"的那道映像（外模式/模式）。
  • 视图对应外模式，索引和存储方式属于内模式。

小结： 数据库系统包括数据库和数据库管理系统；外模式可以有多个，模式和内模式各只有一个；模式/内模式映像保证物理独立性，外模式/模式映像保证逻辑独立性。

9.2 关系模型：关系、码与完整性

有了表，就要回答两个问题：怎样唯一地找到某一行？怎样保证表与表之间的数据对得上（例如选课表里不能出现一个不存在的学号）？前者靠"码"，后者靠"完整性约束"。

关系的形式定义。 域是一组同类型值的集合，例如 D1 = {张, 李}，D2 = {CS, MA, EE}。几个域的笛卡尔积是所有可能的组合，每个组合叫一个元组，元组个数等于各域大小的乘积：2 × 3 = 6。** 关系**是笛卡尔积的一个有意义的子集，写作 R(D1, D2, …, Dn)。在表格里看，关系就是一张表，元组是一行，属性是一列，关系模式 Student(sno, sname, dept, age) 就是表头。[4]

D1={张,李}，D2={CS,MA,EE}：笛卡尔积有 2×3=6 个元组；关系"学生所在系"只取其中 2 个（高亮）

关系有几条基本性质：每一列的值来自同一个域；列的顺序、行的顺序都可以任意交换；任意两个元组不能完全相同（理论上的关系是集合，SQL 的表默认允许重复行，这一点在 9.4 节会再碰到）；每个分量必须是原子值，也就是 1NF。

码（key）。 国内教材多用"码"，与"键"同义。

名词定义在 Student 中
超码能唯一标识一个元组的属性组{sno}、{sno, sname}、{sno, age} ……
候选码能唯一标识元组、而且任何真子集都做不到的属性组，即"最小的超码"{sno}；若规定同系不重名，{sname, dept} 也是
主码从候选码中选定一个，作为这张表的标识sno
主属性出现在某个候选码中的属性sno（若 {sname, dept} 也是候选码，则 sname、dept 也是主属性）
非主属性不出现在任何候选码中的属性age
全码整个属性组才是候选码例如"教师-课程-学生"三者都参与的授课表
外码本表的属性组 F，它对应另一张表（也可以是本表）的主码SC.sno 参照 Student.sno

SC 的主码由两列组成，这两列又各自是外码；外码指向被参照表的主码

完整走一遍：SC 表的码。 SC(sno, cno, grade) 中，一个学生选多门课，所以 sno 会重复；一门课有多个学生，所以 cno 也会重复。只有 (sno, cno) 组合才唯一，并且去掉任何一列都不再唯一，所以 (sno, cno) 是候选码，也选作主码。主码由两列组成完全合法。同时 sno 是参照 Student 的外码，cno 是参照 Course 的外码：一张表可以有多个外码，外码的值可以重复。

三类完整性约束。 DBMS 在每次插入、修改、删除时自动检查这三类规则。

  1. 实体完整性：主码的每个属性都非空，并且主码值唯一。理由是主码用来区分实体，空值意味着"这个实体无法识别"。
  2. 参照完整性：外码的值要么等于被参照表中某个主码值，要么为空（在外码允许为空时）。SC.sno 只能填 Student 中已有的学号。至于 SC 的 sno 能否为空：它同时是主属性，按实体完整性就必须非空。
  3. 用户定义完整性：针对具体业务的规则，例如成绩在 0～100 之间（CHECK）、课程名不重复（UNIQUE）、姓名必填（NOT NULL）。

下面是带约束的建表语句（9.5 节再讲 DDL 语法），以及五次违规操作在 sqlite 中的实际结果：

CREATE TABLE Student (
  sno   TEXT NOT NULL PRIMARY KEY,
  sname TEXT NOT NULL,
  dept  TEXT,
  age   INTEGER CHECK (age BETWEEN 15 AND 60)
);
CREATE TABLE Course (
  cno    TEXT NOT NULL PRIMARY KEY,
  cname  TEXT NOT NULL UNIQUE,
  credit INTEGER
);
CREATE TABLE SC (
  sno   TEXT NOT NULL REFERENCES Student(sno),
  cno   TEXT NOT NULL REFERENCES Course(cno),
  grade INTEGER CHECK (grade BETWEEN 0 AND 100),
  PRIMARY KEY (sno, cno)
);

五个违规操作都被 DBMS 拒绝，报错信息与 practice/ch09_sql.py 中的断言一致

最后一行值得注意：删除被参照的 S1，会让 SC 中 S1 的三条选课记录"悬空"，所以 DBMS 默认拒绝。外码可以声明删除时的处理策略：ON DELETE RESTRICT/NO ACTION（拒绝，默认）、ON DELETE CASCADE（级联删除选课记录）、ON DELETE SET NULL（把外码置空，要求该列允许为空）。

要点：

  • 候选码 = 最小超码；主码从候选码中选一个；主属性是出现在任一候选码里的属性。
  • 实体完整性：主码非空且唯一。参照完整性：外码取被参照主码的值或空。用户定义完整性：NOT NULL、UNIQUE、CHECK、DEFAULT 等。
  • 一张表可以有多个候选码、多个外码，但只有一个主码；主码可以由多列组成。

**代码。sqlite 有一处特殊：外码检查默认关闭，要先执行 PRAGMA foreign_keys = ON。MySQL 的 InnoDB 和 PostgreSQL 默认就会检查外码。[6]

多选 · 理解检查 2　关系 R(A,B,C,D) 只有两个候选码 {A} 和 {B,C}。下列说法哪些正确？

A. 主属性是 A、B、C，非主属性是 D

B. {A,D} 是超码

C. {B} 也是候选码，因为它是 {B,C} 的一部分

D. R 可以同时定义两个主码 A 和 {B,C}

查看答案与每个选项的解析

A · 正确：出现在任一候选码中的属性都是主属性。

B · 正确：包含候选码 A，能唯一标识元组，但它不是最小的，所以只是超码。

C · 错误：候选码要能唯一标识元组；题目给定只有 {A} 和 {B,C} 两个候选码，B 单独做不到。

D · 错误：主码只选一个，另一个仍是候选码，可用 UNIQUE 约束表达。

易错点：

  • 主属性看的是"所有候选码"，只看主码会漏掉。
  • UNIQUE 约束的列可以为空，而且 MySQL、PostgreSQL、sqlite 默认都允许 UNIQUE 列出现多个 NULL（PostgreSQL 15 起可写 NULLS NOT DISTINCT 改变这一点）；要求必填就再加 NOT NULL。
  • CHECK 条件对 NULL 求值得到 UNKNOWN，算作通过，所以 CHECK (grade BETWEEN 0 AND 100) 允许成绩为空。[7]

小结： 超码能唯一区分元组，候选码是最小的超码，主码是从候选码中选定的一个；实体完整性要求主码非空且唯一，参照完整性要求外码的值在被参照表中存在，用户定义的完整性约束业务规则。

9.3 E-R 模型与 E-R 图转关系模式

需求方说："每个系有一位系主任；学生属于某个系；学生可以选多门课，每门课有成绩。"直接动手建表很容易漏掉联系或把属性放错表。E-R 图（实体-联系图）先把这些事实画出来，再按固定规则机械地转成表。

E-R 图有三种元素：

  • 实体（矩形）：可以区分的事物，例如学生、课程、系、教师。
  • 属性（椭圆，本资料的图中画成圆）：实体或联系的特征，例如学号、姓名。实体的码在属性名下加下划线。
  • 联系（菱形）：实体之间的关系，连线上标出类型——一对一（1:1）、一对多（1:n）、多对多（m:n）。

判断联系类型时，我们站在每一端各问一次"一个 A 最多对应几个 B"：一个系有很多学生，一个学生只属于一个系，所以"属于"是 1:n；一个学生选多门课，一门课被多个学生选，所以"选课"是 m:n；一个系只有一位主任，一位教师最多当一个系的主任，所以"管理"是 1:1。

矩形＝实体，圆＝属性，标 ◇ 的圆角框＝联系；连线上的 1、n、m 是联系的类型。"成绩"属于选课联系，而不属于学生或课程

完整走一遍：E-R 图转表。 转换规则只有四条，下面的步骤演示依次应用它们。

E-R 图转关系模式：四个实体、三个联系

1 / 4

第1步 · 规则 1：每个实体变成一张表，实体的码就是表的主码

四张表先各自独立，此时还看不出谁和谁有关系
2 / 4

第2步 · 规则 2（1:1 管理）：把一端的主码放进另一端作外码，并加 UNIQUE

主任工号放进"系"表。UNIQUE 保证一个教师最多当一个系的主任，于是仍是 1:1
3 / 4

第3步 · 规则 3（1:n 属于）：把"1"端的主码放进"n"端作外码

系号放进学生表：每个学生一行，只需记一个系号。放到系表里就要在一格里塞多个学号，违反 1NF
4 / 4

第4步 · 规则 4（m:n 选课）：单独建表，主码 = 两端主码组合，联系属性也放这里

成绩既依赖学生又依赖课程，只能放在选课表；(学号, 课程号) 作主码，两列分别是外码

转换结果：

表主码外码来自
教师(工号, 姓名)工号—实体
系(系号, 系名, 主任工号)系号主任工号 → 教师实体 + 1:1 联系
学生(学号, 姓名, 系号)学号系号 → 系实体 + 1:n 联系
课程(课程号, 学分)课程号—实体
选课(学号, 课程号, 成绩)(学号, 课程号)学号 → 学生，课程号 → 课程m:n 联系

要点：

  • 一个实体转成一个关系模式，实体的码就是关系的码。
  • 1:1 联系：可以并入任意一端，把另一端的码作为外码（加 UNIQUE），联系的属性一起并入；也可以单独成表。
  • 1:n 联系：并入 n 端，把 1 端的码作为 n 端的外码；联系的属性也放在 n 端。也可以单独成表，此时码是 n 端的码。
  • m:n 联系：必须单独成表，码是两端实体码的组合，联系的属性（如成绩）放在这张表里。
  • 三个或更多实体之间的多元联系，也单独成表，码通常是各端码的组合。
  • 计数题公式：n 个实体、若干 m:n 联系、1:1 和 1:n 都并入实体时，最少得到"实体数 + m:n 联系数"张表。本例 4 + 1 = 5 张。

单选 · 理解检查 3　E-R 图中有 3 个实体：员工、部门、项目。员工与部门 n:1（属于），部门与项目 1:n（负责），员工与项目 m:n（参与，带属性"工时"）。1:n 联系都并入 n 端，最少转换成几张表？"工时"放在哪？

A. 4 张；工时放在"参与"表

B. 6 张；每个联系都单独成表

C. 3 张；工时放在员工表

D. 4 张；工时放在项目表

查看答案与每个选项的解析

A · 正确：3 个实体各一张，m:n 的参与单独一张，共 4 张；工时同时依赖员工和项目，只能放在参与表。

B · 错误：1:n 联系可以并入 n 端，题目问的是最少。

C · 错误：m:n 联系必须单独成表；一个员工参与多个项目，有多个工时值，放在员工表违反 1NF。

D · 错误：一个项目有多名员工参与，各自工时不同，项目表放不下。

易错点：

  • 1:n 联系的外码放在"多"的一侧，放到"一"的一侧就要在一格里存多个值。
  • 联系也可以有属性，成绩属于"选课"联系，而不属于学生或课程。

小结： 每个实体转成一张表；1:1 联系可以并入任意一端并加上 UNIQUE；1:n 联系并入 n 端；m:n 联系单独成表，码由两端实体的码组成。

9.4 关系代数：σ、π、⋈、÷ 以及它们对应的 SQL

SQL 告诉数据库"要什么"，DBMS 内部要把它翻译成一串可以执行的运算，这串运算就是关系代数。考试会让你"用关系代数表达查询"，或者反过来"写出与某代数式等价的 SQL"。掌握 σ、π、⋈ 三个记号，就能看懂执行计划里的大多数节点。

关系代数的运算对象是关系，运算结果仍是关系，所以可以层层嵌套。

其中 σ、π、∪、−、× 是五种基本运算，交、连接、除都可以用它们表示，例如 R ∩ S = R − (R − S)。并、差、交要求两个关系"相容"：列数相同，对应列的域相同。

先看 σ 和 π。 σ<sub>dept='CS'</sub>(Student) 横着切，得到 S1、S2 两行；π<sub>dept</sub>(Student) 竖着切，只要 dept 一列，四个值 CS、CS、MA、MA 去重后剩两行。

σ 横着切：σ_dept='CS' 选出第 1、2 行（高亮）；π 竖着切：π_dept 只取 dept 列（描边），去重后剩 CS、MA 两行

SELECT * FROM Student WHERE dept = 'CS';
SELECT DISTINCT dept FROM Student;

关系是集合，所以 π 会自动去重；SQL 的 SELECT 默认保留重复行，要写 DISTINCT 才与 π 完全对应。

完整走一遍：选了"网络"课的学生姓名。 关系代数写法：

π<sub>sname</sub>( Student ⋈ SC ⋈ σ<sub>cname='网络'</sub>(Course) )

画成表达式树，叶子是表，内部结点是运算，数据从下往上流：

  1. 叶子 Course 先经过 σ，只剩 C2 一行。
  2. Student ⋈ SC 按学号连接，得到 7 行（每条选课记录配上学生信息）。
  3. 再与只剩一行的 Course 连接，留下 cno = C2 的两行：S1、S3。
  4. 最后 π<sub>sname</sub> 取姓名：李明、张伟。

把 σ 放在靠近叶子的位置，使参与连接的数据先变少，这就是查询优化中的“选择下推”。DBMS 处理 SQL 的大致流程是：先做语法分析，再翻译成关系代数（查询树），然后按等价规则改写（选择下推、投影下推、调整连接顺序），最后选择具体的算法生成执行计划。对应的 SQL 如下：

SELECT DISTINCT s.sname
FROM Student s
JOIN SC ON s.sno = SC.sno
JOIN Course c ON SC.cno = c.cno
WHERE c.cname = '网络';

除法。 除法回答"……了所有……"一类问题。设 R(X, Y)、S(Y)，R ÷ S 的结果是这样一些 X 值：它在 R 中对应的 Y 值集合（叫 X 的象集）包含了 S 的全部元组。

求选修了全部课程的学生：R = π<sub>sno,cno</sub>(SC)，S = π<sub>cno</sub>(Course) = {C1, C2, C3}。逐个查看每个学号的象集：S1 的象集是 {C1, C2, C3}，包含 S，保留；S2 的象集是 {C1, C3}，缺少 C2；S3 的象集是 {C1, C2}，缺少 C3。结果只有 S1。

SC ÷ π_cno(Course)：每个学号的象集（打勾的课）若包含全部 3 门课就留下；只有 S1 满足

SQL 没有除法运算符，标准写法是"双重否定"：不存在一门课，是这个学生没有选的。

SELECT s.sno, s.sname
FROM Student s
WHERE NOT EXISTS (
  SELECT * FROM Course c
  WHERE NOT EXISTS (
    SELECT * FROM SC
    WHERE SC.sno = s.sno AND SC.cno = c.cno));

读法从内往外：最内层查"学生 s 选了课程 c 吗"；中间层找"s 没选的课"；最外层要求这样的课不存在。另一种常见写法是按学号分组，比较选课门数与课程总数：

SELECT sno
FROM SC
GROUP BY sno
HAVING COUNT(DISTINCT cno) = (SELECT COUNT(*) FROM Course);

两种写法在本例都返回 S1。计数写法依赖一个前提：SC 里的课程号都来自 Course（有外码保证），否则选了一门"表外课程"也会被计数。

集合运算与 SQL。 下面三个查询分别对应 ∪、−、∩，在 sqlite 中的实际结果写在注释里：

SELECT sno FROM SC WHERE cno = 'C1'
UNION
SELECT sno FROM SC WHERE cno = 'C2';
-- 选了 C1 或 C2：S1, S2, S3
SELECT sno FROM Student
EXCEPT
SELECT sno FROM SC;
-- 没有任何选课的学生：S4
SELECT sno FROM SC WHERE cno = 'C1'
INTERSECT

-- 同时选了 C1 和 C3：S1, S2

MySQL 从 8.0.31 起支持 INTERSECT 和 EXCEPT，更早的版本只能改写成 IN / NOT IN 或 EXISTS；PostgreSQL 和 sqlite 一直支持。[8]

要点：

  • 五种基本运算：σ、π、∪、−、×；交、连接、除可由它们导出。
  • 选择对应 WHERE，投影对应 SELECT DISTINCT，连接对应 JOIN，除法对应双重 NOT EXISTS。
  • 笛卡尔积的行数等于两表行数之积，列数等于两表列数之和：Student × Course 有 4 × 3 = 12 行、4 + 3 = 7 列。
  • 查询优化的启发式规则：选择尽早做，投影尽早做，先做小表、选择性高的连接。

**代码。除法的核心只有几行：

def ra_divide(r, s):
    """R(X,Y) ÷ S(Y)：返回那些 X 值，它们在 R 中的象集包含 S 的全部元组。"""
    ra, rt = r
    sa, st = s
    xs = [a for a in ra if a not in sa]
    xi = [ra.index(a) for a in xs]
    yi = [ra.index(a) for a in sa]
    image = {}
    for t in rt:
        image.setdefault(tuple(t[i] for i in xi), set()).add(tuple(t[i] for i in yi))
    return tuple(xs), {x for x, ys in image.items() if st <= ys}

image 把每个 X 值映射到它的象集，最后保留象集包含 S 的那些 X。

9.5 SQL 基础：分类、DDL、DML、单表查询与执行顺序

银行笔试的 SQL 题大多围绕一张表或两张表展开：建表、插入、修改、按条件查询、排序分页。把语句分类和书写模板记牢，再理解"语句按什么顺序执行"，就能自己推出很多规则，例如"WHERE 里为什么不能用 SELECT 中的别名"。

SQL 语句的分类。

教材常分四类；事务控制 COMMIT/ROLLBACK 有时单列为 TCL，有时并入 DCL

DDL：建表、改表、删表。 建表的完整形式已在 9.2 节给出。改表和删表：

ALTER TABLE Student ADD COLUMN phone TEXT;

MySQL 的建表语句常带几个专有选项，笔试和面试都见过：

CREATE TABLE IF NOT EXISTS ticket (
  id         INT UNSIGNED AUTO_INCREMENT,
  title      VARCHAR(100) NOT NULL,
  created_at DATE,
  PRIMARY KEY (id)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;

AUTO_INCREMENT 让主码自动编号；ENGINE = InnoDB 指定存储引擎（支持事务和外码，第 10 章将与 MyISAM 比较）；utf8mb4 能存储表情符号，是 MySQL 8 的默认字符集。sqlite 没有 ENGINE 和 CHARSET，自增写成 INTEGER PRIMARY KEY AUTOINCREMENT；PostgreSQL 写成 GENERATED ALWAYS AS IDENTITY 或 SERIAL。插入两行后，自动编号依次为 1、2。[9]

DML：增、改、删。 三条语句的模板与实际效果：

INSERT INTO Student (sno, sname, dept, age) VALUES ('S5', '孙丽', 'CS', 18);
-- 插入 1 行
UPDATE Student SET age = age + 1 WHERE dept = 'MA';
-- 修改 2 行：S3 年龄 21→22，S4 年龄 20→21
DELETE FROM SC WHERE grade < 70;
-- 删除 1 行：只有 S3-C2 的 60 分小于 70

UPDATE 和 DELETE 都带 WHERE：漏写 WHERE 就会作用于全表。DELETE 逐行删除、可以带条件、可以回滚；TRUNCATE 整表清空、不能带条件，在 MySQL 中会隐式提交，在 PostgreSQL 中可以随事务回滚；DROP 连表结构一起删除。

单表查询的常用条件。

SELECT sname FROM Student WHERE sname LIKE '王%' OR sname LIKE '_明';
-- 李明, 王芳：% 匹配任意多个字符，_ 恰好匹配一个字符
SELECT sno FROM Student WHERE age BETWEEN 19 AND 20 ORDER BY sno;
-- S1, S2, S4：BETWEEN 两端都包含，等价于 age >= 19 AND age <= 20
SELECT sno FROM SC WHERE cno IN ('C2', 'C3') ORDER BY sno, cno;
-- S1, S1, S2, S3：IN 是多个 = 用 OR 连起来

CASE WHEN 按条件给每行算一个新值，从上往下匹配，命中第一个分支就停：

SELECT sno, cno, grade,
       CASE WHEN grade >= 90 THEN '优'
            WHEN grade >= 80 THEN '良'
            WHEN grade >= 60 THEN '及格'
            ELSE '不及格' END AS level
FROM SC
ORDER BY sno, cno;

CASE WHEN 的实际输出：92、90 落入"优"，85、88 落入"良"，其余 3 行落入"及格"；没有低于 60 的成绩，ELSE 分支未用到

逻辑运算的优先级：NOT > AND > OR。 想查"CS 或 MA 系、且年龄大于 20 的学生"，漏写括号会得到不同结果：

SELECT sno FROM Student WHERE dept = 'CS' OR dept = 'MA' AND age > 20;
-- 实际含义 dept='CS' OR (dept='MA' AND age>20)，返回 S1, S2, S3
SELECT sno FROM Student WHERE (dept = 'CS' OR dept = 'MA') AND age > 20;
-- 加括号后只返回 S3

去重与计数。 COUNT(DISTINCT 列) 先去重再计数：

SELECT COUNT(*), COUNT(DISTINCT sno), COUNT(DISTINCT cno) FROM SC;
-- 7, 3, 3：SC 有 7 行，涉及 3 个不同学生、3 门不同课程

排序与分页。 ORDER BY 默认升序（ASC），DESC 为降序，可以按多列排序。分页在三种数据库里写法不同：

SELECT sno, cno FROM SC ORDER BY sno, cno LIMIT 2, 3;
-- MySQL 与 sqlite 写法：LIMIT 跳过行数, 取的行数
SELECT sno, cno FROM SC ORDER BY sno, cno LIMIT 3 OFFSET 2;
-- 标准写法，MySQL、PostgreSQL、sqlite 都支持

MySQL 的 LIMIT 2,3 与标准写法 LIMIT 3 OFFSET 2 相同：跳过前 2 行，取第 3～5 行（下标从 1 数）

第 p 页（从 1 开始）、每页 n 行，写成 LIMIT (p-1)*n, n。例如每页 10 行的第 3 页是 LIMIT 20, 10，返回第 21～30 行。PostgreSQL 只认 LIMIT n OFFSET m；SQL 标准写法是 OFFSET m ROWS FETCH FIRST n ROWS ONLY。

逻辑执行顺序。 一条完整查询的书写顺序是 SELECT、FROM、WHERE、GROUP BY、HAVING、ORDER BY、LIMIT，但 DBMS 按下面的逻辑顺序理解它：

书写顺序是 SELECT…FROM…WHERE…，逻辑执行顺序从 FROM 开始；SELECT 排在第⑤步，所以它起的别名在 WHERE 里还不存在

从这张图可以直接推出三条规则：

  1. WHERE 在 GROUP BY 之前，此时还没有分组，所以 WHERE 里不能用聚合函数，筛选聚合结果要用 HAVING。
  2. SELECT 在 WHERE 之后，SELECT 里起的别名在 WHERE 中还不存在；ORDER BY 在 SELECT 之后，所以 ORDER BY 可以用别名。各数据库在此之外有放宽：MySQL 允许在 GROUP BY、HAVING 中用别名；PostgreSQL 允许在 GROUP BY 中用、HAVING 中不行；sqlite 连 WHERE 都接受别名（实测 SELECT x*10 AS y FROM t WHERE y > 10 能运行）。笔试按标准答：WHERE 不能用 SELECT 别名。
  3. LIMIT 最后执行，所以"先排序再取前几行"总是成立。

这是逻辑顺序，用来确定语义；实际执行时优化器可以重排，只要结果一样，例如把 WHERE 条件下推到连接之前。

四种连接。 把两张表想成韦恩图的两个圆，按 c.id = a.owner_id 能配上的行落在交集里。

  • INNER JOIN（内连接）：只要交集，即配得上的行。
  • LEFT JOIN（左外连接）：交集，加上左表中配不上的行，右表的列补 NULL。
  • RIGHT JOIN（右外连接）：交集，加上右表中配不上的行，左表的列补 NULL。
  • FULL JOIN（全外连接）：交集，加上两边各自配不上的行。

SELECT c.name, a.id
FROM Customer c LEFT JOIN Account a ON c.id = a.owner_id;
SELECT c.name, a.id
FROM Customer c RIGHT JOIN Account a ON c.id = a.owner_id;
SELECT c.name, a.id
FROM Customer c FULL JOIN Account a ON c.id = a.owner_id;

SELECT c.name, a.id
FROM Customer c LEFT JOIN Account a ON c.id = a.owner_id
UNION ALL
SELECT c.name, a.id
FROM Account a LEFT JOIN Customer c ON c.id = a.owner_id
WHERE c.id IS NULL;

SELECT c.name
FROM Customer c LEFT JOIN Account a ON c.id = a.owner_id
WHERE a.id IS NULL;
-- Cy

UNION 与 UNION ALL。 两者都把两个查询的结果上下拼接，要求列数相同、类型兼容。UNION 会去重，UNION ALL 原样保留：

SELECT sno FROM SC WHERE cno = 'C1'
UNION ALL
SELECT sno FROM SC WHERE cno = 'C2';
-- S1, S2, S3, S1, S3 共 5 行；换成 UNION 后只剩 S1, S2, S3

UNION ALL 省掉了去重的排序或哈希，确定没有重复或需要保留重复时优先用它。

NULL 与三值逻辑。 NULL 表示"值未知或不存在"，它既不是 0，也不是空字符串 ''。任何值与 NULL 用 =、<>、<、> 比较，结果都是第三种真值 UNKNOWN。WHERE 和 ON 只保留 TRUE 的行，FALSE 和 UNKNOWN 都被丢掉。判断空值要用 IS NULL / IS NOT NULL。

SELECT NULL = NULL, NULL IS NULL, '' IS NULL, 1 <> NULL;
-- NULL, 1, 0, NULL：NULL=NULL 得 UNKNOWN；空串不是 NULL

三值逻辑的运算：FALSE AND UNKNOWN = FALSE，TRUE OR UNKNOWN = TRUE，NOT UNKNOWN = UNKNOWN，其余与 UNKNOWN 组合都得 UNKNOWN。

聚合函数遇到 NULL。 除 COUNT(*) 外，聚合函数都跳过 NULL：

SELECT COUNT(*), COUNT(balance), SUM(balance), AVG(balance)
FROM Account;
-- 4, 3, 150, 50.0

COUNT(*)=4（数行），COUNT(balance)=3（数非空值），SUM=150，AVG=150/3=50

AVG 的分母是 3 个非空值，结果是 50；若把 NULL 当 0，会算成 37.5。外连接后计数也要小心：

SELECT c.name, COUNT(*) AS n_rows, COUNT(a.id) AS n_acc
FROM Customer c LEFT JOIN Account a ON c.id = a.owner_id
GROUP BY c.id, c.name
ORDER BY c.id;
-- An 2 2；Bo 1 1；Cy 1 0

Cy 没有账户，但左连接为它补了一行 NULL，COUNT(*) 数到 1；COUNT(a.id) 只数非空的账户 id，得到正确的 0。

要点：

  • INNER 只留匹配行；LEFT/RIGHT 保留一侧全部行，另一侧补 NULL；FULL 两侧都保留。
  • 外连接中，右表条件放 ON 表示"参与匹配"，放 WHERE 表示"连接后过滤"，后者会让补 NULL 的行消失。
  • NULL 参与比较得 UNKNOWN，只有 IS NULL 能判断空值。
  • COUNT(*) 数行，COUNT(列) 数非空值；SUM、AVG、MAX、MIN 都忽略 NULL。
  • UNION 去重，UNION ALL 不去重。

9.7 分组与聚合：GROUP BY 把多行压成一行

"每门课有多少人选、最高分多少""平均分 80 以上的学生有哪些"——这类问题都要先把行分成若干组，再对每组算一个统计值。GROUP BY 负责分组，聚合函数负责统计，HAVING 负责按统计结果筛组。

五个常用聚合函数：COUNT（计数）、SUM（求和）、AVG（平均）、MAX（最大）、MIN（最小）。没有 GROUP BY 时，整张表算一组，结果一行；有 GROUP BY 时，分组列取值相同的行归为一组，每组输出一行。

SELECT cno, COUNT(*) AS n, MAX(grade) AS top, MIN(grade) AS low
FROM SC
GROUP BY cno
ORDER BY cno;

按课程分组：每门课一行；n 是选课人数，top/low 是最高、最低分

SELECT 里能写什么。 分组之后，每组只输出一行，所以 SELECT 中的每一项都必须在组内取唯一值。符合这个要求的只有两类：分组列本身，以及聚合函数（或由它们组成的表达式）。上例中 cno 是分组列，COUNT(*)、MAX(grade)、MIN(grade) 是聚合；如果再写一个 sno，C1 组有 S1、S2、S3 三个学号，数据库无法决定输出哪一个。

PostgreSQL 和 MySQL 8（默认开启 ONLY_FULL_GROUP_BY）都会对这种写法报错；sqlite 和关闭该模式的旧版 MySQL 会从组里随便取一行的值，结果不可靠。唯一的放宽是：如果分组列是主码，同表的其他列由它函数决定，PostgreSQL 和 MySQL 允许直接写出。[10] [11]

完整走一遍：WHERE、GROUP BY、HAVING 一起用。 题目："不算网络课（C2），平均分不低于 80 的学生，列出选课门数和平均分，按平均分降序。"

SELECT sno, COUNT(*) AS n, AVG(grade) AS avg_g
FROM SC
WHERE cno <> 'C2'
GROUP BY sno
HAVING AVG(grade) >= 80
ORDER BY avg_g DESC;

按多列分组与 GROUP_CONCAT。 GROUP BY dept, age 按 (dept, age) 的组合分组。MySQL 的 GROUP_CONCAT(列) 把组内的值拼接成一个字符串，例如 SELECT dept, GROUP_CONCAT(sname) FROM Student GROUP BY dept 的结果是 CS 组为“李明,王芳”，MA 组为“张伟,赵敏”（拼接顺序可以在函数内用 ORDER BY 指定）。sqlite 的同名函数 group_concat 用法相同，PostgreSQL 中对应的是 string_agg(sname, ',')。

  • 有 GROUP BY 时，SELECT 中只能出现分组列和聚合函数。
  • WHERE 筛行在分组前，HAVING 筛组在分组后；聚合条件只能写在 HAVING。
  • COUNT(*) 计行数，COUNT(列) 计非空值个数，COUNT(DISTINCT 列) 计不同的非空值个数。
  • 没有 GROUP BY 但用了聚合函数时，全表算一组，结果恰好一行（空表时 COUNT 为 0，SUM、AVG 为 NULL）。

9.8 子查询：非相关、相关与 EXISTS

"年龄大于平均年龄的学生"——平均年龄要先算出来，才能拿每个学生比较。把一个查询嵌进另一个查询，就是子查询。按"内层是否引用外层的列"分为两种，执行方式完全不同。

非相关子查询。 内层独立于外层，可以单独运行，只算一次，结果交给外层使用。

SELECT sno, age
FROM Student
WHERE age > (SELECT AVG(age) FROM Student);
-- 平均年龄 (20+19+21+20)/4 = 20，只有 S3（21 岁）大于 20
SELECT sname FROM Student
WHERE sno IN (SELECT sno FROM SC WHERE cno = 'C2')
ORDER BY sno;
-- 选了 C2 的学生：李明、张伟

第一个是标量子查询，返回一行一列，可以放在比较运算符右边；第二个返回一列多行，配合 IN 使用。写多层嵌套时，先单独运行最内层，确认结果正确，再一层层往外加。

相关子查询。 内层引用了外层当前行的列，所以外层每处理一行，内层就要按这一行的值重新计算一次。题目："找出成绩高于本人平均分的选课记录。"

SELECT sno, cno, grade
FROM SC x
WHERE grade > (SELECT AVG(grade) FROM SC y WHERE y.sno = x.sno)
ORDER BY sno;

内层的 y.sno = x.sno 引用了外层行 x，于是每个学生的"平均分"各不相同：

这里描述的是逻辑语义；优化器常把相关子查询改写成连接或先分组再连接，实际执行未必逐行重算。

EXISTS。 EXISTS (子查询) 只问一件事：子查询有没有返回行。有就为 TRUE，没有就为 FALSE，它从不返回 UNKNOWN。子查询里 SELECT 写什么都行，习惯写 SELECT 1 或 SELECT *。

SELECT sname FROM Student s
WHERE EXISTS (SELECT 1 FROM SC WHERE SC.sno = s.sno)
ORDER BY sno;
-- 有选课记录的学生：李明、王芳、张伟
SELECT sname FROM Student s
WHERE NOT EXISTS (SELECT 1 FROM SC WHERE SC.sno = s.sno);
-- 没有任何选课的学生：赵敏

EXISTS 只问"子查询有没有行"：有就是 TRUE，0 行就是 FALSE；NOT EXISTS 反过来，只留下 S4

NOT IN 遇到 NULL。 找"没有账户的客户"，用 NOT IN 与 NOT EXISTS 结果不同：

SELECT name FROM Customer
WHERE id NOT IN (SELECT owner_id FROM Account);
-- 0 行！
SELECT name FROM Customer c
WHERE NOT EXISTS (SELECT 1 FROM Account a WHERE a.owner_id = c.id);
-- Cy

子查询 SELECT owner_id FROM Account 返回 1、1、2、NULL。对 Cy（id = 3），3 NOT IN (1, 1, 2, NULL) 展开成 3<>1 AND 3<>1 AND 3<>2 AND 3<>NULL，前三项为 TRUE，最后一项为 UNKNOWN，整体是 UNKNOWN，被 WHERE 丢弃。只要子查询结果含一个 NULL，NOT IN 就一行也返回不了。NOT EXISTS 只看"有没有匹配行"，不受影响。要继续用 NOT IN，就在子查询里加 WHERE owner_id IS NOT NULL。

IN 与 EXISTS 怎么选。 两者在没有 NULL 时语义相同。传统经验是"子查询结果小用 IN，外层表小用 EXISTS"；现代优化器（MySQL 8、PostgreSQL）通常会把两者都改写成半连接，性能差别已经不大，以 EXPLAIN 为准。反向查询（"没有……"）优先写 NOT EXISTS，可以避开上面的 NULL 陷阱。

要点：

  • 非相关子查询：内层只执行一次。相关子查询：内层引用外层列，逻辑上外层每行执行一次。
  • EXISTS 只判断有无结果行，只返回 TRUE 或 FALSE。
  • 子查询结果含 NULL 时，NOT IN 返回空集；NOT EXISTS 正常工作。
  • 标量子查询必须只返回一行一列，多行时报错。

查看答案与每个选项的解析

  • 子查询结果可能含 NULL 时，用 NOT EXISTS 代替 NOT IN。

小结： 不相关子查询只执行一次，相关子查询对外层的每一行执行一次；EXISTS 只判断子查询是否返回行；NOT IN 的子查询结果中只要有一个 NULL，整个条件就得不到任何行。

9.9 窗口函数与常见笔试 SQL 题型

"每个部门工资排前两名的员工"——GROUP BY 会把部门压成一行，员工明细就没了。窗口函数在保留每一行的同时，为它计算一个"所在分组内"的统计值或排名，正好解决这类问题。MySQL 8.0、PostgreSQL、sqlite 3.25 起都支持窗口函数。[12] [13]

写法是 函数() OVER (PARTITION BY 分组列 ORDER BY 排序列)：

  • PARTITION BY：把行分成若干"窗口"，函数在每个窗口内独立计算；省略时整张表是一个窗口。
  • ORDER BY：窗口内的排序，决定排名顺序。
  • 三个排名函数在遇到相同值时表现不同：
函数相同值下一名9000, 7000, 7000, 6000 的结果
ROW_NUMBER编号不同连续1, 2, 3, 4
RANK编号相同跳号1, 2, 2, 4
DENSE_RANK编号相同不跳号1, 2, 2, 3

示例： 用 9.6 节的 Emp 表：

SELECT dept, name, salary,
       ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC, id) AS rn,
       RANK()       OVER (PARTITION BY dept ORDER BY salary DESC) AS rk,
       DENSE_RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS drk,
       SUM(salary)  OVER (PARTITION BY dept) AS dept_total
FROM Emp
ORDER BY dept DESC, rn;

PARTITION BY dept 把 IT（4 人）和 HR（3 人）分成两个窗口，各自从 1 开始编号；Ben 与 Cat 同为 7000（黄色），三种排名在这里分道扬镳。7 行明细全部保留

逐列读这张表：

  1. PARTITION BY dept 把 IT 四人、HR 三人分开，每个部门的编号都从 1 开始。
  2. IT 部门中 Ben、Cat 都是 7000。ROW_NUMBER 必须给出不同编号，按 id 排出 2、3；RANK 给两人都是 2，下一个 Dan 跳到 4；DENSE_RANK 也给 2，Dan 接着是 3。
  3. SUM(salary) OVER (PARTITION BY dept) 没有 ORDER BY，计算整个部门的合计：IT 为 9000+7000+7000+6000 = 29000，HR 为 8500+8000+5000 = 21500。每一行都带上了本部门的合计，7 行明细一行没少。

ROW_NUMBER 在并列时谁先谁后取决于 ORDER BY 中的次要排序列，本例加了 id；不加的话，Ben 和 Cat 的先后顺序是不确定的。窗口内加了 ORDER BY 的 SUM 会变成"从第一行累计到当前行"的累计和，这是另一个常考用法。

题型 1：第 N 高的工资。 先对工资去重，降序后跳过 N−1 个：

SELECT (SELECT DISTINCT salary FROM Emp
        ORDER BY salary DESC
        LIMIT 1 OFFSET 1) AS second_salary;
-- 第二高：8500
SELECT MAX(salary) AS second_salary
FROM Emp
WHERE salary < (SELECT MAX(salary) FROM Emp);
-- 另一种写法：比最高工资小的工资里最大的那个，也是 8500

外面再套一层 SELECT (…)，是为了在不存在第 N 高时返回 NULL 而不是空表（这是 LeetCode 176 题的要求）。求一般的第 N 高时，把 OFFSET 写成 N−1：用参数 ? 传入 2 得到第三高的 8000，传入 10 得到 NULL。用窗口函数则写成 DENSE_RANK() = N：

SELECT DISTINCT salary
FROM (SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS drk FROM Emp) t
WHERE drk = 3;
-- 去重后的工资 9000, 8500, 8000, 7000, …，第 3 高是 8000

这里必须用 DENSE_RANK：两个 7000 并列时，第 N 高指的是第 N 个不同的工资值。

题型 2：连续出现至少三次的数字。 Logs 表的 num 按 id 依次为 1, 1, 1, 2, 1, 2, 2：

Logs 按 id 排列：1,1,1,2,1,2,2。数字 1 在 id 1～3 连续 3 次；数字 2 共出现 3 次，但最长只连续 2 次

做法一：自连接三次，要求 id 连续且 num 相同。

SELECT DISTINCT l1.num
FROM Logs l1
JOIN Logs l2 ON l2.id = l1.id + 1
JOIN Logs l3 ON l3.id = l1.id + 2
WHERE l1.num = l2.num AND l2.num = l3.num;
-- 1

做法二：用 LAG 取前一行、前两行的值（LEAD 取后面的行）。

SELECT DISTINCT num
FROM (SELECT num,
             LAG(num, 1) OVER (ORDER BY id) AS p1,
             LAG(num, 2) OVER (ORDER BY id) AS p2
      FROM Logs) t
WHERE num = p1 AND num = p2;
-- 1

两种写法都要 DISTINCT：如果 1 连续出现 4 次，会满足两次条件。自连接写法假设 id 连续无空洞；id 有空洞时，LAG 写法按排序位置比较，更可靠。

题型 3：分组 Top-N。 每个部门工资前两高（相同工资并列）的员工：

SELECT dept, name, salary
FROM (SELECT dept, name, salary,
             DENSE_RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS drk
      FROM Emp) t
WHERE drk <= 2
ORDER BY dept, salary DESC, name;

结果：HR 的 Fay 8500、Eve 8000；IT 的 Amy 9000、Ben 7000、Cat 7000。IT 有两人并列第二，所以返回三人。若要求"每部门恰好两人"，把 DENSE_RANK 换成 ROW_NUMBER。

窗口函数不能直接写在 WHERE 里（它在 SELECT 阶段才计算），所以要先在子查询里算出排名，外层再筛选。没有窗口函数的旧版 MySQL 用相关子查询：比我工资高的不同工资值少于 2 个，我就在前二。

SELECT e1.dept, e1.name, e1.salary
FROM Emp e1
WHERE (SELECT COUNT(DISTINCT e2.salary)
       FROM Emp e2
       WHERE e2.dept = e1.dept AND e2.salary > e1.salary) < 2
ORDER BY e1.dept, e1.salary DESC, e1.name;

9.10 视图、索引、触发器、存储过程与权限

柜员只该看到客户的姓名和余额，看不到身份证号；报表要反复用同一个复杂查询；成绩每次修改都要留痕。这些需求分别由视图、权限、触发器满足；索引则负责让查询变快。

视图。 视图是一个有名字的查询，数据库只保存它的定义，不保存数据；每次查询视图时，DBMS 把它展开成对基本表的查询。所以视图是"虚表"，基本表的数据变了，视图立刻跟着变。

CREATE VIEW cs_student AS
SELECT sno, sname, age FROM Student WHERE dept = 'CS';
SELECT sname FROM cs_student WHERE age >= 20;
-- 李明；把王芳的年龄改成 21 后，再查一次得到李明、王芳

视图是"存起来的查询"，对应外模式；索引是附加在表上的查找结构，对应内模式

视图的三个作用：简化复杂查询；只暴露部分列和行，配合权限实现安全控制；表结构调整后保持旧的查询接口不变，这就是 9.1 节的逻辑独立性。能否通过视图更新数据取决于视图定义：基于单表、不含聚合、DISTINCT、GROUP BY 的视图，MySQL 和 PostgreSQL 一般允许更新；sqlite 的视图只读，要靠 INSTEAD OF 触发器实现更新。物化视图（PostgreSQL 的 MATERIALIZED VIEW）会真正存下结果，需要手动刷新。

索引。 索引是附加在表上的查找结构（多为 B+ 树），用额外空间和写入开销换取查询速度。sqlite 的执行计划直接显示了效果：

CREATE INDEX idx_sc_cno ON SC(cno);
EXPLAIN QUERY PLAN SELECT sno FROM SC WHERE cno = 'C2';
-- 建索引前：SCAN SC ……（扫描）
-- 建索引后：SEARCH SC USING INDEX idx_sc_cno (cno=?)

SC 的主码 (sno, cno) 已有索引，但它先按 sno 排序，单独查 cno 用不上，这与第 10 章联合索引的"最左前缀"规则一致。索引的原理、回表、覆盖索引、EXPLAIN 的 type 等级见第 10 章。

触发器（了解）。 触发器是绑定在表上的一段 SQL，在 INSERT、UPDATE、DELETE 前后自动执行。下面的触发器在成绩被修改后记录日志：

CREATE TABLE grade_log (sno TEXT, cno TEXT, old_grade INTEGER, new_grade INTEGER);
CREATE TRIGGER trg_grade AFTER UPDATE OF grade ON SC
FOR EACH ROW
BEGIN
  INSERT INTO grade_log VALUES (OLD.sno, OLD.cno, OLD.grade, NEW.grade);
END;
UPDATE SC SET grade = 65 WHERE sno = 'S3' AND cno = 'C2';
-- grade_log 中多出一行：S3, C2, 60, 65

OLD 和 NEW 分别表示修改前、修改后的行。触发器适合审计、维护冗余字段，但逻辑隐藏在数据库里，过多使用会让排查变难。

存储过程（简述）。 存储过程是保存在数据库服务器上、带名字和参数的一组 SQL，可以有变量、条件和循环，用 CALL 过程名(参数) 调用。好处是减少网络往返、便于复用和集中授权；缺点是难以调试、和具体数据库绑定。MySQL 用 CREATE PROCEDURE，PostgreSQL 用 CREATE PROCEDURE 或 CREATE FUNCTION。sqlite 是嵌入式数据库，没有存储过程，逻辑写在宿主程序里。

权限：GRANT 与 REVOKE。 自主存取控制用两条 DCL 语句：

GRANT SELECT, UPDATE(grade) ON SC TO wang;               -- 授予查询权和成绩列的修改权
GRANT SELECT ON cs_student TO li WITH GRANT OPTION;       -- li 可以把这个权限再授给别人
REVOKE UPDATE(grade) ON SC FROM wang;                     -- 收回权限
REVOKE SELECT ON cs_student FROM li CASCADE;              -- 连带收回 li 转授出去的权限

U1 拿到"可转授"的权限后再授给 U2、U3；DBA 执行 REVOKE … CASCADE 收回 U1 时，U2、U3 的权限一并收回

权限可以细到列（UPDATE(grade)）；WITH GRANT OPTION 允许被授权者再转授；CASCADE 级联收回转授出去的权限。把视图和 GRANT 组合起来，就能让用户只看到视图对应的行和列。MySQL 中用户写成 'wang'@'localhost'，并且 REVOKE 不支持 CASCADE；PostgreSQL 支持 CASCADE。sqlite 没有用户和权限体系，这四条语句无法在 sqlite 中执行，这里只给出语法。[14] [15]

ORM 与 SQL 注入（补充）。 应用程序常用 ORM（对象关系映射，例如 Python 的 SQLAlchemy、Java 的 Hibernate）把类和对象翻译成 SQL：session.add(Role(name='用户1')) 最终会变成一条 INSERT 语句。ORM 默认使用参数化查询，用户输入作为参数传递，不会被拼接进 SQL 文本，从而避免了 SQL 注入。手写 SQL 时同样要使用占位符（如 sqlite 的 ?）。[16]

要点：

  • 视图是虚表，只存定义；对应外模式，提供逻辑独立性和安全性。
  • 索引加快查询、拖慢增删改、占用空间。
  • 触发器由增删改事件自动触发；存储过程由用户显式调用。
  • GRANT 授权、REVOKE 收回；WITH GRANT OPTION 允许转授，CASCADE 级联收回。

9.11 函数依赖、属性闭包与候选码

把学生、系、课程、成绩全塞进一张大表 R(S, N, D, M, C, G)（学号、姓名、系名、系主任、课程号、成绩），会出现几个麻烦：一个学生选 3 门课，姓名和系主任就存 3 遍（数据冗余）；系主任换人，要改很多行，漏改一行就前后矛盾（更新异常）；新成立的系还没有学生，系主任无处可存（插入异常）；某学生退掉唯一一门课，连带丢掉了他的系信息（删除异常）。要找出问题的根源并系统地拆表，先要能精确描述"哪些属性决定哪些属性"，这就是函数依赖。

函数依赖。 设 X、Y 是关系 R 的属性组。如果 R 的任何合法取值中，两个元组在 X 上相等，它们在 Y 上也一定相等，就说 X 函数决定 Y，记作 X → Y，X 叫决定因素。在 R(S, N, D, M, C, G) 中，业务规则给出：S → N、S → D（一个学号只有一个姓名、一个系），D → M（一个系只有一个主任），SC → G（一个学生的一门课只有一个成绩）。

函数依赖由业务语义决定。表里现有数据恰好没有重名，并不能说明 N → S。

几种依赖的名称：

  • 平凡依赖：Y ⊆ X，例如 SC → S，总是成立，没有信息量。下面讨论的都是非平凡依赖。
  • 完全依赖与部分依赖：X → Y，如果 X 的任何真子集都推不出 Y，就是完全依赖；否则是部分依赖。SC → G 是完全依赖；SC → N 是部分依赖，因为单独 S 就能推出 N。
  • 传递依赖：X → Y、Y → Z，且 Y 不能反推 X，则 Z 传递依赖于 X。S → D → M，所以 M 传递依赖于 S。

R(S,N,D,M,C,G) 的函数依赖：S→N、S→D 只依赖码的一部分（部分依赖），S→D→M 是传递依赖，只有 G 完全依赖整个码 (S,C)

Armstrong 公理。 从已知依赖推出新依赖，只需三条规则（X、Y、Z 都是属性组）：

  1. 自反律：若 Y ⊆ X，则 X → Y。
  2. 增广律：若 X → Y，则 XZ → YZ。
  3. 传递律：若 X → Y 且 Y → Z，则 X → Z。

由它们还能导出三条常用推论：合并律（X → Y、X → Z ⇒ X → YZ），分解律（X → YZ ⇒ X → Y 且 X → Z），伪传递律（X → Y、WY → Z ⇒ WX → Z）。例如已知 A → B、BC → D，用增广律得 AC → BC，再用传递律得 AC → D，这正是伪传递律。Armstrong 公理是正确的（推出的依赖都成立）也是完备的（所有成立的依赖都能推出来）。

属性闭包。 属性组 X 的闭包 X⁺ 是"从 X 出发、按 F 能推出的全部属性"。它是本节所有计算的工具：X → Y 成立，当且仅当 Y ⊆ X⁺；X 是超码，当且仅当 X⁺ 包含全部属性。

求闭包的算法：先令结果 = X；然后反复扫描 F 中的每条依赖 V → W，只要 V 已全部在结果里，就把 W 加进去；扫描一整遍都没有新属性时停止。

def closure(attrs, fds):
    """属性集 attrs 在函数依赖集 fds 下的闭包。"""
    result = set(attrs)
    changed = True
    while changed:
        changed = False
        for lhs, rhs in fds:
            if set(lhs) <= result and not set(rhs) <= result:
                result |= set(rhs)
                changed = True
    return result
变量含义
attrs起点属性组，例如 'ACE'
fds依赖列表，('AB', 'C') 表示 AB → C
result当前已推出的属性集合
changed本轮是否加入了新属性；为 False 就说明到达不动点

按 L、R、LR、N 分类求候选码。 直接枚举所有属性子集太慢。先把每个属性按它在 F 中出现的位置分成四类：

类别出现位置结论
L 类只在依赖左部出现必在每个候选码中（没有任何依赖能推出它）
R 类只在右部出现一定不在任何候选码中
N 类左右都不出现必在每个候选码中
LR 类左右都出现不确定，需要逐个尝试

求解步骤如下：先令 K 为 L 类与 N 类属性的并集，求出 K⁺；如果 K⁺ 已经包含全部属性，K 就是唯一的候选码；否则从 LR 类中按个数从少到多选取属性加入 K，凡是闭包为全集、且不包含已找到的候选码的，就是一个候选码。

继续用 R1：A、E 只在左部，是 L 类；G 只在右部，是 R 类；B、C、D 两边都有，是 LR 类；没有 N 类。

  1. K = {A, E}，(AE)⁺ = {A, E, G}，缺 B、C、D，还要补。
  2. 从 LR 类各取一个试：(ABE)⁺ = {A, B, E, G, C, D}，全了；(ACE)⁺ 前面已算过，全了；(ADE)⁺ = {A, D, E, B, G, C}，全了。
  3. 再取两个的组合都会包含上面某个候选码，不必再试。

所以 R1 有三个候选码：ABE、ACE、ADE。主属性是 A、B、C、D、E，非主属性只有 G。

def candidate_keys(R, fds):
    """L 类和 N 类必在每个候选码中，R 类一定不在；只需在 LR 类里从小到大补属性。"""
    L, Ronly, LR, N = classify(R, fds)
    core = L | N
    if closure(core, fds) >= set(R):
        return [''.join(sorted(core))]
    keys = []
    for k in range(1, len(LR) + 1):
        for extra in combinations(sorted(LR), k):
            cand = core | set(extra)
            if any(set(key) <= cand for key in keys):
                continue                      # 包含已找到的候选码，不是最小的
            if closure(cand, fds) >= set(R):
                keys.append(''.join(sorted(cand)))
    return keys

最小函数依赖集。 同一组约束可以写成很多等价的依赖集，其中"没有任何多余成分"的那种叫最小依赖集 Fm，规范化分解（9.12 节的 3NF 合成）就从它出发。最小依赖集满足三条：右部都是单个属性；左部没有多余属性；没有多余的依赖。求法正好对应这三条：

  1. 拆右部：把 X → YZ 拆成 X → Y、X → Z。
  2. 去左部多余属性：对左部有多个属性的依赖 XB → A，若在当前 F 下 X⁺ 已包含 A，B 就是多余的，化简成 X → A。
  3. 去多余依赖：逐条试删 X → A，若用剩下的依赖求 X⁺ 仍包含 A，这条就是多余的。

def minimal_cover(fds):
    # 第 1 步：右部拆成单个属性
    G = [(l, a) for l, r in fds for a in r]
    # 第 2 步：去掉左部多余属性
    G2 = []
    for lhs, a in G:
        lhs = set(lhs)
        for b in sorted(lhs):
            if len(lhs) > 1 and a in closure(lhs - {b}, G):
                lhs = lhs - {b}
        G2.append((''.join(sorted(lhs)), a))
    G = list(dict.fromkeys(G2))               # 去掉重复的依赖
    # 第 3 步：去掉多余依赖
    i = 0
    while i < len(G):
        rest = G[:i] + G[i + 1:]
        lhs, a = G[i]
        if a in closure(lhs, rest):
            G = rest
        else:
            i += 1
    return G

最小依赖集不一定唯一：尝试删除的顺序不同，可能得到不同但等价的结果。判断两个依赖集是否等价，就看它们能否互相推出。

要点：

  • X → Y 成立 ⇔ Y ⊆ X⁺；X 是超码 ⇔ X⁺ = U；X 是候选码 ⇔ X⁺ = U 且 X 的每个真子集的闭包都不是 U。
  • L 类、N 类属性必在每个候选码中，R 类必不在；L ∪ N 的闭包为全集时，它就是唯一候选码。
  • 最小依赖集三步：拆右部、去左部多余属性、去多余依赖；结果可能不唯一。

单选 · 理解检查 12　F = {AB→C, A→B, B→C, A→C}，它的最小依赖集是哪一个？

9.12 范式与模式分解

上一节的大表 R(S, N, D, M, C, G) 有冗余和三种异常。范式（Normal Form，NF）给出一级比一级严格的"好表"标准；规范化就是通过拆表，把一张低范式的表变成若干张高范式的表，同时保证拆开后既能拼回原数据，又不丢失约束。

四个范式的定义。

范式判定条件（在前一级的基础上）消除了什么
1NF每个属性都是不可再分的原子值一格存多个值、表中套表
2NF每个非主属性都完全依赖于每个候选码非主属性对码的部分依赖
3NF每个非主属性既不部分依赖、也不传递依赖于码非主属性对码的传递依赖
BCNF每个非平凡依赖 X → Y 的决定因素 X 都包含码（是超码）主属性对码的部分依赖和传递依赖

每一级都在上一级基础上再消除一类依赖：BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF

3NF 还有一个便于判定的等价写法：对每个非平凡依赖 X → A，要么 X 是超码，要么 A 是主属性。它和 BCNF 只差"要么 A 是主属性"这半句，所以 BCNF 一定是 3NF，反过来不一定。

1NF 的例子。 学生表中有一列"电话"存着 "138…, 139…" 两个号码，就违反 1NF。修正方法是把电话拆成单独的表 (学号, 电话)，每个号码一行。关系数据库中的表都要求满足 1NF。

判定步骤。 拿到一张表和它的依赖集，按顺序回答四个问题：

  1. 求出全部候选码，分出主属性和非主属性（9.11 节的方法）。
  2. 有没有非主属性只依赖于某个候选码的一部分？有就只到 1NF。
  3. 有没有非主属性依赖于一个"非超码"的属性组（传递依赖）？有就只到 2NF。
  4. 有没有任何非平凡依赖的决定因素不是超码？有就只到 3NF，否则是 BCNF。

完整走一遍：从 1NF 分解到 BCNF。 R(S, N, D, M, C, G)，F = {S → N, S → D, D → M, SC → G}。

  1. S、C 只在左部，是 L 类；(SC)⁺ = {S, C, N, D, M, G}，所以唯一候选码是 SC。主属性 S、C，非主属性 N、D、M、G。
  2. S → N：N 只依赖于码 SC 的一部分 S，部分依赖，R 只属于 1NF。
  3. 把"只依赖于 S"的属性拆出去：学生(S, N, D, M)，码 S；选课(S, C, G)，码 SC。码只有一个属性，学生表不可能再有部分依赖，达到 2NF。
  4. 学生表中 S → D → M，M 传递依赖于 S，只到 2NF。把传递链拆开：学生(S, N, D) 和 系(D, M)。
  5. 检查三张表：学生(S, N, D) 的依赖 S → N、S → D，决定因素 S 是码；系(D, M) 的 D → M，D 是码；选课(S, C, G) 的 SC → G，SC 是码。三张表都是 BCNF。

先按"只依赖 S 的属性"拆出学生表达到 2NF，再把传递链 D→M 拆成系表达到 3NF（这里同时是 BCNF）

拆完以后：系主任只存一次；新系没有学生也能插入系表；学生退课只删选课表的行。四个问题全部消失。

3NF 与 BCNF 的区别：STJ 例。 关系 STJ(S 学生, T 教师, J 课程)，规定每位教师只教一门课（T → J），每个学生的每门课只由一位教师讲授（SJ → T）。

STJ：(S,J)→T，T→J。候选码 SJ 和 ST，三个属性都是主属性，所以满足 3NF；T 不是超码却决定 J，所以违反 BCNF

求候选码：S 只在左部，是 L 类；T、J 两边都出现，是 LR 类；(S)⁺ = {S} 不够；加 J：(SJ)⁺ = {S, J, T}；加 T：(ST)⁺ = {S, T, J}。候选码是 SJ 和 ST，三个属性全是主属性，没有非主属性，因此 STJ 满足 3NF。但 T → J 的决定因素 T 不是超码，违反 BCNF。它仍有冗余：一位教师教 30 个学生，"T 教 J"这件事就重复存 30 遍。

分解的两个要求。 拆表时要同时考虑两件事：

  • 无损连接：把分解后的表自然连接起来，恰好得到原表，不多也不少。
  • 保持函数依赖：原来的每条依赖，都能在分解后的某些表上检查，不需要先连接起来。

对上面的大表用 3NF 合成算法，得到 (D, N, S)、(D, M)、(C, G, S) 三张表；对 STJ 做 BCNF 分解，得到 (J, T) 和 (S, T)；再分别用追踪法（chase）检验无损性，用依赖投影检验是否保持依赖。下面的范式判定函数按 2NF、3NF、BCNF 的顺序依次检查：

def normal_form(R, fds):
    """假定已满足 1NF，返回 '1NF' / '2NF' / '3NF' / 'BCNF' 中最高的一个。"""
    keys = candidate_keys(R, fds)
    prime = set(''.join(keys))
    split = [(l, a) for l, r in fds for a in r if a not in l]
    for key in keys:                          # 2NF：非主属性部分依赖于候选码
        for k in range(1, len(key)):
            for part in combinations(key, k):
                if closure(part, fds) - prime:
                    return '1NF'
    if any(not closure(l, fds) >= set(R) and a not in prime for l, a in split):
        return '2NF'                          # 3NF：决定因素不是超码，且右部是非主属性
    if any(not closure(l, fds) >= set(R) for l, a in split):
        return '3NF'                          # BCNF：每个决定因素都必须是超码
    return 'BCNF'

它判 2NF 的方式是：候选码的任何真子集，闭包里如果出现了非主属性，就存在部分依赖。

要点：

  • 1NF 原子值；2NF 消除非主属性对码的部分依赖；3NF 消除非主属性对码的传递依赖；BCNF 要求每个决定因素都是超码。
  • 判定先求候选码、分主属性和非主属性，再依次查部分依赖、传递依赖、非超码决定因素。
  • 码是单个属性的 1NF 关系必定是 2NF；只有两个属性的关系必定是 BCNF；全部属性都是主属性的关系至少是 3NF。
  • 二元分解无损 ⇔ R1 ∩ R2 → R1 − R2 或 R1 ∩ R2 → R2 − R1。
  • 分解到 3NF 总能同时做到无损和保持依赖；分解到 BCNF 能保证无损，但可能丢依赖。
  • 范式越高冗余越少，但表越多、查询要连接的越多；实际设计常停在 3NF，报表库还会有意"反规范化"。

小结： 1NF 要求属性值是原子的，2NF 消除非主属性对码的部分依赖，3NF 消除非主属性对码的传递依赖，BCNF 要求每个决定因素都是超码；二元分解是否无损，看公共属性能否决定其中一侧；3NF 合成算法能同时保证无损和保持依赖，BCNF 分解可能丢失依赖。

9.13 分布式数据库与数据分片

一家全国性银行的客户数据如果只放在北京的机房，上海的柜台每笔查询都要跨城往返，北京机房一停电全国业务都停。分布式数据库把数据分散到多个场地，同时让用户觉得自己在用一个数据库。这一节的分片运算正好是 σ、π、∪、⋈ 的直接应用。[17] [18]

分布式数据库系统是物理上分散、逻辑上集中的数据库系统：数据存储在由网络连接的多个场地（节点）上，由分布式数据库管理系统（DDBMS）统一管理。与之对照，传统的集中式数据库所有数据都在一个场地。它的优点是性能（就近访问）、可用性（副本）、可扩展性（增减场地）；缺点是系统复杂、维护开销大、需要分布式的并发控制，安全问题也更多。

两大特性：

  • 分布透明性：用户按全局模式写查询，不必关心数据怎样分片（分片透明）、存在哪个场地（位置透明）、有几份副本（复制透明）。分片透明的层次最高。
  • 场地自治性：每个场地的局部 DBMS 能独立决定自己的数据库设计（设计自治）、是否及如何与其他场地通信（通信自治）、以什么方式执行局部操作（执行自治）。只访问本地数据的叫局部应用，访问多个场地的叫全局应用。

模式结构。 国内标准草案把分布式数据库抽象为四层：全局外层、全局概念层、局部概念层、局部内层。全局概念模式经过分片模式（数据怎样切）和分配模式（每片放在哪个场地）映射到各场地的局部模式。这就是在三级模式之上多出的两层映像。

分布式数据库在三级模式之上多了"分片"和"分配"两层，用户看全局模式就像在用一个集中式数据库

分片。 分片是对全局关系的划分，划分出的每一块叫片段。分片必须满足三条原则：

  1. 完备性：全局关系的每一个数据都必须属于某个片段。
  2. 可重构性：所有片段能重新构成全局关系。
  3. 不相交性：水平分片的片段之间没有重复的元组；垂直分片的片段之间除主码外没有重复的属性。

四种分片方式：

方式怎么切关系代数怎么拼回
水平分片按元组，由分片谓词决定σ<sub>谓词</sub>(R)并 ∪
垂直分片按属性，每片都要带主码π<sub>属性</sub>(R)按主码连接 ⋈
导出水平分片按另一个相关关系的分片条件切半连接并 ∪
混合分片先垂直再水平（或反之）组合先并后连接

水平分片按行切（σ），用 UNION 拼回；垂直分片按列切（π，每片都带主码 sno），用连接拼回；虚线是分配到场地

用学生表验证一遍（在 sqlite 中执行，重构的结果与原表完全相同，两个水平片段的交集为空）：

CREATE TABLE Student_CS AS SELECT * FROM Student WHERE dept = 'CS';
CREATE TABLE Student_MA AS SELECT * FROM Student WHERE dept = 'MA';
SELECT * FROM Student_CS
UNION ALL
SELECT * FROM Student_MA;
CREATE TABLE Student_V1 AS SELECT sno, sname FROM Student;
CREATE TABLE Student_V2 AS SELECT sno, dept, age FROM Student;
SELECT v1.sno, v1.sname, v2.dept, v2.age
FROM Student_V1 v1 JOIN Student_V2 v2 ON v1.sno = v2.sno;

水平分片的完备性可以用谓词证明：按部门 Dno 把员工分成三片 Dno = 201、Dno = 202、Dno ≠ 201 且 Dno ≠ 202。第三个谓词正好是前两个谓词之并的否定，三个谓词的析取恒为真，所以任何元组都会落到某一片中，满足完备性。设计水平分片的步骤是：找出一组完备且最小的简单谓词（只含一个比较，如 SAL > 30000）；把它们组合成小项谓词（多个简单谓词的合取，如 TITLE = '工程师' ∧ SAL > 30000）；删去没有意义（恒假或无数据）的小项。

分配。 片段到场地的映射叫分配。每个片段只存一个场地叫非复制分配（全分割式）；每个场地都存全部片段叫全复制；部分片段存在部分场地叫部分复制。复制能就近读取、提高可用性和均衡负载，代价是每次更新都要同步所有副本，一致性维护成本上升。设计分布式数据库通常采用自顶向下（从需求、概念设计到分片和分配，适合新建系统）或自底向上（把已有的多个数据库集成起来）两种策略。

分类（了解）。 按分布性、异构性、自治性三个维度区分。数据、数据库系统或平台不同叫异构；按自治程度从低到高有集中式系统、联邦式系统、多数据库系统。体系结构上，应用处理器（AP）处理访问多个场地的请求，数据处理器（DP）相当于局部 DBMS，通信管理器（CM）负责场地间通信。

要点：

  • 分布式数据库：物理分散、逻辑集中；两大特性是分布透明性（分片、位置、复制透明）和场地自治性。
  • 分片三原则：完备性、可重构性、不相交性。
  • 水平分片用 σ、用并重构；垂直分片用 π、必须带主码、用连接重构。
  • 分配方式：非复制、全复制、部分复制；复制提高可用性和读性能，增加更新代价。

单选 · 理解检查 15　把 Emp(eno, ename, salary, dno) 垂直分片为 E1 = π_{eno,ename}(Emp) 和 E2 = π_{salary,dno}(Emp)。这个设计违反了哪条原则？

A. 可重构性：E2 没有主码 eno，无法与 E1 连接还原

B. 完备性：有属性没有被分进任何片段

C. 不相交性：两个片段有重复属性

D. 没有违反任何原则

查看答案与每个选项的解析

A · 正确：垂直分片的每个片段都要带主码，重构时按主码连接；E2 缺 eno，薪水和部门对不上是谁的。

B · 错误：eno、ename、salary、dno 四个属性都出现在某个片段中。

C · 错误：E1、E2 没有重复属性；即使重复的是主码，也是允许的。

D · 错误：E1 ⋈ E2 没有公共属性，结果是笛卡尔积，无法还原原表。

易错点：

  • 垂直分片的每个片段都要保留主码，主码重复出现是允许的。
  • 复制提高的是读性能和可用性，写入时要同步更新所有副本。

小结： 分布式数据库在物理上分散，在逻辑上集中；分片透明性是最高级别的透明性；分片要满足完备性、可重构性和不相交性；水平分片用选择得到，用并操作重构，垂直分片用投影得到，每个片段都带上主码，用连接操作重构。
