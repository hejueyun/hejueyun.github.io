1　会话日志：一切从日志派生

1.1　只追加的事件日志

会话里发生的每件事都按顺序记进一份只能往后添、不能改的日志，模型看到的历史从这份日志里算出来。

可以把它想成记账。账本只往后写新的一行，写错了也不涂改，而是再写一行更正（会计上叫「冲正」）。日志里的每一条叫一个事件，带一个连续的序号。

写入只有一个入口。每次追加，它做三件事：

  • 给要写的内容拍一张快照，并冻结成只读，之后谁也改不了；
  • 检查内容是「无损 JSON」，也就是存成 JSON 再读回来，必须和原来一模一样。有些值做不到这一点，比如超大整数、自己引用自己的对象、带空洞的数组、负零。这些值在追加的那一刻就被拒绝，而不是等到写文件时才出错；
  • 通知订阅者。负责落盘（把内容写进磁盘上的文件）的插件就是订阅者之一，它把事件写进一个 JSONL 文件，即每行一条 JSON 记录的文本文件。

拍快照（也就是把内容复制一份）和检查，是在同一遍遍历里同时完成的。README 解释了原因：有些对象的属性是读取时现算的，两次读可能得到不同的值。如果先检查、再复制，检查通过的和最后存下来的就可能不是同一个东西。

事件的种类很多：一轮开始、一步结束这类边界记录，工具调用这类执行记录，压缩开始这类插件自己的记录，还有请求快照。其中只有五种会变成模型看到的消息：系统提示词、开发者消息、用户消息、模型回复、工具结果。

日志里的一段事件，下方数字是序号。高亮的会变成模型看到的消息；其余只是记在日志里的事实，用来重放、诊断和给界面展示

1.2　模型看到的是一张序号清单

日志永远只往后添；「替换」某条消息，实际是在一张序号清单上换掉一段指向，原来的事件仍然留在日志里。

问题是：日志不能改，可压缩、截断长输出都需要「把旧消息换成新的」。DSH 的办法是在日志之外再维护一张清单，叫 surface（可以理解为「模型眼前的那一面」）。它只是一个序号数组：按模型看到的顺序，列出当前有效的那些消息的序号。

五种消息事件追加时，都必须说明自己怎样改这张清单，只有两种选择：

  • 接到清单末尾；
  • 替换清单上从某个序号到某个序号的一段。

看一个例子。第 4 号事件是一条 30 万字的测试输出，后来要把它换成截断版：

第 6 号事件声明"替换清单上的第 4 号"。日志里第 4 号仍在，只是清单不再指向它

替换是有规矩的。下面每条检查失败都会直接报错，这次追加不生效：

规则防的是什么

从头回放整份日志，就能算出当前的清单；运行中则边追加边更新。按清单把事件变成消息，冻结后缓存起来，就是上一篇第 5.4 节里「从日志现算出来的消息列表」。

1.3　为什么要绕这一圈

绕这一圈换来的是：发给模型的每一个请求都能从日志精确重建。

直接在内存里维护一个消息数组显然更简单。但那样的话，「模型当时到底看到了什么」就只能靠猜。README 把 DSH 的原则叫作「模型可见即已记录」。

除了消息，请求里的其他部分也记在日志里。有一种叫「请求头」的事件（和 HTTP 请求头无关），保存请求里消息以外的部分：调用配置、适配器的默认值、组装好的工具说明。循环每次启动、这些内容每次变化，都写一份新的，用的时候取最近的一份。系统提示词不在请求头里，它是清单的第一条。

有了这些，几种看起来不相关的功能就走同一条路：

  • 恢复：重新打开 JSONL 文件，回放出同样的清单和请求头；
  • 分叉：复制一段事件前缀，作为新会话的开头；
  • 调试：回放到某一个序号，就是模型当时看到的全部内容。

1.4　崩溃后的修补

进程崩溃会在日志里留下「有调用、没结果」的半截记录；恢复时补一条结果，并且如实告诉模型这次调用到底有没有开始。

模型的工具调用和结果必须成对出现，大多数模型服务看到一个没有结果的调用会直接报错。设想进程在执行 rm 时被杀，日志里就只有调用，没有结果。

恢复会话时，修补程序扫描最后一个没有关闭的步，给缺结果的调用补一条错误结果，再关闭这一步和这一轮。补什么，取决于日志里有没有「工具已开始」的记录：

恢复时给缺结果的调用补的两种结果

第二种情况（日志里有「工具已开始」，却没有结果）补的那句话值得注意：「只读或幂等的可以重试；可能有副作用的先核实或者问用户。不要盲目重试」。幂等的意思是做一次和做两次效果一样，比如「把文件内容设为 X」；「给账户转 100 元」就不是。一条 rm 或者一次数据库写入，可能已经执行完了，只是结果没来得及落盘。修补程序不替模型判断该不该重试，而是把「结果未知」如实告诉它，同时给出判断的依据。可靠篇会在自己写的 harness 上复现这种恢复。

2　工具：一次调用要过几道关

2.1　定义一个工具

一个工具就是「名字、说明、参数格式、执行函数」四样东西；注册之后，它自动出现在模型的工具列表和系统提示词里。

README 里的示例是一个读文件的工具：

逐行看：第一行把工具登记到工具注册表；name 和 description 是模型看到的名字和说明；parameters 规定参数的格式，这里路径必填，起始行和行数可选；execute 是真正干活的函数，它收到参数和一个「取消信号」，再把信号转交给读文件的操作。示例里还有一项输出声明，规定结果的类型和怎样显示，这里略去了。

有两点要注意。

第一，出错不会结束这一轮。参数在执行前按格式检查，不合格就变成一条普通的错误结果。调用了不存在的工具、工具执行时抛了异常，也一样。模型看到的是「Error: 原因」，可以自己纠正后再试。

第二，取消要工具自己配合。用户按了取消，框架只是把取消信号置上，工具必须自己去看这个信号，及时停下。如果取消发生在工具开始之前，结果是「开始前就被取消」；如果发生在开始之后，只有本来会「成功」的结果才被改写成「被取消」，失败、超时这些更具体的结果保持原样。

2.2　执行管线

每次调用都走同一条管线：先问能不能执行，再执行，再处理结果；每一关都留了让插件插手的口子。

一次工具调用的完整管线。前两关都管"能不能执行"，但分工不同

预检和守卫这两关都管「能不能执行」，分工最有讲究。

预检是执行前的第一道检查，由若干个插件一起把关，比如用户的权限设置（「读文件不用问」）。它用的是上一篇第 4 节讲的 waterfall 派发：这些插件一层套一层，每一层都可以放行、拒绝、取消，也可以要求「问人」，外层还能改掉里层的结论。预检只给出「要问人」这个结论，真正去问、等回答，是审批服务的事（4.2 节）。如果组合里没有审批服务，「问人」一律按拒绝处理。

守卫在预检之后。守卫是一个简单的函数：返回一个理由就是拒绝，什么都不返回就是不表态。README 用的词是「单调」：一旦有守卫拒绝，后面谁也不能把它改回允许。

为什么要分两层？举个例子。用户在设置里允许 agent 不经询问就删除文件，这条策略放在预检里，别的插件可以调整它。但部署方（比如公司的运维）规定「任何情况下都不许碰系统目录」，这条底线就该放在守卫里，用户的设置、别的插件都推翻不了。

还有一个刻意的限制：预检不能改写参数。README 的理由是：一旦改了，日志里记的参数、界面上显示的参数、实际执行的参数就会对不上。

2.3　并行还是独占，由写工具的人说了算

一个调用能不能和别人同时跑，只由工具自己的声明决定，别的插件插不上手。

上一篇第 5.5 节讲过调度：工具声明了「并发安全」并且对这组参数回答「是」，才能并行，其他一律独占。README 的「已知限制」里补了一句：这个判断不经过任何事件，而是直接读工具的定义；插件只能给自己的工具声明，不能替别人的工具做主。换句话说，并发安全由写工具的人负责。

2.4　给某个 agent 隐藏一部分工具

工具注册表可以给某个 agent 套上「掩码」，也就是一份规定它能用哪些工具的过滤规则；子 agent 只拿到一部分工具，就是这样做到的。

可以给某一个 agent 套一个掩码，规定它允许或禁止哪些工具。套了多个掩码时取交集，即只剩每个掩码都允许的工具。agent 被销毁时，掩码自动解除。这个 agent 自己注册的工具不受影响。

多个掩码依次过滤，剩下的就是每个掩码都允许的工具，即取交集（例子里的工具和掩码是假设的）

被隐藏的工具，连说明都不发给模型，所以也不占上下文。

2.5　让模型写程序来调工具

有一种模式下，模型只拿到一个「运行代码」工具，它写一段程序，在程序里调用其他工具，一次跑完。

问题是往返次数。一个小任务要十几次工具调用，按普通方式，每次调用都要回到模型一趟：模型提出调用，外壳执行，结果塞回上下文，模型再提下一个。十几趟下来又慢，中间结果又全堆在上下文里。

这个模式（PTC，「用程序调工具」）下，模型看到的只有一个「运行代码」工具，外加一段自动生成的接口声明（TypeScript 或 Python，看装了哪种运行时）。模型写一段程序，在程序里依次调用读文件、执行命令等工具；几个只读调用还可以并发。

一次往返完成十几次工具调用；每次子调用仍然走完整的管线，审批和守卫一个不少

程序里的每一次子调用照样走上一节那条管线，审批和守卫一个都不少；只有程序最后打印或返回的内容进入对话。代价是：中间值只存在于执行过程中，不在日志里，事后不能重放。

3　上下文压缩

3.1　什么时候触发

每一步调模型之前量一下对话有多长，超过阈值就压缩；模型服务报「太长了」时，再做一次尽可能大的压缩然后重试。

上下文窗口是模型一次能看的最大长度，用 token 计（token 是模型计数文字的单位，按序章（中）的实测，中文 1 个字大约合 0.7 到 1 个 token）。对话一长，迟早会装不下。压缩插件在两个地方插手：

  • 每一步开始前（上一篇第 5.2 节），量一下当前清单加上请求头（1.3 节）一共多少 token，超过阈值就先压缩；
  • 模型服务明确回答「上下文超长」时，不管平时的阈值，做一次尽可能大的压缩，然后要求重试。只有清单真的被替换过，才允许重试；否则原样重发同一个超长请求，只会再失败一次。

阈值的默认算法写在 README 里。设窗口为 $W$，这次请求最多输出 $O$ 个 token，再留出余量 $B = 65536$（留给压缩时写摘要的那次模型调用，见序章（中）3.1 节）：

$$
\text{阈值} = \lfloor \min(0.8 W,\ W - O - B) \rfloor
$$

也就是取「窗口的八成」和「窗口减去输出、再减去余量」两者中较小的一个。代入几个数看看（$O$ 都取 8,000，数字是为了演示）：

压缩时，最近的一段原样保留，长度是 $(W - O)$ 的 16%。按上表第二行算，大约是最后 19,200 个 token。

3.2　长输出的两道闸：执行完立刻落盘，压缩时再裁剪

工具输出太长，有两个时机可以处理：工具刚执行完时，和很多步之后压缩时。DSH 在两个时机各放了一道闸，交给两个独立的插件。

先看问题。agent 跑了一次测试，输出 30 万字，大约几十万 token。原样塞进上下文会怎样？轻则一次就把上下文占满大半，后面每一步都要为这堆字付钱，还会很快触发压缩；重则直接超过窗口，请求失败。可是直接扔掉也不行，失败的测试名可能就在中间某一行。

两道闸处理的是不同的情况：

两道闸的位置：一道在结果进入对话之前，一道在压缩开始之后

第一道闸：执行完立刻落盘。 这一道管的是「这一次的输出就太长」。完整的基础组合里配置了一个落盘策略（spill，意思是「溢出到文件」）：单个工具输出超过 12,500 个 token 时，完整内容写进一个只属于这个会话的私有文件，模型只看到一段预览和文件路径。

落盘：全文进文件，上下文里只留预览和路径，模型按需去读或搜索

这样做的好处是信息一点没丢，只是换了个地方放。模型需要时自己去读那个文件，或者用 grep（按关键字搜索文本的命令）找出相关的几行。

第二道闸：压缩时裁剪。 这一道管的是「历史里累积的长输出」。一个两千字的结果当时不算长，可二十步之后，对话里攒了一堆这样的结果。如果组合里装了「裁剪工具结果」的插件，压缩一触发，它先出手：超过 8,192 个字符的工具结果，只保留开头 4,096 个字符和结尾 1,024 个字符，中间换成一个标记。

裁剪一条超过 8,192 字符的工具结果：留下头尾，中间换成标记。对测试和构建的输出来说，结尾往往是汇总和报错

这一步不调用模型，又快又便宜。裁剪完如果已经回到阈值以下，就不再做总结。裁剪也是用第 1.2 节的替换完成的：工具结果只能被替换内容，调用编号等其他字段不变；原来的完整结果仍在日志里。

两道闸互不依赖，各管一种情况：落盘在结果进入对话之前，按 token 算一条结果有多大；裁剪在压缩开始之后，按字符处理历史里已有的结果。所以它们是两个独立的插件，可以只装其中一个。

3.3　切在哪里

总结的对象是最早的一段「平衡区间」：工具调用和它的结果必须在同一侧，系统提示词永远不进区间。

裁剪完还不够，就要请模型把最早的一段对话写成摘要。切点不能随便选：

上：调用 B 被总结掉，结果 B 留在外面，成了一条没有调用的孤立结果。下：调用和结果在同一侧，系统提示词不动

所谓平衡，就是一个工具调用和它的结果不能被切到区间两边，否则剩下的那一半在模型看来就是一条孤立的调用或结果，模型服务会报错。区间总是从系统提示词之后的第一条开始，所以系统提示词永远不会被卷进摘要。

如果找不到这样的切点，就什么都不做，日志里也不写任何东西。比如整段历史只有一轮，模型在这一轮里连着发了一串工具调用，调用和结果一直交替到最后，从哪里切都会把某个调用和它的结果分到两边。

3.4　总结请求也要命中缓存

写摘要的那次模型调用，被刻意构造成「原对话的前缀加一条新指令」，好复用模型服务已经算好的缓存。

模型服务有前缀缓存：请求的开头和之前某次一字不差，这一段就不用重新计算（专业的叫法是复用 KV 缓存，即模型读过这段文字后留下的中间结果）。

所以压缩插件这样构造总结请求：先放系统提示词，然后一个字节都不改地重放要被压缩的那段消息，带上最近一次请求的工具说明，最后才追加一条「请总结」的指令。

绿色部分两次完全相同，可以命中缓存；只有"请总结"和输出的摘要需要新算（消息条数是举例）

在模型服务看来，总结请求就是原对话的一个前缀加一条新消息，只有最后那条指令和写出的摘要是新算的。这和上一篇第 5.2 节把会变的信息挪出系统提示词是同一个考虑：尽量不让前缀变。

3.5　压缩本身是一笔记在日志里的事务

压缩分几步写进日志，第一步就是一把锁；锁也在日志里，所以崩溃之后能分清是旧锁还是真有压缩在跑。

事务的意思是：一组操作要么全部完成，要么当没发生过。压缩的过程是：

一次压缩在日志里留下的记录。模型看到的摘要会被一个"已压缩摘要"的标记包住

日志里有「压缩开始」却没有对应的「压缩结束」，就说明有一次压缩正在进行，这时再来第二次压缩会被告知「忙」。锁要等所有步骤都写完才释放：先写「压缩开始」，摘要和替换都写进日志以后，最后才写「压缩结束」。这样进程如果在中途崩溃，日志里留下的是一个只有开始、没有结束的锁，重启后一眼就能认出这是上次没做完的压缩；反过来，如果先写「结束」再做替换，崩溃后日志会谎称压缩已经完成。

拿到摘要后的两项检查也有用处：等模型写摘要的这段时间里，对话可能又往前走了，清单变了，旧的摘要就不该再套上去；摘要如果比原文还长，压缩就没有意义。

4　安全边界

DSH 的权限分三层：沙箱限制命令能碰哪些文件，审批决定要不要问人，子 agent 的规则决定权限怎样往下传。

三层权限：每条命令都要过审批和沙箱，子 agent 的两项设置在委派时就定死了

4.1　沙箱

沙箱把一条命令包装成「只能碰规定文件」的版本再执行；包不了就不执行，绝不悄悄放行。

沙箱服务只有一个核心操作：给它一条命令和一个策略，它返回包装后的、可以真正执行的命令。策略有三种模式：

模式效果
只读除了必需的输出（比如丢弃输出用的空设备）之外，禁止写任何文件
可写工作区（默认）允许写工作目录和系统临时目录
完全放开不做限制，直接执行原命令

具体怎样限制，每个操作系统有自己的机制。Linux 上依次尝试 bubblewrap（一个把程序关进受限文件视图的小工具）和 Landlock（Linux 内核自带的文件访问限制），macOS 用系统自带的 Seatbelt，Windows 用访问控制令牌。几个候选同时可用时，先做一次功能探测再选。

三条设计原则写在 README 里：

  • 做不到就不执行（英文叫 fail closed）：没有哪种机制能执行要求的模式时，直接报错「沙箱不可用」，绝不在不加限制的情况下照常执行；
  • 报告管住了多少：每次调用返回「完全」或「部分」。Windows 的方式和旧版 Landlock 只能管住一部分文件操作，报「部分」；需要绝对边界的调用方可以拒绝它；
  • 策略跟着调用走：策略不绑定在某种机制上，两个工具可以同时用不同的策略。

命令被沙箱拒绝时，模型会看到一条「在某模式下文件访问被拒绝」的提示，以及怎样申请升级。升级的规矩很严：

升级只能沿箭头往更宽的方向走。每次升级都要带理由、经审批，而且只对这一次调用有效

模型可以带上两样东西，把同一个调用重试一次：一是要升到的模式：必须比原来宽，又只能选够用的档位里最窄的那个（比如原来只读，只是要改工作区里的文件，就申请「可写工作区」，而不是「完全放开」）；二是一段理由。这次重试要经过审批，批准了也只对这一次调用有效，下一次调用又回到原来的模式。

4.2　审批

工具管线的预检给出「要问人」（2.2 节），或者模型申请沙箱升级（4.1 节）时，这次调用就交给审批服务。审批服务自己不判断该不该执行，也从不亲自问人，只负责把问题派发给能回答的一方；没人回答，就当作拒绝。

审批的三种去向。审计记录写不进日志时，宁可让请求失败，也不给出一个没有记录的决定

审批服务把请求作为一个 waterfall 事件派发出去，由组合里的「回答者」处理。网页界面、命令行界面、自动化规则都可以当回答者。

  • 策略「问」（默认）：交给回答者；
  • 策略「从不问」：在派发之前就确定地拒绝一切请求，适合持续集成（代码提交后自动跑的构建和测试）这类无人值守的场合；
  • 组合里一个回答者都没有：请求返回「不可用」，同样按拒绝处理。

每次请求和决定都在日志里记一条审计事件，事后可以查「谁在什么时候批准了什么」。审计写不进日志时，请求直接失败。模型看不到审计事件，只看到最终的工具结果，以及运行时上下文里当前的审批策略。

4.3　子 agent

子 agent 有两种起法：从空白开始，或者复制父对话的前缀；不管哪种，它的权限在委派那一刻就固定下来，之后也要不到更多。

子 agent 是父 agent 派出去完成一项子任务的另一个 agent。两种起法的区别在于它带不带父对话：

全新起步只有一条任务描述；分叉起步复制父会话已完成的轮，正在进行的那一轮不复制

起法子 agent 的起点代价
全新起步空白会话，任务描述是唯一的用户消息不复制父对话，但上下文从零开始，任务描述必须写得完整，不看父对话也能懂
分叉起步父会话里已经结束的那些轮（原样复制），再加任务描述用同一个模型时能复用父对话的缓存；正在进行的这一轮不复制

另外还可以把任务交给外部的 agent，比如 Claude Code、Codex，或者任何支持 ACP 协议的 agent。外部 agent 只执行一次，不能继续对话，权限由外部系统自己管。

权限往下传有三条规则：

  • 委派的那一刻，记下父会话当前的沙箱模式和权限预设，写进子会话的日志。父会话之后再改，影响不到已经启动的子 agent；

  • 只要组合里有审批服务，子 agent 的审批策略固定为「从不问」，也就是需要审批的操作一律拒绝。子 agent 不能在自己会话里要更多权限；

  • 子 agent 的运行时上下文里固定加一段话：

    You are a delegated subagent: your permission scope was fixed when you were started and cannot be widened from inside this session — operations that require approval are rejected automatically. When the task needs access beyond that scope, do not retry the denied operation; state the limitation in your reply so the delegating agent can handle it.

    意思是：你的权限在启动时就固定了，需要审批的操作会被自动拒绝；权限不够时不要重试，在回复里说明，交给派你出来的 agent 处理。

还有两个数量限制。委派深度默认最多 1 层，即只允许直接的子 agent，子 agent 不能再派子 agent。同时活跃的子 agent 默认最多 8 个，满了就直接拒绝，不排队。

为什么不排队？README 给的理由是：一个父 agent 可能正在等它的子 agent。如果让新请求排队等空位，父 agent 等的可能正是自己占着的那个位置。举个示意的例子：委派深度调大以后，本身是子 agent 的 A 占着一个位置，又派出了 B；位置满了，B 只能排队，而位置要等 A 结束才空出来，A 却在等 B 的结果。

如果排队，就可能出现互相等待的圈：谁也走不动（死锁）。直接拒绝就打破了这个圈

这种「几方互相等对方先放手、谁也走不动」的局面叫死锁。直接拒绝，父 agent 至少能拿到一个失败结果，自己决定下一步。

4.4　防兜圈子

模型反复用一模一样的参数调用同一个工具时，DSH 只提醒，不阻止。

有一个小插件专门盯这件事：模型连续第 3、5、8 次用完全相同的参数调用同一个工具时，它在调用结果后面追加一条提醒。它只提醒、不阻止，因为有些重复是正当的，比如反复查询一个后台任务跑完了没有。

5　小结

这几块基础设施有一个共同的做法：把约束放在数据结构和代码里，而不是放在提示词里。

  • 模型能看到什么，由清单的替换规则保证，而不是由「请不要修改系统提示词」之类的说明保证；
  • 工具调用的底线由单调的守卫保证，后面的插件改不回来；
  • 沙箱不可用就不执行，而不是提醒模型「请小心」；
  • 子 agent 的权限在委派时固定并写进日志，它在自己会话里无论怎样请求都拿不到更多。

提示词里当然也有对应的说明，比如子 agent 那段话、沙箱拒绝时的提示。但它们的作用是让模型理解发生了什么、该怎样应对，而不是靠它们来保证安全。

这是 DSH 的工程层。它的地基，也就是这些插件怎样装上、怎样在依赖变化时重载、怎样卸干净，见原理篇。
