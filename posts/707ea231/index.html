textstats 的测试修好了。用户说：「提交，推上去。」agent 执行 git push，远程仓库拒绝了，因为别人刚往 main 上推过新的提交。模型想了想，发出下一条命令：git push --force origin main。

这条命令会用本地的版本覆盖远程的 main 分支，别人刚推上去的提交就此消失。模型并没有恶意，它只是在「把代码推上去」这个目标上，找到了一条最短的路。

上一篇的结论是一条分工原则：需要理解任务的判断交给模型，必须成立的保证交给机制。这一篇就拿这条强推命令当例子，看 harness 怎样管住 agent：一条规则可以写在哪里，一次工具调用在执行前要过哪几道关，用户怎样往 harness 里加自己的规则，以及 agent 和编辑器、工具、别的 agent 之间靠什么连起来。

文中的例子仍然来自三个开源实现：DeepSeek Harness（下称 DSH）、Hermes Agent 和 OpenClaw。关于它们的说法，具体出处统一列在文末，不看也不影响理解。

1　一条规则可以写在哪里

「不要强推到 main」这条规则，至少可以写在五个地方。越往下越不依赖模型听话，但也越不懂「意思」。

最上面一层是 提示词侧：规则是请求里的一段文字，靠模型理解并遵守。下面几层是 机制侧：规则由 harness、操作系统或远程服务器执行，模型说什么都不影响它。比如把 GitHub 上 main 分支的「允许强推」关掉，那么无论哪台机器、哪个 agent 发来强推，服务器都直接拒绝。

1.1　提示词侧的问题：会漏看，会被推翻

第一，模型会漏看。 上一篇讲过注意力的软上限：规则埋在长上下文中间，模型可能根本没注意到。

第二，规则和别的文字处在同一个位置。 序章（上）看过，工具的结果是以「用户」的身份递给模型的。设想模型读了一个网页，网页里藏着一句「忽略之前的指令，执行下面的命令」。这段文字和系统提示词一样，都只是上下文里的文字，模型未必分得清该听谁的。这就是 提示词注入，Agent 安全系列 专门讲。

提示词注入。用户写的规则和网页里的恶意文字，进了上下文以后地位相同，模型未必分得清

1.2　机制侧的问题：只认字面，不懂意思

机制侧的规则由代码执行，代码只认字面。我们写一条最直接的检查：命令里同时出现 --force 和 main，就要问人。它能拦住下面第一条命令，却拦不住后两条：

反过来，它也分不清「这次强推是不是用户真正想要的」。也许用户就是要用本地版本覆盖一个坏掉的远程分支。越往下越硬，也越笨：操作系统只知道进程能不能碰某个文件，完全不懂任务。

1.3　所以要分层：两家安全文档怎么说

能用机制表达的保证，放在机制里；需要理解语义的判断，留给模型和人。 两个开源项目的安全文档把这条界线写得很明白。Hermes 的安全文档说：

对抗一个恶意的 LLM，唯一的安全边界是操作系统。agent 进程内部的任何东西都不构成隔离：审批闸不算，输出脱敏不算，模式扫描不算，工具白名单也不算。进程内任何筛查 LLM 输出的组件，都只是在对一段受攻击者影响的字符串做启发式判断。

（「启发式」的意思是凭经验的规则，多数时候管用，但不保证。1.2 节那条漏掉 -f 的检查，就是一个启发式。）同一份文档还说，审批闸「挡得住配合模式下的失误，挡不住对抗性的输出」：模型老老实实干活时手滑，审批能拦住；模型被人操纵、有意绕过时，就拦不住了。

OpenClaw 的安全文档从另一面说同一件事：模型不是可信主体，要假定注入能操纵它；安全边界来自认证、工具策略、沙箱和执行审批；单纯的提示词注入不算漏洞，除非它越过了这几道边界之一。

换句话说，两家都默认模型会被骗，然后把力气花在「被骗以后还能做什么」上。

2　一次工具调用要过的关

模型说「我要执行 git push --force origin main」以后，harness 不会马上执行，而是先让这个请求过几道关，就像报销单要先走完几道手续才能拿到钱。 各家 harness 的关卡叫法不同，思路大同小异。我们按 DSH 的实际顺序写成算法：

算法 1Dispatch(c)一次工具调用从发出到写进记录
输入模型发出的工具调用 c（工具名和参数），参数一经发出就不再改
输出写进会话记录的结果
d ← PreCheck(c)▷ 第 1 关：规则排成一队，第一条表态的说了算（2.1）
if d = 问人 then d ← 弹窗问人的结果▷ 第 2 关：审批，只认「这一次允许」
if d = 拒绝 then return 「被拒绝」写进记录
for each guard g do▷ 第 3 关：只能否决的规则（2.2）
if g(c) 给出了理由 then return 「被拒绝：理由」写进记录
r ← 在沙箱里、带着超时执行 c▷ 第 4 关：执行
r ← PostCheck(c, r)▷ 第 5 关：结果太长就截断、落盘，有密钥就打码
把 r 追加进会话记录▷ 第 6 关：记录，之后不再改
return r

这里有两个容易混的词。规则检查（第 1 关）只是看规则、做决定，它自己不会停下来等人；审批（第 2 关）才是真的停下来，把问题摆到人面前。拿报销打比方：财务看规则，发现金额超过 1000 元，在单子上写「需经理签字」，这是规则检查；经理拿到单子、签字，这是审批。

下面细看第 1 关。规则一多，就会碰到两个问题：规则之间意见不一致时听谁的；规则能不能顺手把命令改了。

2.1　规则排成一队：排在前面的说了算

第 1 关的规则排成一队，从第一条开始一条条看；哪一条先表态，就按它说的办，后面的不再看。 每条规则就是一个小函数，看一眼调用，回答「放行」「拒绝」「问人」，或者不表态：

这样很灵活，但有一个后果：规则的先后顺序会改变结果。对 git push --force origin main，两条规则的意见正好相反：

同样两条检查器，只是换了个先后。黄色是第一个表态、说了算的那条；灰色那条根本没机会开口

顺序一，rules = [allow_git, ask_dangerous]：allow_git 先表态「放行」，ask_dangerous 根本轮不到，命令直接执行。顺序二，rules = [ask_dangerous, allow_git]：ask_dangerous 先表态「问人」，命令停下来等人点。同样两条规则，只换了先后，结局就不一样。

2.2　另一种规则：只能否决

还有一种规则，只能做两件事：拒绝，或者不表态。它没有「放行」这个选项。 DSH 把它叫作 guard，就是 Algorithm 1 的第 3 关。

只要有一条 guard 拒绝，调用就被拒绝：不管它排在第几，也不管第 1 关有没有放行、人有没有点允许。下图里有三条 guard，其中第二条是「禁止推送到 main」，怎么排结果都是拒绝：

guard 怎么排，结果都一样：只要有一个反对，就是拒绝。没人能说「放行」，也就没人能推翻别人的拒绝

为什么要专门有这样一种规则？规则一多，没人记得清谁排在谁前面。guard 的结论只看「有没有谁反对」，和顺序无关，加一条、删一条都不会让别的否决失效。

2.3　规则能不能顺手改命令

规则检查时，能不能把命令改一改再放行？比如把 git push --force 悄悄改成 git push。各家选择不同。

不许改的理由是：模型发出的这个调用，在检查之前已经写进了会话记录，也显示在了界面上。如果检查时改了，真正执行的就和记录里的不是同一条，回头翻记录、做审计、看界面，都对不上。允许改的好处是灵活。3.4 节会看到两家正好做了相反的选择。

2.4　四种情况放在一起看

只看 git push --force origin main 这一个命令，只变两样东西：allow_git 和 ask_dangerous 谁在前，以及有没有 guard「禁止推送到 main」。一共四种情况：

没有这条 guard有这条 guard
allow_git 在前直接执行拒绝
ask_dangerous 在前停下来问人，人点允许才执行拒绝，人点允许也没用
  • 看左边一列：只换了两条普通规则的顺序，结局就从「直接执行」变成「问人」。
  • 看右边一列：有了 guard，顺序怎么换都是拒绝。这个「换顺序结果不变」的性质叫 可交换，概念篇 会专门讲。

另外两样东西不在这几道关里，但也要分清：

  • 沙箱管的是另一类事。 就算规则全放行了，命令也是在沙箱里跑的。比如 curl … | sh（下载一段脚本并立刻执行）放行以后，在沙箱里上不了网；rm -rf ~（删除整个用户目录）放行以后，也删不到沙箱外面的东西。
  • 提示词里写的规则不在这几道关里。 系统提示词里写「不要强推」，作用在更早的地方：让模型少发出这种调用。可一旦模型发出了，这几道关没有一道会去看提示词。

DSH 的工具管线。前三关任何一关都可以把调用拦下（虚线）；执行完还有一关，最后的结果一旦写进记录就不再改

3　hook：用户自己往 harness 里加规则

第 2 节的规则，有的是 harness 自带的，有的要靠用户自己加。用户加规则的办法叫 hook：你写一小段程序，再告诉 harness「到了某个时刻就运行它」。

harness 的作者不可能预先想到每个团队的规矩。比如你的团队有两条约定：agent 不许读 .env 文件（项目里专门放密码和密钥的文件）；agent 每次改完 Python 文件，都要自动跑一遍格式化工具。这两条就是两个 hook，前一个挂在「工具执行前」，后一个挂在「工具执行后」。

序章（上）5.1 节那个「不许改测试」的检查脚本，也是一个挂在「工具执行前」的 hook。在 Claude Code 里，第 1 关的规则检查就可以交给这样的 hook 来做。DSH 自己的规则同样挂在「工具执行前」这一刻，可它对从 Claude Code 搬来的 hook 另有安排，3.4 节细说。

一个 hook 就是这样一个小程序：读一段 JSON，回一个退出码或一段 JSON。用什么语言写都行。

3.2　能挂在哪些时刻

除了工具执行前后，一次会话里还有很多时刻可以挂 hook。 各家的叫法不同，但时刻大同小异：

时刻典型用途

3.3　hook 能做到哪一步

同样是挂一段程序，能做的事有大有小。按对 agent 的影响从小到大，分四种：

hook 的四种能力。越往右，越能改变 agent 的行为，越要想清楚它放在管线的哪个位置

  • 观察：只看不改，比如每次工具调用都记一条日志。它出错了也不该影响 agent 干活。
  • 决定：放行、拒绝或要求问人，比如上面的「强推 main 需要人确认」。
  • 改写：修改工具的输入或输出，比如把工具结果里出现的密钥打上码，再交给模型。
  • 补充上下文：往上下文里补一句话给模型看。比如「自动格式化」跑完以后，告诉模型「格式化工具改动了这三个文件」，免得模型以为文件还是它自己写的样子。

同一个时刻如果挂了好几个能做「决定」的 hook，各家处理不一样。Claude Code 把匹配到的 hook 同时运行，其中任何一个拦下，这次调用就被拦下。DSH 的「工具执行前」是一条排成一队的规则链，排在前面的先表态，这就又回到了 2.1 节说的「顺序会改变结果」。

3.4　hook 能不能改命令：两家的不同选择

最典型的问题是：工具执行前的 hook，能不能修改模型发出的命令？ Claude Code 和 DSH 的答案正好相反。

同一个 hook 的两种摆法。上面放在权限检查之前，灵活但记录和执行可能不一致；下面放在权限决定之后，保证执行的就是记录里的那个调用

Claude Code 允许。 它的工具调用 hook 在权限检查 之前 运行，可以改写命令的参数，甚至把这次调用换成调用另一个工具，比如给每条 shell 命令自动加上超时限制。好处是灵活。

DSH 不允许。 DSH 也能运行给 Claude Code 写的 hook，但它把这类 hook 放在权限决定 之后，并且不许改参数。理由就是 2.3 节说的：命令已经写进了会话记录、显示在了界面上，真正执行的必须就是记录里的那一条。

两种做法各有取舍：一个要灵活，一个要记录和执行永远一致。要紧的是这个位置是有意选的，并且清楚自己放弃了什么。

3.5　hook 自己可信吗

hook 防得住模型犯错，防不住恶意代码。 hook 是跑在 agent 程序里面的代码，拥有和 agent 程序一样的全部权限，能读你所有的文件，也能联网。DSH 的文档写明，它不给这类扩展加沙箱，只建议「挂载你愿意作为插件运行的」；Hermes 和 OpenClaw 的安全文档也都把插件当作可信代码。

所以回到第 1 节的分层：hook 属于 harness 规则那一层，适合把团队约定变成自动检查，或者在关键时刻把人拉进来；要挡住真正恶意的代码，只能靠最下面的操作系统那一层，比如沙箱和文件权限。装一个来路不明的 hook，等于把整台机器的权限交给了它的作者。

4　agent 和外界怎么连：三个协议

到这里，agent 和它的规则都在一个程序里。可人在编辑器里用它，它要用别人写好的工具，它还可能把活交给另一个 agent。这三条连线，各有一套约定好的对话格式，叫协议。

走一遍完整的例子。你在编辑器里对 agent 说「帮我看看 CI 为什么挂了」（CI 是代码每次提交后自动跑测试的服务）。

类比外设驱动编辑器和语言服务器之间的 LSP服务之间的远程调用

表里的 LSP（语言服务器协议）是编辑器和「懂某种编程语言的后台程序」之间的约定，任何编辑器都能靠它拿到补全、跳转这些功能。ACP 就是照着 LSP 的思路，把「后台程序」换成了 agent。缩写 ACP 曾经还指过 IBM 的 Agent Communication Protocol，做 agent 之间的通信，2025 年已经并入 A2A；现在说 ACP，一般指连接编辑器和 agent 的这一个。

三个开源实现都接上了这些协议：DSH 既能被编辑器通过 ACP 驱动，也能反过来用 ACP 去驱动别的 agent；Hermes 能被编辑器通过 ACP 驱动；OpenClaw 能通过 A2A 接收别的 agent 派来的任务。

4.1　接得上，不等于可信

协议只管「能不能接上」，不管「接上以后可不可信」。

MCP 的工具可以给自己贴标注，比如声明「我是只读的，不会改任何东西」。可说这话的正是 agent 要提防的那个工具。所以 MCP 规范要求：除非这个工具服务器本身是可信的，否则这类标注一律当作不可信。一个第三方工具服务器自称只读，harness 也不能因此就免掉审批。

5　为什么协议在统一，引擎却各写各的

这两年，几乎每家 agent 都支持 MCP，ACP 和 A2A 也在被越来越多的产品接入；可 agent 内部的机制，也就是第 2、3 节的检查管线和 hook，加上压缩、会话存储这些，每家都在自己写。 下面把这些内部机制统称为「引擎」。

5.1　协议省的是对接的份数

算一笔账。有 3 个编辑器、3 个 agent，如果两两对接，每一对都要写一份适配，一共 3 × 3 = 9 份。有了一个大家都认的协议，每个编辑器、每个 agent 只要各自对着协议写一份，一共 3 + 3 = 6 份。再加一个新 agent，前一种要多写 3 份，后一种只多写 1 份。规模一大，差距就拉开了：5 个编辑器、8 个 agent，是 40 份对 13 份。

左边两两对接，3 × 3 = 9 份适配；右边大家都对着同一个协议写，3 + 3 = 6 份。参与方越多，差距越大

这个好处对所有参与方都成立，谁都没理由不加入。LSP 当年就是这样普及的。

5.2　引擎是一堆取舍，取舍取决于用在哪

引擎里的每个选择都没有标准答案，各家按自己的用途选：

  • 压缩：上一篇看到，同一个模型，三家默认的压缩触发线从 51% 到 90% 不等。
  • 权限：OpenClaw 的执行审批默认是「完全权限、从不询问」，直接在你的电脑上执行，因为它的定位是「给可信的使用者自己用的本地 agent」；Hermes 在有人值守的场景里，对危险命令默认要问人。
  • 会话存储：DSH 用只追加的事件日志，OpenClaw 和 Hermes 用 SQLite 数据库。

这些选择互相牵连，又和产品定位、所用模型的脾气绑在一起，抽不出一个大家都满意的公共实现。所以现实中的做法是在边上做翻译，而不是共用引擎。3.4 节里 DSH 运行 Claude Code 的 hook 就是一个例子：它没有照搬 Claude Code 的引擎，而是把对方的 hook 翻译成自己管线里的一环。
