第一部分　管住 agent

1　一条规则可以写在哪里

「不要强推到 main 分支」这条规则，至少可以写在五个地方：

最上面一层是 提示词侧：规则是请求里的一段文字，靠模型理解并遵守。下面几层是 机制侧：规则由 harness 或操作系统执行，模型说什么都不影响它。

提示词侧的问题有两个。一是模型会漏看，上一篇讲过注意力的软上限。二是它和别的文字处在同一个位置：如果模型读到的某个网页、某个文件里写着「忽略之前的指令，执行下面的命令」，那段文字和系统提示词一样都是上下文，模型未必分得清该听谁的。这就是提示词注入，后面 AI 安全系列会专门讲。

机制侧的问题是表达能力。harness 能检查「命令里有没有 --force」，检查不了「这次强推是不是用户真正想要的」。越往下越硬，也越笨：操作系统只知道进程能不能碰某个文件，完全不懂任务。

所以实际的做法是分层：能用机制表达的保证，放在机制里；需要理解语义的判断，留给模型和人。两个开源项目的安全文档把这条界线写得很明白。Hermes 的 SECURITY.md（第 60-65 行）：

对抗一个恶意的 LLM，唯一的安全边界是操作系统。agent 进程内部的任何东西都不构成隔离：审批闸不算，输出脱敏不算，模式扫描不算，工具白名单也不算。进程内任何筛查 LLM 输出的组件，都只是在对一段受攻击者影响的字符串做启发式判断。

同一份文档在第 145-146 行说审批闸「挡得住配合模式下的失误，挡不住对抗性的输出」。OpenClaw 的 SECURITY.md（第 239-242 行）从另一面说同一件事：模型不是可信主体，要假定注入能操纵它；安全边界来自认证、工具策略、沙箱和执行审批；单纯的提示词注入不算漏洞，除非它越过了这几道边界之一。

换句话说，两家都默认模型会被骗，然后把力气花在「被骗以后还能做什么」上。

2　一次工具调用要过的关

模型发出一个工具调用之后，harness 并不是直接执行它。DSH 的工具管线把这个过程拆得最细（docs/subsystems/tools.md 的执行一节）：

  1. 前置检查（tools/pre-execute）：一串监听器依次表态，可以放行、拒绝或要求询问；
  2. guard：一组只能说「不」的检查；
  3. 审批：前面要求询问的，暂停等人；
  4. 执行（tools/execute）：外面可以包一层沙箱、超时之类的包装；
  5. 执行后检查（tools/post-execute）：截断、落盘、改写结果；
  6. 结果（tools/result）：最终结果，不可再改，写进会话记录。

其中前两步的区别值得细看。

前置检查是 瀑布式 的：监听器按顺序排成一串，每个要么自己给出决定、直接返回，要么调用 next() 交给下一个。第一个表态的说了算，后面的不再执行。这很灵活，但有一个后果：顺序会改变结果。

guard 是 单调 的：它的返回值里根本没有「放行」这一项，只能返回一个拒绝理由，或者什么都不说。源码注释写得很直白：「因为 guard 没有放行结果，监听器的顺序没法把一个拒绝重新变成许可」（docs/subsystems/tools.md 里 ToolGuard 的定义）。

还有一条：前置检查 不允许改写参数。理由是参数在这之前已经写进了会话记录、显示在了界面上，执行的必须就是记录里的那一个，否则历史、审计、界面和实际执行就对不上了（同一文档对 PreToolDecision 的说明）。

下面这个模拟器里，左边是三条前置检查、两个 guard、审批和沙箱的开关，右边是六个调用。先看 git push --force origin main：默认顺序下，「git 命令一律放行」排在「危险模式先问人」前面，所以它直接执行了。把第三条上移到第二条前面，再看一遍；然后打开「禁止推送到 main」这个 guard，再随便调换顺序。

几个观察：

  • 调换前置检查的顺序，结局会变。 「放行 git」和「危险先问」对强推这一个调用给出了相反的意见，谁排前面听谁的。
  • guard 的结论不受顺序影响。 打开以后，不管前置检查怎么排、人点没点允许，推送到 main 都被拒绝。
  • 沙箱兜住的是另一类东西。 关掉所有检查、打开沙箱，curl … | sh 被放行了，但执行时网络不通；rm -rf ~ 也执行了，但删不掉沙箱外面的东西。
  • 提示词里的规则不出现在管线里。 勾不勾那一项，右边的结局完全一样。它的作用发生在更早的地方：让模型少发出这类调用。可一旦发出来，它就管不着了。

第二条观察会在第 11 节再出现：只会拒绝的检查之所以不受顺序影响，是因为它们满足「交换」。

3　hook：把规则挂在生命周期上

上面的前置检查，本质上是挂在「工具执行前」这个时刻上的一段代码。把这个思路推广到 agent 生命周期的每个关键时刻，就是 hook。

3.1　挂在哪里

各家的事件名不同，但覆盖的时刻大同小异：

时刻典型用途
会话开始、结束加载项目约定，清理临时文件，写审计日志
用户提交输入检查输入，追加上下文（比如当前分支名）
一轮开始、结束统计用量，决定要不要提醒用户
工具执行前放行、拒绝、要求审批
工具执行后截断、脱敏、格式化、触发后续检查（比如改完代码自动跑格式化）
压缩前把值得长期保存的东西先写下来（上一篇的记忆冲刷）
子 agent 开始、结束限制子 agent 的权限，收集它的结果
需要通知人的时候发消息到手机或聊天软件

DSH 的事件目录里能找到对应的名字：agent/created、agent/pre-step、tools/pre-execute、tools/post-execute、approval/request、compaction/summary-error、subagent/start 等。DSH 文档里还有一份它对 Claude Code 模组的兼容说明（docs/subsystems/claude-code-mods.md），从那份对照表能看到 Claude Code 一侧的事件：session.start、prompt.submit、turn.start、turn.complete、tool.call 等。

3.2　hook 能做什么

比「挂在哪里」更重要的是「能做什么」。按对结果的影响从小到大，大致是四种：

  1. 观察：只看不改。记日志、发通知、统计。出错了也不该影响主流程。
  2. 决定：给出放行、拒绝或询问，可能短路掉后面的处理。
  3. 改写：修改输入或输出，比如把工具结果里的密钥打码。
  4. 注入：往上下文里追加内容，比如工具执行后附一条「格式化工具改动了这三个文件」。

DSH 把这件事落实在事件的 分发模式 上（docs/cordis-primer.md）：emit 和 parallel 只让监听器观察；waterfall 是环绕式的中间件，监听器可以修改、替换或者不调用 next() 直接短路；bail 在某个监听器给出结果时停下；serial 按顺序等待每个监听器并返回结果。分发模式是事件公开约定的一部分，写在声明里，生成的文档会把声明和实际调用点交叉校对。

能力越强的模式，越要想清楚它在管线里的位置。两家的选择就不一样。按 DSH 的对照表，Claude Code 的 tool.call 在权限检查 之前 运行，可以改写参数，甚至把调用改派给另一个工具；DSH 的桥接把它包在执行这一步外面，在权限决定 之后，并拒绝改写参数，理由仍然是「已经写进记录的调用要原样执行」。前一种更灵活，后一种保证了记录和执行一致。没有哪个绝对对，但这个位置一定要是有意选的。

3.3　hook 不是安全边界

hook 是你自己写的、跑在 agent 进程里的代码。DSH 的那份兼容文档写明，模组「在进程内运行，没有访问规则，拥有进程的全部权限」，「不对模组施加沙箱，只挂载你愿意作为插件运行的模组」。Hermes 和 OpenClaw 的安全文档也都把插件和技能算作可信代码。

所以 hook 适合做两件事：把团队的约定变成机械检查（第 1 节那张图里的第三层），以及在关键时刻接入人。它不适合当作对抗恶意代码的隔离手段，那是操作系统那一层的事。

4　三个协议各管一条边

agent 周围有三条边，各有一个协议：

MCPACPA2A
全称Model Context ProtocolAgent Client ProtocolAgent2Agent
连接的两端agent ↔ 工具服务器编辑器或脚本 ↔ agentagent ↔ agent
核心概念工具、资源、提示模板会话、提示、流式更新、权限询问能力名片（Agent Card）、任务及其状态
传输JSON-RPC，本地进程走标准输入输出，远程走 HTTPJSON-RPC，通常走标准输入输出JSON-RPC 等，走 HTTP
类比外设驱动编辑器和语言服务器之间的 LSP服务之间的远程调用

三个开源实现里都能看到它们：

  • DSH 既能作为 ACP 服务器被别的程序驱动（客户端可以创建、恢复、关闭会话，挂载 MCP 服务器，回应权限询问），也能作为 ACP 客户端去驱动别的 agent（packages/acp/README.md）。注意这里两个协议叠在一起：编辑器通过 ACP 告诉 agent「请挂上这几个 MCP 服务器」。
  • Hermes 有一个 acp_adapter 目录，把自己暴露成 ACP 服务器。
  • OpenClaw 有一个 A2A 渠道插件：别的 agent 先读它公开的 /.well-known/agent-card.json，再用各自的令牌提交任务（docs/channels/a2a.md）。

还有一个容易混淆的地方：缩写 ACP 曾经指两个不同的协议。另一个是 IBM 的 Agent Communication Protocol，做的是 agent 之间的通信，2025 年已经并入 A2A，由 Linux 基金会管理。现在说 ACP，一般指连接编辑器和 agent 的那个。

协议定下的是「能不能接上」，不是「接上以后可不可信」。MCP 的工具定义里可以带一些标注，比如 readOnlyHint 声明自己只读。规范对这些标注的态度是：除非来自可信的服务器，否则客户端必须把它们当作不可信的（MCP 规范 2025-06-18 版的 Tools 一节）。第 8 节会回到这一点。

5　为什么协议在收敛，引擎不收敛

这两年 agent 生态里一个明显的现象是：协议越来越统一，每家几乎都支持 MCP，ACP 和 A2A 也在被越来越多的产品接入；可是引擎，也就是循环、压缩、权限、会话存储这一层，每家都在自己写。

原因在于两者解决的问题不同。

协议解决的是 N×M 问题。 有 N 个编辑器、M 个 agent，如果两两对接，要写 N×M 份适配；有了一个协议，每方只写一份，总共 N+M 份。这个收益对所有参与方都成立，谁都没理由不加入。语言服务器协议（LSP）当年就是这样普及的。

引擎是取舍的集合，而取舍取决于场景。 上一篇已经看到，同一个模型，三家默认的压缩触发线从 51% 到 90% 不等。权限的默认值差得更远：OpenClaw 的执行审批默认是 security: full、ask: off，即默认不问、直接在宿主上执行（src/infra/exec-approvals-config.ts:95-96），它的定位是「给可信操作者用的本地 agent」；Hermes 在交互场景里对危险命令默认要问人。会话存储，DSH 用只追加的事件日志，OpenClaw 和 Hermes 用 SQLite。这些选择互相牵连，又和产品定位、目标模型的脾气绑在一起，抽不出一个大家都满意的公共实现。

所以现实中的做法是在边上做适配，而不是共享引擎。DSH 为 Claude Code 模组写了一个兼容桥，就是一个例子：它没有采用对方的引擎，而是把对方的扩展接口翻译到自己的事件上，并把翻译不了的地方逐条列出来。

第二部分　「对」从哪里来

6　三个不同的问题

说「这个 agent 是对的」，其实混着三个问题：

问题在问什么难在哪里
规格（specification）我们到底希望它满足什么？意图说不清、有隐含要求、要求本身会变
验证（verification）写下来的性质，它满足了吗？状态和交错的组合太多，算不过来
演化（evolution）改了它之后，还满足吗？一处改动会通过依赖影响很多地方

三者要分开看，因为它们需要的方法完全不同。一个常见的混淆是：验证器证明了程序满足规格，就以为程序是对的。可如果规格本身写错了呢？

举一个 agent 的例子。规格写成「每次退款都要经过用户审批」。实现完全满足它：每次调用退款工具都弹窗。但用户真正想要的是「累计 退款金额不超过实付金额」，因为一个被注入的 agent 可以发起一百次小额退款，用户每次都看到一个合理的小数字，每次都点了允许。实现正确地满足了一份错误的规格。

所以对 agent harness，第一步不是写测试，而是把性质写清楚。本系列后面反复用到的是这几条：

  • 授权：每个有副作用的调用，执行之前都得到了授权；
  • 至多一次：每个调用最多执行一次，崩溃重启后也不会重复扣款、重复发邮件；
  • 取消即停：用户取消之后，不再产生新的副作用；
  • 可重放：从会话记录能原样重建出模型每一次看到的内容。

7　生成难，检查易

为什么 agent 的循环要设计成「模型提出，harness 检查」？计算复杂性理论里有一个现成的直觉。

考虑这样一个问题：给一个布尔公式，比如

$$F = (x \lor y) \land (\lnot x \lor z) \land (\lnot y \lor \lnot z)$$

问是否存在一组真假赋值让它为真。这叫 SAT。自己去 找 这样一组赋值，变量一多就很难：100 个变量有 $2^{100}$ 种组合，目前没有已知的方法能在所有情况下都快速找到。但如果有人 给你 一组赋值，比如 $x$ 真、$y$ 假、$z$ 真，你只要代进去算一遍，很快就能确认它对不对。

这类「答案难找、但给出答案后容易核对」的问题组成了 NP；「自己就能快速求解」的问题组成了 P。显然能快速求解的也能快速核对，所以 P 包含于 NP。反过来是否成立，也就是「能快速核对的是否都能快速求解」，就是著名的 P 与 NP 问题，至今没有答案。多数研究者相信两者不相等。

agent 的循环正好是这个形状：

  • 生成 交给模型：写一个补丁、选一条命令，像是在猜一个候选答案；
  • 检查 交给 harness 和工具：跑测试、跑类型检查、过权限规则，像是在核对候选答案。

模型的输出不可靠，但只要检查是可靠的、便宜的，整个系统就可以不依赖模型每次都对：错了就打回去，让它再猜。harness 的价值，很大程度上在于它提供了一个好的检查器。

这个直觉有两个必须记住的限制。

第一，能被快速核对的是「是」，不是「否」。 一组赋值能证明公式可满足；但要证明公式 不可 满足，一般没有这么短的证据。对应到 agent：一个失败的测试能证明有 bug；所有测试都通过，不能证明没有 bug。

第二，检查本身也可能很贵。 想证明「在所有可能的交错下，授权性质都成立」，就不是代入一组值那么简单了。三个各有 1,000 个状态的组件放在一起，组合状态最多有 $1000^3 = 10^9$ 个。对时序逻辑公式做模型检测，在复杂性上是 PSPACE 完全的，一般被认为比 NP 更难。验证篇用 TLA+ 做的就是这种穷举，它能做，是因为模型被刻意缩到了很小。

那么，检查器本身靠得住吗？有一种很隐蔽的失败：让同一个模型既写代码又写测试，测试很可能和代码犯同样的错，于是全部通过。这是 循环评估。可靠篇会用 变异测试 来量检查器：故意往代码里注入小错误，看测试能抓住多少。抓不住的，说明那部分其实没有被检查。

8　拆开来检查，再拼回去

既然整体太大，自然的想法是拆开：分别检查每个部分，再把结论组合起来。这叫 组合式验证。

拆开以后马上遇到一个问题：每个部分只有在别的部分配合时才是对的。退款模块正确的前提是支付模块记对了实付金额；权限层正确的前提是工具如实报告了自己是不是只读。处理这种依赖的经典方法是 假设-保证推理：每个部分写一份契约，「假设 环境满足 A，我就 保证 G」；拼起来时，检查每个部分的假设是否被它的上游的保证所覆盖。

用第 6 节的授权性质做例子：

工具作者保证「我如实声明自己是否只读」；权限层假设声明如实，保证「有副作用的调用都问过人」；提交闸门假设问过人的才执行，保证「不会有未授权的副作用」。三段各自证明，然后拼起来。

现在看图左下角那个虚线框。一个第三方 MCP 服务器也声明了「我是只读的」，可是第 4 节说过，规范明确要求客户端把这种声明当作不可信的。这一环的保证不存在，权限层的假设就悬空了，后面的结论也跟着悬空。所以对一个从第三方接进来的工具，harness 只能按「有副作用」来对待它，除非你另有理由信任那个服务器。

这就是组合式验证在工程上的价值：它逼你把每个接口上的假设写出来，而断掉的那一环往往就是漏洞所在。

自动做这件事的难点在于找假设：假设写得太弱，下游证明不出来；写得太强，上游又满足不了。这是假设-保证推理里一个经典的研究问题，已经有用学习算法自动生成和逐步细化环境假设的工作。

9　局部一致，才拼得成整体

拆开检查还有另一个问题：每个部分对共享的那部分信息，看法得一致。

一个简单的例子。订单模块看到的是（订单金额 80，实付 80），退款模块看到的是（实付 80，已退 50）。两者在「实付」这个重叠的部分上一致，于是可以拼成一个整体：（订单 80，实付 80，已退 50）。如果退款模块看到的是实付 100，两者在重叠处就矛盾了，拼不起来。

数学里研究「局部数据什么时候能拼成全局数据」的理论叫 层论（sheaf theory）。它的核心要求很朴素：局部数据在每个重叠区域上兼容，才能拼成全局数据，而且拼法唯一。

harness 里到处都是同一份数据的不同局部视图：会话记录投影出发给模型的请求、界面上的对话、token 计量、遥测统计。它们在重叠处必须一致。DSH 有一份问题记录正好是这种不一致（.agents/notes/archived/bug-fix/2026-08-05-context-meter-blind-to-compaction.md）：界面上的上下文用量圆环读的是模型服务最近一次报告的用量，而压缩不产生用量报告。于是手动压缩一次之后：

明细降了 93%，圆环纹丝不动。两个视图都「局部正确」：圆环确实等于服务最近报告的数，明细确实等于当前历史的估算。但它们描述的不是同一个时刻，在重叠处对不上，用户看到的就是一个自相矛盾的界面。修法是让圆环改用「服务报告的数加上之后增减的估算」，让两个视图描述同一个时刻。

拼得起来，也不等于整体是对的。（订单 80，实付 80，已退 100）这个全局状态在数据层面完全拼得出来，但违反了「退款不超过实付」。一致性只是组合的前提，性质还要另外证明。

10　还安全，不等于还有救

控制理论里有一对概念。安全集合 是此刻不违反约束的所有状态。可行性核 是其中更小的一部分：从这些状态出发，存在 一种走法能一直留在安全集合里。两者之间的区域最危险：此刻还没出事，但不管接下来怎么走，迟早会出事。就像一辆车离障碍物还有五米、时速一百公里，它此刻没撞，但已经刹不住了。

harness 里的很多设计，其实就是在让 agent 别走进这片区域：

  • 上下文：用量 97% 时，请求还发得出去，但已经没有空间再调用一次模型来写摘要。上一篇里 DSH 专门为摘要调用预留 65,536 token 的 headroom，就是为了在还来得及的时候动手。
  • 不可撤销的操作：删除文件、推送代码、转账，一旦执行就回不去。所以审批和提交闸门要放在执行 之前，而不是执行之后再检查。
  • 预算：步数、时间、花费只剩一点时，agent 应该先把未完成的事务收尾，而不是开始一个新的长操作。

可行性核依赖于你允许的操作和你要维持的约束。要算它，得先把这两者写清楚，这又回到了第 6 节的规格问题。

11　换个顺序，结果一样吗

最后一个概念是 交换。两件事 A 和 P，先做 A 再做 P，和先做 P 再做 A，如果结果在我们关心的意义上等价，就说它们可交换。写成式子是

$$P(A(S)) \simeq A(P(S))$$

为什么要关心这个？因为一个可以不停扩展的系统，插件、规则、功能是一件件加上去的，加的顺序往往是偶然的。如果顺序会改变结果，每加一样东西都要重新想一遍它和所有已有东西的先后关系；如果可交换，它们就互不打扰，可以各自独立地推理。

第 2 节的模拟器里已经看到了正反两个例子：

  • 瀑布式前置检查不可交换。 「放行 git」和「危险先问」换个顺序，强推的结局就变了。
  • 只会拒绝的 guard 可交换。 每个 guard 只能把「允许的集合」缩小，最终结果是「所有 guard 都没意见」，这和它们的先后无关。这是 DSH 把 guard 设计成没有放行选项的原因。

DSH 的压缩也有一处交换性的要求（docs/subsystems/compaction.md 的事件一节）：手动压缩是异步的，在等待摘要的那段时间里，可能有一条不相关的上下文注入进来。设计上要求压缩落地之后，那条注入仍然保留在替换后的历史里，也就是「先注入再压缩」和「先压缩再注入」得到同样的结果。

不过不能要求一切都可交换。有些事情天然有先后：数据库结构必须先迁移，依赖新结构的功能才能启用。工程上真正需要的是：在允许的演化路径上，保持规定的性质。哪些操作必须可交换、哪些有固定顺序，本身就是设计的一部分。

DSH 底下的插件框架 Cordis 把「插件装上、卸下、替换之后系统状态是对的」作为核心目标，它的作者为此写了一篇论文，用代数的方法刻画什么样的修改可以互不打扰。形式化三篇会从头讲这篇论文。
