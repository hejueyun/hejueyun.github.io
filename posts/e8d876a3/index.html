找零先拿大钞，排队先让快的人，开车能不加油就不加：这些做法有一个共同点，每一步只挑眼前看起来最好的那个，不去比较以后会怎样。这种做法叫 贪心。它写出来往往只有一个循环，难的是两件事：规则从哪里想出来，以及想出来的规则会不会错。读完这一章，你应该能够：

  • 用三个常用的想法提出贪心规则；
  • 用反例排除错的规则，用交换或领先的办法说明对的规则为什么对；
  • 分清哪些问题能贪心，哪些问题条件稍微一变就不能贪心。

9.1 贪心从哪里来

有一类问题要在很多方案里挑最好的，每个方案又是一步步做选择拼出来的；把每一步的选择都试一遍太慢，贪心的想法是每一步只挑眼前看起来最好的那一个。

一类问题：一步步做选择，找最好的方案

下面这几个问题看起来各不相同：

  • 找零：一张一张拿纸币，要拿的张数最少；
  • 排会议：一场一场决定排不排，要排上的场数最多；
  • 装货：一件一件决定装不装，要装的件数最多；
  • 开车：一个一个加油站决定加不加油，要加油的次数最少。

它们的结构却是一样的：一步步做选择，所有选择合起来是一个方案，要在所有方案里找最好的那一个。这类"在很多方案里找最好的"问题叫 最优化问题。

一定对的办法：把所有选法都试一遍

第 6 章已经会做这类问题：每一步把能做的选择都试一遍，每种选择一个分支（6.6）。画出来是一棵树，从根到叶子的每条路就是一个方案，全部比较一遍，最好的那个就找到了。

下图是找零 7 元、只有 5 元和 1 元两种纸币时的这棵树。每个节点写着还差多少钱，每条边是拿了哪一张。

把所有选法都试一遍：每一步每种选择开一个分支，整棵树走完才知道哪条路最好

这个办法一定对，问题是太慢。树的大小随步数成倍增长：30 场会议，每场排或不排两种选择，方案就有 2³⁰，大约 10.7 亿种。

省事的想法：每一步只挑眼前最好的

要快，就得少走路。如果每一步不用看后面的结果，就能知道哪个选择好，那就不必展开整棵树，只走一条路。

人在生活里正是这样做的。收银员找你 37 元，手里有 100、50、20、10、5、1 元的纸币，她不会把所有拿法都比一遍，而是每次拿一张"不超过还差多少的最大面额"：

只走一条路：每一步只问“还差的钱里，能拿的最大面额是多少”

100 和 50 都比 37 大，拿不了，先拿 20；还差 17，拿 10；还差 7，拿 5；还差 2，拿两张 1。一共 5 张。

这种做法就叫 贪心：每一步按一条固定的规则只做一个选择，选了就不再改，直到问题解决。英文叫 greedy，字面意思是"贪婪"：每一步只抓眼前最大的好处，不考虑以后。那条规则叫 贪心规则，找零的规则是"拿不超过还差多少的最大面额"。

这样找出来的 5 张一定最少吗？ 对人民币这套面额来说一定是，而且能严格证明（9.3 末尾）。但规则本身是凭经验想出来的，换一套面额就可能不是最少（9.3 的 1、3、4 分硬币）。所以贪心总是分两步：规则靠启发式想出来，对不对靠反例和证明来检验。

把所有选法都试一遍贪心
每一步试几个选择所有能做的选择规则指定的那一个
走过的路整棵树一条路
写法递归一个循环
结果一定最好吗一定不一定

贪心快，是因为每一层只剩一个分支，递归退化成了一条直线，可以直接写成循环（6.8）。代价是它不再比较别的选择，所以 规则选错了，它自己发现不了。这就引出了这一章的两个问题：好的规则怎样想出来（9.2）？怎样知道它没选错（9.3～9.6）？

贪心的五句话：三句话，只试一个选择

第 6 章写递归用三句话：含义、最小情况、相信函数。贪心是同一个结构，只是"相信函数"那一句 不再把每种选择都试一遍，只试规则指定的那一个。写贪心时，把下面五句话都写出来：

  1. 含义：要解决的问题是什么。
  2. 最小情况：什么时候停。
  3. 规则：这一步在所有能做的选择里，只挑哪一个。
  4. 剩下的问题：选完以后，剩下的是不是同一个问题的更小版本；整体最好的结果，是不是"这一步 + 剩下部分最好的结果"。这一句叫 最优子结构。
  5. 为什么不会选错：按规则走了第一步以后，最好的方案仍然走得到，这一步不会把通往最好方案的路堵死。这一句叫 贪心选择性质，先用反例检验，再用交换或领先证明（9.3～9.6）。

前三句就是第 6 章的三句话，只是第三句只试一个选择。后两句是贪心要多做的检查：第 4 句保证"剩下的交给同一个办法"说得通，第 5 句保证"只试一个"没有漏掉最好的。本章每个例子都把这五句写出来。

五句话找零
含义还差 a 元，最少拿几张
最小情况还差 0 元，停
规则拿不超过 a 的最大面额 c
剩下的问题拿了 c 以后还差 a − c 元，还是找零，金额变小了。37 元拿了 20，剩下 17 元最少 4 张（10、5、1、1），整体 1 + 4 = 5 张
为什么不会选错人民币面额下成立，9.3 末尾证明；换成 1、3、4 分就不成立（9.3）

写成代码只有一个循环：

// 按贪心规则找零：每次拿不超过剩余金额的最大面额。
// amount：要找的钱（≥ 0）；notes：面额，从大到小排好，最后一种是 1。返回依次拿出的每一张。
vector<int> giveChange(int amount, const vector<int>& notes) {
    vector<int> taken;                         // taken = 已经拿出的纸币
    for (int x : notes) {                      // x = 当前考虑的面额，从大到小
        while (amount >= x) {                  // 还能拿这种面额，就一直拿
            taken.push_back(x);                // 拿一张 x
            amount -= x;                       // 剩余金额减少 x
        }
    }
    return taken;
}
# 按贪心规则找零：每次拿不超过剩余金额的最大面额。
# amount：要找的钱（≥ 0）；notes：面额，从大到小排好，最后一种是 1。返回依次拿出的每一张。
def give_change(amount, notes):
    taken = []                                 # taken = 已经拿出的纸币
    for x in notes:                            # x = 当前考虑的面额，从大到小
        while amount >= x:                     # 还能拿这种面额，就一直拿
            taken.append(x)                    # 拿一张 x
            amount -= x                        # 剩余金额减少 x
    return taken

notes 已经从大到小排好。外层循环依次看每种面额，内层的 while 在"还差的钱不少于这种面额"时一直拿。面额从大到小看，所以每次拿的都是能拿的最大面额。

要点

  1. 贪心针对的是最优化问题：一步步做选择，在所有方案里找最好的。
  2. 把所有选法都试一遍一定对，但方案数成倍增长；贪心每一步只按规则挑一个，只走一条路。
  3. 写贪心先写五句话：含义、最小情况、规则、剩下的问题（最优子结构）、为什么不会选错（贪心选择性质）。前三句就是第 6 章的三句话，只试一个选择。

A. 每一步只按规则挑一个选择，不展开其他分支，整棵树只走一条路

B. 贪心用了记忆化，同一个子问题只算一次

C. 贪心一定能找到最好的方案，所以不用比较

D. 贪心总是先排序

查看答案与每个选项的解析

A · 正确：试所有选法要走完整棵树，贪心只走其中一条路。

B · 错误：那是 6.5 的记忆化，贪心根本不展开其他分支，用不着记。

C · 错误：贪心不一定最好，它快恰恰是因为放弃了比较。

D · 错误：排序只是很多贪心的准备步骤，快的原因是只走一条路。

9.2 贪心规则从哪里来：三个常用的想法

贪心规则要从题目里找：先看要什么、什么东西不够用，再挑"让目标前进最多"或"用掉最少、给后面留下最多"的那个选择。

找零的规则很自然，因为人人都做过。换一个没见过的问题，规则从哪里来？常用的想法有三个。

三个想法：左边是问自己的问题，右边是由此得到的规则

想法一：盯住目标，每一步让目标前进最多

找零的目标是张数最少。每拿一张，还差的钱就少一些；要张数少，每一张就要让还差的钱减得最多，所以拿最大的面额。

这个想法最直接，但它只看这一步前进了多少，不看这一步之后留下的局面好不好。9.3 会看到它出错的例子。

想法二：盯住不够用的东西，每一步给后面留下最多余地

很多问题里有一样东西是有限的，每做一个选择就要用掉一些。这时问自己：什么东西不够用？哪个选择用得最少、给后面留下的最多？

  • 会议室的时间不够用。排一场会就占掉一段时间；要多排几场，每次就排 结束最早 的那场，留给后面的时间最多。
  • 卡车的载重不够用。装一件货就用掉一些载重；要装的件数多，每次就装 最轻 的那件，留给后面的载重最多。
  • 加油的次数要少。每加一次油，就要让这箱油用得最久：等到非加不可时再加，而且在开得到的最远的加油站加。

这个想法比想法一更可靠，因为它直接照顾到了"以后"。

想法三：要排先后时，给每个选择算一个数

有些问题的选择是"先做谁、后做谁"。这时找一个数，衡量"先做它划算不划算"，按这个数排序：

  • 排队打水：用时短的人先接，后面每个人都少等一些，所以按用时从短到长排；
  • 装能切开的货：每公斤越值钱越该先装，所以按"价值 ÷ 重量"从高到低排。

这个数怎样严格地推出来，9.5 用相邻交换讲。

想法只给出候选，对不对还要检验

同一个问题，按不同的想法常常会得到好几条规则，而且每条听起来都有道理。安排会议就至少有三条：

  • 开始最早的先排："早点开始，别浪费时间"；
  • 开得最短的先排："短的占用时间少"；
  • 结束最早的先排："早点结束，给后面留时间"。

9.4 会看到，前两条都是错的。所以 想法只是起点：用想法提出规则，再用反例和证明去检验它。下一节先看一条规则为什么会错，以及怎样尽快发现它错了。

要点

  1. 想法一：盯住目标，每一步让目标前进最多。
  2. 想法二：盯住不够用的东西，每一步用掉最少、留下最多。
  3. 想法三：要排先后时，给每个选择算一个数，按它排序。
  4. 想法只给出候选规则，对不对要用反例和证明检验。

A · 正确：每参加一个活动就用掉一段时间，结束最早的给后面留下的时间最多。

B · 错误：活动很多，有限的是时间；最长的活动用掉的时间最多。

C · 错误：开始早不等于结束早，一个很长的活动会把后面都挡住。

D · 错误：名字和用掉多少时间无关。

9.3 只看眼前为什么会错：换一套面额试试

同一条贪心规则，在这套数据上对，换一套数据就可能错；判断它对不对，要靠反例和证明，不能靠"听起来合理"。

用 1、3、4 分的硬币凑 6 分

假设某个国家的硬币只有 1 分、3 分、4 分三种，要凑出 6 分，最少要几枚？

照搬 9.1 找零的规则：能拿的最大面额是 4，拿一枚，还差 2；3 太大，拿 1，还差 1；再拿 1。一共 3 枚：4、1、1。

可是 3 + 3 = 6，只要 2 枚。

第一步拿 4 看起来最好，却让剩下的 2 分只能用两枚 1 分来凑

错在第一步。拿 4 让还差的钱降得最快，看起来最好；但剩下的 2 分偏偏只能用 1 分凑。拿 3 在第一步看起来差一点，剩下的 3 分却正好再用一枚 3 分。贪心只看眼前这一步，看不到这一步给后面留下了什么。 这正是 9.2 想法一的弱点：拿 4 让目标前进得最多，却把"3 + 3"这条更好的路堵死了。贪心又不回头，所以错了也不知道。

把五句话套上去，就看得出错在哪一句：

五句话用 1、3、4 分凑 6 分
含义还差 a 分，最少几枚
最小情况还差 0 分，停
规则拿不超过 a 的最大面额
剩下的问题成立：拿了 c，剩下"凑 a − c 分"还是同一个问题。第一枚拿 3 时，剩下 3 分最少 1 枚，整体 1 + 1 = 2
为什么不会选错不成立：规则让第一枚拿 4，剩下 2 分最少要 2 枚，整体 3 枚；最好的拿法 3 + 3 根本没有 4，第一步拿 4 就把它堵死了

最优子结构还在，贪心选择性质没了。 这时不能只试一个，要把第一枚的每种面额都试一遍，再取最好的：这就是下面对拍用的 bestCount，加上记忆化就是第 10 章的动态规划。

人民币的面额是专门设计过的，贪心找零总是最少张数（本节末尾证明）；面额换成 1、3、4，同样的规则就错了。可见 一条贪心规则对不对，取决于问题本身的数据，而不是规则本身听起来多合理。

怎样发现贪心错了：和"试所有"对比

手算只能试几个金额。更可靠的办法是写两个程序：一个是要检查的贪心；另一个慢一点，但一定对，就是把所有拿法都试一遍。让两个程序跑同样的金额，比较结果。这种做法叫 对拍。

一定对的那个程序，用第 6 章的三句话来写：

  1. 含义：bestCount(a) 返回凑出 a 分的最少枚数。
  2. 最小情况：a = 0 时不用硬币，返回 0。
  3. 相信函数：第一枚拿哪种不知道，每种都试。拿了面额 c，剩下的 a − c 交给 bestCount(a − c)，相信它已是最少，当前答案是所有 c 里 1 + bestCount(a − c) 最小的那个。

同一个金额会被反复问到，所以用 6.5 的记忆化，把算过的结果存进 memo。

// 贪心找零的张数：coins 从大到小排好，最后一种是 1。返回贪心拿出的硬币枚数。
int greedyCount(int amount, const vector<int>& coins) {
    int count = 0;                             // count = 已拿的枚数
    for (int c : coins) {                      // c = 当前面额，从大到小
        count += amount / c;                   // 这种面额能拿几枚就拿几枚
        amount %= c;                           // 剩下的交给更小的面额
    }
    return count;
}

// 试所有拿法，求凑出 amount 的最少枚数（6.5 的记忆化）。coins 里有 1，所以总能凑出。
// memo[a] = 凑出 a 的最少枚数，-1 表示还没算过。
int bestCount(int amount, const vector<int>& coins, vector<int>& memo) {
    if (amount == 0) return 0;                 // 最小情况：金额为 0，不用硬币
    if (memo[amount] != -1) return memo[amount];  // 算过就直接用
    int best = amount;                         // 全用面额 1，最多 amount 枚
    for (int c : coins) {                      // 第一枚拿 c，每种都试
        if (c <= amount) {
            best = min(best, 1 + bestCount(amount - c, coins, memo));  // 相信剩下的已是最少
        }
    }
    return memo[amount] = best;                // 记下来再返回
}

// 金额从 1 试到 limit，返回第一个贪心不是最少枚数的金额；都一样则返回 -1。
int firstCounterexample(const vector<int>& coins, int limit) {
    vector<int> memo(limit + 1, -1);           // 所有金额共用一张表
    for (int a = 1; a <= limit; ++a) {         // a = 正在检查的金额
        if (greedyCount(a, coins) != bestCount(a, coins, memo)) return a;  // 找到反例
    }
    return -1;                                 // limit 以内没有反例
}
# 贪心找零的张数：coins 从大到小排好，最后一种是 1。返回贪心拿出的硬币枚数。
def greedy_count(amount, coins):
    count = 0                                  # count = 已拿的枚数
    for c in coins:                            # c = 当前面额，从大到小
        count += amount // c                   # 这种面额能拿几枚就拿几枚
        amount %= c                            # 剩下的交给更小的面额
    return count


# 试所有拿法，求凑出 amount 的最少枚数（6.5 的记忆化）。coins 里有 1，所以总能凑出。
# memo[a] = 凑出 a 的最少枚数，-1 表示还没算过。
def best_count(amount, coins, memo):
    if amount == 0:                            # 最小情况：金额为 0，不用硬币
        return 0
    if memo[amount] != -1:                     # 算过就直接用
        return memo[amount]
    best = amount                              # 全用面额 1，最多 amount 枚
    for c in coins:                            # 第一枚拿 c，每种都试
        if c <= amount:
            best = min(best, 1 + best_count(amount - c, coins, memo))  # 相信剩下的已是最少
    memo[amount] = best                        # 记下来再返回
    return best


# 金额从 1 试到 limit，返回第一个贪心不是最少枚数的金额；都一样则返回 -1。
def first_counterexample(coins, limit):
    memo = [-1] * (limit + 1)                  # 所有金额共用一张表
    for a in range(1, limit + 1):              # a = 正在检查的金额
        if greedy_count(a, coins) != best_count(a, coins, memo):
            return a                           # 找到反例
    return -1                                  # limit 以内没有反例

greedyCount 是贪心：每种面额能拿几枚拿几枚（amount / c），余下的交给更小的面额。bestCount 是试所有选法。firstCounterexample 从 1 分开始逐个金额比较，返回第一个两者不同的金额。

  • firstCounterexample({4, 3, 1}, 30) 返回 6；
  • firstCounterexample({10, 7, 1}, 30) 返回 14：贪心拿 10、1、1、1、1 共 5 枚，最少是 7 + 7 两枚；
  • firstCounterexample({100, 50, 20, 10, 5, 1}, 300) 返回 −1，300 以内找不到反例。

对拍找到反例，就证明了贪心是错的；找不到反例，只说明试过的范围里没出错，并不等于证明它对。 要确认它一定对，需要证明。下面先用人民币证明一次，下一节再讲一般的办法。

人民币面额下，贪心为什么一定最少

思路：任取一种张数最少的找法，证明它在每种面额上拿的张数都和贪心一样。

第一步，看最少的找法里每种面额最多能有几张。只要某种面额太多，就能换成更少的纸币，和"张数最少"矛盾：

  • 1 元最多 4 张：5 张 1 元可以换成 1 张 5 元；
  • 5 元最多 1 张：2 张 5 元换成 1 张 10 元；
  • 10 元最多 1 张：2 张 10 元换成 1 张 20 元；
  • 20 元最多 2 张：3 张 20 元（60 元）换成 50 + 10，3 张变 2 张；而且 2 张 20 元和 1 张 10 元不会同时出现，20 + 20 + 10 = 50，换成 1 张 50 元；
  • 50 元最多 1 张：2 张 50 元换成 1 张 100 元。

第二步，算一算比某种面额小的纸币，在最少的找法里加起来最多是多少：

面额比它小的纸币最多凑出比这个面额小吗
10050 + 20 + 20 + 5 + 4 × 1 = 99小
5020 + 20 + 5 + 4 = 49小
2010 + 5 + 4 = 19小
105 + 4 = 9小
54小

第三步，拿 100 元来说：贪心能拿几张 100 元，就拿几张；如果最少的找法少拿了一张 100 元，这 100 元就得靠更小的纸币凑出来，可它们最多只能凑出 99 元，凑不出。所以 最少的找法拿的 100 元张数和贪心一样。剩下的金额对 50、20、10、5 依次用同样的理由，每种面额的张数都和贪心一样，所以贪心找出来的就是最少张数。

这里用的"把太多的纸币换成更少的纸币"，就是 9.4 要讲的交换论证。

换一套面额，怎样判断贪心还对不对？ 记两个简单的结论就够了：

  • 每种面额都是前一种的整数倍（比如 1、2、4、8，或 1、10、100），贪心一定最少。反过来不成立：人民币的 50 不是 20 的倍数，贪心照样最少。
  • 不满足整数倍时，就用上面的对拍去试，试到下面这个范围为止。

任意一套面额，对拍要试到多大？ 这个问题数学上有答案：只要有 1 元、面额从小到大排好，如果贪心在某个金额上不是最少，那么最小的这个金额一定小于最大的两种面额之和。[1] 所以对拍只要试到这个范围，找不到反例就等于证明了贪心永远对。人民币是 100 + 50 = 150，上面试到 300 都没有反例，贪心永远对；1、3、4 的范围是 4 + 3 = 7，反例 6 就在里面；1、7、10 的范围是 17，反例 14 也在里面。

要点

  1. 贪心只看眼前一步，看不到这一步给后面留下了什么。
  2. 同一条规则，换一套数据可能就错。
  3. 对拍：拿"试所有选法"的程序和贪心比较，是找反例最省力的办法；找不到反例不等于证明了它对。

9.4 怎样证明贪心不会选错：会议室安排

证明贪心对，最常用的办法是交换：任取一个最好的方案，把它的第一步换成贪心的选择，说明换完以后仍然一样好。

题目

公司只有一间会议室，同一时间只能开一场会。有 6 场会申请使用，时间如下（[1, 4) 表示从 1 点开到 4 点，4 点整就可以开下一场）。最多能安排几场？

每一行是一场会占用的时段；时段重叠的两场会不能都排

先猜规则，再找反例

每一步要做的选择是"下一场排哪个会"。9.2 列出了三条听起来都有道理的候选规则，先用小例子把错的排除掉。

猜法一：开始最早的先排。 最早开始的是 C [0, 6)，排上以后 A、B、D 都和它冲突，接着只能排 E [6, 10)，F 又和 E 冲突。一共 2 场。可是 A、D、F 三场互不冲突，所以这个规则错了：一场开始很早但开得很长的会，会把后面好几场都挡住。

猜法二：开得最短的先排。 看下面三场会：[1, 5)、[6, 10)、[4, 7)。最短的是 [4, 7)，只有 3 个小时，可是它和另外两场都冲突，排了它就只剩 1 场；而 [1, 5) 和 [6, 10) 可以都排上，是 2 场。这个规则也错了。

最短的会恰好压在另外两场中间，排了它，另外两场都排不了

猜法三：结束最早的先排。 按结束时间看，A 最早结束（4 点），排 A；B 和 C 都在 4 点以前开始，和 A 冲突，跳过；D 在 5 点开始，排 D；E 在 6 点开始，D 7 点才结束，跳过；F 在 8 点开始，排 F。一共 3 场：A、D、F。

按结束最早的规则：选中 A、D、F，其余的和已选的会冲突

直觉上的理由是：一场会结束得越早，留给后面的时间就越多。 但前两种猜法的直觉听起来也很合理，所以还需要一个真正的说明。

为什么不会选错下面的交换论证

第 4 句为什么成立：剩下的会都在 g 结束以后开始，和 g 都不冲突，g 不会限制剩下的会怎么排；剩下的排得越多，整体就越多，所以整体最好 = 1 + 剩下部分最好。

第 5 句：交换论证，为什么"结束最早"不会选错

要说明的是：第一步排结束最早的那场会，不会让我们错过最好的结果。

设所有会议里结束最早的是 g（例子里是 A）。任意拿一个最好的安排方案，把它的会按时间排好，第一场叫 x。

  1. g 是所有会议里结束最早的，所以 g 结束得不比 x 晚。
  2. 方案里排在 x 后面的会，都在 x 结束以后才开始，所以也都在 g 结束以后才开始，和 g 不冲突。
  3. 把方案里的 x 换成 g，得到的仍然是一个互不冲突的安排，场数一样多，所以 换完以后仍是一个最好的方案。

例子里，B、D、F 是一个 3 场的最好方案，第一场是 B [3, 5)。把 B 换成 A [1, 4)：A 结束得更早，和 D、F 都不冲突，换完还是 3 场。

B 换成更早结束的 A，后面的 D、F 一场都不受影响，场数不变

所以第一步排 g，最好的方案还在。两句合起来：

  • 第 5 句，贪心选择性质：按规则做的第一个选择，一定能出现在某个最好的方案里，不会把通往最好方案的路堵死。上面的交换证明的就是这一句；9.3 里拿 4 分硬币，就是把"3 + 3"这条路堵死了。
  • 第 4 句，最优子结构：做完这个选择，剩下的是同一个问题的更小版本，剩下部分最好的结果加上这个选择，就是整体最好的结果。

排了 g 以后，对剩下的会再用一次这两句：第一步还是排结束最早的，还是不会错过最好的方案。一步步推下去，一直到没有会可排，排出来的就是最好的。

更深一层（了解即可）。 有一大类问题是"从一堆元素里挑出一个互不冲突的子集，让权重之和最大"。数学上已经把它刻画清楚了：如果"互不冲突"满足一种叫 拟阵 的结构，那么"按权重从大到小，能加就加"的贪心对任何权重都是最优的，22.12 的 Kruskal 最小生成树就属于这一类。但很多贪心题不是拟阵，比如这里的会议室：已选 [1, 10) 一场，另一种选法有 [1, 2)、[3, 4) 两场，可这两场哪一场都加不进前一种选法，拟阵要求的"总能从多的那组里借一个过来"不成立。这类题仍然要像上面这样，逐题用交换或领先来证明。

代码

// 一场会占用 [start, end)：从 start 开到 end，end 这一刻就可以开下一场。
struct Meeting {
    int start, end;
};

// 排序用：结束早的排在前面。
bool endsEarlier(const Meeting& a, const Meeting& b) {
    return a.end < b.end;
}

// 一间会议室最多安排几场会。返回按"结束最早"规则选中的会议，按选中的先后排列。
vector<Meeting> pickMeetings(vector<Meeting> meetings) {
    sort(meetings.begin(), meetings.end(), endsEarlier);  // 按结束时刻排序
    vector<Meeting> chosen;                    // chosen = 已选中的会议
    int freeAt = -1000000000;                  // freeAt = 会议室从这个时刻起空闲
    for (const Meeting& m : meetings) {        // m = 结束最早的、还没看过的会议
        if (m.start >= freeAt) {               // 开始时会议室已空出来：选它
            chosen.push_back(m);
            freeAt = m.end;                    // 会议室到它结束才空闲
        }
    }
    return chosen;
}
# 一间会议室最多安排几场会。meetings 的每个元素是 (start, end)，end 这一刻就可以开下一场。
# 返回按"结束最早"规则选中的会议，按选中的先后排列。
def pick_meetings(meetings):
    chosen = []                                # chosen = 已选中的会议
    free_at = float("-inf")                    # free_at = 会议室从这个时刻起空闲
    by_end = sorted(meetings, key=lambda m: m[1])  # 按结束时刻排序
    for start, end in by_end:                  # 结束最早的、还没看过的会议
        if start >= free_at:                   # 开始时会议室已空出来：选它
            chosen.append((start, end))
            free_at = end                      # 会议室到它结束才空闲
    return chosen

Meeting 把一场会的开始和结束放在一起；endsEarlier 告诉 sort 按什么排：结束早的在前。排好以后，依次看到的就是"还没看过的会里结束最早的"。freeAt 记录会议室从什么时刻起空闲。一场会的开始时刻不早于 freeAt，就和已经排上的会都不冲突，排上它，把 freeAt 改成它的结束时刻。条件写成大于等于，是因为 4 点结束、4 点开始不算冲突。

排序 O(n log n)，之后扫一遍 O(n)，总时间 O(n log n)。

要点

  1. 先猜几条规则，用小例子把错的排除掉，再去证明剩下的那条。
  2. 交换论证：任取一个最好的方案，把它的第一步换成贪心的选择，说明换完仍然一样好。
  3. 五句话的后两句是贪心能用的两个条件：第 4 句最优子结构（剩下的是同一个问题的更小版本，整体最好 = 这一步 + 剩下最好），第 5 句贪心选择性质（第一步按规则选，不会错过最好的方案）。

9.5 按什么顺序排：相邻交换

很多贪心是"按某个顺序排好，再依次处理"；要找出按什么排，就比较相邻两个元素交换前后的代价。

排队打水

一个水龙头前排着 3 个人，接满水分别要 3、1、2 分钟。每个人的 等待时间 是从开始到他自己接完的时间。怎样安排顺序，所有人的等待时间加起来最少？

按原来的顺序 3、1、2：第一个人 3 分钟接完，第二个人 3 + 1 = 4 分钟，第三个人 4 + 2 = 6 分钟，总和 3 + 4 + 6 = 13。

第 5 句：相邻交换是什么

相邻交换是证明"按某个顺序排好就最优"的一种方法：只比较顺序里挨着的两个元素，谁在前面更好，然后说明任何顺序都能一步步换成按这个规则排好的样子，而且每换一次都不会变差。

它用在答案是一个 顺序 的题上，比如几个人怎么排队、几个任务先做哪个。分三步：

  1. 只看相邻的一对。 在任意一个顺序里，挑出挨着的两个元素 p、q，比较"p 在前"和"q 在前"两种情况的总代价，其他元素的位置都不动。
  2. 说明交换只影响这两个人。 如果交换 p、q 只改变它们俩自己的代价，前面和后面的元素都不受影响，那么两种情况的差就只和 p、q 有关，能写成一个比较条件，例如"p 的用时更短，p 就该在前"。这个条件就是排序的规则。
  3. 说明一路换下去不会变差。 任意拿一个顺序，只要有挨着的两个不符合规则，就把它们交换，总代价不会变大。像冒泡排序那样一直换，最后一定变成按规则排好的顺序。拿最好的那个顺序来这样换，换完的代价不会比它大，所以 按规则排好的顺序也是最好的。

和 9.4 的交换论证比：那里换的是"最好方案的第一步"，这里换的是"顺序里挨着的两个"，道理一样，都是换完不变差。

用在排队打水上

第 1 步：只看相邻的一对。 队伍里挨着的两个人 p、q，接水分别要 tp、tq 分钟，他们前面的人一共用了 T 分钟。

  • p 在前：p 在 T + tp 接完，q 在 T + tp + tq 接完；
  • q 在前：q 在 T + tq 接完，p 在 T + tp + tq 接完。

第 2 步：交换只影响这两个人。 前面的人不受影响；后面的人开始接水的时刻，两种情况下都是 T + tp + tq，也不受影响。所以只比这两个人自己：后接完的那个人两种情况都是 T + tp + tq，差别只在先接的那个人，p 在前是 T + tp，q 在前是 T + tq。tp > tq 时，把 q 换到前面，总等待少了 tp − tq。比较条件就是：用时短的在前。

tp = 3、tq = 1：p 在前，两人在 3、4 分钟接完，共 7；q 在前，在 1、4 分钟接完，共 5

第 3 步：一路换下去不会变差。 拿原来的顺序 3、1、2 试一试：

顺序每人接完的时刻总等待这一步做了什么

1、3、21、4、6113 和 1 挨着且 3 更长，交换，少了 3 − 1 = 2
1、2、31、3、6103 和 2 挨着且 3 更长，交换，少了 3 − 2 = 1

再也没有"长的紧挨在短的前面"了，顺序就是从短到长，总等待 10，和上面把 6 种顺序全算一遍得到的最小值一样。任何顺序都能这样换到从短到长，每一步都不变差，所以 按用时从短到长排，一定是最好的。

代码

// 一个水龙头，t[i] 是第 i 个人接水要用的分钟数。每个人的等待时间 = 从开始到他接完的时间。
// 返回所有人等待时间之和的最小值。
long long minTotalWait(vector<int> t) {        // t 按值传入，排序的是副本
    sort(t.begin(), t.end());                  // 用时短的排前面
    long long now = 0, total = 0;              // now = 当前时刻；total = 等待时间之和
    for (int x : t) {                          // x = 下一个人的用时
        now += x;                              // 他接完的时刻
        total += now;                          // 他的等待时间就是这个时刻
    }
    return total;
}

// 按给定顺序接水时的等待时间之和，用来和最优顺序对照。
long long totalWaitInOrder(const vector<int>& t) {
    long long now = 0, total = 0;              // now = 当前时刻；total = 等待时间之和
    for (int x : t) {                          // x = 下一个人的用时，不排序
        now += x;
        total += now;
    }
    return total;
}

# 返回所有人等待时间之和的最小值。
def min_total_wait(t):
    now = total = 0                            # now = 当前时刻；total = 等待时间之和
    for x in sorted(t):                        # 用时短的排前面；x = 下一个人的用时
        now += x                               # 他接完的时刻
        total += now                           # 他的等待时间就是这个时刻
    return total


# 按给定顺序接水时的等待时间之和，用来和最优顺序对照。
def total_wait_in_order(t):
    now = total = 0                            # now = 当前时刻；total = 等待时间之和
    for x in t:                                # x = 下一个人的用时，不排序
        now += x
        total += now

now 是当前时刻，每个人接完，now 加上他的用时，这时的 now 就是他的等待时间，累加进 total。minTotalWait({3, 1, 2}) 返回 10，totalWaitInOrder({3, 1, 2}) 返回 13。时间主要花在排序上，是 O(n log n)。

要点

  1. 相邻交换用来证明"按某个规则排好就最优"，分三步：只看相邻的一对；说明交换只影响这两个；说明一路换下去不变差。
  2. 比较相邻两个的两种顺序，得到的条件就是排序规则（排队打水：用时短的在前）。
  3. 任何顺序都能像冒泡排序那样换成按规则排好的样子，每一步不变差，所以按规则排好的就是最好的。

9.6 一边走一边记住最远能到哪：开车加油

另一种常用的证明是"始终领先"：说明贪心每走一步，都不落后于任何其他方案。

题目

一辆车油箱加满能跑 10 公里，出发时是满的。路上的加油站在第 3、8、12、17、21 公里处，终点在第 25 公里。每次加油都加满，最少加几次油能到终点？

规则：非加不可的时候，在最远的那个加

能不加就不加：油够开到前面，就不停。等到再往前就要没油了，才非加不可；这时在开得到的加油站里，选 最远的那一个 加满。

  1. 满油从 0 出发，最远到 10。3、8 开得到，12 开不到，所以 12 之前必须加一次油。开得到的里面最远的是 8，在 8 加满，最远到 18。
  2. 12、17 开得到，21 开不到，在 17 加满，最远到 27。
  3. 27 已经超过终点 25，到了。一共加 2 次油。

每一行是一箱油能开到的范围：只在 8 和 17 加油，第 3 箱油就越过了终点 25

换一种做法对比：在 3 就加油，最远到 13；只好在 12 再加，最远到 22；再在 21 加一次，才能到终点。一共 3 次。早加油，等于把油箱里还没用完的油浪费了。

五句话

五句话开车加油
含义从当前位置满油出发，最少再加几次油到终点
最小情况这箱油已经能开到终点，停
规则非加不可时，在开得到的加油站里选最远的那个加满
剩下的问题在加油站 s 加满以后，剩下的是"从 s 满油出发，最少加几次到终点"，还是同一个问题。例子里在 8 加满，剩下的"从 8 出发"只要再在 17 加 1 次，整体 1 + 1 = 2 次
为什么不会选错下面的始终领先

第 5 句：始终领先，为什么在最远的那个加不会错

要说明贪心最好，就拿它和"随便另一个能到终点的方案"比，看每加完一次油，谁能开得更远。 下面把这个"另一个方案"叫作 方案 B。

先用具体的例子看。方案 B 就用上面那个早加油的做法：在 3、12、21 加油。贪心在 8、17 加油。

加完第几次油贪心：在哪加，最远到哪方案 B：在哪加，最远到哪
0 次（刚出发）最远 10最远 10
1 次在 8 加，最远 18在 3 加，最远 13
2 次在 17 加，最远 27，到终点了在 12 加，最远 22
3 次在 21 加，最远 31，到终点了

每一行，贪心那一列的"最远"都不比方案 B 小：10 和 10，18 和 13，27 和 22。这就是 始终领先。

为什么换成任何别的方案 B，贪心也总是领先？一次一次看：

  1. 刚出发： 两边都是满油，最远都到 10，一样远。
  2. 假设加完第 k 次以后，贪心最远能到的不比方案 B 近。 方案 B 第 k + 1 次在某个加油站 s 加油，s 是方案 B 开得到的，所以 s 不超过方案 B 的最远处，也就不超过贪心的最远处，贪心也开得到 s。贪心选的是开得到的加油站里最远的那个，所以它选的不会比 s 近；两边都加满一箱，贪心加完以后最远能到的，也就不比方案 B 近。
  3. 从第 0 次开始一次次推下去，每加完一次油，贪心最远能到的地方都不比方案 B 近。

方案 B 加 m 次油到了终点；贪心加完 m 次以后开得一样远或更远，也能到终点。所以贪心加油的次数不会比方案 B 多。方案 B 是随便取的，换成加油次数最少的那个方案也一样，所以贪心的次数就是最少的。

这种说法叫 领先论证：说明每一步之后，贪心都至少和任何方案一样好。它和上一节的交换论证是证明贪心最常用的两种办法。

代码

// 油箱加满能跑 d 公里，出发时是满的；路上的加油站位置从小到大排在 s 里；终点在 L 公里处。
// 返回最少加几次油；到不了终点返回 -1。
int minStops(int d, const vector<int>& s, int L) {
    int reach = d;                             // reach = 不再加油最远能开到哪
    int stops = 0;                             // stops = 已加油的次数
    int i = 0;                                 // i = 下一个还没经过的加油站
    while (reach < L) {                        // 还到不了终点，就得再加一次
        int best = -1;                         // best = 能开到的最远的加油站
        while (i < (int)s.size() && s[i] <= reach) {  // 开得到的都看一遍
            best = s[i];
            ++i;
        }
        if (best == -1) return -1;             // 一个新的加油站都开不到：到不了
        reach = best + d;                      // 在最远的那个加满
        ++stops;
    }
    return stops;
}
# 油箱加满能跑 d 公里，出发时是满的；路上的加油站位置从小到大排在 s 里；终点在 L 公里处。
# 返回最少加几次油；到不了终点返回 -1。
def min_stops(d, s, L):
    reach = d                                  # reach = 不再加油最远能开到哪
    stops = 0                                  # stops = 已加油的次数
    i = 0                                      # i = 下一个还没经过的加油站
    while reach < L:                           # 还到不了终点，就得再加一次
        best = -1                              # best = 能开到的最远的加油站
        while i < len(s) and s[i] <= reach:    # 把开得到的加油站都看一遍
            best = s[i]
            i += 1
        if best == -1:                         # 一个新的加油站都开不到：到不了
            return -1
        reach = best + d                       # 在最远的那个加满
        stops += 1
    return stops

reach 是不再加油最远能到哪。还到不了终点，就把 reach 以内、还没经过的加油站都看一遍，记下最远的那个 best，在那里加满，reach 变成 best + d。一个新的加油站都开不到，说明两个加油站之间的距离超过了一箱油，返回 −1：比如一箱油跑 5 公里，加油站在 3 和 9，从 3 加满最远到 8，到不了 9。

下标 i 只往前走，每个加油站只看一次，所以时间是 O(n)。同一道题用动态规划写是 O(n²)，两种写法的对比放在 10.7。

要点

  1. 非加不可时，在开得到的最远的加油站加：用掉的油最多，浪费最少。
  2. 领先论证：说明贪心每走一步，都不落后于任何方案，最后自然也不落后。
  3. 这类题在一个变量里维护"目前最远能到哪"，一边走一边更新。

9.7 什么时候不能贪心：两种背包

交换论证用到的那一步"换"，在问题条件变了以后可能就做不到；做不到时贪心就会出错，要改用试所有选法或动态规划。

同样的货物，两种装法

背包最多装 50 公斤。有三种货物：

货物甲乙丙
重量10 公斤20 公斤30 公斤
价值60 元100 元120 元
每公斤价值6 元5 元4 元

情况一：货物可以切开拿，像大米、沙子一样，拿多少算多少钱。规则：每公斤最值钱的先装。甲 10 公斤全装（60 元），乙 20 公斤全装（100 元），还剩 20 公斤，装丙的 20 公斤（80 元）。一共 240 元，这就是最好的。

为什么对？用交换说明：如果背包里有一公斤便宜的货，外面还有更贵的货没装完，把这一公斤便宜的换成一公斤贵的，重量不变，价值变多。所以最好的装法里，一定是贵的先装满。

情况二：货物只能整件拿，像电视、冰箱一样。照用同样的规则：甲（10 公斤）装上，乙（20 公斤）装上，还剩 20 公斤，丙要 30 公斤，装不下。一共 160 元。可是不装甲，装乙和丙，正好 50 公斤，220 元。贪心错了。

同样的规则，货物能切开时是最好的，只能整件拿时就错了

错在哪里？情况一的交换是"一公斤换一公斤"。只能整件拿时换不了一公斤，只能整件换，重量对不上：把甲换成丙，要多出 20 公斤的空间，而背包里没有。交换论证的那一步做不到了，贪心选择性质就不成立了。

两种情况的五句话放在一起：

五句话可以切开只能整件拿
含义容量还剩 c，最多装多少钱同左
最小情况容量用完或货装完，停同左
规则装每公斤最值钱的，能装多少装多少装每公斤最值钱的那件，装得下就装
剩下的问题成立：装了 x 公斤以后，剩下"容量少 x 公斤"的同一个问题成立：装了乙以后，剩下"30 公斤里从甲、丙中挑"，还是同一个问题
为什么不会选错成立：一公斤换一公斤不成立：整件换不了，甲、乙、丙就是反例

只能整件拿时，和 9.3 的 1、3、4 分硬币一样：第 4 句成立，第 5 句不成立。最优子结构还在，说明"装了某件以后，剩下的交给同一个问题"仍然对；只是不知道第一步该拿哪件，那就每种都试。

这时怎么办

只能整件拿的时候，每件货只有装和不装两种选择，正是 6.6 的"每层做一个决定"。把所有装法都试一遍，就一定能找到最好的：

// 一种货物：重量（公斤，> 0）和价值（元）。
struct Item {
    int weight, value;
};

// 排序用：每公斤价值高的排在前面（交叉相乘，避免小数）。
bool worthMore(const Item& a, const Item& b) {
    return (long long)a.value * b.weight > (long long)b.value * a.weight;
}

// 可以切开拿的背包：cap 是容量，返回能装的最大价值。
double fractionalKnapsack(vector<Item> items, int cap) {
    sort(items.begin(), items.end(), worthMore);  // 每公斤最值钱的先装
    double total = 0;                          // total = 已装的价值
    for (const Item& it : items) {             // it = 还没装的里面每公斤最值钱的
        if (cap == 0) break;                   // 装满了
        int take = min(cap, it.weight);        // 能装下就全装，装不下就装满为止
        total += (double)it.value * take / it.weight;  // 按比例算价值
        cap -= take;
    }
    return total;
}

// 只能整件拿的背包，照用上面的规则（会出错，作为对照）。
int greedy01(vector<Item> items, int cap) {
    sort(items.begin(), items.end(), worthMore);  // 每公斤最值钱的先看
    int total = 0;                             // total = 已装的价值
    for (const Item& it : items) {
        if (it.weight <= cap) {                // 整件装得下才装
            total += it.value;
            cap -= it.weight;
        }
    }
    return total;
}

// 只能整件拿的背包，试所有装法（6.6 的选或不选）。
// 从第 i 件起、容量还剩 cap，返回能装的最大价值。
int best01(const vector<Item>& items, int i, int cap) {
    if (i == (int)items.size()) return 0;      // 最小情况：没有货了
    int skip = best01(items, i + 1, cap);      // 不装第 i 件
    if (items[i].weight > cap) return skip;    // 装不下，只能不装
    // 装第 i 件：得到它的价值，容量减少它的重量
    int take = items[i].value + best01(items, i + 1, cap - items[i].weight);
    return max(skip, take);
}
# 可以切开拿的背包。items 的每个元素是 (重量, 价值)，重量 > 0。
# cap 是背包容量，返回能装的最大价值。
def fractional_knapsack(items, cap):
    value = 0.0                                # value = 已装的价值
    order = sorted(items, key=lambda it: it[1] / it[0], reverse=True)  # 每公斤最值钱的先装
    for w, v in order:                         # w = 重量，v = 价值
        if cap == 0:                           # 装满了
            break
        take = min(cap, w)                     # 能装下就全装，装不下就装满为止
        value += v * take / w                  # 按比例算价值
        cap -= take
    return value


# 只能整件拿的背包，用按单位价值贪心的办法（会出错，作为对照）。
def greedy01(items, cap):
    value = 0                                  # value = 已装的价值
    order = sorted(items, key=lambda it: it[1] / it[0], reverse=True)  # 每公斤最值钱的先看
    for w, v in order:                         # w = 重量，v = 价值
        if w <= cap:                           # 整件装得下才装
            value += v
            cap -= w
    return value


# 只能整件拿的背包，试所有装法（6.6 的选或不选）。
# 从第 i 件起、容量还剩 cap，返回能装的最大价值。
def best01(items, i, cap):
    if i == len(items):                        # 最小情况：没有物品了
        return 0
    skip = best01(items, i + 1, cap)           # 不装第 i 件
    if items[i][0] > cap:                      # 装不下，只能不装
        return skip
    # 装第 i 件：得到它的价值，容量减少它的重量
    take = items[i][1] + best01(items, i + 1, cap - items[i][0])
    return max(skip, take)
  • Item 是一种货物的重量和价值。worthMore 告诉 sort 把每公斤价值高的排在前面；为了不用小数，"a 每公斤比 b 值钱"写成 a.value × b.weight > b.value × a.weight。
  • fractionalKnapsack 是情况一的贪心，返回 240。
  • greedy01 把同样的规则用在情况二，返回 160。
  • best01 用三句话写成：含义是"从第 i 件起、容量还剩 cap，能装的最大价值"；最小情况是没有货了，返回 0；相信函数，就是装和不装各试一次，取大的。它返回 220。

best01 每件货分两支，n 件货要试 2ⁿ 种装法。同样的 (i, cap) 会被反复问到，加上 6.5 的记忆化，就变成了 动态规划，第 10 章会专门讲。

  • 第 4 句成立、第 5 句不成立：不能只试一个，每种选择都试，再加记忆化，就是动态规划。
  • 第 4 句也不成立，剩下的不是同一个问题：只能用回溯把方案都试一遍。

9.8 练习

三道题各用到本章的一个办法：先自己想规则、找反例，再看提示。

练习 1　卡车装货

一辆卡车限重 cap 公斤，仓库里有几件货，重量各不相同。不在乎装的是哪几件，只想装的 件数 最多。写函数 maxItems(w, cap)，w 是每件货的重量，返回最多能装几件。

样例 1：w = {7, 2, 9, 4, 3}，cap = 10，答案 3。装 2、3、4 公斤这三件，共 9 公斤；再加任何一件都超过 10。

样例 2：w = {12, 15}，cap = 10，答案 0。最轻的一件都装不下。

提示
  • 含义：载重还剩 c，最多再装几件。
  • 最小情况：剩下最轻的一件也装不下，停。
  • 规则：在剩下的货里装最轻的。
  • 剩下的问题：装了一件重 w 的以后，剩下"载重 c − w、少一件货"还是同一个问题，整体件数 = 1 + 剩下最多的件数。
  • 为什么不会选错：交换。任何一种装法如果没装最轻的那件，把它装的任意一件换成最轻的，总重量不会变大，件数不变。

写法：先把 w 从小到大排序，依次装，装不下就停，后面的更重，也装不下。

参考答案
// 练习 9.8-1：卡车最多装几件货。w：每件货的重量；cap：卡车限重。返回最多能装的件数。
int maxItems(vector<int> w, int cap) {         // w 按值传入，排序的是副本
    sort(w.begin(), w.end());                  // 从轻到重排好
    int count = 0;                             // count = 已装的件数
    for (int x : w) {                          // x = 下一件最轻的货
        if (x > cap) break;                    // 最轻的都装不下，后面更重，结束
        cap -= x;                              // 装上，剩余载重减少
        ++count;
    }
    return count;
}
# 练习 9.8-1：卡车最多装几件货。w：每件货的重量；cap：卡车限重。返回最多能装的件数。
def max_items(w, cap):
    count = 0                                  # count = 已装的件数
    for x in sorted(w):                        # 从轻到重看；sorted 不改 w
        if x > cap:                            # 最轻的都装不下，后面更重，结束
            break
        cap -= x                               # 装上，剩余载重减少
        count += 1
    return count

练习 2　放检查点

一条路上有几段施工区间，每段是 [l, r]（两端都算）。要在路上放检查点，使每段施工区间里至少有一个检查点。最少放几个？写函数 minPoints(segs)。

样例 1：segs = {[1,4], [2,6], [5,8], [7,9]}，答案 2。在 4 和 8 各放一个：[1,4]、[2,6] 都包含 4，[5,8]、[7,9] 都包含 8。

样例 2：segs = {[1,2], [3,4], [5,6]}，答案 3。三段互不相交，每段要各放一个。

提示
  • 含义：还有一些区间没被覆盖，最少再放几个点。
  • 最小情况：所有区间都被覆盖了，停。
  • 规则：在没被覆盖的区间里找右端最小的那段，在它的右端放一个点。
  • 剩下的问题：放了这个点以后，去掉所有包含它的区间，剩下的区间还是同一个问题，整体 = 1 + 剩下最少的点数。
  • 为什么不会选错：交换。右端最小的那段一定要有一个点；任何方案里覆盖它的那个点，往右挪到它的右端，仍然在它里面。原来包含这个点的区间，右端都不比它小，挪过去以后仍然包含，不会失去覆盖。

写法：按右端从小到大排序，依次看区间，已经包含上一个点的跳过，没包含的就在它的右端放一个新点。

参考答案
// 练习 9.8-2：一段施工区间 [l, r]，两端都算在内。
struct Segment {
    int l, r;
};

// 排序用：右端小的排在前面。
bool rightSmaller(const Segment& a, const Segment& b) {
    return a.r < b.r;
}

// 每段施工区间里至少要有一个检查点，返回最少放几个。
int minPoints(vector<Segment> segs) {
    sort(segs.begin(), segs.end(), rightSmaller);  // 按右端排序
    int count = 0;                             // count = 已放的检查点个数
    long long last = -4000000000LL;            // last = 最后一个检查点的位置，开始时没有
    for (const Segment& s : segs) {            // s = 右端最小的、还没看过的区间
        if (s.l > last) {                      // 现有的点都不在 s 里
            last = s.r;                        // 在 s 的右端放一个新点
            ++count;
        }
    }
    return count;
}
# 练习 9.8-2：每个区间 [l, r]（两端都含）里至少要有一个检查点，最少放几个。
def min_points(segs):
    count = 0                                  # count = 已放的检查点个数
    last = float("-inf")                       # last = 最后一个检查点的位置，开始时没有
    by_right = sorted(segs, key=lambda seg: seg[1])  # 按右端排序
    for l, r in by_right:                      # 右端最小的、还没看过的区间
        if l > last:                           # 现有的点都不在这个区间里
            last = r                           # 在它的右端放一个新点
            count += 1
    return count

练习 3　踩石头过河

河里有一排石头，从第 0 块出发，在第 i 块石头上最多能往前跳 a[i] 块（也可以跳得更少）。能不能跳到最后一块？写函数 canCross(a)。

样例 1：a = {2, 3, 1, 1, 4}，答案 true。从 0 跳到 1，再从 1 跳 3 块到最后一块。

样例 2：a = {3, 2, 1, 0, 4}，答案 false。从 0、1、2 最远都只能跳到第 3 块，而第 3 块上一步都跳不动。

提示
  • 含义：目前最远能到第 far 块，从第 i 块往后看，能不能到最后一块。
  • 最小情况：所有石头都看完了，返回 true；看到的第 i 块已经超过 far，它根本到不了，返回 false。
  • 规则：不去决定具体跳到哪块，每看一块，就用它能跳到的最远处 i + a[i] 更新 far。
  • 剩下的问题：看完第 i 块以后，剩下的是"far 已更新，从第 i + 1 块往后看"，还是同一个问题。
  • 为什么不会选错：领先。也可以跳得比 a[i] 少，所以 far 以内的石头都到得了；任何一种具体跳法能到的石头，都不会超过 far。

和开车加油一样，只用一个变量记"目前最远能到哪"。

参考答案
// 练习 9.8-3：踩石头过河。a[i] 是在第 i 块石头上最多能往前跳几块。
// 从第 0 块出发，返回能否跳到最后一块。
bool canCross(const vector<int>& a) {
    int far = 0;                               // far = 目前最远能到第几块
    for (int i = 0; i < (int)a.size(); ++i) {  // i = 当前站的石头
        if (i > far) return false;             // 这块石头根本到不了
        far = max(far, i + a[i]);              // 从这里起跳，最远能到 i + a[i]
    }
    return true;                               // 每块都到得了，最后一块也是
}
# 练习 9.8-3：踩石头过河。a[i] 是在第 i 块石头上最多能往前跳几块。
# 从第 0 块出发，返回能否跳到最后一块。
def can_cross(a):
    far = 0                                    # far = 目前最远能到第几块
    for i in range(len(a)):                    # i = 当前站的石头
        if i > far:                            # 这块石头根本到不了
            return False
        far = max(far, i + a[i])               # 从这里起跳，最远能到 i + a[i]
    return True                                # 每块都到得了，最后一块也是
