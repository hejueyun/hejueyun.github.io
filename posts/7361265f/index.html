ProverB深度导读·PV0与PV1-从linter到SMT求解器

2026-05-11

1. 第二章 · PV0：沾形式化的边，但不承诺什么

ProVerB 自己都承认 PV0 是”一个故意不打算填满的房间”。它的存在是一种界碑：
有一些工具看起来跟形式化沾边——它们操作文法、自动机、高精度数——
但它们并不做证明，也不声称做证明。

举几个典型：

  • ANTLR：你可能写过词法分析器。ANTLR 严格地按照你给的 BNF/EBNF 生成 parser，
    但没有人会说 ANTLR “证明了”你的语言定义对某条性质成立。它只是”很守规矩”。
  • CUDD：操作 BDD（二叉决策图）的 C 库。BDD 是后面第五章要讲的符号模型检验的骨头，
    但 CUDD 本身不做检验，它只提供数据结构。

什么是 BDD？

BDD（Binary Decision Diagram，二叉决策图）是一种用来紧凑地表示布尔函数的数据结构。
最笨的方法是列真值表——3 个变量就有 $2^3 = 8$ 行，30 个变量就是 $10^9$ 行，完全不可行。

BDD 的思路是把真值表压缩成一棵有向无环图：每个内部节点是一个布尔变量，
左分支代表”这个变量取 0”，右分支代表”取 1”，叶子节点只有两个——true 和 false。
然后做两步压缩：

  1. 消除冗余节点：如果一个变量的两条分支指向同一个地方，它根本不影响结果，直接跳过。
  2. 共享相同子图：结构相同的子树只保留一份。

经过这两步得到的叫 ROBDD（Reduced Ordered BDD），它有一个神奇的性质：
对于固定的变量顺序，任何布尔函数的 ROBDD 是唯一的。
这意味着判断两个布尔函数是否等价，只要看它们的 BDD 是不是同一张图——O(1) 的操作。

用 f(a, b) = a ∧ b 走一遍建图过程：

第 0 步：完整二叉决策树（真值表变树，4 片叶子）

第 1 步：共享相同叶子（三个 F 合并为同一个节点）

第 2 步：合并相同子树（左边的 [b] 和右边的 [b] 结构完全一样：0→F、1→T，合并成一个）

这就是最终 ROBDD。底部的 [F] 和左边的 [F] 是同一个对象（指针相同）。

为什么唯一？ 换一个等价公式 g(a, b) = ¬(¬a ∨ ¬b)（德摩根等价，逻辑上与 a ∧ b 完全相同），
真值表一模一样，建出来的 ROBDD 就是同一张图——不是”长得像”，
而是指针级别的同一个对象。判断 f ≡ g 只需比较根节点指针，O(1) 就是这么来的。

直觉上：ROBDD 是布尔函数的**”身份证”**，建图很贵（可能指数级），但建完之后等价性、
可满足性判断都极快。这正是 Ken McMillan 1993 年用它做符号模型检验的底气。

为什么重要？第五章会讲到 Ken McMillan 用 BDD 来表示状态集合
而不是逐个枚举状态，让模型检验从几千个状态一跳到 $10^{20}$ 个状态。
CUDD 就是那一层的地基。

BDD 和 SAT 解决的是同一类问题（布尔函数的可满足性），但策略完全不同：
BDD 先花大力气建图，建完之后查询极快（等价性 O(1)）；
SAT 不建图，每次从头搜索，但单次搜索很高效。
第五章讲 BMC 时会说”不用 BDD，直接用 SAT”——那篇 1999 年的论文就是发现：
对于很多实际问题，SAT 的”每次重新搜”反而比 BDD 的”先建完整图”更快，
因为 BDD 在变量多的时候可能指数爆炸。

  • MPFR / Apfloat：多精度浮点库。数值分析从业者很爱它，但它也不验证任何事。
  • Crab：抽象解释框架的”建造模具”。注意，Crab 本身只是提供域（interval, octagon, polyhedra 等）
    的组合原语；在此之上搭出来的分析器通常属于 PV1。

PV0 的意义更像是历史学意义上的——它提醒你，在每一个真正做验证的工具背后，
往往有一个不显眼的 PV0 库在做底层的数据结构和运算。
下一次你看到 Z3 内部用到 MPFR 做浮点理论判定，或者 nuXmv 内部使用 CUDD，
你会明白 PV0 为什么必须独占一章。

2. 第三章 · PV1：自动化的第一个承诺——从 linter 到求解器

PV1 是整本书里工具数量第二多的一层（约 98 个工具），原因简单：
它是程序员最先能用起来的一层——你不用写规约，也不用写证明，
直接把代码或者一条逻辑公式喂进去，它告诉你”这里不对劲”。

但 PV1 自己内部又被历史切成两截：一截是linter / 静态分析的血统，
另一截是求解器的血统。这两条线后来在上层工具里结合，
但它们的出身完全不同，值得分开讲。

2.1. 3.1 linter 那一支：从类型检查到抽象解释

这条线的始祖其实不是 linter，是 1950 年代 ALGOL 时代的”类型检查”——
类型系统本身就是一个轻量的证明系统，你写 int + float 编译器拒绝你，
就是一次小型的形式化验证。
Dijkstra、Hoare 在 1960–70 年代把这套思路推广成了 Hoare Logic：
用 {P} C {Q} 的三元组来描述”在前置条件 P 下执行 C 后后置条件 Q 成立”。
1976 年 Patrick Cousot 和 Radhia Cousot 夫妇在 POPL 上发表了
抽象解释（Abstract Interpretation），给”静态近似程序行为”第一次有了统一的数学底座。

抽象解释的思想一句话能讲清楚：
你不可能精确地知道”变量 x 在这一行可能取什么值”（停机问题），
那就用一个保守的近似代替——比如用区间 [1, 10] 代替所有可能的具体值。
只要这个近似是”单调”且”安全”的，你就能自动地跑到不动点。

ProVerB 里属于这一支血统的现代代表是 Frama-C：一个 C 代码分析的框架
（所以它既属 PV1 又属 Frameworks 分类），上面挂载了十几个 plugin——
EVA 做值分析，WP 做演绎验证（这个接到 PV4 的 Why3/Alt-Ergo），
E-ACSL 做运行时断言检查。你应该把 Frama-C 理解为”Eclipse 之于 Java”——
它本身不是验证器，它是容纳各种验证器的底盘。

其中 EVA（Evolved Value Analysis） 是 Frama-C 最能代表 PV1 气质的插件，
值得展开讲一下。它基于 Cousot 夫妇的抽象解释理论，做的事情是：
沿着程序的控制流图，用保守的区间近似自动追踪每个变量在每一行的可能取值范围，

数组越界、空指针解引用等问题。它的回答永远是”这里可能有问题”，
因为它是 sound 但不 complete 的：如果它说”没问题”，那就真没问题（近似是保守的，
覆盖了所有可能的路径）；但它可能报假阳性——说”这里可能溢出”，而那条路径实际上永远不会执行。

这正是 PV1 “便利店饭团”式约定的精确体现：用户投入近乎零（不写规约、不指定性质），
工具回报是”指出不一致”（告诉你哪里可能出错，但不保证每条报告都是真 bug）。
对比 PV3 的 CBMC——虽然现代 CBMC 也有大量内置检查开关（--signed-overflow-check 等），
但它的核心模式仍是用户写 assert 并选择展开深度 --unwind k，
用户对”查什么”和”查多深”承担判断责任；
对比 PV4 的 ESBMC——它用 k-induction 能做到真正的”证毕”，
而 EVA 只能说”在我的近似范围内没发现问题”。

澄清一个容易混淆的地方。 你可能已经注意到前面出现过两句看似打架的话：
一句是”如果 EVA 说没问题，那就真没问题”，另一句是”EVA 只能说’在我的近似范围内
没发现问题’”。前者听起来是铁打的保证，后者又像是打了折扣——这两句其实并不矛盾，
它们说的是不同维度的事。

“如果 EVA 说没问题，那就真没问题”——说的是 sound 的含义：
EVA 的抽象解释是 over-approximation，分析的范围比真实行为更大。
如果连放大后的范围里都没 bug，真实执行里也不可能有。
这个保证是真实的，不是打折扣的。

“在近似范围内没发现问题”——说的是 覆盖范围的局限：
EVA 在实际跑真实项目时，输出里通常有三类结果：

结果类型含义
Definite alarm确定有 bug
Possible alarm可能有，可能是假警报（需人工判断）
UnknownEVA 分析不了这里（函数指针、外部库调用、复杂数据结构等）

真实项目上，EVA 几乎不会给出一个干净的”全员绿灯”——
它通常有一堆 Unknown，意思是”我没分析这里，所以我也没说这里没问题”。

所以正确的理解是：

  • EVA 说”这里没问题” → 那里真的没问题（sound，可信）
  • EVA 说”Unknown” → 它没分析，不知道，不等于没问题
  • ESBMC k-induction 说”证毕” → 对整个属性、全部执行长度，构造了数学归纳证明

两者的本质区别不是”谁的结论更可信”，而是”谁能分析完整个程序”：
EVA 在复杂代码上会留下大量 Unknown；ESBMC 的 k-induction 当它成功时，
给出的是一个没有盲区的数学定理。

同一条血统上还有：

  • AProVE：Aachen 搞的终止性自动分析器，从 2000 年代初开始统治 termination 比赛。
  • Loopus / iRankFinder / RanK / TcT：估算循环复杂度和找 ranking function 的专用工具。
  • Spot：巴黎团队做的 LTL / ω-自动机操作库——本身不做验证，
    但几乎所有 LTL 模型检验器背后都有 Spot 在做公式翻译。

2.2. 3.2 求解器那一支：SAT 革命

PV1 的另一条血统在气质上完全不同，它来自组合搜索而不是程序分析。

组合搜索 (Combinatorial Search) 是指：答案藏在一个有限但指数级大的离散空间里，
求解方式是在这个空间里系统地探索组合可能性。

典型的组合搜索空间：n 个布尔变量 → $2^n$ 种 true/false 赋值组合。n=50 时这个数字已经
超过太阳系里的沙粒数——暴力枚举不可行，必须靠聪明的剪枝。

对比程序分析的工作方式：程序分析读的是程序的结构（语法树、控制流图、类型信息），
沿着结构做推导，不需要枚举 $2^n$ 种状态。两者在气质上完全不同：程序分析是”读懂代码”，
组合搜索是”在巨大空间里找答案”。

BDD 和 SAT 都是组合搜索的工具，但策略不同：

  • SAT：搜索”有没有一种赋值让公式成立”（找一个解）
  • BDD：把 $2^n$ 空间紧凑地表示成一张图，然后在图上做集合操作（表示所有解）

但你要理解后面的 CBMC / ESBMC / Z3 / Dafny，就必须先理解 SAT 是怎么在 1990 年代末到
2000 年代初变成一个”可用的工业技术”的。

故事从 1962 年讲起：Davis、Putnam、Logemann、Loveland 提出
DPLL 算法——一个带回溯的 CNF 判定过程。

先复习一下术语，因为后面 CBMC/ESBMC/Z3 全部都建在这个基础上：

布尔变量 (Boolean variable) 是最简单的一种变量——它只有两个值：true（真） 或
false（假）。名字来自数学家 George Boole（1815–1864），他第一个把逻辑推理变成了代数运算。
在编程里你已经见过它：C 的 _Bool、Java/C++ 的 bool、Python 的 True/False。

布尔变量之间可以用三种基本运算组合成布尔公式：

运算符号含义例子
与 (AND)∧两边都为真才为真a ∧ b
或 (OR)∨至少一边为真就为真a ∨ b
非 (NOT)¬取反¬a

任何复杂的逻辑条件——if (x > 0 && y < 10)、循环守卫、断言——最终都可以拆成
布尔变量和这三种运算的组合。这就是为什么 SAT/SMT 求解器的核心是在操纵布尔公式。

可满足性 (satisfiability)：给定一个布尔公式，问”存不存在一组对变量的
true/false 赋值，使整个公式为真”。存在就叫可满足 (SAT)，不存在就叫
不可满足 (UNSAT)。注意这里问的是”存在性”，而不是”所有赋值下都为真”——
后者叫永真 (tautology)，是另一个问题（虽然 “φ 永真” 等价于 “¬φ 不可满足”，
两者可以互相归约）。

SAT 问题就是可满足性的判定问题：给一条布尔公式，判断它是 SAT 还是 UNSAT。
比如 (a ∨ b) ∧ (¬a ∨ c) ∧ (¬b ∨ ¬c)——能不能找到一组 a, b, c 的
true/false 赋值让整个公式为真？（能：a=true, b=false, c=true，所以它是 SAT。）

CNF（合取范式） 是把公式写成”若干子句用 AND 连起来，每个子句内部用 OR 连起来”的标准形式。
上面那个公式已经是 CNF——三个子句：(a ∨ b)、(¬a ∨ c)、(¬b ∨ ¬c)。

为什么要统一成 CNF？因为所有布尔公式都可以等价转成 CNF，
而 CNF 的结构让求解器可以用统一的算法来处理。

理论上它能判定任何 SAT 问题，但实际中三个变量还行，三万个变量就要猜到地老天荒了。
整整 37 年里，SAT 都是”理论 NP-complete 的那个 hello world”，离工业完全没关系。
Cook 和 Karp 1970 年代初证明它 NP-complete 之后，大部分人把这当作”劝退状“——
既然最坏情况指数级，那就别指望了嘛。

这种态度一直持续到 1990 年代末都没变。那时候硬件验证社区的人如果想查一个电路，
第一反应是 BDD，不是 SAT——因为 SAT 被公认是”理论上漂亮、工程上废”的东西。

转折发生在 Chaff (2001)——Princeton 的 Matthew Moskewicz 等人在 DAC’01 发的论文里
做了两件看起来很工程的事：两字面值 watching 和 冲突驱动的子句学习 (CDCL)。
这两件事加在一起让 SAT 求解器的规模一夜之间从几百个变量跳到几万个变量。

差异在于：DPLL 是”猜错了，退一步，换个猜”；CDCL 是”分析错在哪，把教训写成子句，
直接跳到根源”。在这个四子句例子里差距很小，但当变量数达到 10000 时：

这叫非时序回溯（non-chronological backtracking）。

两字面值 watching 则解决了另一个瓶颈——每次给一个变量赋值后，
经典 DPLL 需要遍历所有包含这个变量的子句来检查”有没有新的推导”。
Chaff 的做法是：每个子句只盯住两个”哨兵文字”，只要这两个哨兵还没被赋值，
整个子句就不用管。这把”传播”这个最频繁的操作从 O(子句长度) 砍到了几乎 O(1)。

如果你想要一个不那么技术的比喻：
DPLL 是 1960 年代的拖拉机——原理正确、慢、但能动；
Chaff 是给这辆拖拉机装上了涡轮引擎——同样的四个轮子、同样的底盘，
但引擎换了以后这辆车突然可以在高速公路上开了。
这两件事在算法复杂度意义上没什么惊天动地的，但在常数因子上砍掉了三四个数量级。

然后有了 MiniSat (2003)：Niklas Eén 和 Niklas Sörensson 在 Chalmers 做的一个
极简主义重写。ProVerB 关于 MiniSat 的一句话说得很妙：

“MiniSAT has been implemented to be a minimalistic implementation of a Chaff-like SAT solver.”

MiniSat 全部源码两千行不到，但它变成了所有后续 SAT 求解器的参考实现——
你在 ProVerB 里看到的 Glucose、Lingeling、plingeling、CryptoMiniSat、CaDiCaL、Kissat，
几乎都可以把血统追到 MiniSat。其中：

  • Glucose (2009)：Armin Biere 的学生 Gilles Audemard 和 Laurent Simon 在 MiniSat 基础上
    加了 LBD（Literal Block Distance）作为子句质量的衡量——这让子句删除策略更聪明。
  • Lingeling / plingeling (2010)：Biere 自己做的，把并行化推到极致。
  • CaDiCaL：Biere 在 Johannes Kepler 后做的，明确地作为”干净重写”给研究者当基础。
  • Kissat：Biere 最新一代，2020 年 SAT Competition 上连续夺冠。

这条线的关键是：SAT 求解器从 2001 年到 2020 年这二十年里，
速度大致提升了六个数量级。这不是”摩尔定律”——它是算法本身的突破。
而这条曲线是整个形式化验证自动化的物理基础。
没有 2001 年之后的 SAT 革命，就没有后面所有 BMC、SMT、auto verifier 的可用性。

ProVerB 把 MiniSat 归到 PV4 而不是 PV1，正是因为 SAT 求解器在 PV 的意义下
是”你把问题编码成 CNF，我在固定的 SAT 范式下给答案”，这符合 PV4 的”内置范式”定义。
但在历史意义上，它是 PV1 向上生长的真正支柱。

2.3. 3.3 从 SAT 到 SMT：DPLL(T) 和一群求解器的诞生

SAT 只能判 CNF，但程序里有加法、数组、位运算、未解释函数——
这些都不是单纯的布尔变量。于是 1990 年代末到 2000 年代初人们开始把 SAT 和”背景理论 (Theory)”
结合起来，形成了 SMT（Satisfiability Modulo Theories）。

先讲清楚 SAT 和 SMT 这两个缩写——后面几乎每一章都要用到：

  • SAT (Boolean Satisfiability)：给一个纯布尔公式（只有 AND、OR、NOT 和变量），
    问”有没有一组变量赋值让它为真？”这就是 SAT。
    公式通常写成 CNF (Conjunctive Normal Form，合取范式)——
    一堆”子句”用 AND 连接，每个子句里面是变量用 OR 连接。
    例如 (x₁ ∨ ¬x₂) ∧ (x₂ ∨ x₃) ∧ (¬x₁ ∨ ¬x₃)。
    SAT 是 NP-complete 的祖师爷问题（Cook 1971），但前面讲的 CDCL 革命让它在实践中变得可解。
  • SMT (Satisfiability Modulo Theories)：SAT 只管布尔，但真实程序里有整数、数组、
    指针、浮点数——这些不是布尔变量。SMT 的意思是”在某个数学理论下判可满足性”。
    它把 SAT 当骨架，在旁边挂一个”理论求解器”来处理非布尔的部分。

SMT 里的 “Theory” 是什么？你可以把它理解成一套数学背景公理。
不同的理论让 SMT 能”听懂”不同类型的表达式：

Theory 缩写全称管什么事在验证中用在哪
QF_LIA量词无关的线性整数算术x + 2*y ≤ 10 这类整数加减不等式循环边界、数组下标
QF_LRA量词无关的线性实数算术同上但是实数控制系统、浮点近似
QF_BV量词无关的位向量32 位 / 64 位整数的精确位运算、溢出CBMC、ESBMC 编码 C 语义
QF_A / QF_AX数组理论a[i] = v、store(a,i,v)数组越界、内存模型
QF_UF未解释函数f(x) = f(y) → x = y（只管相等性）函数抽象、等价性检查
QF_FP浮点算术IEEE 754 浮点加减乘除数值计算验证
QF_S字符串理论字符串拼接、正则匹配Web 安全、XSS 检查

2.3.1. 为什么到处都是 QF_？——量词无关 (Quantifier-Free) 的意义

你可能注意到上面每个 theory 缩写都以 QF_ 开头。QF = Quantifier-Free（量词无关），
意思是公式里不允许出现 ∀（对所有）和 ∃（存在）。

先看区别：

  • 无量词：x + y > 0 ∧ x < 10 — 变量都是”自由”的，问题只是”有没有一组赋值让它成立？”
  • 有量词：∀x. (x > 0 → ∃y. x + y = 0) — “对所有正整数 x，是否都存在一个 y 使得 x + y = 0？”

无量词公式本质上是一个搜索问题：找到一组值满足约束。
一旦加上量词，问题就变成了博弈：

这是在说：”无论对手怎么选 x，我都能找到一个 y，
使得无论对手再怎么选 z，P 都成立。”
每多一层量词交替（∀∃∀∃…），就多一层博弈嵌套，复杂度通常指数级跳升。

这不是”先解决里面、再解决外面”那么简单。 你的直觉其实描述的是
量词消除 (Quantifier Elimination) 的思想——Tarski 1948 年证明了实数算术可以
一层一层地把量词”消掉”，得到等价的无量词公式。但代价是每消一层，公式可能平方级膨胀，
总复杂度是双重指数。而对整数算术的非线性情况，连量词消除都做不到——
这就是 Hilbert 第十问题 (Matiyasevich 1970 证明不可判定) 告诉我们的。

量词对可判定性的影响有多大？看这张表：

Theory无量词 (QF_)有量词
线性实数算术 (LRA)可判定，多项式时间可判定，但需要量词消除，复杂度高得多
线性整数算术 (LIA)可判定，NP-complete可判定（Presburger 算术），但三重指数复杂度
非线性实数算术 (NRA)可判定（Tarski 定理）可判定，但双重指数
非线性整数算术 (NIA)不可判定（Hilbert 第十问题）不可判定

注意最后一行：连无量词版本都不可判定。这就是为什么 SMT-LIB 里
QF_NIA 的求解器都标注 “incomplete”——它们尽力而为，但不保证总能给出答案。

所以 QF_ 前缀不是装饰，而是一个可判定性承诺：
当 CBMC 把 C 代码编码成 SMT 公式时，它故意只生成无量词公式。
这保证了 solver 在 QF_BV 和 QF_LIA 上的判定过程是完备的。
如果编码引入了量词，solver 就可能回答 unknown，整个验证链条就断了。

小结：QF_ 意味着”我只问搜索问题，不问博弈问题”——
在这个约束下，多数理论都是可判定的，solver 保证给你 sat 或 unsat。
一旦放开量词，你要么付出指数级膨胀的代价（量词消除），
要么直接撞上不可判定的墙。

CBMC/ESBMC 主要用的是 QF_BV（因为 C 的语义本质是位运算）加 QF_A（因为有数组和指针）。
Dafny / Boogie 更多用 QF_LIA + QF_UF（因为 Dafny 的整数是数学整数，不溢出）。

SMT 的核心算法叫 DPLL(T)：
底层的 SAT 求解器当成一个”黑盒大脑”来负责命题骨架，
旁边挂一个理论求解器——如果遇到算术原子 x + y > 5 或者数组原子 a[i] = v，
把这些原子的”真值指派”交给专门的 T-solver 检查一致性，冲突时回传子句。
这样一来你就能判定”带加法的 CNF”、”带数组的 CNF”、”带位向量的 CNF”了。

一个类比：SAT 像是一个只会下象棋的大脑——规则固定，只处理黑白棋子（布尔变量）。
SMT 像是在这个象棋大脑旁边放了几个专科顾问：
一个懂算术、一个懂数组、一个懂位运算。大脑管全局推理，
遇到”2+3 是不是等于 6”这种问题就转头问顾问，顾问说”不是”，大脑就回溯。
DPLL(T) 的 T 就是”理论顾问”的意思。

ProVerB 里 SMT 求解器家族的血统大致如下：

  • CVC → CVC Lite → CVC3 → CVC4 → cvc5：Stanford 的 Clark Barrett 主导，
    一个非常老的家族。cvc5 是 2022 年的最新一代，支持字符串、BV、量词、SyGuS 等。
  • Z3 (2008)：Microsoft Research 的 Leonardo de Moura 和 Nikolaj Bjørner 做的。
    Z3 的影响力之大，以至于当你说”SMT 求解器”的时候，工业界默认你在说 Z3。
    Dafny、Boogie、SPARK、Viper、Why3 这些上层工具全部把 Z3 作为默认后端。
  • Yices, MathSAT, Boolector / Bitwuzla, Alt-Ergo, SMTInterpol：其它活跃的竞争者，
    各自在某个理论上（BV、浮点、量词、线性算术）做得特别快。

这些都被 ProVerB 归到 PV4。但如果你把视角切换到”时间线“，它们是 PV1 linter 派
和 PV4 自动验证派之间的桥梁——所有 PV4 的自动验证器，内部都是靠一个 SMT 求解器在跑。

2.3.2. 为什么有这么多求解器？它们通用吗？

你可能会问：既然都是”判定 SMT 公式”，Z3、cvc5、Bitwuzla、Yices 这些不就是同一个东西吗？
能不能随便换？

答案是：格式上通用，性能上不通用。

首先，感谢 SMT-LIB 标准——所有主流求解器都接受同一种输入格式（就是前面 overflow.smt2
那种 S-expression 语法）。你写一份 QF_BV 的公式，喂给 Z3 或 Bitwuzla 或 cvc5，
它们应该给出相同的 sat / unsat 答案。在这个意义上，它们是可以互换的。

但实际上，没有一个求解器在所有问题类型上都最快。原因很直觉：

求解器擅长的理论不擅长 / 不支持的典型用户
Z3几乎什么都支持：BV、整数、实数、数组、字符串、量词、Horn clauses没有”最快”的单项冠军Dafny, Boogie, SPARK, Viper, SolCMC
Bitwuzla位向量 (BV)、浮点 (FP)——这两项世界第一不支持整数算术、不支持字符串硬件验证、密码学
cvc5字符串、代数数据类型、量词、SyGuS 综合BV 略弱于 Bitwuzla形式化语言研究
Yices 2线性算术（LIA、LRA）——极快字符串、复杂数据类型支持有限嵌入式系统验证
MathSAT 5Craig 插值、优化 (MaxSMT)闭源（学术免费）CEGAR 类工具
Alt-Ergo量词实例化理论覆盖面窄SPARK / Why3 生态

关键词是理论覆盖和算法特化：

  • Bitwuzla 不支持整数算术——你根本不能把 Dafny 生成的 (declare-const x Int) 喂给它。
    但在纯位向量问题上（硬件电路、密码算法），Bitwuzla 比 Z3 快几倍甚至几十倍，
    因为它的底层 SAT 引擎是 Armin Biere 的 CaDiCaL（常年 SAT 竞赛冠军），
    并且所有预处理都专门为 BV 结构优化过。
  • Z3 什么理论都支持、量词也能处理、还内置了 Horn clause 引擎（Spacer）——
    这就是为什么几乎所有程序验证工具选它做默认后端。
    但”全能”意味着开发资源分散，任何一个单项上都未必是最快的。
  • cvc5 在字符串理论上是最强的——如果你验证的程序大量操作字符串（Web 应用、正则匹配），
    cvc5 会比 Z3 快很多。

SMT-COMP（SMT 求解器竞赛，每年和 CAV 会议一起举行）最能说明这种特化现象：
竞赛分 40 多个赛道，每个赛道对应一种 SMT-LIB 逻辑（QF_BV、QF_LIA、QF_S 等），
从来没有一个求解器赢下所有赛道。Bitwuzla 拿 QF_BV 冠军的那年，
QF_LIA 的冠军往往是 Yices，QF_S 的冠军是 cvc5。
这不是质量问题——是算法选择的必然结果。

所以像 Boogie 和 Why3 这样的中间层工具会支持多个后端：
Why3 可以把验证条件分别发给 Alt-Ergo、Z3、cvc5，
哪个先回答就用哪个。这叫 portfolio 策略——用求解器的多样性换整体成功率。

一句话总结：SMT-LIB 让你”能换”，但 SMT-COMP 告诉你”不该随便换”——
选对求解器，等于免费提速几十倍；选错了，可能直接 timeout。

这条逻辑链非常重要，我希望你记住：

SAT 革命 (2001) → SMT 诞生 (2003 前后) → BMC 和 auto verifier 可用化 (2004+)

CBMC 就是在这条链条末端诞生的。

2.3.3. 实战：在 Z3 “裸跑”一个 SMT 查询

你平时用 CBMC/ESBMC 的时候，Z3 藏在后台——你看不到它。
但如果你直接打开 Z3，喂给它一段 SMT-LIB 格式的公式，
就能看到你写的那些 assert 最终变成了什么。

比如这个问题：”有没有一个 32 位整数 x，使得 x > 0 但 x + x < 0？”
（这其实就是有符号整数溢出的本质。）

Z3 说 sat——是的，存在这样的 x。具体值 0x40000001（即 1073741825），
加上自己等于 0x80000002，最高位为 1，在有符号解释下是负数。

这就是 CBMC 在幕后做的事情：它把你的 C 代码和 assert 翻译成类似这样的
位向量公式，然后问 Z3 “有没有一组输入能让 assert 失败”。
如果 Z3 回答 sat——有反例；unsat——安全。

再看一个 unsat 的例子——“有没有整数 x 同时大于 5 又小于 3？”：

没有。数学上不可能。这就是 SMT 求解器做的事情——判定一个公式是否可满足。
当 CBMC 编码出的公式得到 unsat 时，你就得到了 VERIFICATION SUCCESSFUL。

一个关键的视角：BMC 是”找反例”，不是”找证据”。 你可能会觉得奇怪——
我想证明程序正确，为什么工具是在问”有没有输入能让断言失败“？

原因很简单：SAT/SMT 求解器只会回答一种问题——“存在一组赋值使这个公式为真吗？”。
你没办法直接让它回答”所有赋值下这个性质都成立吗”。于是验证工具必须把”我想证明的东西”
翻译成一个存在性问题的否定：

你想证明的事翻译成 SAT/SMT 问题结果含义
在 $k$ 步内 assert 永远成立存在一条 $≤k$ 步的执行使 ¬assert 成立吗？SAT = 找到反例（有 bug）；UNSAT = 该范围内安全

所以 CBMC/ESBMC 的工作流程是：

  1. 展开 (unwind)：把循环展 $k$ 次、递归展 $k$ 层，得到一段直线程序。
  2. SSA 化：x1 = 2147483647 ∧ x2 = x1 + 1 ∧ ...，把每次赋值变成独立变量。
  3. 取反断言：把 assert(P) 中的 P 取反后合取进去，得到
    程序语义 ∧ ¬P。
  4. 问 SMT：
    • SAT → 求解器给出一组具体输入值，这就是反例——照着跑一遍程序就能触发 bug。
    • UNSAT → 在展开界 $k$ 内，没有任何输入能让 ¬P 成立，所以 P 在 $k$ 步内永远为真。

这就是 BMC 工具天生是证伪机器 (bug hunter) 的原因：
它强在”能给出可重放的反例”，弱在”展开界外的世界它一无所知”——
所以标准的 BMC 只能说”在 $k$ 步内没找到 bug”，不能说”这程序永远没 bug”。
后面讲 ESBMC 的 k-induction 时会看到，这个缺口是怎样被补上的。

顺带一提：“证明 = 证伪它的否定” 是所有基于 SAT/SMT 的验证工具的共同套路——
Dafny、Why3、F* 也都是这么干的。每次你写一个 assert 或 ensures，
后台都是有人（某个 solver）在努力找一个反例，找不到才算你赢。
