3.1 从 .java 到运行：JDK、JRE、JVM

写完第一个 Java 程序，面试官常问两件事："JDK、JRE、JVM 有什么区别？""Java 为什么能跨平台？"这两个问题其实是一件事：Java 源代码先被翻译成一种与操作系统无关的中间格式（字节码），再由每个平台各自的虚拟机去执行。

三者是逐层包含的关系：

  • JVM（Java Virtual Machine，Java 虚拟机）：真正执行字节码的程序，负责类加载、解释执行、即时编译（JIT）、垃圾回收。
  • JRE（Java Runtime Environment，运行环境）：JVM 加上核心类库（java.lang、java.util 等），有它就能运行 Java 程序。
  • JDK（Java Development Kit，开发工具包）：JRE 加上开发工具（编译器 javac、打包工具 jar、文档工具 javadoc、调试器 jdb 等），有它才能开发 Java 程序。

JDK ⊃ JRE ⊃ JVM：开发要 JDK，运行要 JRE，真正执行字节码的是 JVM

一个程序的完整旅程

我们用最小的程序走一遍。文件名必须是 Hello.java，因为文件里的 public 类叫 Hello。[1]

public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, Java");
    }
}
$ javac Hello.java      # 编译：生成 Hello.class（字节码）
$ java Hello            # 运行：写类名，不带 .class 后缀
Hello, Java

编译一次得到 .class；每个平台的 JVM 把同一份字节码翻译给本机 CPU，这就是“一次编译，到处运行”

  1. javac 检查语法和类型，把源代码翻译成字节码，存成 .class 文件。字节码是 JVM 的指令集，与 Windows、Linux 无关。
  2. java Hello 启动 JVM，类加载器找到 Hello.class，经过验证、准备、初始化（3.21 详讲）。
  3. JVM 从 main 开始执行。起初由解释器逐条执行字节码；某段代码被频繁执行（热点代码）后，JIT 编译器把它编译成本机机器码并缓存，之后直接运行机器码。所以 Java 是"解释 + 编译"混合执行。

要点：

  • JDK 包含 JRE，JRE 包含 JVM 和核心类库。
  • 跨平台的原因：Java 程序编译成与平台无关的字节码，由各平台的 JVM 解释或编译执行；跨平台的是字节码，JVM 本身与平台相关。
  • 一个 .java 文件最多一个 public 顶层类，且类名与文件名相同；可以另有多个非 public 类。

3.2 基本类型与包装类：== 到底比较什么

Java 里的值分两大类：基本类型直接存数值，引用类型存一个指向堆上对象的引用。集合（List<Integer>）只能装对象，所以每种基本类型都配了一个包装类。两者之间自动转换，面试最爱考的 Integer a = 127, b = 127; a == b 就出在这里。[2]

整数运算先看类型再赋值：5 / 2 是整数除法得 2，赋给 double 变量也只是 2.0；100000 * 100000 两个 int 先相乘、先溢出，得到 1410065408，之后才赋值给 long，所以要写 100000L * 100000。byte b = 1; b += 1; 合法，因为复合赋值自带强制转换；b = b + 1 编译报错，因为 b + 1 已经提升成 int。

自动装箱、拆箱与 Integer 缓存

  • 装箱：Integer x = 5; 编译器改写成 Integer x = Integer.valueOf(5);
  • 拆箱：int y = x; 编译器改写成 int y = x.intValue();

Integer.valueOf 的实现带一个缓存：−128 到 127 之间的值直接返回缓存数组里早已建好的对象，范围外每次新建对象。上界可用 JVM 参数 -XX:AutoBoxCacheMax 调大，下界固定为 −128。Byte、Short、Long 的缓存同样是 −128 ～ 127，Character 缓存 0 ～ 127，Boolean 缓存 TRUE/FALSE 两个对象；Float、Double 没有缓存。[3] [4]

Integer a=127,b=127 指向同一个缓存对象；c=128,d=128 各自 new 了一个对象

Integer a = 127, b = 127;
Integer c = 128, d = 128;
int e = 128;
Long f = 127L;
System.out.println(a == b);        // true
System.out.println(c == d);        // false
System.out.println(c == e);        // true
System.out.println(c.equals(d));   // true
System.out.println(f.equals(127)); // false
  1. a == b：两边都是 Integer 引用，== 比较是否同一个对象。127 在缓存范围内，两次 valueOf(127) 拿到同一个对象，输出 true。
  2. c == d：128 超出缓存，两次 valueOf(128) 各 new 一个对象，引用不同，输出 false。
  3. c == e：一边是基本类型 int，编译器先把 c 拆箱成 128，再比较数值，输出 true。
  4. c.equals(d)：Integer 重写了 equals，比较的是数值，输出 true。
  5. f.equals(127)：127 装箱成 Integer，而 Long.equals 要求参数也是 Long，类型不同直接返回 false。

  • == 对基本类型比较值，对引用类型比较内存地址；equals 默认比较地址，被重写后比较内容。
  • Integer 缓存范围 −128 ～ 127；包装类比较数值一律用 equals（或先拆箱）。
  • 包装类为 null 时拆箱会抛 NullPointerException，例如 Integer n = null; int v = n;。

3.3 String：不变性、常量池与 intern

String 是最常用的类，也是最常考的类。面试三连问："String 为什么设计成不变的？""new String("ab") 创建了几个对象？""StringBuilder 和 StringBuffer 的区别？"要答好它们，我们先弄清 String 对象放在哪里。[5]

不变性：原因与好处

String 内容一旦创建就固定。它在源码层面由三点保证（JDK 9 起底层是 byte[]，JDK 8 是 char[]）：

  1. 类被 final 修饰，没有子类能改变它的行为；
  2. 保存字符的数组是 private final，外部拿不到；
  3. 所有"修改"方法（concat、replace、substring、toUpperCase）都返回新对象。

String 不可变的好处有四条，也是标准答案：一是可以放进常量池共享，相同的字面量只存一份；二是hashCode 可以缓存，作为 HashMap 的键时很快；三是天然线程安全，多线程共享时无需加锁；四是安全，类名、文件路径、URL、数据库连接串用 String 传递后，不会被他人中途篡改。

常量池与堆对象

字符串常量池是 JVM 维护的一张从字面量到 String 对象的映射表（JDK 7 起放在堆中）。代码中的字面量 "ab" 在类加载后首次解析时进入常量池，之后所有相同的字面量都指向池中的这一个对象。new String("ab") 则一定会在堆上另建一个对象，内容复制自池中的 "ab"。

String s1 = "ab";
String s2 = "a" + "b";            // 两个字面量：编译期就折叠成 "ab"
String a  = "a";
String s3 = a + "b";              // a 是变量：运行期拼接，新对象
final String fa = "a";
String s4 = fa + "b";             // fa 是 final 常量：仍在编译期折叠
String s5 = new String("ab");     // 堆上新对象
System.out.println(s1 == s2);           // true
System.out.println(s1 == s3);           // false
System.out.println(s1 == s4);           // true
System.out.println(s1 == s5);           // false
System.out.println(s1.equals(s5));      // true
System.out.println(s5.intern() == s1);  // true

绿色是池中唯一的 "ab"；运行期拼接和 new 都在堆上另建对象，intern() 把它们引回池中对象

逐行解释：

  1. s2 = "a" + "b"：两个操作数都是编译期常量，javac 直接把它算成 "ab" 写进字节码，所以 s2 与 s1 是同一个池对象。[6]
  2. s3 = a + "b"：a 是普通变量，编译器不知道它的值，拼接发生在运行期（JDK 9 起通过 StringConcatFactory，JDK 8 通过 StringBuilder），结果是堆上的新对象。
  3. s4 = fa + "b"：final 且用常量初始化的变量叫常量变量，同样参与编译期折叠。
  4. intern()：如果池里已有相同内容，返回池中对象；如果没有，JDK 7 起把当前这个堆对象的引用记进池里并返回它本身。

String s = new String("ab"); 创建几个对象？标准答案：1 个或 2 个。如果池中还没有 "ab"，类加载解析字面量时先在池中建一个，再由 new 在堆上建一个，共 2 个；如果池中已有，只新建堆上那 1 个。

StringBuilder 与 StringBuffer

循环里反复 s = s + i 每次都生成新 String，n 次拼接复制约 n²/2 个字符。用可变的 StringBuilder 只在内部数组上追加：

StringBuilder sb = new StringBuilder();
for (int i = 0; i < 3; i++) sb.append(i).append(',');
String r = sb.toString();     // "0,1,2,"
类可变线程安全速度场景
String否安全（内容固定）拼接慢少量拼接、作 key
StringBuilder是非线程安全最快单线程大量拼接（最常用）
StringBuffer是方法加 synchronized稍慢多线程共享同一个缓冲区

要点：

  • String 不变的原因：final 类 + private final 数组 + 修改方法返回新对象；好处：常量池复用、缓存 hash、线程安全、安全。
  • 字面量和编译期常量拼接进常量池；含变量的拼接在运行期生成堆对象。
  • 字符串内容比较一律用 equals。

多选 · 理解检查 3　String x = "java"; String y = "ja"; String z = y + "va"; 下面哪些输出 true？

A. x == "ja" + "va"

B. x == z

C. x == z.intern()

D. x.equals(z)

查看答案与每个选项的解析

A · 正确：两个字面量在编译期折叠为 "java"，与 x 是同一个池对象。

B · 错误：y 是普通变量，z 在运行期拼接，是堆上的新对象。

C · 正确：池里已有 "java"，intern 返回的正是 x 指向的池对象。

D · 正确：equals 比较内容，二者都是 java。

易错点：

  • s.toUpperCase(); 单独一行对 s 没有任何影响，要写 s = s.toUpperCase();。
  • final String fa = "a" 能折叠，final String fa = getA() 就不能：右边要是编译期常量。
  • StringBuffer 只保证单次方法调用原子，"先判断长度再追加"这种组合操作仍需外部加锁。

小结： String 不可变由 final 类、private final 数组和不提供修改方法三点共同保证；字面量进入常量池，用变量拼接会产生新对象；单线程拼接字符串用 StringBuilder，多线程共享时用 StringBuffer。

3.4 Java 只有值传递

C++ 有按值和按引用两种传参，Java 只有一种：按值传递。可是把数组传进方法后，方法里改了元素，调用者明明看到了变化，这又是怎么回事？答案是：引用类型变量里存的是"引用"这个值，传参时复制的正是这个引用值，于是形参和实参指向同一个对象。[7]

我们用一个例子走完四个状态：

static void f(int n, int[] arr) {
    n = 9;              // 改的是副本
    arr[0] = 9;         // 通过副本引用改了共享的数组
    arr = new int[]{7}; // 副本引用改指新数组，调用者不受影响
    arr[0] = 8;         // 改的是新数组
}
int n = 1;
int[] arr = {1};
f(n, arr);
System.out.println(n + " " + arr[0]);   // 1 9

f(n, arr) 调用前后：引用值被复制

1 / 5

第1步 · 调用前：main 的 n=1，arr 指向数组 X=[1]

2 / 5

第2步 · 进入 f：n 复制出 1，arr 复制出同一个引用，两个 arr 都指向 X

3 / 5

第3步 · n = 9 只改副本；arr[0] = 9 改的是共享的 X

4 / 5

第4步 · arr = new int[]{7}：形参改指新数组 Y，main 的 arr 仍指 X

5 / 5

第5步 · 返回后：f 的局部变量全部消失，main 看到 n=1、arr[0]=9

输出：1 9

规律只有两条：通过引用改对象内容，调用者看得到；让形参改指别的对象，调用者看不到。 所以 Java 写不出 C++ 那样的 swap(a, b)：

static void swap(Integer x, Integer y) { Integer t = x; x = y; y = t; }
Integer x = 1, y = 2;
swap(x, y);              // 之后 x 仍是 1，y 仍是 2

方法里交换的只是两个引用副本。要交换，得把值放进数组或对象里，再交换元素。

要点：

  • Java 只有值传递。基本类型传值的副本；引用类型传引用的副本，形参和实参指向同一个对象。
  • 方法内修改对象内容会影响调用者；给形参重新赋值只影响方法内部。

小结： Java 传参就是复制变量中的值；在方法中修改对象的内容，调用者看得到，让参数指向另一个对象，调用者看不到。

3.5 面向对象：封装、继承、多态，重载与重写

银行系统里有储蓄账户、信用卡账户，它们都"能查询余额、能扣款"，但扣款规则不同。面向对象用三个特性组织这种代码：封装把余额设为 private，只能通过方法改，保证规则统一；继承让子类复用父类代码，Java 类只能单继承，可以实现多个接口；多态让 Account acc = new CreditAccount(); 调用 acc.withdraw() 时，自动执行信用卡账户的实现。[8]

多态成立的三个条件：有继承（或实现接口）、子类重写父类方法、父类引用指向子类对象。

重载与重写：分两步决定调用谁

对比重载 overload重写 override
发生位置同一个类（或父子类）里同名方法子类重新实现父类的实例方法

受检异常无要求小于等于父类
何时确定编译期，看变量的声明类型运行期，看对象的实际类型

重写规则的口诀是"两同两小一大"：方法名、参数列表相同；返回类型、抛出的受检异常小于等于父类；访问权限大于等于父类。private、static、final 方法不能被重写（static 方法同名时叫"隐藏"）。

下面这段代码把两步分得很清楚：

class A {
    String f(Object x) { return "A:Object"; }
}
class B extends A {
    @Override String f(Object x) { return "B:Object"; }
    String f(String x) { return "B:String"; }
}
A a = new B();
System.out.println(a.f("hi"));   // B:Object
B b = new B();
System.out.println(b.f("hi"));   // B:String

重载按声明类型在编译期选签名，重写按实际对象在运行期选实现；运行期不会重新挑 f(String)

  1. 编译期，a 的声明类型是 A。编译器只在 A 中找名叫 f、能接受 String 实参的方法，只有 f(Object)，于是字节码里写死"调用 f(Object)"。
  2. 运行期，JVM 看到 a 实际指向 B 对象，查 B 是否重写了 f(Object)：重写了，执行 B 的版本，输出 B:Object。
  3. b.f("hi") 的声明类型是 B，编译期候选里有 f(String)，它比 f(Object) 更具体，于是选它，输出 B:String。

重载选择还有固定的优先级：先找精确匹配或基本类型拓宽，再找装箱，最后找可变参数。所以有 over(long) 和 over(Integer) 两个版本时，over(1) 选 over(long)（int 拓宽成 long 优先于装箱）。[6]

要点：

  • 三大特性：封装、继承、多态；多态 = 继承 + 重写 + 父类引用指向子类对象。
  • 重载是编译时多态，看参数列表；重写是运行时多态，遵守"两同两小一大"。

3.6 static、final 与类初始化顺序

面试读代码题里有一类专考"先打印谁"：父类、子类各有静态块、实例块、构造器，new Child() 时输出顺序是什么？要答对它，先弄清 static 和实例成员分别在什么时候初始化。[9]

static 与 final

  • static 成员属于类，所有对象共享一份，在类初始化时执行一次；实例成员属于对象，每 new 一次执行一次。static 方法里没有 this，只能直接访问 static 成员。
  • final 有三种用法：修饰类，类不能被继承（如 String）；修饰方法，方法不能被重写；修饰变量，变量只能赋值一次（引用类型则是引用不能改指，对象内容可改）。

初始化的完整顺序

class Parent {
    static { System.out.println("父静态块"); }
    { System.out.println("父实例块"); }
    Parent() { System.out.println("父构造器"); }
}
class Child extends Parent {
    static { System.out.println("子静态块"); }
    { System.out.println("子实例块"); }
    Child() { System.out.println("子构造器"); }
}
new Child();
new Child();

1 / 5

3 / 5

5 / 5

总共 10 行

把规则总结成一句：先类后对象，先父后子；类部分（静态）只做一次，对象部分（实例块 + 构造器）每次都做；同一类中，实例块（以及字段初始化）在构造器体之前执行。 同一类中的多个静态块和静态字段初始化按书写顺序执行，实例块和实例字段初始化也一样。

类初始化只在"首次主动使用"时触发：new 对象、读写非常量静态字段、调用静态方法、反射 Class.forName、初始化子类时先初始化父类、包含 main 的启动类。下面两种情况不触发：读取 static final 编译期常量（值已被内联到调用方），以及创建该类的数组 new Lazy[3]。这两条都在 Ch11Concurrency.classInit 中验证。

要点：

  • 父类静态 → 子类静态 → 父类实例块 → 父类构造器 → 子类实例块 → 子类构造器。
  • 静态部分每个类只执行一次；实例部分每 new 一次执行一次。

3.8 equals 与 hashCode 的约定

我们定义一个账户编号类 Key，重写了 equals 让"编号相同就相等"，把它放进 HashMap 后，用另一个编号相同的 Key 去查，却查不到。原因在于 HashMap 查找分两步：先用 hashCode 定位桶，再在桶里用 equals 比较。只重写 equals，两个"相等"的对象 hashCode 来自 Object 默认实现（通常各不相同），第一步就走进了不同的桶。[10] [11]

约定的内容

  1. 两个对象 equals 为 true，hashCode 必须相等。
  2. hashCode 相等，equals 可以为 false（哈希冲突，允许发生）。
  3. equals 要满足自反、对称、传递、一致，且 x.equals(null) 为 false。

只重写 equals 会怎样

final class BadKey {
    final int id;
    BadKey(int id) { this.id = id; }
    @Override public boolean equals(Object o) {
        return o instanceof BadKey k && k.id == id;
    }
    // 没有重写 hashCode
}
Map<BadKey, String> m = new HashMap<>();
m.put(new BadKey(1), "x");
System.out.println(m.get(new BadKey(1)));   // null
m.put(new BadKey(1), "y");
System.out.println(m.size());               // 2

两个 equals 相等的键，默认 hashCode 不同，第一步定位就进了不同的桶

修正方法是按 equals 用到的同一组字段计算 hashCode：

@Override public int hashCode() { return Objects.hash(id); }

要点：

  • 重写 equals 必须重写 hashCode，否则 HashMap、HashSet 中相等的对象会被当成不同的键。
  • equals 相等 ⇒ hashCode 相等；hashCode 相等 ⇏ equals 相等。

易错点：

  • 键放进 HashMap 后再修改参与 hashCode 的字段，键会"留在旧桶里"再也查不到；键最好用不可变对象，String、Integer 正合适。
  • equals 的参数类型要写 Object，写成 equals(Key k) 是重载而非重写。

小结： HashMap 先比较 hash 再调用 equals；equals 相等的两个对象 hash 必须相等，所以重写 equals 时必须同时重写 hashCode。

3.9 异常体系与 try-catch-finally

转账时余额不足、网络断开、文件找不到，程序都需要一种机制把"出错了"传给能处理它的地方。Java 用异常对象沿调用栈向上抛出，直到遇到匹配的 catch。[12]

  • Error：JVM 层面的严重问题，如内存溢出、栈溢出，程序通常无法恢复。
  • 受检异常（checked）：Exception 中除 RuntimeException 以外的部分。编译器强制处理：要么 try-catch，要么在方法上 throws 声明。它们代表外部环境造成、可预期的问题，如 IOException。
  • 非受检异常（unchecked）：RuntimeException 及其子类，加上 Error。编译器不强制处理，通常是程序 bug，如空指针、数组越界、除以零。

throw 在方法体里抛出一个异常对象；throws 写在方法签名上，声明可能抛出的异常类型。

try-catch-finally 的执行顺序

执行顺序是：try 正常执行到底，跳过 catch；try 中抛异常，跳到第一个匹配的 catch；无论哪种情况，finally 都在最后执行。多个 catch 要按"先子类、后父类"排列，否则子类分支永远到不了，编译报错。

finally 和 return 组合是最常考的读代码题：

static int f1() {
    int x = 1;
    try { return x; }
    finally { x = 2; }
}                                  // 返回 1
static int f2() {
    try { return 1; }
    finally { return 2; }
}                                  // 返回 2
static StringBuilder f3() {
    StringBuilder sb = new StringBuilder("A");
    try { return sb; }
    finally { sb.append("B"); }
}                                  // 返回的对象内容为 "AB"

f1()：return 的值先保存，再执行 finally

1 / 5

第1步 · 执行 try 中的 return x：先计算返回值 1，存入一个临时槽

2 / 5

第2步 · 方法还没真正返回，转去执行 finally：x = 2

x 是局部变量，改它影响不到返回槽
3 / 5

第3步 · finally 正常结束，取出返回槽中的值返回

f1() 返回 1
4 / 5

第4步 · 对比 f2：finally 自己执行了 return 2，覆盖了返回槽里的 1

f2() 返回 2；finally 中 return 还会吞掉 try 中的异常，所以禁止这样写
5 / 5

第5步 · 对比 f3：返回槽里存的是引用，finally 通过同一个引用改了对象内容

调用者拿到的对象内容为 AB

规律：try 中的 return 先把返回值算好暂存，再执行 finally；finally 改基本类型局部变量不影响返回值，finally 里的 return 会覆盖原返回值；返回的是对象引用时，finally 修改对象内容，调用者看得到。

finally 几乎总会执行，例外是 try 中调用了 System.exit()、JVM 崩溃或线程被强制终止。

try-with-resources

Java 7 起，实现了 AutoCloseable 的资源可以写在 try 后的括号里，代码块结束时自动关闭，多个资源按声明的逆序关闭。主体抛异常、close 也抛异常时，close 的异常作为"被抑制异常"挂在主异常上（getSuppressed()）。[13]

try (BufferedReader in = new BufferedReader(new FileReader("a.txt"));
     BufferedWriter out = new BufferedWriter(new FileWriter("b.txt"))) {
    out.write(in.readLine());
}   // 先关 out，再关 in

要点：

  • Throwable 分 Error 和 Exception；Exception 分受检异常（编译器强制处理）和运行时异常（RuntimeException，不强制）。
  • finally 在 return 之前执行；try 中 return 的值已暂存，finally 改局部变量不影响它；finally 中 return 会覆盖。
  • 资源用 try-with-resources，自动逆序关闭。

  • 空 catch 块吞掉异常却不记录，线上排查会非常困难，至少要打日志。

小结： Error 一般不处理，checked 异常必须处理，unchecked 异常通常说明程序有错误；return 的值先暂存，再执行 finally；资源用 try-with-resources 关闭。

3.10 泛型、类型擦除、Comparable 与 Comparator

没有泛型时，List 里取出的都是 Object，要手动强转，放错类型要到运行时才报 ClassCastException。泛型把类型检查提前到编译期：List<String> 里放 Integer 直接编译报错，取出时也不用强转。

类型擦除

Java 泛型只存在于编译期。编译器检查完类型后，把类型参数擦除成它的上界（没写上界就擦成 Object），并在取值处自动插入强制转换。所以运行时 List<String> 和 List<Integer> 是同一个类：new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass() 为 true。

类型参数在字节码中被擦除为 Object（或上界），取值处由编译器补上强制转换

擦除带来的限制：不能 new T()、不能 new T[n]、不能 obj instanceof List<String>、类型参数不能是基本类型（List<int> 要写成 List<Integer>）。

通配符的口诀是 PECS（Producer Extends, Consumer Super）：只从集合里读，用 List<? extends Number>；只往集合里写，用 List<? super Integer>。List<Integer> 不是 List<Number> 的子类型。

fail-fast 与 ConcurrentModificationException

ArrayList、HashMap 等内部有一个 modCount 计数器，每次结构性修改（增、删）都加 1。迭代器创建时记下 expectedModCount = modCount，每次 next() 前检查两者是否相等，不相等就立刻抛 ConcurrentModificationException，这就是 fail-fast（快速失败）。

List<Integer> xs = new ArrayList<>(List.of(1, 2, 3, 4));
for (Integer x : xs) if (x == 1) xs.remove(x);   // 抛 ConcurrentModificationException

增强 for 底层就是迭代器。xs.remove(x) 改了 modCount，下一次 next() 检查失败。正确写法有两种：

for (Iterator<Integer> it = xs.iterator(); it.hasNext(); )
    if (it.next() % 2 == 0) it.remove();         // 迭代器自己的 remove 会同步 expectedModCount
xs.removeIf(x -> x % 2 == 0);                    // Java 8，最简洁

要点：

  • ArrayList 底层数组，随机访问快，默认容量 10，按 1.5 倍扩容；LinkedList 底层双向链表，插删本身快但定位慢。
  • fail-fast：迭代时集合被结构性修改，迭代器检测到 modCount 变化，抛 ConcurrentModificationException；删除元素用 Iterator.remove() 或 removeIf。
  • java.util.concurrent 下的集合（如 CopyOnWriteArrayList、ConcurrentHashMap）的迭代器是 fail-safe / 弱一致的，遍历期间被修改也不抛异常。

3.12 HashMap 原理：数组 + 链表 + 红黑树

HashMap 是面试中被问得最深入的类：它的结构、hash 怎样计算、下标怎样计算、put 的流程、怎样扩容、什么时候转为红黑树。下面按结构、定位、插入、扩容的顺序讲解，每一步都手工计算。本节描述的是 JDK 8 及以后的实现（以 OpenJDK 21 源码为准）。[11] [19]

结构

HashMap 内部是一个 Node<K,V>[] table 数组，数组每个位置叫一个桶。每个 Node 存 hash、key、value、next 四个字段。多个键落到同一个桶（哈希冲突）时，用 next 串成链表；链表太长时转成红黑树，把桶内查找从 O(n) 降到 O(log n)。

table 数组的每个桶：空、单个节点、链表（桶 1）或红黑树（桶 3，链表过长后转换）

第 1 步：扰动函数

static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

h >>> 16 把 hashCode 的高 16 位移到低 16 位，再与原值异或。原因在下一步：下标只取 hash 的低几位，如果不扰动，高位不同、低位相同的键会全部挤进同一个桶。null 键的 hash 固定为 0，放在桶 0。

第 2 步：下标 (n − 1) & hash

int index = (n - 1) & hash;     // n 是 table.length

当 n 是 2 的幂时，n − 1 的二进制是低位全 1（n=16 时为 1111），与 hash 按位与，正好取出 hash 的低 4 位，结果等于 hash % n（hash 非负时），而位运算比取模快得多。这就是 HashMap 容量必须是 2 的幂 的原因；new HashMap<>(13) 时，构造器会把容量调成不小于 13 的最小 2 的幂，即 16。

我们手算两个键（容量 16）：hashCode 分别是 0x10005 和 0x20005，它们的低 16 位相同，只有高位不同。

树化与 JDK 7 的问题

  • 树化：链表长度超过 8（TREEIFY_THRESHOLD = 8），且数组长度 ≥ 64（MIN_TREEIFY_CAPACITY）时，该桶转成红黑树；数组长度不足 64 时优先扩容。红黑树节点数降到 6 个及以下（扩容拆分时检查）退回链表。阈值 8 来自泊松分布：负载因子 0.75 下，一个桶出现 8 个节点的概率约亿分之六（0.00000006），几乎只在 hashCode 写得很差时出现。
  • JDK 7 是"数组 + 链表"，插入用头插法，多线程同时扩容时链表可能被反转成环，之后 get 死循环。JDK 8 改为尾插法并保持顺序，解决了成环，但 HashMap 依旧线程不安全（并发 put 会丢数据），多线程请用 ConcurrentHashMap。

LinkedHashMap 与 TreeMap

  • LinkedHashMap：在 HashMap 基础上用一条双向链表串起所有节点，遍历顺序等于插入顺序；构造时传 accessOrder = true 则按访问顺序排列，最近访问的移到链尾。再重写 removeEldestEntry 让 size() > 容量 时返回 true，就是一个 LRU 缓存。[20]
  • TreeMap：基于红黑树，按键排序，增删查 O(log n)，提供 floorKey、ceilingKey、headMap 等范围操作。[21]
class LRU<K, V> extends LinkedHashMap<K, V> {
    private final int cap;
    LRU(int cap) { super(16, 0.75f, true); this.cap = cap; }
    @Override protected boolean removeEldestEntry(Map.Entry<K, V> e) { return size() > cap; }
}
// 容量 2：put a, put b, get a, put c  →  淘汰 b，剩下 [a, c]

要点：

  • JDK 8 HashMap = 数组 + 链表 + 红黑树；hash = h ^ (h >>> 16)；下标 = (n − 1) & hash，容量为 2 的幂；负载因子 0.75，超过阈值扩容为 2 倍。
  • 扩容时元素要么留在原下标，要么移到原下标 + 旧容量，由 hash & oldCap 决定。
  • 链表长度超过 8 且数组长度 ≥ 64 时转红黑树，节点数 ≤ 6 时退回链表。
  • HashMap 允许一个 null 键和多个 null 值，线程不安全。

3.13 ConcurrentHashMap：线程安全的 HashMap

HashMap 在多线程下会丢数据。最简单的补救是 Hashtable 或 Collections.synchronizedMap，它们给每个方法加同一把锁，任何时刻只有一个线程能读写整张表，并发度只有 1。ConcurrentHashMap（下称 CHM）把锁的粒度缩小到每个桶。[22] [23]

JDK 8 的 put：CAS + synchronized 锁桶头

空桶用 CAS 无锁插入；非空桶只锁住这个桶的头节点，其他桶的写入可以同时进行

  • 桶为空：用 CAS（3.16）直接把新节点放进去，不加锁。
  • 桶正在迁移（头节点是特殊的 ForwardingNode）：当前线程先帮忙迁移，再重试。
  • 桶不空：synchronized 锁住桶的头节点，在链表或红黑树里插入。不同桶的写互不阻塞。
  • 读操作 get 不加锁：Node 的 value 和 next 用 volatile 修饰，保证读到最新值。

JDK 7 的 CHM 是另一种设计：分成 16 个 Segment（每个 Segment 继承 ReentrantLock，管着一个小 HashMap），锁粒度是一个段，最大并发度是段数。JDK 8 去掉了 Segment，锁粒度细化到桶。

对比HashtableConcurrentHashMap（JDK 8）
锁所有方法 synchronized，锁整张表CAS + synchronized 锁单个桶头
并发度1约等于桶数
读加锁不加锁（volatile）
null 键/值不允许不允许
迭代器fail-fast（Enumeration 不检查）弱一致，不抛 CME

CHM 不允许 null，是因为并发下 get(k) 返回 null 时无法区分"没有这个键"和"值就是 null"，单线程的 HashMap 可以再调 containsKey 确认，而并发时两次调用之间别的线程可能已经改了。

复合操作仍要用原子方法：CHM 保证每个方法本身线程安全，if (!map.containsKey(k)) map.put(k, v); 两次调用之间仍可能插进别的线程。应改用 putIfAbsent、computeIfAbsent、merge 这些单个原子方法，例如计数写成 map.merge(word, 1, Integer::sum)。

要点：

  • JDK 8 ConcurrentHashMap 用 CAS + synchronized 实现：空桶 CAS 插入，非空桶锁桶头节点；读不加锁，依赖 volatile。
  • JDK 7 用 Segment 分段锁（继承 ReentrantLock）。
  • Hashtable 锁整张表，效率低；CHM 和 Hashtable 都不允许 null 键值。

  • "JDK 8 CHM 用分段锁"是旧答案，面试时要区分 JDK 7 和 JDK 8。

小结： Hashtable 用一把锁锁住整个表；ConcurrentHashMap 在 JDK 7 中使用分段锁，在 JDK 8 中使用 CAS 加上锁住桶的头结点；读操作不加锁；不允许 null 键和 null 值；组合操作用 merge 或 computeIfAbsent。

3.14 线程基础：创建方式与状态转换

银行后台同时处理成千上万笔请求，每笔请求在一个线程里执行。线程是 CPU 调度的基本单位，同一进程中的线程共享堆内存，各自有自己的栈（进程与线程的区别见第 5 章）。[24]

创建线程的方式

// ① 继承 Thread，重写 run
class MyThread extends Thread { public void run() { System.out.println("A"); } }
new MyThread().start();
// ② 实现 Runnable，交给 Thread（推荐，可以再继承别的类）
new Thread(() -> System.out.println("B")).start();
// ③ 实现 Callable，有返回值、可抛受检异常，配合 FutureTask / 线程池
FutureTask<Integer> task = new FutureTask<>(() -> 1 + 1);
new Thread(task).start();
int r = task.get();          // 阻塞等待结果 2
// ④ 线程池（实际开发的做法，见 3.18）

本质上只有一种方式：创建 Thread 对象并调用 start()，Runnable 和 Callable 只是描述"要执行的任务"。start() 会启动新线程，由新线程调用 run()；直接调用 run() 只是在当前线程里执行一次普通方法。同一个 Thread 对象只能 start 一次，第二次抛 IllegalThreadStateException。

两个线程各给同一个计数器加 10000 次，结果常常少于 20000。问题出在 count++ 这一行：它在字节码里是三步——读出 count、加 1、写回。两个线程的三步交错执行，就会丢掉一次更新（第 5 章 5.10 节讲过同样的竞态）。

两个线程都读到 5，各自加 1 后写回 6：两次 ++ 只生效一次

synchronized：用监视器锁保护临界区

synchronized 让同一时刻只有一个线程能进入被保护的代码，三种写法锁住的对象不同：[26]

原理：每个 Java 对象都可以关联一个监视器（monitor）。同步代码块编译后在入口生成 monitorenter、出口生成 monitorexit 指令（异常路径上还有一个 monitorexit，保证抛异常也能释放锁）；同步方法则在方法标志里加 ACC_SYNCHRONIZED，由 JVM 在调用时自动加锁解锁。监视器内部记录 owner（持有锁的线程）、计数器（同一线程重入一次加 1，所以 synchronized 是可重入锁）、EntryList（等锁的线程，状态 BLOCKED）和 WaitSet（调用了 wait 的线程，状态 WAITING）。

锁升级

偏向锁被移除的原因：现代程序多用 java.util.concurrent 的并发工具，偏向锁带来的收益变小，而撤销偏向锁需要在安全点停顿，维护成本高。面试答"锁升级"时按四级回答，再补一句"偏向锁在 JDK 15 默认禁用、JDK 18 后被移除"就很完整。

volatile：可见性与禁止重排序

先看一个动机例子：

static boolean stop = false;           // 没有 volatile
// 线程 B
while (!stop) { }                       // 可能永远停不下来
// 线程 A（1 秒后）
stop = true;

线程 A 改了 stop，线程 B 却可能一直看不到。原因有两层：每个 CPU 核心有自己的缓存，B 可能一直读自己缓存里的旧值；更常见的是 JIT 发现循环体里没有修改 stop，把读取提到循环外，变成 if (!stop) while (true) {}。把字段声明为 volatile boolean stop 就解决了，这就是 volatile 的第一个作用。

  1. 可见性：对 volatile 变量的写会立即刷新到主存，读总是从主存读最新值；JIT 也不会把它的读取提出循环。
  2. 禁止指令重排序：编译器和 CPU 会为了性能调整指令顺序，volatile 读写前后插入内存屏障，禁止跨过它重排。

第二条的经典应用是双重检查锁（DCL）单例：

class Singleton {
    private static volatile Singleton instance;
    private Singleton() { }
    static Singleton get() {
        if (instance == null) {                    // 第一次检查：已创建就不加锁
            synchronized (Singleton.class) {
                if (instance == null)              // 第二次检查：防止重复创建
                    instance = new Singleton();
            }
        }
        return instance;
    }
}

instance = new Singleton() 分三步完成：分配内存；调用构造器初始化；把地址赋给 instance。没有 volatile 时，后两步可能被重排序，变成先赋地址再初始化，另一个线程在第一次检查时看到 instance 非空，就会直接拿走一个尚未初始化完成的对象。volatile 禁止了这种重排序。

volatile 只保证可见性和有序性，不保证原子性：volatile int count; count++ 仍是读-改-写三步，照样丢更新。

要点：

  • synchronized 基于对象监视器：代码块用 monitorenter/monitorexit，方法用 ACC_SYNCHRONIZED 标志；可重入、非公平。
  • 锁升级：无锁 → 偏向锁 → 轻量级锁（CAS + 自旋）→ 重量级锁（操作系统互斥量），只升不降；偏向锁在 JDK 15 默认禁用、JDK 18 移除。
  • volatile 保证可见性和有序性（禁止重排），不保证原子性；synchronized 三者都保证。

3.16 CAS、原子类、AQS 与 ReentrantLock

synchronized 拿不到锁就让线程阻塞。如果临界区只是"给一个数加 1"，阻塞和唤醒的代价远大于加 1 本身。CAS 提供了另一条路：不加锁，失败就重试。

CAS 与 AtomicInteger

CAS（Compare And Swap，比较并交换） 有三个操作数：内存位置 V、期望值 A、新值 B。** 只有当 V 的当前值等于 A 时，才把 V 改成 B**，否则什么也不做；整个"比较 + 写入"由一条 CPU 原子指令（x86 上是 lock cmpxchg）完成。[29]

AtomicInteger.incrementAndGet() 就是一个“读取、CAS、失败则重试”的循环（自旋）：

两个线程用 CAS 同时给 count=5 加 1

A: expect=5, new=6   B: expect=5, new=6
2 / 4

第2步 · A 先执行 CAS(5→6)：当前值 5 等于期望值，成功

3 / 4

第3步 · B 执行 CAS(5→6)：当前值已是 6，不等于期望值 5，失败，什么都不写

4 / 4

第4步 · B 重新读到 6，再执行 CAS(6→7)，成功

两次 +1 都生效，没有丢更新

CAS 的三个问题：

  1. ABA 问题：值从 A 改成 B 又改回 A，CAS 只比较值，会认为它没有被修改过。解决办法是加上版本号，AtomicStampedReference 同时比较值和版本号：值回到 1 但版本号已经改变时，CAS 失败。

AQS：并发工具的骨架

ReentrantLock、CountDownLatch、Semaphore 内部都基于 AQS（AbstractQueuedSynchronizer，抽象队列同步器）。它的思想只有两部分：[30]

  • 一个 volatile int state 表示同步状态，用 CAS 修改。对 ReentrantLock，state = 0 表示没人持有，> 0 表示被持有的重入次数；对 CountDownLatch，state 是剩余计数；对 Semaphore，state 是剩余许可数。
  • 一个 FIFO 双向等待队列（CLH 队列的变体）。获取失败的线程包装成节点排到队尾，然后用 LockSupport.park() 挂起；释放时唤醒队头的后继节点。

A 用 CAS 把 state 从 0 改为 1 拿到锁；B、C 的 CAS 失败，排进双向队列挂起，A 释放时唤醒 B

ReentrantLock

ReentrantLock 是基于 AQS 的显式锁，用法要配 try-finally：[31]

ReentrantLock lock = new ReentrantLock();       // 默认非公平；new ReentrantLock(true) 为公平锁
lock.lock();
try {
    count++;
} finally {
    lock.unlock();                              // 必须在 finally 中释放
}

它比 synchronized 多出四种能力：

  1. 可中断：lockInterruptibly() 等锁期间可以响应 interrupt() 退出，synchronized 等锁时无法被中断。
  2. 超时：tryLock(1, TimeUnit.SECONDS) 拿不到就返回 false，可以用来避免死锁。
  3. 公平锁：公平锁按排队顺序发锁；非公平锁的新线程先试一次 CAS 插队，吞吐量更高，所以是默认值。
  4. 多个条件变量：lock.newCondition() 可以建多个 Condition，await()/signal() 对应 wait()/notify()，生产者和消费者可以分别在"不满"和"不空"两个条件上等待，唤醒更精准。

死锁

转账时，线程 1 执行从 A 到 B 的转账，先锁 A 再锁 B；线程 2 执行从 B 到 A 的转账，先锁 B 再锁 A。两个线程各拿到一把锁，又都在等待对方的那一把，就会永远等下去。死锁的四个必要条件（第 5 章 5.13 节已详细讲解）是互斥、占有且等待、不可抢占、循环等待，破坏其中任意一个即可。

两个线程以相反顺序加锁形成环

最常用的解法是破坏循环等待：所有线程按同一顺序加锁，例如总是先锁账户 ID 小的那个。也可以用 tryLock(timeout) 拿不到就释放已有的锁并重试，破坏"占有且等待"。排查时用 jstack <pid>，它会直接打印 "Found one Java-level deadlock"。

要点：

  • CAS 是乐观锁：比较内存值与期望值，相等才更新，由 CPU 原子指令保证；问题是 ABA（用版本号解决）、自旋开销、只能保护一个变量。
  • AQS = volatile int state + CAS + FIFO 等待队列；ReentrantLock、CountDownLatch、Semaphore 都基于它。
  • ReentrantLock 相比 synchronized：可中断、可超时、可公平、可绑定多个 Condition，需手动在 finally 中 unlock。
  • 死锁四条件：互斥、占有且等待、不可抢占、循环等待；按固定顺序加锁最常用。

单选 · 理解检查 17　AtomicInteger v = new AtomicInteger(5); 依次执行 boolean r1 = v.compareAndSet(5, 6); boolean r2 = v.compareAndSet(5, 7); 之后 r1、r2 和 v.get() 分别是？

B · 错误：第二次 CAS 的期望值 5 与当前值 6 不符，不会写入。

3.17 ThreadLocal 与三个并发工具

有些数据需要"每个线程一份"：Web 服务里当前请求的用户信息、数据库连接、SimpleDateFormat（它不是线程安全的）。加锁共享一份太慢，ThreadLocal 让每个线程各自持有一份副本。另有一类需求是"线程之间协调节奏"：主线程等 N 个子任务全部完成、N 个线程互相等齐再一起出发、限制同时访问的线程数，分别对应 CountDownLatch、CyclicBarrier 和 Semaphore。

ThreadLocal 的原理

很多人以为 ThreadLocal 内部是一个 Map<Thread, 值>，实际方向正好相反：每个 Thread 对象里有一个 ThreadLocalMap 字段，map 的键是 ThreadLocal 对象，值是该线程的副本。tl.get() 就是"取当前线程的 map，用 tl 作键查值"。[32]

Thread 持有 map，map 的 Entry 弱引用 ThreadLocal、强引用 value

内存泄漏的原因：Entry 的键是弱引用，当外部不再引用 ThreadLocal 对象（栈上的 tl 消失）时，下一次 GC 就会回收它，Entry 的 key 变成 null。但 value 仍被 Entry 强引用，而 Entry 被 map 引用、map 被 Thread 引用。线程池里的线程会长期存活，这条 Thread → map → Entry → value 引用链一直存在，value 就无法回收。ThreadLocalMap 在 get/set 时会顺带清理 key 为 null 的条目，但不保证及时。

规范用法：用完在 finally 中调用 tl.remove()。线程池复用线程时，不 remove 还会把上一个请求的数据"串"给下一个请求。

static final ThreadLocal<String> USER = new ThreadLocal<>();
try {
    USER.set("alice");
    handleRequest();          // 调用链中任何地方都能 USER.get()
} finally {
    USER.remove();
}

CountDownLatch、CyclicBarrier、Semaphore

CountDownLatch done = new CountDownLatch(3);
for (int i = 0; i < 3; i++)

每来一个请求就 new Thread()，线程创建和销毁的开销很大，请求一多还会创建成千上万个线程把内存耗尽。线程池预先养着一批线程反复使用，并且用参数限定线程数和排队长度。面试必考的是 ThreadPoolExecutor 的七个参数、任务提交流程和拒绝策略。[36]

线程数怎么设？常用经验值：CPU 密集型任务取 CPU 核数 + 1；I/O 密集型任务取 2 × CPU 核数，或按 核数 × (1 + 等待时间 / 计算时间) 估算，最终以压测为准。

execute(Runnable) 没有返回值，任务抛出的异常会打印并结束该工作线程；submit() 返回 Future，异常被包装起来，调用 future.get() 时才抛出 ExecutionException，从不 get 就看不到异常。

要点：

  • 七个参数：核心线程数、最大线程数、空闲存活时间、时间单位、任务队列、线程工厂、拒绝策略。
  • 提交流程：小于核心数就新建线程 → 否则入队 → 队列满且小于最大数就新建非核心线程 → 否则执行拒绝策略。
  • 拒绝策略：Abort（抛异常，默认）、CallerRuns（调用者执行）、Discard（丢弃）、DiscardOldest（丢最老的）。
  • Executors 的 Fixed/Single 用无界队列，Cached 线程数无上限，都可能 OOM。

3.20 垃圾回收：分代、判活、算法与收集器

Java 程序员不用手动 free 内存，代价是要理解 GC 何时启动、为什么会卡顿。GC 要回答三个问题：哪些对象是垃圾？怎样回收？什么时候回收？[39]

哪些是垃圾：可达性分析

引用计数法给每个对象记录被引用次数，归零即回收，但两个对象互相引用时计数永远不为 0，回收不了。JVM 采用的是可达性分析：从一组称为 GC Roots 的根对象出发，沿引用链遍历，走不到的对象就是垃圾。

A、B、C 能从根到达，存活；D、E 互相引用，但从任何根都到不了，会被回收

可以作为 GC Roots 的对象：虚拟机栈中局部变量引用的对象、方法区中类静态变量引用的对象、方法区中常量引用的对象、本地方法栈中 JNI 引用的对象，以及被 synchronized 持有的对象、存活线程本身等。

四种引用

[40]

引用写法回收时机用途
强引用Object o = new Object()只要可达就永不回收，宁可 OOM普通引用
软引用SoftReference<T>内存不足、即将 OOM 时回收内存敏感的缓存
弱引用WeakReference<T>下一次 GC 就回收WeakHashMap、ThreadLocalMap 的 key
虚引用PhantomReference<T>随时；get() 永远返回 null配合 ReferenceQueue 得到"对象已被回收"的通知，管理堆外内存

强度从强到弱：强 > 软 > 弱 > 虚。

堆分代与对象晋升

经验表明绝大多数对象"朝生夕死"，少数对象会存活很久。于是堆被分成新生代和老年代，分别用不同的策略回收。以经典分代收集器（如 JDK 8 默认的 Parallel）的默认值为例：新生代 : 老年代 = 1 : 2（-XX:NewRatio=2），新生代内 Eden : S0 : S1 = 8 : 1 : 1（-XX:SurvivorRatio=8）。

以新生代的 1/10 为一份：Eden 8 份，两个 Survivor 各 1 份；老年代 20 份，是新生代的 2 倍

2 / 5

第4步 · ④ 如此在 S0、S1 之间来回复制，每熬过一次 Minor GC 年龄加 1

5 / 5

第5步 · ⑤ 年龄达到 15（-XX:MaxTenuringThreshold 默认值）时晋升到老年代

提前晋升的三种情况：
1. Minor GC 后 Survivor 放不下
2. 大对象直接进老年代
3. 同年龄对象总大小超过 Survivor 一半，该年龄及以上直接晋升（动态年龄判定）
  • Minor GC（Young GC）：只回收新生代，Eden 满时触发，频繁但很快。
  • Major GC / Full GC：Full GC 回收整个堆和方法区，停顿时间长。常见触发原因：老年代空间不足、元空间不足、显式调用 System.gc()、Minor GC 前估计老年代放不下晋升对象。线上要尽量避免频繁 Full GC。

  • System.gc() 只是建议 JVM 执行 Full GC，执行时机由 JVM 决定。
  • GC 回收的是内存。仍被某个全局集合引用、业务上已经没用的对象依然可达，造成"内存泄漏"；文件句柄、数据库连接也要自己 close。

小结： 判断对象是否存活用从 GC Roots 出发的可达性分析；新生代用复制算法，老年代用标记-整理算法；Eden 与两个 Survivor 的比例为 8:1:1，对象年龄达到 15 时晋升到老年代；低停顿的 CMS 已被移除，G1 是默认收集器，ZGC 的停顿在亚毫秒级；引用分为强、软、弱、虚四种。

3.21 类加载过程与双亲委派

类加载器与双亲委派

JDK 9 起有三层内置类加载器（JDK 8 中第二层叫扩展类加载器 Extension ClassLoader）：[45]

加载器负责加载在 Java 中的表示
启动类加载器 Bootstrap核心类库 java.lang.* 等（java.base 模块）C++ 实现，String.class.getClassLoader() 返回 null

请求自下而上委派到顶层；父加载器加载不了，才逐层退回由子加载器自己 findClass

双亲委派模型：一个类加载器收到加载请求时，先不自己加载，而是委派给父加载器；每一层都这样做，请求最终到达启动类加载器。只有父加载器在自己的范围内找不到这个类时，子加载器才自己尝试加载。ClassLoader.loadClass 的逻辑是：已经加载过就直接返回；否则交给 parent.loadClass；父加载器找不到，再调用自己的 findClass。

意义：

  1. 避免重复加载：父加载器已经加载过的类，子加载器不会再加载一次，同一个类在 JVM 中只有一份。
  2. 保护核心类库：自己写的 java.lang.String 加载请求总会先到达启动类加载器，它加载的是 JDK 自带的 String，伪造的类永远不会被使用，防止核心 API 被篡改。

打破双亲委派的场景：JDBC 等 SPI 机制（接口在核心库，实现在 classpath，启动类加载器看不到实现，于是借助线程上下文类加载器）、Tomcat 为每个 Web 应用使用独立类加载器以隔离不同版本的同名类、热部署。

要点：

  • 类加载过程：加载、验证、准备、解析、初始化；准备阶段给静态变量赋零值，初始化阶段执行 <clinit> 赋真正的值（static final 常量在准备阶段就赋值）。
  • 双亲委派：先委派父加载器，父加载器无法加载时子加载器才自己加载；作用是避免重复加载、保证核心类库安全。
  • 同一个类必须由同一个类加载器加载才被视为同一个类。

单选 · 理解检查 22　class Config { static int port = 8080; static final int MAX = 10; } 在类加载的准备阶段结束、初始化阶段开始之前，port 和 MAX 的值分别是？

A. 0 和 10

B. 8080 和 10

C. 0 和 0

D. 未分配内存

查看答案与每个选项的解析

A · 正确：普通静态变量准备阶段赋零值；static final 编译期常量带 ConstantValue 属性，准备阶段直接赋值。

B · 错误：port = 8080 是在初始化阶段的 <clinit> 中执行的。

C · 错误：编译期常量在准备阶段就已赋为 10。

易错点：

  • 类加载器的"父子"是组合关系（parent 字段），不是继承关系。
  • 双亲委派是 JDK 推荐的模型，并非强制约束，重写 loadClass 就可以打破它；只想自定义加载逻辑应重写 findClass。

小结： 类加载过程依次是加载、验证、准备、解析、初始化；准备阶段给静态变量赋零值，初始化阶段赋真正的初值；双亲委派先交给父加载器加载，可以避免重复加载并保护核心类库。

3.22 Java 8：lambda 与 Stream

Java 8 之前，给按钮加回调、给列表排序都要写一个匿名内部类，五六行代码里只有一行是真正的逻辑。Java 8 引入 lambda 表达式和 Stream API，让"对一组数据做筛选、转换、汇总"可以写成一条流水线。[46]

lambda 与函数式接口

函数式接口是只有一个抽象方法的接口（可用 @FunctionalInterface 标注），lambda 就是这个方法的简写。

接口方法例子
Runnablevoid run()() -> System.out.println("hi")
Comparator<T>int compare(T a, T b)(a, b) -> a.age - b.age
Function<T,R>R apply(T t)s -> s.length()
Predicate<T>boolean test(T t)x -> x > 0
Consumer<T>void accept(T t)x -> list.add(x)
Supplier<T>T get()() -> new ArrayList<>()

方法引用是 lambda 的进一步简写：s -> s.toUpperCase() 可以写成 String::toUpperCase，x -> System.out.println(x) 写成 System.out::println。

Stream 流水线

List<String> names = List.of("bob", "alice", "carol", "dave");
List<String> r = names.stream()
        .filter(s -> s.length() > 3)     // 中间操作：留下长度 > 3 的
        .map(String::toUpperCase)        // 中间操作：转大写
        .sorted()                        // 中间操作：排序
        .collect(Collectors.toList());   // 终止操作：收集成 List
// r = [ALICE, CAROL, DAVE]

Stream 流水线逐步变化

1 / 4

第1步 · 源：names.stream()

2 / 4

第2步 · filter(len > 3)：bob 被过滤

3 / 4

第3步 · map(toUpperCase)

4 / 4

第4步 · sorted() + collect：得到新 List，原 names 不变

Stream 的三个特点：不存储数据（只是对数据源的一次计算视图）；中间操作是惰性的（filter、map 只记录操作，遇到 collect、forEach、count 等终止操作才真正执行）；一个流只能消费一次。常用终止操作还有 count()、sum()（需先 mapToInt）、Collectors.groupingBy 分组。parallelStream() 用 ForkJoinPool 并行处理，适合数据量大、无共享状态的计算。

要点：

  • lambda 是函数式接口（只有一个抽象方法）的实现简写；方法引用是 lambda 的简写。
  • Stream 由数据源、中间操作（惰性）、终止操作组成，终止操作触发计算；流只能用一次，不修改源集合。

单选 · 理解检查 23　List.of(1, 2, 3, 4).stream().mapToInt(x -> x * x).sum() 的结果是？

A. 30

B. 10

C. 100

D. 编译错误：Stream 没有 sum 方法

查看答案与每个选项的解析

A · 正确：1 + 4 + 9 + 16 = 30。

B · 错误：10 是 1+2+3+4，没有平方。

C · 错误：100 是 (1+2+3+4) 的平方。

D · 错误：mapToInt 返回 IntStream，IntStream 有 sum()。

易错点：

  • 只有中间操作而没有终止操作的流水线什么都不会执行，stream.peek(System.out::println) 单独一行不输出。
  • lambda 里引用的局部变量必须是事实上 final，想在 lambda 里累加计数要改用 AtomicInteger 或直接用 count()。

小结： lambda 表达式实现函数式接口；Stream 由数据源、惰性的中间操作和终止操作组成，一个流只能使用一次。
