06.1 程序、进程与 PCB：操作系统怎样记住一个正在运行的程序

同一个记事本程序双击两次，桌面上会出现两个窗口，各自编辑不同的文件。磁盘上只有一份程序文件，内存里却有两个互不干扰的运行实例。操作系统需要一个概念来描述"正在运行的一份程序"，并替它记账：它运行到了哪条指令、占了哪些内存、打开了哪些文件、现在该不该给它 CPU。这个概念就是进程。

程序是存放在磁盘上的指令和数据，是静态的文件。进程是程序在一个数据集合上的一次执行过程，是动态的，会被创建、会运行、会结束。教材把进程在内存中的样子称为进程实体（也叫进程映像），它由三部分组成：

  • 程序段：要执行的指令；
  • 数据段：程序运行时用到的全局变量、堆、栈等数据；
  • PCB（Process Control Block，进程控制块）：操作系统为每个进程建立的一份"档案"，记录管理这个进程所需的全部信息。

创建进程，本质是为它建立 PCB；撤销进程，本质是回收它的 PCB。所以考试的标准说法是：PCB 是进程存在的唯一标志。 Linux 内核里对应的结构体叫 task_struct。

一份程序文件运行两次，得到两个进程；每个进程 = 程序段 + 数据段 + PCB，PCB（高亮）是操作系统管理它的入口

PCB 里存四类信息，选择题常按这四类出题：

类别例子用途
进程标识PID、父进程 PID、用户 ID区分不同进程，记录家族关系
处理机状态（现场）程序计数器 PC、通用寄存器、栈指针、程序状态字进程被换下 CPU 时保存，换上时恢复
调度信息进程状态、优先级、等待原因、已用 CPU 时间调度程序据此挑选下一个运行的进程
控制信息程序和数据的地址、打开文件表、占有的资源清单管理内存、文件和资源

系统里有成百上千个 PCB，常见的组织方式有两种：链接方式把同一状态的 PCB 串成队列（就绪队列、各种阻塞队列）；索引方式为每种状态建一张索引表，表项指向 PCB。调度程序从就绪队列里挑进程，就是在这些队列上操作。

进程有四个基本特征：动态性（最基本的特征，进程有生命周期）、并发性（多个进程在一段时间内同时推进）、独立性（进程是独立获得资源和独立接受调度的基本单位）、异步性（各进程按各自不可预知的速度推进，正因为如此才需要后面讲的同步机制）。

这里顺便分清两个词。并发是多个任务在同一段时间内都在推进，单核 CPU 靠快速轮流执行就能做到；并行是同一时刻真正同时执行，需要多个核。单核机器上的多个进程是并发的，四核机器上同时有四个进程在跑才叫并行。

对比项程序进程

06.2 进程的状态：五状态模型与挂起

一个进程从创建到结束，并非一直占着 CPU：有时在等 CPU，有时在等磁盘读完数据，有时在等用户按键。操作系统要知道每个进程此刻"卡在哪"，才能决定把 CPU 给谁。所以教材把进程的生命周期划分成几个状态，并规定状态之间怎样转换。

五个基本状态：

  • 新建（创建）态：正在建立 PCB、分配资源，还没准备好运行；
  • 就绪态：除了 CPU 以外，运行所需的一切都已具备，只要分到 CPU 立刻就能运行；
  • 运行态：正在 CPU 上执行（单核时任一时刻最多一个进程处于运行态）；
  • 阻塞态（也叫等待态、睡眠态）：在等某个事件，比如 I/O 完成、拿到锁、收到消息；这时即使 CPU 空闲，它也无法运行；
  • 终止态：运行结束或被撤销，系统正在回收资源，PCB 暂时保留，供父进程读取退出信息。

五状态模型：只有“运行→阻塞”是进程自己主动发起的（它调用了需要等待的操作）；阻塞结束后先回到就绪，再等调度

图中每条箭头都有固定的触发原因，按"谁触发"来记最清楚：

转换触发原因谁触发
新建 → 就绪PCB 建好、资源分配完毕操作系统
就绪 → 运行调度程序选中它调度程序
运行 → 就绪时间片用完，或被更高优先级的进程抢占时钟中断 / 调度程序
运行 → 阻塞进程自己请求 I/O、申请暂时拿不到的资源、等待消息进程自己（主动）
阻塞 → 就绪等待的事件发生，如 I/O 完成中断到来其他进程或中断处理程序（被动）
运行 → 终止正常结束、出错、被杀死进程自己或操作系统

我们跟着一个进程走一遍：用户敲下命令，系统为它建立 PCB（新建）；建好后放进就绪队列（就绪）；调度程序选中它（运行）；它执行到 read() 读磁盘，数据还没到，于是把自己挂到磁盘的等待队列上（阻塞）；磁盘读完发出中断，中断处理程序把它移回就绪队列（就绪）；再次被调度（运行）；执行完 exit()（终止）。

状态转换由原语完成。 原语是由若干条指令组成、执行期间不可被中断的程序段。操作系统用四个原语控制进程：创建原语（申请空白 PCB、分配资源、初始化 PCB、插入就绪队列）、撤销原语、阻塞原语 block（停止运行、改 PCB 状态、插入阻塞队列、转调度）、唤醒原语 wakeup（移出阻塞队列、改状态、插入就绪队列）。block 由进程自己调用，wakeup 由别的进程或中断处理程序调用，二者必须成对出现，否则被阻塞的进程永远醒不过来。

挂起：把进程暂时换到外存

内存紧张时，系统可以把一些暂时不运行的进程整个换到磁盘上，腾出内存给其他进程，这个动作叫挂起；条件允许时再调回内存，叫激活。引入挂起的原因有：内存不足需要调节负荷、用户调试时想暂停程序、父进程想暂停子进程、系统检查资源使用情况。

加入挂起后，就绪和阻塞各分成两种："活动"表示在内存，"静止"表示在外存。于是得到常说的七状态模型：

七状态模型：上排在内存，灰色两个在外存。挂起 / 激活在内存与外存之间搬运进程；静止阻塞的进程等到事件后变成静止就绪，仍在外存，要激活后才可能被调度

教材还允许“运行 → 静止就绪”：高优先级进程抢占 CPU 且内存不足时，正在运行的低优先级进程可以直接被挂起到外存，图中省略了这条边。

挂起和阻塞都会让进程暂停，区别在于原因和位置：阻塞是进程在等事件，仍在内存；挂起是系统把它换出到外存，原因是腾内存或外部请求。被挂起的进程即使等到了事件，也要先被激活回内存，才可能被调度。负责挂起和激活的正是下一节要讲的"中级调度"。

06.3 进程的创建与终止：fork、exec、wait，僵尸与孤儿

在 Linux 终端输入 ls，shell 要做三件事：造一个新进程、让新进程去执行 ls 这个程序、等它结束后拿回结果再显示下一个提示符。这三件事分别对应 fork、exec、wait 三个系统调用，面试经常让你画出它们的时间线。

系统调用是用户程序请求操作系统服务的受控入口。普通程序运行在用户态，只能执行普通指令；需要创建进程、读写文件这类特权操作时，通过系统调用切换到内核态，由内核代为完成，再返回用户态。fork、read、exit 是系统调用；memcpy、strlen 只在用户态计算，是普通库函数；printf、fopen 是库函数，但它们内部会调用 write、open 等系统调用。

  • fork()：复制当前进程，得到一个几乎一样的子进程。它调用一次、返回两次：在父进程中返回子进程的 PID（一个正整数），在子进程中返回 0，出错时返回 −1。程序靠这个返回值区分"我是父还是子"。[7]
  • exec 系列（如 execve）：把当前进程的程序段和数据段替换成另一个程序，PID 保持不变。exec 成功后不再返回，原来的代码已经被换掉了。[8]
  • wait / waitpid：父进程阻塞，直到某个子进程结束，然后取回它的退出状态，并让内核回收子进程的 PCB。[9]
  • exit()：进程结束，释放内存和文件等资源，只留下 PCB 里的退出码，等父进程来取。

shell 执行一条命令的完整时间线：fork 造进程，exec 换程序，wait 等结束并回收

写时复制（Copy-On-Write）：fork 之后父子进程逻辑上各有一份独立的地址空间，但内核并不立刻复制所有内存，而是让双方先共享同一批物理页，并把它们设为只读；哪一方先写某一页，才为它复制这一页。fork 之后紧接着 exec 的情况下，几乎什么都不用复制，开销很小。

下面是父进程 fork 一个子进程并等待它退出码的最小程序（practice/ch06_banker.cpp 中带断言）。变量含义：pid 是 fork 的返回值，status 保存 waitpid 取回的退出状态，WEXITSTATUS 从中提取 exit 时传的数。

int forkAndWait(int code) {
    pid_t pid = fork();
    if (pid < 0) return -1;
    if (pid == 0) _exit(code);                        // 子进程：fork 返回 0
    int status = 0;                                   // 父进程：fork 返回子进程 PID
    waitpid(pid, &status, 0);
    return WIFEXITED(status) ? WEXITSTATUS(status) : -1;
}

调用 forkAndWait(7)：子进程拿到返回值 0，立刻以退出码 7 结束；父进程拿到子进程 PID，在 waitpid 处阻塞，子进程结束后被唤醒，取回 7。

僵尸进程与孤儿进程

左：子先死、父不收尸 → 僵尸；右：父先死、子还活着 → 孤儿，被 1 号进程收养

  • 僵尸进程：子进程已经结束，但父进程还没调用 wait 回收它，子进程的 PCB 和退出码仍占着进程表的位置。ps 中显示为 Z 或 <defunct>。僵尸本身不运行、不占内存，危害在于占用 PID；大量积累会导致系统无法创建新进程。解决办法是让父进程 wait（或处理 SIGCHLD 信号），或者结束父进程，让僵尸变成孤儿后被 1 号进程回收。
  • 孤儿进程：父进程先退出，子进程还在运行。它会被 1 号进程（init 或 systemd）收养，将来由 1 号进程负责 wait。孤儿进程无害。守护进程（后台服务）就是刻意制造的孤儿：fork 后让父进程退出，子进程脱离终端在后台长期运行。

考场结论

  • fork 调用一次返回两次：父进程得到子进程 PID，子进程得到 0。
  • exec 替换程序、保持 PID；fork 新建进程。"fork + exec"是 Unix 启动新程序的标准组合。
  • 僵尸：子死父未收尸，占 PID；孤儿：父死子还活，被 1 号进程收养，无害。

06.4 线程：进程内的多条执行线索

一个浏览器进程要同时做几件事：下载图片、解析网页、响应鼠标点击。如果每件事都开一个进程，进程之间的地址空间互相隔离，共享网页数据要借助复杂的通信机制，创建和切换的开销也大。更自然的做法是在一个进程里开几条执行线索，它们共享同一份数据，各自往前走。这就是线程。

线程是进程内的一个执行单元，是 CPU 调度的基本单位；进程是资源分配的基本单位。同一进程的多个线程共享进程的代码段、全局数据、堆和打开的文件；每个线程私有自己的程序计数器、寄存器、栈和线程状态。描述一个线程的数据结构叫 TCB（Thread Control Block，线程控制块），里面有线程 ID、PC、寄存器、栈指针、状态、优先级、线程私有存储和信号屏蔽字。

同一进程的线程共享绿色部分，各自私有高亮部分（每个线程一套 TCB 现场和一个栈）

对比项进程线程
基本单位资源分配的基本单位CPU 调度的基本单位
地址空间各自独立同一进程内共享
创建、切换开销大：要建地址空间、切换页表小：只保存和恢复寄存器、栈指针
通信要借助 IPC（06.5 节）直接读写共享变量（要加同步）
健壮性一个进程崩溃一般不影响别的进程一个线程非法访问内存，整个进程会被终止

切换开销的差别来自地址空间。同一进程内切换线程，页表不变；切换到另一个进程，要换页表，CPU 中缓存地址翻译结果的 TLB（快表，第 07 章 07.3 节）里的旧条目随之失效，切换后的一段时间内访存会变慢。

用户级线程与内核级线程

线程可以由谁来管理？有两种做法：

  • 用户级线程（ULT）：由用户态的线程库管理，创建、切换都在用户态完成，内核只看到一个进程。优点是切换极快、无需陷入内核；缺点是一个线程执行阻塞系统调用（如读磁盘）时，内核会阻塞整个进程，其他线程也跟着停；而且内核只把这个进程当成一个调度对象，多核也无法让它的多个线程并行。
  • 内核级线程（KLT）：由内核管理，内核为每个线程维护 TCB 并直接调度。一个线程阻塞，其他线程照常运行，多个线程能在多核上并行；代价是创建和切换都要进内核，开销比 ULT 大。

用户线程最终要落到内核线程上才能真正被 CPU 执行，二者的对应方式有三种映射模型：

U 是用户线程，K 是内核线程。多对一：一个 K 承载全部 U；一对一：每个 U 一个 K；多对多：n 个 U 动态复用 m 个 K（虚线表示可以换到另一个 K 上）

模型做法优点缺点典型例子
多对一多个用户线程映射到一个内核线程线程管理在用户态，开销小一个线程阻塞，全部阻塞；无法利用多核早期的纯用户级线程库
一对一每个用户线程对应一个内核线程并发性好，一个阻塞其他照常；可多核并行每建一个线程就要建一个内核线程，开销较大Linux 的 pthread（NPTL）、Windows、Java 线程
多对多n 个用户线程映射到 m 个内核线程（m ≤ n）兼顾前两者：开销小，又能并行实现复杂Go 语言的 goroutine 调度器

协程可以看成"由程序自己决定何时让出 CPU 的用户态函数"：一个协程运行到 await 或 yield 时主动把控制权交回调度器，切换只需保存几个寄存器，不进内核，一个线程上能跑成千上万个协程。Python 的 asyncio、C++20 的协程、Go 的 goroutine 都属于这一思路。协程适合大量等待网络 I/O 的场景；纯计算任务仍要靠多线程或多进程利用多核。

考场结论

  • 进程是资源分配的基本单位，线程是调度的基本单位（引入线程后）。
  • 同一进程的线程共享代码、数据、堆、文件；私有 PC、寄存器、栈。
  • 用户级线程：内核不可见，切换快，一阻全阻；内核级线程：内核调度，可并行，开销大。

06.5 进程间通信（IPC）：六种常用方式

进程有各自独立的地址空间，进程 A 里的变量地址拿到进程 B 里毫无意义。可现实中进程经常要合作：shell 把 ls 的输出交给 grep 过滤，数据库服务进程把查询结果发给客户端进程，父进程要通知子进程"该退出了"。操作系统为此提供了进程间通信（Inter-Process Communication，IPC）机制，让数据或通知能够跨越地址空间。

教材把通信方式分成三大类：共享存储（双方映射同一块内存，直接读写）、消息传递（通过系统提供的 send/receive 原语收发格式化消息；消息直接发给目标进程叫直接通信，先放进一个叫"信箱"的中间实体、接收方再去取叫间接通信）、管道通信（通过一个特殊的共享文件按字节流传送）。Linux 中常用的具体方式有六种：

  • 管道（pipe）：内核中的一块缓冲区，一端写、一端读，数据按字节流先进先出。匿名管道只能用在有亲缘关系的进程之间（通常是父子进程，fork 时继承了管道的两个文件描述符），shell 中的 ls | grep txt 就是匿名管道。命名管道（FIFO）在文件系统中有一个路径名，用 mkfifo 创建，无亲缘关系的进程也能通过路径打开它。管道是半双工的（同一时刻数据单向流动），容量有限，写满时写者阻塞，读空时读者阻塞。[10]
  • 消息队列：内核中的一个消息链表。发送方把带类型的消息放进队列，接收方按类型或先后取出。与管道相比，它保留消息边界（发送一条就收到一条，管道只是一串字节），还能按类型挑选。[11]
  • 共享内存：内核把同一块物理内存映射进多个进程的地址空间，双方像访问普通变量一样直接读写。数据不需要在内核和用户空间之间来回拷贝，所以它是最快的 IPC 方式；代价是内核不负责同步，必须配合信号量或互斥锁使用。[12]
  • 信号量：一个由内核维护的计数器，用于进程间的同步与互斥，本身不传送数据，常与共享内存搭配。原理在 06.11 节详细讲。[13]
  • 信号（signal）：一种异步通知，只携带一个编号，如 SIGINT（按 Ctrl+C）、SIGKILL（kill -9，强制终止）、SIGCHLD（子进程结束时发给父进程）。进程收到信号后执行默认动作或自定义的处理函数。[14]
  • 套接字（socket）：最通用的方式，既能用于同一台机器上的进程（Unix 域套接字），也能跨网络通信（TCP/UDP，第 08 章）。

上路：管道和消息队列，数据先拷进内核、再拷给对方；下路：共享内存，双方直接访问同一块内存，配合信号量防止同时修改

方式传什么能否跨无亲缘进程能否跨机器特点
匿名管道字节流只限父子等亲缘进程本机半双工；最简单，shell 的 `
命名管道 FIFO字节流能（通过路径名）本机半双工；有文件名
消息队列带类型的消息能本机保留消息边界，可按类型读取
共享内存任意数据能本机最快，无需内核拷贝；要自己做同步
信号量不传数据，只计数能本机用于同步互斥，常配共享内存
信号一个信号编号能本机异步通知，信息量最少
套接字字节流或数据报能能最通用，网络通信的基础

考场结论

  • 最快的 IPC：共享内存（少了内核与用户空间之间的数据拷贝）；需要配合信号量做同步。
  • 能跨机器通信的只有套接字。
  • 匿名管道只能用于有亲缘关系的进程；命名管道没有这个限制。
  • 信号量用于同步，信号用于通知；两者名字相近，作用不同。

06.6 处理机调度：三级调度与评价指标

银行营业厅只有几个窗口，却有几十个客户在排队：先来先办？先办简单业务？VIP 优先？不同的规则，会让客户平均等待时间差别很大。CPU 就是操作系统里最稀缺的"窗口"，处理机调度就是决定"下一个把 CPU 交给谁"的规则。调度题是 408 和银行笔试的必考计算题，这一节先把概念和指标讲清，后面三节逐个算法手算。

三级调度

一个作业从提交到完成，可能经历三个层次的调度：

高级调度决定“谁能进内存”，中级调度决定“谁暂时出内存”，低级调度决定“内存里谁用 CPU”

层次别名做什么频率状态变化
高级调度作业调度从外存后备队列选作业调入内存，为它建立进程最低（分钟级）无 → 新建 → 就绪
中级调度内存调度把暂时不能运行的进程换到外存，或把外存的进程换回中等挂起 ↔ 激活
低级调度进程调度从就绪队列选一个进程分配 CPU最高（毫秒级）就绪 → 运行

作业是用户交给计算机的一项完整任务（如"编译、链接、运行一个程序"），每一步叫作业步；系统用作业控制块 JCB 记录作业信息。批处理系统才有作业调度；分时系统和个人电脑上通常只有进程调度，可能加上中级调度。三级中进程调度是必不可少的。

抢占与非抢占

  • 非抢占式：一旦把 CPU 给了某个进程，就让它一直运行，直到它完成或自己阻塞，才重新调度。
  • 抢占式：有更"该运行"的进程出现时（如更短的作业或更高优先级的进程到达、时间片用完），系统可以强行收回 CPU。

下面几种情况内核暂不切换进程：正在处理中断、进程处在操作系统内核的临界区里、正在执行原语。等这些动作结束再调度。

评价指标

设某作业的到达时刻为 a，要求的 CPU 服务时间为 s，第一次获得 CPU 的时刻为 b，完成时刻为 c：

  • 周转时间 T = c − a：从提交到完成的总时间。
  • 带权周转时间 W = T ÷ s：周转时间是服务时间的几倍。W ≥ 1，越接近 1 说明这个作业几乎没等；短作业等了很久，W 会很大。
  • 等待时间 = T − s：在就绪队列里等 CPU 的总时间（本章作业没有 I/O）。
  • 响应时间 = b − a：从提交到第一次得到 CPU。交互式系统最看重它。

平均周转时间、平均带权周转时间就是对所有作业取平均。此外还有 CPU 利用率（CPU 忙的时间占比）和吞吐量（单位时间完成的作业数）。

以 SRTF 中的作业 C 为例：服务时间 5，带权周转 W = 12 ÷ 5 = 2.4，响应时间 = 10 − 3 = 7

06.8 HRRN 与优先级调度：兼顾等待时间和紧迫程度

SJF 偏爱短作业，长作业可能一直等；FCFS 偏爱先来的，短作业吃亏。能不能让作业"等得越久越优先"，同时短作业仍占便宜？高响应比优先就是这样一个折中。另一方面，银行系统里转账交易和日志整理的紧迫程度完全不同，需要按优先级调度。

HRRN：高响应比优先

HRRN（Highest Response Ratio Next）是非抢占算法，每次调度时为每个已到达的作业计算响应比，选最大的：

响应比 = (等待时间 + 要求服务时间) ÷ 要求服务时间 = 1 + 等待时间 ÷ 要求服务时间

  • 等待时间相同时，服务时间越短，响应比越高 → 退化为 SJF；
  • 服务时间相同时，等待越久，响应比越高 → 退化为 FCFS；
  • 长作业等得足够久，响应比也会升高，最终能被选中，不会饥饿。

最先到达的 A 被抢占三次、最后才完成，周转 15。优先级调度的风险就在这里：只要不断有高优先级作业到达，低优先级作业会一直等下去（饥饿）。常用的解决办法是老化（aging）：作业每等待一段时间，优先级就提高一级，等得足够久总能运行。优先级分静态（创建时确定，不再改变）和动态（随等待时间、已用 CPU 时间调整）两种，老化属于动态优先级。HRRN 也可以看成一种动态优先级，"优先级"就是响应比。

优先级反转

优先级调度和锁放在一起，会出现一种反常现象：三个任务 H（高）、M（中）、L（低），L 先运行并拿到一把锁；H 到达，抢占 L，也要这把锁，只好阻塞等待 L 释放；这时 M 到达，它比 L 优先级高，抢占了 L 并一直运行。结果 H 实际在等 M，高优先级任务被中优先级任务间接拖住，这叫优先级反转（优先级倒置）。

t=2 H 抢占 L，t=3 H 要锁被阻塞；M 抢占 L 运行 4 个单位，L 拖到 t=8 才放锁，H 直到 8 才继续

优先级继承是标准解法：当 H 因为 L 持有的锁而阻塞时，临时把 L 的优先级提升到和 H 一样，M 就无法抢占 L；L 用完锁、释放后恢复原优先级，H 立刻拿到锁运行。同样的例子里，L 在 t=3 继承 H 的优先级运行到 4 放锁，H 在 4–6 完成，M 在 6 之后才运行。1997 年火星探路者号的反复重启，就是优先级反转造成的，后来通过远程打开优先级继承修复。

L 临时升到 H 的优先级，M 无法插队；H 在 t=6 就完成，比无继承时提前 4 个单位

考场结论

  • 响应比 = 1 + 等待时间 ÷ 服务时间；HRRN 是非抢占的，兼顾短作业和长作业，不会饥饿，代价是每次调度都要重算。
  • 优先级调度可能使低优先级作业饥饿，用老化解决。
  • 优先级反转：高优先级任务因低优先级任务持锁而等待，期间被中优先级任务抢占；解法是优先级继承（或优先级天花板）。

06.10 临界区与互斥：四条准则、Peterson 算法与硬件指令

两个取款线程同时给余额 100 加 1，结果可能是 101 而不是 102。x++ 在机器上是三步：读出 x、加 1、写回。两条线程的三步交错时：

T2 读到的是 T1 写回之前的旧值，两次加 1 只生效一次

问题出在 T2 读到的状态已经过期。像这样结果取决于线程执行先后的情况叫竞态条件。一次只允许一个进程使用的资源叫临界资源（打印机、共享变量）；访问临界资源的那段代码叫临界区。解决办法是保证同一时刻最多一个进程在临界区内，即互斥。

每个进程访问临界区的代码都分成四段：进入区（检查能否进入并"上锁"）、临界区、退出区（"解锁"）、剩余区。设计进入区和退出区时，要满足四条准则：

准则含义
空闲让进临界区空闲时，请求进入的进程应能立即进入
忙则等待已有进程在临界区内时，其他进程必须等待
有限等待请求进入的进程应在有限时间内进入，不会饿死
让权等待进不去时应立即释放 CPU，避免"忙等"

前三条是必须满足的；让权等待是"最好满足"，后面的 Peterson 算法和自旋锁都在原地循环检查，违反让权等待。

Peterson 算法

两个进程 i、j 用两个变量协商：flag[i] 表示 i 想进入，turn 表示"如果两人都想进，让谁先"。

进程 i 的进入区：flag[i] = true;  turn = j;  while (flag[j] && turn == j) ;  // 忙等
临界区
退出区：        flag[i] = false;

关键在 turn = j：每个进程都先把机会让给对方。两人同时想进时，后写 turn 的那个人会把 turn 写成对方，于是先写的人先进。只设 flag 的两种写法都有缺陷：先检查对方的 flag 再置自己的 flag，两人可能同时看到对方是 false 而一起进入，违反忙则等待；先置自己的 flag 再等对方的 flag 变 false，两人可能同时置 true 后互相等待，谁也进不去，违反空闲让进。practice/ch06_sync.py 穷举了这三种写法的所有交错，结果与上述一致。Peterson 算法满足前三条准则，但忙等违反让权等待。

硬件方法

  • 关中断：进入临界区前关中断，退出后再开。只适用于单处理机；把关中断的权力交给用户程序很危险。
  • TestAndSet（TSL）指令：硬件保证"读出旧值并把它置为 true"一步完成。while (TestAndSet(&lock)) ; 返回 false 说明原来没锁、自己已经锁上，可以进入。
  • CAS（Compare-And-Swap）：CAS(&x, 期望值, 新值)：若 x 等于期望值，就原子地把 x 改成新值并返回成功，否则失败。用它可以写出无锁的 x++：读出 x，循环 CAS(&x, 旧值, 旧值+1) 直到成功。CAS 存在 ABA 问题：x 从 A 被改成 B 又改回 A，CAS 看到的仍是 A，误以为没人动过；解决办法是给值附加版本号（第 11 章 11.16 节的 AtomicStampedReference）。

CAS 重试循环：比较和写入在一条硬件指令内完成，失败就重读重试

硬件方法同样是忙等。在多核上，现代 CPU 和编译器为了提速会重排指令（在单线程看来结果不变的前提下调换读写顺序），Peterson 这类纯软件算法在真实硬件上需要加内存屏障才可靠，这也是工程中直接使用锁和原子操作的原因。

06.11 信号量与管程：让等不到的进程去睡觉

Peterson 和 TSL 让等不到的进程原地空转，浪费 CPU。更好的做法是：进不去就把自己挂到一个等待队列上睡眠，等别人用完再叫醒。Dijkstra 提出的信号量就是这样一个工具。[17]

记录型信号量由一个整数 value 和一个等待队列组成，只能通过两个原语操作：

P(S):  S.value--;  if (S.value < 0) 把自己加入 S.queue 并阻塞 (block);
V(S):  S.value++;  if (S.value <= 0) 从 S.queue 唤醒一个进程 (wakeup);

P 来自荷兰语"尝试"，也写作 wait；V 来自"增加"，也写作 signal。value 的含义：

  • value > 0：还有 value 个资源可用；
  • value = 0：资源恰好用完，没有进程在等；
  • value < 0：资源用完，且 |value| 个进程正在等待。

信号量有两种基本用法。互斥：设 mutex = 1，临界区前 P(mutex)、后 V(mutex)；P、V 在同一个进程里成对出现。同步（规定先后）：设 S = 0，要先做的进程做完后 V(S)，要后做的进程开始前 P(S)；P、V 分在两个进程里。

管程

信号量的 P、V 散落在各个进程里，顺序写错一处就会死锁（下一节会看到）。管程把共享数据和操作它的过程封装在一起，并规定同一时刻只有一个进程能在管程内执行，互斥由编译器自动保证，程序员只需处理同步。管程内用条件变量处理"条件不满足就等"：x.wait() 让当前进程阻塞在 x 上并释放管程，x.signal() 唤醒一个在 x 上等待的进程。Java 的 synchronized 加 wait/notify、C++ 的 mutex 加 condition_variable 都是管程思想的实现。[18]

管程：入口保证互斥；条件不满足的进程在条件变量上等待，并让出管程

06.12 经典同步问题：生产者消费者、读者写者、哲学家、前驱图

PV 题的解题套路只有三步：① 找出有哪些互斥关系和同步关系；② 每种关系设一个信号量，定初值（互斥设 1，资源计数设资源数，先后关系设 0）；③ 在"用之前"写 P，在"用完 / 做完之后"写 V。下面四个经典问题都按这个套路来。

生产者消费者

生产者把产品放进容量为 n 的缓冲区，消费者从中取出。关系有三种：缓冲区要互斥访问（mutex=1）；缓冲区满时生产者要等（空槽数 empty=n）；缓冲区空时消费者要等（产品数 full=0）。

semaphore mutex = 1, empty = n, full = 0;
producer: while (1) { 生产一个产品; P(empty); P(mutex); 放入缓冲区; V(mutex); V(full); }
consumer: while (1) { P(full); P(mutex); 从缓冲区取出; V(mutex); V(empty); 消费产品; }

两个 P 的顺序不能颠倒。 如果生产者先 P(mutex) 再 P(empty)：缓冲区满时，生产者拿着 mutex 在 empty 上睡眠；消费者要取产品，先过了 P(full)，又在 P(mutex) 上睡眠。生产者等消费者腾空位，消费者等生产者放锁，双方永远等下去。规律是先 P 同步信号量，再 P 互斥信号量；两个 V 的顺序可以交换。

practice/ch06_sync.py 中还有一个用 Python threading 写的可运行版本（threading.Semaphore 即计数信号量，Lock 即 mutex），[19] 一个生产者、一个消费者，缓冲区容量 3：

def producer_consumer_threads(items, capacity):
    buf = deque()
    empty = threading.Semaphore(capacity)
    full = threading.Semaphore(0)
    mutex = threading.Lock()
    consumed = []
    peak = [0]

    def produce():
        for x in items:
            empty.acquire()                # P(empty)
            with mutex:                    # P(mutex) ... V(mutex)
                buf.append(x)
                peak[0] = max(peak[0], len(buf))
            full.release()                 # V(full)

    def consume():
        for _ in items:
            full.acquire()                 # P(full)
            with mutex:
                consumed.append(buf.popleft())
            empty.release()                # V(empty)

    ts = [threading.Thread(target=produce), threading.Thread(target=consume)]
    for t in ts:
        t.start()
    for t in ts:
        t.join()
    return consumed, peak[0]

运行 producer_consumer_threads(list(range(1, 11)), 3) 输出确定：消费顺序为 1 到 10，缓冲区中的产品数从未超过 3。线程交错每次可能不同，但信号量保证了结果不变。C++ 条件变量版本见 practice/ch06_banker.cpp 的 BoundedBuffer。[20]

读者写者

多个读者可以同时读文件，写者必须独占：读读可以并发，读写互斥，写写互斥。

读者优先：用 readcount 记录正在读的人数；第一个读者负责"锁住"文件挡住写者，最后一个读者负责放开。

semaphore rmutex = 1, wmutex = 1;  int readcount = 0;
reader: P(rmutex); if (readcount == 0) P(wmutex); readcount++; V(rmutex);
        读文件;
        P(rmutex); readcount--; if (readcount == 0) V(wmutex); V(rmutex);
writer: P(wmutex); 写文件; V(wmutex);

rmutex 保护 readcount 的修改；判断条件是比较 readcount == 0，写成赋值 readcount = 0 会让条件恒为假、计数被清零，整个算法失效（用户博客原文这里写成了单个等号，应改正）。[21] 只要读者源源不断，readcount 永远不归零，写者会饿死。

写者优先：增加信号量 re（初值 1）作为读者进入的"门"，再用 writecount 记录等待和正在写的写者数。第一个写者到来时关上这道门，后来的读者都被挡在门外；最后一个写者离开才开门。正在读的读者读完后，排队的写者就能写。

semaphore rmutex = 1, wmutex = 1, re = 1, file = 1;  int readcount = 0, writecount = 0;
reader: P(re); P(rmutex); if (readcount == 0) P(file); readcount++; V(rmutex); V(re);
        读文件;
        P(rmutex); readcount--; if (readcount == 0) V(file); V(rmutex);
writer: P(wmutex); if (writecount == 0) P(re); writecount++; V(wmutex);
        P(file); 写文件; V(file);
        P(wmutex); writecount--; if (writecount == 0) V(re); V(wmutex);

两种策略的饥饿方向相反：读者优先可能饿死写者，写者优先可能饿死读者。若写者只做 P(re); P(file); 写; V(file); V(re);，读者和写者按到达顺序在 re 上排队，得到读写公平版本。三个版本都在 practice 中穷举验证了互斥和无死锁。

06.13 死锁：四个必要条件与预防

转账系统中，线程 1 执行"A 转给 B"，先锁 A 账户再锁 B；线程 2 执行"B 转给 A"，先锁 B 再锁 A。两人各拿一把锁、等对方那把，就会永远等下去。死锁是指一组进程中每个进程都在等待只有组内其他进程才能释放的资源，结果谁都无法推进。

死锁的四个必要条件（同时满足才可能死锁）：

  1. 互斥：资源一次只能被一个进程使用；
  2. 请求并保持（占有并等待）：进程已经占有资源，又在申请新资源，申请不到也不释放已有的；
  3. 不可剥夺：已分配的资源只能由占有者主动释放，别人不能强行抢走；
  4. 循环等待：存在一个进程链，每个进程都在等下一个进程占有的资源。

资源分配图把这些关系画出来：圆圈是进程，方框是资源类（框里的点数是该类资源的实例数）；从资源指向进程的边是分配边，从进程指向资源的边是请求边。

有环：P1 占 R2 等 R1，P2 占 R1 等 R2。每类资源只有 1 个实例，有环就一定死锁

无环：P1 等 R2，但 P2 不再申请任何资源，P2 用完 R2 释放后 P1 就能运行

死锁预防就是设计规则，让四个条件中至少一个永远不成立：

破坏的条件做法缺点
互斥把资源改造成可共享的，如用 SPOOLing 把打印机虚拟成共享设备大多数资源本身必须互斥，适用面很窄
请求并保持静态分配：进程运行前一次性申请全部资源资源利用率低；进程可能长时间凑不齐，产生饥饿
不可剥夺申请新资源得不到时，释放已占有的全部资源，以后再重新申请实现复杂，反复申请释放开销大，可能导致前面的工作白做
循环等待资源有序分配：给所有资源编号，每个进程只能按编号递增的顺序申请编号难定，新增资源不便；进程需要的顺序与编号不一致时浪费

转账的例子用第 4 种最方便：规定总是先锁账户号小的那个，两个线程都先锁 A 再锁 B，就不会成环。

"至少多少资源一定不会死锁"

问题： 系统有 n 个进程，每个最多需要 k 个同类资源。资源总数 R 至少是多少，才能保证一定不会死锁？

推导： 最坏情况是每个进程都拿到 k−1 个、都只差 1 个，此时若资源恰好分完，大家都在等，就死锁了，这需要 n(k−1) 个资源。只要再多 1 个，就至少有一个进程能凑够 k 个，运行完后释放全部资源，其他进程依次也能完成。所以：

R ≥ n(k − 1) + 1

一般形式：若进程 i 最多需要 kᵢ 个，则 R ≥ Σ(kᵢ − 1) + 1 时一定不会死锁。

例：3 个进程，每个最多要 4 台打印机。3 × 3 = 9 台时，可能每人拿 3 台都在等，死锁；至少 10 台才安全。反过来问"6 台磁带机，每个进程最多要 2 台，最多允许几个进程并发而保证不死锁"：n(2−1)+1 ≤ 6，n 最大为 5。两个例子都在 practice 中用穷举验证过。

06.14 死锁避免：银行家算法

死锁预防定的规则太死，资源利用率低。死锁避免放宽要求：允许进程动态申请资源，但每次分配前先"演算"一下：如果分了以后系统可能陷入无法挽回的局面，就先不分。这就像银行放贷：只有确认放出这笔钱后，所有客户仍能按某种顺序拿够额度、还清贷款，才放贷。这个算法由 Dijkstra 提出，叫银行家算法。

安全状态：存在一个进程顺序 ⟨P₁, P₂, …, Pₙ⟩（叫安全序列），按这个顺序，每个进程都能拿到它还需要的全部资源、运行完毕并归还资源。不存在安全序列就是不安全状态。不安全状态有可能发展成死锁，安全状态一定不会死锁。

需要的数据结构（m 类资源，n 个进程）：

  • Available[m]：每类资源当前可用的数量；
  • Max[n][m]：每个进程对每类资源的最大需求；
  • Allocation[n][m]：每个进程已经分到的数量；
  • Need[n][m] = Max − Allocation：每个进程还需要的数量。

安全性检查

  1. 设工作向量 Work = Available，所有进程的 Finish = false；
  2. 找一个 Finish = false 且 Need ≤ Work（每个分量都不超过）的进程；
  3. 找到就假设它拿到资源运行完毕：Work = Work + Allocation，Finish = true，回到第 2 步；
  4. 找不到时，若所有 Finish 都为 true，系统安全；否则不安全。

第 3 步加的是这个进程已分配的 Allocation（它运行完后还给系统的），而非它的 Max。

处理一次资源请求

进程 Pi 发出请求向量 Request 时，按四步处理：

  1. 若 Request > Need[i]（有分量超过），出错：它要的比声明的最大需求还多；
  2. 若 Request > Available，资源不够，Pi 等待；
  3. 试分配：Available −= Request，Allocation[i] += Request，Need[i] −= Request；
  4. 对试分配后的状态做安全性检查。安全就正式分配；不安全就撤销试分配，恢复原状态，Pi 等待。

请求 1：P2 申请 (0,2,1,0)。 ≤ Need₂ (0,5,1,0)，≤ Available (1,5,2,0)。试分配后 Available = (1,3,1,0)，P2 的 Need 变为 (0,3,0,0)。安全性检查：P2 的 Need ≤ Work，P2 先完成，Work = (1,3,1,0) + (1,6,4,2) = (2,9,5,2)，之后与上表相同，安全序列 ⟨P2, P1, P3, P4⟩。批准。

请求 2：P1 申请 (0,4,2,0)。 ≤ Need₁ (0,6,4,2)，≤ Available (1,5,2,0)，前两步都通过。试分配后 Available = (1,1,0,0)，P1 的 Need 变为 (0,2,2,2)。检查：P1 需要 C 类 2 个、Work 只有 0；P2 需要 B 类 5 个；P3 需要 D 类 2 个；P4 需要 B 类 7 个，全都不满足，不安全。撤销试分配，P1 等待。

核心代码（practice/ch06_banker.cpp）。变量：work 是演算中的可用资源，finish[i] 表示进程 i 已被假设完成，order 收集安全序列。

bool isSafe(const Vec& available, const Mat& alloc, const Mat& need, vector<int>& order) {
    int n = alloc.size(), m = available.size();
    Vec work = available;
    vector<bool> finish(n, false);
    order.clear();
    for (int round = 0; round < n; ++round) {
        int pick = -1;
        for (int i = 0; i < n; ++i)
            if (!finish[i] && leq(need[i], work)) { pick = i; break; }
        if (pick == -1) return false;                 // 没人能完成：不安全
        for (int j = 0; j < m; ++j) work[j] += alloc[pick][j];
        finish[pick] = true;
        order.push_back(pick);
    }
    return true;
}

06.15 死锁检测与解除：资源分配图化简

预防和避免都要在每次分配时付出代价。Unix、Linux 这类追求效率的系统往往干脆不管，偶尔死锁就由人来重启，这叫鸵鸟策略；需要处理时，则采用检测 + 解除：允许死锁发生，定期检查，发现了再解决。越早下手处理死锁（预防 > 避免 > 检测），对系统正常运行的限制越大。

资源分配图化简

检测的方法是化简资源分配图：

  1. 找一个既不阻塞、也非孤立的进程：它的每个请求都能被当前空闲资源满足；
  2. 假设它运行完，删去它的所有请求边和分配边，资源变为空闲；
  3. 重复，直到找不到这样的进程。

死锁定理：若资源分配图能被完全化简（所有边都能删掉），则当前没有死锁；不能完全化简时，剩下的进程就是死锁进程。下面的例子中，R1 有 2 个实例，R2 有 1 个，图中有环 P1 → R2 → P2 → R1 → P1，却能完全化简：

死锁解除

  • 资源剥夺：挂起某些死锁进程，抢占它们的资源分给其他死锁进程；
  • 撤销进程：撤销全部死锁进程，或按代价从小到大逐个撤销（看优先级、已运行时间、还需时间、占用资源多少），直到死锁解除；
  • 进程回退：让一个或多个进程回退到足以避免死锁的检查点，要求系统记录历史状态。
策略什么时候处理做法代价
预防设计时破坏四个必要条件之一资源利用率低，限制最严
避免每次分配前银行家算法，只进入安全状态要预知最大需求，每次分配都要计算
检测与解除死锁发生后化简资源分配图，剥夺 / 撤销 / 回退解除时可能丢失进程的工作
忽略不处理鸵鸟策略偶尔死锁需人工处理

饥饿和活锁与死锁不同：饥饿是某个进程长期得不到资源，但其他进程在正常推进；活锁是进程都在运行、不断改变状态（比如互相谦让），却没有任何实际进展；死锁是一组进程全部阻塞、谁也动不了。

多选 · 理解检查 15　关于死锁检测，哪些正确？

A. 资源分配图能完全化简，说明当前没有死锁

B. 多实例资源的分配图中有环，就一定死锁

C. 检测算法和安全性检查结构相同，只是用 Request 代替 Need

D. 按代价从小到大撤销进程，是解除死锁的一种方法

查看答案与每个选项的解析

A · 正确：这是死锁定理。

B · 错误：本节的例子有环，却能完全化简。

C · 正确：检测看的是进程当前实际的请求，而非未来的最大需求。

D · 正确：逐个撤销，直到剩下的进程能继续推进。

易错点

  • 化简时删去的是进程的全部边（请求边和分配边），被删进程占的资源全部变为空闲。
  • 鸵鸟策略并非错误答案：它是通用操作系统的实际做法，考题问"Unix 如何处理死锁"时要选它。

速记： 能完全化简就无死锁，化简不掉的就是死锁进程；检测 = 安全检查把 Need 换成 Request；解除：剥夺、撤销、回退；越早处理代价越大。

06.16 本章小结

本章主线：有了进程和线程 → 要调度 CPU → 并发要同步 → 同步不当会死锁

主题必会的结论或公式
进程PCB 是唯一标志；进程是资源分配单位，线程是调度单位
状态运行→阻塞主动，阻塞→就绪被动；阻塞不能直接到运行；挂起 = 换到外存
fork / exec / waitfork 返回两次（父得 PID，子得 0）；exec 换程序 PID 不变；子死父不收 → 僵尸，父先死 → 孤儿
IPC共享内存最快，需配合信号量；只有套接字能跨机器
调度指标周转 = 完成 − 到达；带权 = 周转 ÷ 服务；等待 = 周转 − 服务；响应 = 首次运行 − 到达
调度算法同时到达 SJF 平均等待最短；动态到达 SRTF 最优；响应比 = 1 + 等待 ÷ 服务；RR 的 q 过大退化为 FCFS
同步四准则：空闲让进、忙则等待、有限等待、让权等待；信号量负值的绝对值 = 等待进程数
PV 套路互斥 1、资源 n、先后 0；先 P 同步、再 P 互斥
死锁四个必要条件；最少资源 n(k−1)+1；银行家 Need = Max − Allocation、Work += Allocation；能完全化简则无死锁
