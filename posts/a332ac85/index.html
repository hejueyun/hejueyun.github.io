10.1 存储与页：数据库按"页"读写磁盘

为什么需要它。 机械磁盘一次随机读约 10 毫秒，内存访问约 100 纳秒，相差约 10 万倍。1000 万行的表若逐行从磁盘读，要读 1000 万次。所以数据库的第一原则是：少访问磁盘，每次多拿一些。

它是什么。 数据库和磁盘交换数据的最小单位叫页（page）。InnoDB 默认页大小是 16KB（16384 字节），由 innodb_page_size 在实例初始化时决定。[1] 读一行数据时，InnoDB 把这一行所在的整页读进内存。页在磁盘上又按更大的单位组织：

层次含义InnoDB 默认值
表空间一个 .ibd 文件，存一张表的数据和索引每表一个文件
段一棵索引树的叶子页集合、非叶页集合各是一个段—
区（extent）连续的一组页，分配空间时整区申请1MB = 64 页
页磁盘与内存交换的单位，B+ 树的一个结点就是一页16KB
行一条记录，存在页里由表结构决定

内存中的缓冲池（buffer pool）缓存最近用过的页，命中就不访问磁盘；修改也只改缓冲池里的页（叫脏页），稍后刷盘。为什么不怕崩溃，10.11 节回答。

查询总是以页为单位读写；缓冲池命中时不访问磁盘

完整走一遍。 表 user 每行约 1KB，一页能放 16 行（16384 ÷ 1024 = 16）。查询 id = 7：

  1. 数据库算出 id = 7 所在的页（怎样算出，就是下一节索引的工作）；
  2. 查缓冲池，没有这页，从磁盘读入整页 16KB，顺带把同页的另外 15 行也读进了内存；
  3. 在页内找到 id = 7 的行返回。接下来再查 id = 8，大概率在同一页，直接命中缓冲池。

考场结论。

  • 数据库与磁盘交换数据的单位是页，InnoDB 默认 16KB；索引的目标是少读页。
  • 缓冲池缓存热点页；修改先改内存，脏页稍后刷盘，崩溃安全靠日志。

速记： 页是 I/O 单位（InnoDB 16KB），缓冲池缓存页，索引的目标是少读页。

10.2 B+ 树索引：为什么三四层就能管住千万行

为什么需要它。 对有序数据二分，每步一次磁盘读，1000 万行要 24 步。我们希望每读一页就把范围缩小上千倍，这就是 B+ 树。

它是什么。 B+ 树（第 03 章 03.14 节）的每个结点占一页。非叶结点只存"键 + 子页号"，用来指路；叶子存全部数据（或指向数据的信息），叶子之间按键的顺序用指针连成链表。一个非叶页能放多少个"键 + 指针"，叫这棵树的扇出（fan-out）。扇出越大，树越矮，查找要读的页越少。

高度估算公式。 设页大小为 P，非叶页的一项占 k + p 字节（k 为键长，p 为指针长），叶子页每页能放 r 行。则：

  • 扇出 f = ⌊P ÷ (k + p)⌋；
  • 树高为 h 层时，最多能存 f^(h−1) × r 行。

页 16KB、BIGINT 主键 8 字节、页号指针 6 字节、每行 1KB：3 层 B+ 树约存 2190 万行

完整走一遍（计算例）。 条件：InnoDB 页 16KB = 16384 字节；主键 BIGINT 占 8 字节，子页号指针占 6 字节；每行 1KB。为了好算，忽略页头、页尾和预留空间（真实页插满时约 15/16 满[1]，结果会略小，量级不变）。

  1. 扇出：16384 ÷ (8 + 6) = 1170.3，取整得 f = 1170。
  2. 叶子容量：16384 ÷ 1024 = 16 行。
  3. 2 层：根直接指向叶子，最多 1170 × 16 = 18,720 行。
  4. 3 层：1170² × 16 = 21,902,400 行，约 2190 万。
  5. 4 层：1170³ × 16 = 25,625,808,000 行，约 256 亿。

所以 1000 万行的表，B+ 树只有 3 层：查一条记录最多读 3 页；根页和第 2 层常驻缓冲池，实际往往只有 1 次磁盘读。同样 2190 万行若用二叉搜索树，高度至少 ⌈log₂(2190 万 + 1)⌉ = 25 层。

def fanout(page_bytes, key_bytes, ptr_bytes):
    return page_bytes // (key_bytes + ptr_bytes)

def max_rows(height, f, leaf_rows):          # height 按层数计，最后一层是叶子
    return f ** (height - 1) * leaf_rows

def min_height(n_rows, f, leaf_rows):
    h = 1
    while max_rows(h, f, leaf_rows) < n_rows:
        h += 1
    return h

f = fanout(16384, 8, 6)                       # 1170
print(max_rows(3, f, 16), min_height(10**8, f, 16))   # 21902400 4

规律与考场结论。

  • 标准答案：数据库索引用 B+ 树，因为 ① 非叶结点只存键和指针，一页能放上千个键，扇出大、树矮，查找只需 3～4 次磁盘 I/O；② 所有数据在叶子，每次查找都走到叶子，性能稳定；③ 叶子用链表相连，范围查询和排序只需顺序扫描叶子。
  • 键越短，扇出越大，树越矮：这就是"主键尽量用短的整数"的原因之一。
  • 树高按层数计，h 层最多存 f^(h−1) × r 行；数千万行通常是 3 层。

  • 第 03 章按 408 约定"n 个键对应 n 棵子树"；InnoDB 实际实现是"键是子树的分隔值"。两种约定算出的扇出只差 1，估算高度时没有影响。
  • B+ 树的层数少，指的是页访问次数少；每一页内部仍要做查找（InnoDB 用页目录做二分）。

速记： 扇出 = 页大小 ÷ (键 + 指针)；h 层容量 = f^(h−1) × 每页行数；16KB 页、BIGINT 主键：3 层约 2000 万行。

10.3 聚簇索引与二级索引：回表、覆盖索引、索引下推

为什么需要它。 数据只能按一种顺序存放，表按主键 id 排好了，按 name 查怎么办？InnoDB 再给 name 建一棵 B+ 树。两棵树怎样配合，决定了查询要走几棵树。

它是什么。

  • 聚簇索引（clustered index，也叫主键索引）：叶子存整行数据，表的数据本身就按主键顺序存在这棵树里，所以一张表只有一个聚簇索引。InnoDB 选主键做聚簇索引；没有主键时选第一个所有列都 NOT NULL 的 UNIQUE 索引；都没有时自动生成一个 6 字节的隐藏行号 DB_ROW_ID 做聚簇索引。[2]
  • 二级索引（secondary index，也叫辅助索引、非聚簇索引）：叶子存"索引列的值 + 这一行的主键值"。[2]
  • 回表：通过二级索引找到主键值以后，再拿主键到聚簇索引里查出整行。一次查询走了两棵树。
  • 覆盖索引：查询需要的列全部在二级索引里（索引列 + 主键），不必回表。EXPLAIN 的 Extra 显示 Using index。[3]
  • 索引下推（Index Condition Pushdown，ICP）：WHERE 里有些条件只涉及索引里的列，但不能用来缩小扫描范围。ICP 让存储引擎在二级索引上先用这些条件过滤，过滤通过的才回表。EXPLAIN 显示 Using index condition。[4]

查 name='张敏'：① 在二级索引找到 (张敏, 5)；② 拿主键 5 从聚簇索引的根往下查，到叶子取整行

完整走一遍。 表 user(id PK, name, age, city)，有 6 行（见上图），另建索引 idx_name(name) 和联合索引 idx_na(name, age)。

name LIKE '张%' 是范围条件，age 不能再缩小扫描范围；但 age 在索引里，ICP 把它下推到引擎层先过滤，回表从 4 次降到 2 次。

规律与考场结论。

  • 标准答案：InnoDB 的聚簇索引叶子存整行，二级索引叶子存索引列和主键值；通过二级索引查整行要先找主键再回聚簇索引，叫回表。
  • 覆盖索引：查询的列都在索引中，不需要回表，常用手段是建联合索引把要查的列包含进去。
  • 索引下推（MySQL 5.6 引入）：在存储引擎层用索引中的列先过滤，减少回表次数，只用于二级索引。[4]
  • 主键要短：每个二级索引的叶子都存一份主键，主键越长，所有二级索引越大。[2]

A. SELECT id, age FROM user WHERE name = '张敏'

B. SELECT name, city FROM user WHERE name = '张敏'

C. SELECT COUNT(*) FROM user WHERE name = '张敏' AND age = 20

D. SELECT * FROM user WHERE name = '张敏'

查看答案与每个选项的解析

A · 正确：id 是主键，存在二级索引叶子里；age、name 是索引列。全部覆盖。

B · 错误：city 不在 idx_na 里，必须回聚簇索引取。

C · 正确：条件列都在索引里，计数不需要其他列。

D · 错误：* 包含 city，需要回表。

易错点：

  • 覆盖索引仍可能访问聚簇索引：二级索引记录被标记删除或页被较新的事务改过时，InnoDB 要回聚簇索引检查行版本是否可见。[5]
  • 索引下推减少的是回表次数，扫描的索引项数量不变；Using index condition 表示还要回表，Using index 才是覆盖索引。
  • PostgreSQL 的表是堆表，索引指向行的物理位置，没有"聚簇索引叶子存整行"这回事；它的 index-only scan 还要看可见性映射。[6]

速记： 聚簇叶子存整行，二级叶子存主键；回表 = 二级找主键再查聚簇；覆盖 = 不回表；ICP = 先在索引里过滤，少回表。

10.4 联合索引、最左前缀、索引失效与 EXPLAIN

为什么需要它。 面试最常问"这条 SQL 走不走索引"。答案取决于联合索引按什么顺序排：顺序决定哪些条件能把扫描范围缩成连续一段。

它是什么。 联合索引 idx(a, b, c) 的叶子按 (a, b, c) 的字典序排列：先按 a 排；a 相同的再按 b 排；a、b 都相同的再按 c 排，就像电话簿先按姓、再按名排。

等值条件从最左列开始逐列加上，区间一层层缩小

b = 2 的项散落在 a=1、a=2、a=3 三段里，构不成一个连续区间

最左前缀规则（正面说法）。 用联合索引定位扫描区间时：

  1. 从最左列开始，条件按索引列的顺序连续地用；
  2. 每一列是等值条件（=、IN、IS NULL）时，可以继续用下一列；
  3. 遇到第一个范围条件（>、<、BETWEEN、LIKE 'x%'）时，这一列还能用，它后面的列不再参与确定区间。[7]

条件在 WHERE 里的书写顺序无关紧要，优化器会自己对齐：WHERE b = 2 AND a = 1 和 WHERE a = 1 AND b = 2 一样。

完整走一遍。 对上图的 7 项：

con.execute('CREATE INDEX idx_abc ON t(a, b, c)')
plan(con, 'SELECT * FROM t WHERE a = 1 AND b = 2')         # SEARCH t USING INDEX idx_abc (a=? AND b=?)
plan(con, 'SELECT * FROM t WHERE b = 2')                   # SCAN t
plan(con, 'SELECT * FROM t WHERE a = 1 AND b > 2 AND c = 3')   # SEARCH t USING INDEX idx_abc (a=? AND b>?)

plan(con, 'SELECT * FROM t WHERE a + 0 = 1')               # SCAN t

SEARCH 表示用索引定位区间，SCAN 表示全表扫描；第 3 条里只出现了 a=? AND b>?，c 没有参与定位。

索引失效清单：每一条都能用"有序性"解释

"索引失效"指优化器没用索引定位扫描区间，退化成全表或全索引扫描。原因可归为两类：条件与索引的排序对不上，或优化器算出走索引更贵。

写法例子原因
缺最左列idx(a,b) 上只写 WHERE b = 2索引先按 a 排，b 的值散在各段（见上图）
范围之后的列a = 1 AND b > 1 AND c = 2 中的 c范围内 c 不再有序，只能过滤
对索引列用函数或运算WHERE YEAR(birth) = 2000、WHERE a + 1 = 2索引按列的原值排序，函数值的顺序与之不同；改写成 birth >= '2000-01-01' AND birth < '2001-01-01'，或在 MySQL 8.4 建函数索引 [8]
隐式类型转换字符串列 phone 上写 WHERE phone = 13800000000MySQL 把字符串列转成数字再比较，'1'、' 1'、'1a' 都等于 1，相当于对列套了函数 [9]
前导通配符WHERE name LIKE '%伟'索引按前缀排序，开头不确定就找不到起点；LIKE '张%' 可以走范围
OR 的一边没有索引WHERE a = 1 OR d = 'x'（d 无索引）满足 d='x' 的行只能全表找，既然要全表扫描就一起扫；两边都有索引时 MySQL 可用 index_merge 合并 [10]
!=、<>、NOT INWHERE status != 0结果通常占表的大部分，回表代价高于全表扫描，优化器选择全表扫描
IS NOT NULL 选出大部分行WHERE email IS NOT NULL同上，按代价放弃；IS NULL 本身可以用索引，type 为 ref 或 ref_or_null [11]
选择性太低或表太小性别列、只有几十行的表走索引加回表比顺序读全表还慢

10.5 事务与 ACID：转账要么全做，要么全不做

为什么需要它。 A 给 B 转 10 元要两条 UPDATE。第一条执行完就崩溃，钱凭空少了 10 元；两人同时给 A 转账，修改可能互相覆盖。数据库要把一组操作作为整体管理，这就是事务。

它是什么。 事务（transaction）是用户定义的一个数据库操作序列，这些操作要么全做，要么全不做，是一个不可分割的工作单位。一个事务由三部分组成：开始标识（BEGIN / START TRANSACTION）、若干数据库操作、结束标识（COMMIT 提交或 ROLLBACK 回滚）。[12] 事务有四个特性，合称 ACID：

特性含义转账例子靠什么实现（InnoDB）
原子性 Atomicity事务中的操作要么全做，要么全不做只扣 A 不加 B 的状态不会留下undo log：失败时按旧值撤销
一致性 Consistency事务把数据库从一个正确状态变到另一个正确状态转账前后 A + B 总额不变由 A、I、D 加上约束和正确的程序共同保证
隔离性 Isolation并发执行的事务互不干扰两笔转账同时进行，结果与先后执行一样锁 + MVCC
持久性 Durability事务一旦提交，修改永久保存，故障也不丢提交后马上断电，重启后转账仍在redo log + 先写日志

一致性是目的，原子性、隔离性、持久性是达到它的手段

完整走一遍（sqlite3 演示）。 用 Python 自带的 sqlite3 建账户表，余额有 CHECK (balance >= 0) 约束。转账先给 B 加钱、再从 A 扣钱。转 200 元时扣钱违反约束、抛异常，with con: 自动回滚，已执行的"B 加 200"也被撤销。

def transfer(con, frm, to, amount):
    try:
        with con:   # 正常结束自动 COMMIT，抛异常自动 ROLLBACK
            con.execute('UPDATE account SET balance = balance + ? WHERE id = ?', (amount, to))
            con.execute('UPDATE account SET balance = balance - ? WHERE id = ?', (amount, frm))
        return True
    except sqlite3.IntegrityError:
        return False

规律与考场结论。

  • 标准答案：事务的 ACID 特性是原子性、一致性、隔离性、持久性。原子性靠 undo log 回滚，持久性靠 redo log，隔离性靠锁和 MVCC，一致性是目的，由前三者和数据库约束共同保证。
  • 事务是恢复和并发控制的基本单位。
  • 在程序里，把"一组必须同时成功的修改"放进同一个事务；任何一步失败就回滚。

10.6 并发异常与隔离级别：先把异常画成时间线

为什么需要它。 事务串行执行最安全但太慢，交错执行又会读错、写丢。先把问题画出来，再看数据库提供的几档隔离强度。

它是什么：四种并发异常（王珊教材的分类）。

  • 丢失修改：T1、T2 读入同一数据并修改，后提交的结果覆盖了先提交的，先提交的修改丢失。
  • 读"脏"数据（脏读）：T1 修改了数据但未提交，T2 读到了这个值，之后 T1 回滚，T2 读到的是从未存在过的"脏"值。
  • 不可重复读：T1 读了数据，T2 修改并提交了它，T1 再读，得到了不同的值。
  • 幻读（幻影）：T1 按条件查到一批行，T2 插入或删除了满足条件的行并提交，T1 再按同样条件查，行数变了。

丢失修改：两个事务都基于旧值计算，后写覆盖先写

完整走一遍：怎样一眼区分。 看三个问题：

  1. T2 读到的值，写它的事务提交了没有？没提交就是脏读。
  2. 两次读的是同一行的值变了，还是满足条件的行数变了？前者是不可重复读，后者是幻读。
  3. 两个事务都写同一数据，且都基于旧值？那是丢失修改。

隔离级别。 SQL 标准定义了四个隔离级别，每个级别规定"最多允许出现哪些异常"：

隔离级别脏读不可重复读幻读典型实现
读未提交 READ UNCOMMITTED可能可能可能读不加锁
读已提交 READ COMMITTED避免可能可能每条 SELECT 新建快照；PostgreSQL、Oracle 默认
可重复读 REPEATABLE READ避免避免标准允许整个事务用一个快照；MySQL InnoDB 默认
可串行化 SERIALIZABLE避免避免避免加锁或冲突检测

隔离级别越高，避免的异常越多，并发度越低；脏写在所有级别都被禁止

另外两种：脏写（覆盖别人未提交的写）所有级别都禁止；写偏斜：规定至少一名医生在岗，T1 看到 B 在岗就让 A 离岗，T2 同时看到 A 在岗就让 B 离岗，两者改不同的行，快照隔离下都能提交，结果无人值班，只有可串行化能完全避免。[14]

规律与考场结论。

  • 标准答案：脏读是读到其他事务未提交的数据；不可重复读是同一事务内两次读同一行，结果因其他事务的修改提交而不同；幻读是同一事务内两次按相同条件查询，结果集因其他事务的插入或删除而不同。
  • 四个隔离级别：读未提交、读已提交（解决脏读）、可重复读（再解决不可重复读）、可串行化（再解决幻读）。MySQL 默认可重复读，Oracle 和 PostgreSQL 默认读已提交。
  • 不可重复读重点在"修改"，幻读重点在"新增或删除"。

10.7 封锁：锁类型、封锁协议、两段锁与死锁

为什么需要它。 10.6 的异常都来自两个事务同时碰同一数据。最直接的办法是碰之前先加锁；加什么锁、什么时候放，决定能防住哪些异常。

它是什么：两种基本锁。

  • 排他锁（X 锁，写锁）：事务 T 对 A 加 X 锁后，T 可读可写 A，其他事务不能再对 A 加任何锁，直到 T 释放。
  • 共享锁（S 锁，读锁）：事务 T 对 A 加 S 锁后，T 可读 A 不可写，其他事务还可以对 A 加 S 锁，但不能加 X 锁。

意向锁。 锁可以加在行上，也可以加在表上。想给整表加 X 锁时，逐行检查有没有行被锁太慢，于是规定给行加锁前先在表上挂一个意向锁：行 S 锁前加 IS，行 X 锁前加 IX。InnoDB 表级锁相容矩阵：[17]

表级锁相容矩阵：S 与 S 相容；X 与一切冲突；意向锁之间都相容

记三句话：S 和 S 相容；X 和谁都冲突；意向锁之间互相相容（两个事务可能各锁不同的行）。王珊教材另有 SIX 锁（S + IX），只和 IS 相容。

三级封锁协议：锁什么时候放

只规定"加锁"还不够，还要规定"什么时候放"。王珊教材定义了三级封锁协议：

协议写（X 锁）读（S 锁）防丢失修改防脏读防不可重复读
一级修改前加 X 锁，事务结束才放不加锁✓✗✗
二级同一级读前加 S 锁，读完即放✓✓✗
三级同一级读前加 S 锁，事务结束才放✓✓✓

完整走一遍。 回到 10.6 的丢失修改：T1 先对 A 加 X 锁读到 100；T2 申请 X 锁被阻塞；T1 写回 90、提交、放锁；T2 拿到锁读到 90，写回 70，修改不再丢失（一级）。二级协议要求读前加 S 锁，T2 必须等 T1 的 X 锁释放才能读，读不到脏数据；但 S 锁读完就放，两次读之间别人仍能改。三级协议把 S 锁保持到事务结束，别人改不了，就能重复读。

两段锁协议（2PL）

为什么需要它。 多个数据项交错时整体对不对，要用可串行化衡量（10.8 节），两段锁是保证它的标准方法。

它是什么。 两段锁协议（Two-Phase Locking，2PL）要求每个事务分两个阶段加锁和解锁：

  1. 扩展阶段（第一阶段）：可以申请锁，不能释放任何锁；
  2. 收缩阶段（第二阶段）：可以释放锁，不能再申请任何锁。

换句话说：事务一旦释放了某个锁，就不能再申请新锁。 最后一次加锁的时刻叫封锁点。

2PL 的锁数曲线先只升不降（扩展阶段），过了封锁点后只降不升（收缩阶段）

完整走一遍：判断一个事务是否遵守 2PL。 从左到右扫描操作，记住"是否已经解过锁"：

  • SL(A) R(A) XL(B) R(B) W(B) XL(C) W(C) U(A) U(B) U(C)：前 6 步只加锁，第 8 步开始只解锁，遵守。
  • SL(A) R(A) U(A) XL(B) W(B) U(B)：第 3 步解了 A 的锁，第 4 步又申请 B 的锁，违反。
def is_two_phase(ops):
    unlocked = False
    for op in ops:
        if op.startswith(('SL', 'XL')):     # 加锁
            if unlocked:
                return False                 # 解过锁后又加锁
        elif op.startswith('U'):             # 解锁
            unlocked = True
    return True

变种：实际数据库多用严格两段锁，X 锁保持到事务结束，避免级联回滚；强严格两段锁连 S 锁也保持到事务结束。[18] 三级封锁协议的锁都到事务结束才放，所以一定遵守 2PL。

死锁与活锁

两段锁可能造成死锁：T1 锁了 A 想要 B，T2 锁了 B 想要 A，彼此等待。

两个事务按相反顺序加锁，形成循环等待

方法做法
预防：一次封锁法事务开始时一次锁住要用的全部数据；缺点是要预知全部数据，并发度低
预防：顺序封锁法所有事务按同一顺序加锁（例如按账户号从小到大）
诊断：超时法等待超过时限就认为死锁；InnoDB 的 innodb_lock_wait_timeout 默认 50 秒
诊断：等待图法事务为结点，T1 等 T2 就画边 T1→T2，图中有环即死锁；InnoDB 默认开启这种检测 [19]
解除选一个处理代价最小的事务回滚，释放它的锁；InnoDB 选修改行数少的事务回滚

活锁：T2 等的锁每次释放都被后来者抢走，T2 永远等下去；用先来先服务排队解决。

悲观锁与乐观锁：先加锁再访问是悲观锁（SELECT … FOR UPDATE），适合冲突多的场景；冲突少时用乐观锁，加版本号列，UPDATE … SET v = v + 1 WHERE id = ? AND v = 旧版本，受影响行数为 0 就重读重试。

规律与考场结论。

  • 标准答案：两段锁协议指所有事务分两个阶段对数据加锁和解锁：扩展阶段只能申请锁、不能释放锁；收缩阶段只能释放锁、不能申请锁。遵守两段锁协议是可串行化调度的充分条件，但不是必要条件；遵守两段锁协议的事务可能发生死锁。
  • 一级封锁协议防丢失修改，二级再防读脏数据，三级再防不可重复读。
  • 死锁预防：一次封锁法、顺序封锁法；诊断：超时法、等待图法；解除：撤销代价最小的事务。活锁用先来先服务避免。

  • 2PL 允许边执行边加锁，只要求解锁后不再加锁；一次封锁法开始时就全部锁上，能预防死锁，2PL 不能。
  • 遵守 2PL 能保证可串行化；反过来，可串行化的调度里，事务未必遵守 2PL。
  • 意向锁只在表级别起"告示"作用，IX 和 IX 相容：两个事务可以同时改同一张表的不同行。

速记： S 读 X 写，X 与一切冲突；一级防丢失、二级防脏读、三级防不可重复读；2PL = 先只加后只放，可串行化的充分条件，可能死锁。

10.8 可串行化与冲突图

为什么需要它。 交错执行的结果对不对？标准是：与按某种顺序串行执行的结果相同，这叫可串行化。考试给一个调度，让我们画冲突图来判断。

它是什么。

  • 调度：多个事务的操作按时间排成的序列。记号 R1(A) 表示 T1 读 A，W2(B) 表示 T2 写 B。
  • 可串行化调度：多个事务的并发执行结果，与按某一次序串行执行它们的结果相同。可串行化是并发事务正确调度的准则。
  • 冲突操作：两个操作来自不同事务、访问同一数据、至少一个是写。共三种：读-写、写-读、写-写。冲突操作的先后次序不能随便交换。
  • 冲突可串行化：在不改变冲突操作次序的前提下，通过交换不冲突的相邻操作，能把调度变成串行调度。
  • 冲突图（优先图）：每个事务一个结点；对每一对冲突操作，从先执行的事务向后执行的事务画一条边。冲突图无环 ⟺ 调度冲突可串行化，图的拓扑序就是等价的串行顺序。[20]

def conflict_edges(ops):              # ops: [('R', 1, 'A'), ('W', 2, 'A'), ...]
    edges = set()
    for i, (k1, t1, x1) in enumerate(ops):
        for k2, t2, x2 in ops[i + 1:]:
            if t1 != t2 and x1 == x2 and 'W' in (k1, k2):
                edges.add((t1, t2))
    return edges

def serial_order(ops):                # 拓扑序；有环返回 None
    nodes = sorted({t for _, t, _ in ops})
    edges = conflict_edges(ops)
    indeg = {t: 0 for t in nodes}
    for _, b in edges:
        indeg[b] += 1
    order, ready = [], [t for t in nodes if indeg[t] == 0]
    while ready:
        t = ready.pop(0)
        order.append(t)
        for a, b in sorted(edges):
            if a == t:
                indeg[b] -= 1
                if indeg[b] == 0:
                    ready.append(b)
    return order if len(order) == len(nodes) else None

变量表：ops 是调度；edges 是冲突图的边集，(1, 2) 表示 T1→T2；indeg 是每个事务的入度；ready 是当前入度为 0、可以排在前面的事务。对上面的 S，serial_order 返回 [1, 2, 3]；对丢失修改的调度返回 None。

规律与考场结论。

  • 标准答案：可串行化是并发事务正确调度的准则。一个调度是冲突可串行化的，当且仅当它的冲突图（优先图）无环；冲突可串行化是可串行化的充分条件。
  • 画边口诀：不同事务、同一数据、至少一个写，先发生的指向后发生的。

10.9 MVCC：读写不阻塞的多版本并发控制

为什么需要它。 只靠锁时，一行在被修改，所有读它的事务都得等，报表查询会被写操作反复卡住。MVCC（多版本并发控制）的思路是：写时保留历史版本，读时按自己的快照挑一个合适的版本，读写互不等待。

它是什么：InnoDB 的三件工具。

  1. 隐藏列：InnoDB 在聚簇索引的每一行里加了几个隐藏字段：DB_TRX_ID（6 字节，最后一次插入或修改这行的事务 ID）、DB_ROLL_PTR（7 字节，回滚指针，指向 undo log 中这行的上一个版本），以及没有主键时才用到的 DB_ROW_ID。[5] 事务 ID 按事务开始的先后递增分配。
  2. undo 版本链：每次修改一行，InnoDB 先把旧值写进 undo log，再改行本身，并让回滚指针指向这条 undo 记录。多次修改后，从当前行出发，沿回滚指针能一路找到更早的版本，形成版本链。
  3. ReadView（读视图，即快照）：事务做一致性读时生成的一个"可见性判断表"，记录四个值：
    • m_ids：生成 ReadView 时正在活跃（已开始、未提交）的读写事务 ID 列表；
    • min_trx_id：m_ids 中最小的 ID；
    • max_trx_id：生成 ReadView 时系统下一个要分配的事务 ID；
    • creator_trx_id：生成这个 ReadView 的事务自己的 ID。

可见性规则。 拿版本链上某个版本的 trx_id，按顺序判断：[21]

  1. trx_id == creator_trx_id：是自己改的，可见；
  2. trx_id < min_trx_id：生成快照前就已提交，可见；
  3. trx_id >= max_trx_id：生成快照之后才开始的事务改的，不可见；
  4. min_trx_id ≤ trx_id < max_trx_id：看它在不在 m_ids 里。在，说明生成快照时它还没提交，不可见；不在，说明它已经提交了，可见。

不可见就沿回滚指针找上一个版本，继续判断，直到找到可见的版本。

版本链：当前行经回滚指针指向 undo 中的旧版本，越往右越旧

判断规则写成代码只有几行：

class ReadView:
    def __init__(self, active_ids, creator, next_id):
        self.m_ids = sorted(active_ids)
        self.min_trx_id = min(active_ids) if active_ids else next_id
        self.max_trx_id = next_id
        self.creator = creator

    def visible(self, trx_id):
        if trx_id == self.creator:
            return True
        if trx_id < self.min_trx_id:
            return True
        if trx_id >= self.max_trx_id:
            return False
        return trx_id not in self.m_ids

def read_version(chain, view):        # chain：从新到旧的 (值, trx_id)
    for value, trx_id in chain:
        if view.visible(trx_id):
            return value
    return None

ReadView 什么时候生成。 这是 RC 和 RR 唯一的区别：

隔离级别生成时机效果
读已提交 RC每条一致性读 SELECT 都生成新的 ReadView能看到别人新提交的数据，会出现不可重复读
可重复读 RR事务中第一次一致性读时生成，之后一直复用整个事务看到同一个快照

注意 RR 的快照建立在第一次执行 SELECT 的时刻，不是执行 BEGIN 的时刻。MySQL 文档原文：同一事务中的所有一致性读，读取的都是该事务第一次这样的读所建立的快照。[22] 想在 BEGIN 时就建立快照，要用 START TRANSACTION WITH CONSISTENT SNAPSHOT。

快照读与当前读

MVCC 只管"读历史版本"。可是更新数据时，必须基于最新的值，否则又会丢失修改。所以 InnoDB 区分两种读：

读的种类语句读到什么加锁
快照读（一致性读）普通 SELECTReadView 规定的可见版本不加锁
当前读（锁定读）SELECT … FOR UPDATE、SELECT … FOR SHARE、UPDATE、DELETE、INSERT最新已提交版本FOR SHARE 加 S 锁，其余加 X 锁

SELECT … FOR UPDATE 对读到的行加 X 锁，其他事务不能修改这些行、也不能对它们加 FOR SHARE 锁，直到本事务提交或回滚；FOR SHARE（旧写法 LOCK IN SHARE MODE）加 S 锁，别人能读不能改。两者都要在事务里使用，锁在事务结束时释放。MySQL 8.0 起还可加 NOWAIT（拿不到锁立即报错）或 SKIP LOCKED（跳过已被锁的行，适合做任务队列）。[23]

典型用法是"先查后改"的扣库存：

START TRANSACTION;
SELECT stock FROM item WHERE id = 7 FOR UPDATE;   -- 当前读并加 X 锁，别人改不了
UPDATE item SET stock = stock - 1 WHERE id = 7;    -- 应用层确认 stock > 0 后再扣
COMMIT;

规律与考场结论。

  • 标准答案：InnoDB 的 MVCC 通过隐藏列（事务 ID、回滚指针）、undo log 版本链和 ReadView 实现。读已提交在每次 SELECT 时生成 ReadView，可重复读在第一次 SELECT 时生成并复用。
  • 快照读是普通 SELECT，读历史版本、不加锁；当前读是 SELECT … FOR UPDATE / FOR SHARE 以及 INSERT、UPDATE、DELETE，读最新版本并加锁。
  • 可见性四条：自己改的可见；小于 min 可见；大于等于 max 不可见；中间看是否在活跃列表里。

10.10 MySQL 的行锁：记录锁、间隙锁、临键锁

为什么需要它。 当前读读最新数据。如果只锁已有的行，别人仍能往范围里插入新行，再次当前读就多出一行（幻读）。InnoDB 的办法是连行与行之间的空隙一起锁住。

它是什么。 InnoDB 的行锁加在索引记录上，有三种：[17]

  • 记录锁（Record Lock）：锁住一条索引记录。
  • 间隙锁（Gap Lock）：锁住两条索引记录之间的开区间，只阻止别人往这个间隙插入；间隙锁之间不冲突。
  • 临键锁（Next-Key Lock）：记录锁 + 这条记录前面的间隙，是左开右闭区间。

索引里有 10、11、13、20 四个值时，临键锁的区间是：(−∞, 10]、(10, 11]、(11, 13]、(13, 20]、(20, +∞)。

临键锁 = 记录锁 + 左侧间隙，按左开右闭划分

完整走一遍。 表 t(id 主键) 有 id = 10、11、13、20。在可重复读级别下，T1 执行：

SELECT * FROM t WHERE id > 12 AND id < 18 FOR UPDATE;
  1. InnoDB 沿主键索引从 12 开始扫描，第一条记录是 13，满足条件，加临键锁 (11, 13]；
  2. 继续扫到 20，不满足 < 18，扫描停止；为了挡住 13～20 之间的插入，对 20 加的锁退化成间隙锁 (13, 20)；
  3. 结果：(11, 13] 和 (13, 20) 被锁住。此时 T2 执行 INSERT INTO t VALUES (15)，15 落在被锁的间隙里，T2 阻塞；T1 再次执行同一条 FOR UPDATE，仍然只有 13 一行，没有幻读。

间隙锁挡住了插入，当前读两次结果一致

加锁规则要点。

情况加什么锁
可重复读下的范围查询、普通索引扫描临键锁（防幻读）
唯一索引等值查询，且记录存在只加记录锁，不需要间隙锁
唯一索引等值查询，记录不存在间隙锁
读已提交基本不用间隙锁，只在外键检查和唯一性检查时使用
查询条件列上没有索引只能扫描整个聚簇索引，每一行和每个间隙都被锁住，效果相当于锁表

最后一条在工程上很重要：UPDATE … WHERE 的条件列没有索引时，InnoDB 会锁住全表的行，并发更新全部排队。

规律与考场结论。

  • 标准答案：InnoDB 行锁有记录锁、间隙锁和临键锁三种；临键锁 = 记录锁 + 间隙锁，锁左开右闭区间。InnoDB 在可重复读级别下用 MVCC 解决快照读的幻读，用临键锁解决当前读的幻读。
  • InnoDB 的行锁是加在索引上的；没有可用索引时会退化成锁住所有行。
  • 意向锁是表级锁，由 InnoDB 在加行锁前自动加上，用户不需要手动申请。

  • 间隙锁之间不冲突：两个事务可以同时持有同一间隙的间隙锁，但随后都想往里插入时会互相等待，容易造成死锁。
  • 间隙锁是可重复读的产物；把隔离级别改成读已提交，间隙锁基本关闭，并发更高，但当前读会出现幻读。[17]
  • 普通 SELECT 是快照读，不加任何行锁，也不受这些锁阻塞。

速记： 记录锁锁行、间隙锁锁空隙只防插入、临键锁 = 行 + 左侧间隙（左开右闭）；RR 下当前读靠临键锁防幻读；没索引就锁全表。

10.11 日志与恢复：WAL、redo、undo、binlog 与检查点

为什么需要它。 修改先改内存页，脏页稍后才刷盘。已提交但脏页没刷就断电，修改会丢（持久性）；没提交但脏页已刷就崩溃，半截修改留在磁盘（原子性）。两个问题都靠日志解决。

WAL：先写日志。 预写日志（Write-Ahead Logging）规则：先写日志，后写数据库，数据页写盘之前，描述这次修改的日志必须已经落盘。[24] 崩溃后按日志就能恢复；而且日志是顺序追加写，提交时只需日志落盘，比随机写数据页快得多。

WAL：提交时只要日志落盘；数据页什么时候刷都行

两阶段提交：让 redo log 和 binlog 一致

事务既写 redo log 又写 binlog。只写成一个就崩溃，主库（看 redo）和从库（看 binlog）就会不一致。InnoDB 用两阶段提交把两者绑在一起：[26]

redo log 与 binlog 的两阶段提交

1 / 3

第1步 · 阶段一 prepare：redo log 写入并刷盘，标记为 prepare

此时崩溃：redo 是 prepare、binlog 里没有这个事务 → 回滚。
2 / 3

第2步 · 写 binlog 并刷盘

此时崩溃：redo 是 prepare，但 binlog 中能找到这个事务的 XID → 提交。从库会通过 binlog 收到它，所以主库也必须提交。
3 / 3

故障类型例子恢复方法需要 DBA 介入吗

系统故障断电、操作系统崩溃，内存丢失但磁盘完好撤销故障时未完成的事务，重做（REDO）已提交的事务不需要，重启时自动完成

系统故障既要 UNDO 又要 REDO：已提交事务的修改可能还在内存没刷盘，要 REDO；未提交事务的修改可能已刷到磁盘，要 UNDO。

检查点：恢复时不必从头扫日志

日志越来越长，从头扫太慢。检查点定期把日志缓冲和脏页都写入磁盘，再在日志里写一条检查点记录，记下此刻正在执行的事务。恢复时从最近的检查点开始。

恢复算法（王珊教材）。

  1. 从最近的检查点记录中取出当时的活跃事务，放入 UNDO-LIST；REDO-LIST 置空。
  2. 从检查点开始正向扫描日志：遇到新开始的事务，放入 UNDO-LIST；遇到提交的事务，从 UNDO-LIST 移到 REDO-LIST。扫到日志末尾为止。
  3. 对 UNDO-LIST 中的事务反向扫描执行撤销（写回旧值）；对 REDO-LIST 中的事务正向扫描执行重做（写入新值）。

检查点之前就已提交的事务，修改在做检查点时已经写入磁盘，不需要任何处理。

求两个列表的程序就是把上面的规则照搬：

def recovery_lists(log):
    ck = max(i for i, r in enumerate(log) if r[0] == 'CKPT')
    undo = list(log[ck][1])          # 检查点时的活跃事务
    redo = []
    for r in log[ck + 1:]:
        if r[0] == 'START':
            undo.append(r[1])
        elif r[0] == 'COMMIT':
            undo.remove(r[1])
            redo.append(r[1])
    return sorted(redo), sorted(undo)

规律与考场结论。

  • 标准答案：WAL（先写日志原则）要求：① 登记的次序严格按并发事务执行的时间次序；② 必须先写日志文件，后写数据库。
  • 事务故障：撤销该事务；系统故障：撤销未完成事务、重做已提交事务；介质故障：装入后备副本，再重做已提交事务。
  • 检查点恢复：检查点之前提交的事务不处理；检查点之后、故障之前提交的 REDO；故障时仍未提交的 UNDO。
  • redo log 是 InnoDB 的物理日志，保证持久性、用于崩溃恢复；undo log 保证原子性并支持 MVCC；binlog 是 Server 层的逻辑日志，用于主从复制和时间点恢复；redo 与 binlog 通过两阶段提交保持一致。

10.12 备份：转储的分类与组合

为什么需要它。 磁盘坏了，数据文件本身就没了。办法是冗余：定期把数据库复制一份，叫转储，副本叫后备副本。

它是什么：两组分类（王珊教材）。

分类角度类型含义优缺点
转储时是否允许事务运行静态转储系统中无事务运行时转储，转储期间不允许修改得到一致的副本；但要等事务结束、期间不能更新，降低可用性
动态转储转储与用户事务并发进行不影响业务；但副本不一定一致，必须同时登记转储期间的日志，恢复时副本 + 日志才能到一致状态
每次转储多少数据海量转储每次转储全部数据库恢复简单，只装一个副本
增量转储每次只转储上次转储后更新过的数据每次转储快；恢复时要按顺序装多份

两组组合起来有四种：动态海量、动态增量、静态海量、静态增量。

MySQL 的叫法：冷备份≈静态转储，热备份≈动态转储，温备份是运行中但锁住不让改；全量/增量备份（增量靠 binlog）；物理备份复制数据文件、恢复快，逻辑备份导出 SQL（如 mysqldump）、可移植。[27]

时间点恢复：全量 + 增量 + binlog，停在误操作之前

完整走一遍。 周二 10:16 有人误删了一张表。恢复步骤：① 装入周日的全量备份；② 依次装入周一、周二的增量备份；③ 用 mysqlbinlog 从周二 0 点重放 binlog，停在 10:15（误删语句之前）。数据库回到误删前一刻。这叫基于时间点的恢复。

规律与考场结论。

  • 标准答案：数据转储按状态分为静态转储和动态转储，按方式分为海量转储和增量转储。动态转储必须把转储期间各事务的活动登记下来，建立日志文件，后备副本加日志文件才能把数据库恢复到某一时刻的正确状态。
  • 介质故障的恢复 = 后备副本 + 日志重做。

10.14 分布式数据库简介：分片、分配与半连接

为什么需要它。 全国性银行的数据一台服务器装不下，各省分行又主要访问本省数据。把数据分散到多个地点、同时让用户感觉在用一个数据库，就是分布式数据库。

它是什么。 分布式数据库系统是物理上分散、逻辑上集中的数据库系统：数据分布在网络的多个场地上，各场地能独立处理局部应用，整体又支持跨场地的全局应用。[29]

它的两个基本特性：

  • 分布透明性：从高到低分三层：分片透明性（用户感觉表没被切开）、位置透明性（知道分片，但不必知道放在哪）、局部数据模型透明性（不必知道场地上用什么数据库）；另有复制透明性（不必知道有几个副本）。
  • 场地自治性：各场地的局部数据库管理系统能独立决定自己的设计（设计自治）、是否及如何与其他场地通信（通信自治）、以何种方式执行局部操作（执行自治）。

分片。 把一张全局表切成多个片段，这一步叫分片；把片段放到哪些场地，叫分配。[30]

分片方式做法关系代数重构全局表
水平分片按行切，每片是满足某条件的元组选择 σ并 ∪
垂直分片按列切，每片都保留主键投影 π按主键连接 ⋈
导出水平分片按另一张相关表的分片条件切本表半连接并
混合分片先垂直再水平（或反之）组合组合

分片要满足三条原则：完备性（每条全局数据都属于某个片段）、可重构性（片段能拼回全局表）、不相交性（水平分片的片段互不重叠；垂直分片除主键外的列不重复出现）。

水平分片 E1 ∪ E2 = EMP；垂直分片 V1 ⋈ V2 = EMP（按主键 eno 连接）

分配有三种：非复制（每个片段只存一个场地）、全复制（每个场地都存全部片段）、部分复制（片段在部分场地有副本）。副本越多，读越快、可用性越高，但更新时要同步所有副本，维护一致性的代价越大。

模式结构分四层：全局外层、全局概念层、局部概念层、局部内层；全局概念模式经分片模式（怎样切）和分配模式（放哪里）映射到局部。[31]

分布式查询。 总代价 = 通信 + I/O + CPU，网络慢时以通信为主：C_com(X) = C₀ + C₁ × X，C₀ 是每次传输的启动代价，C₁ 是每字节代价，X 是传输量。[32] 处理分四层：查询分解 → 数据本地化（全局表换成片段，去掉不可能有结果的片段）→ 全局优化 → 局部优化。[33]

半连接。 R 对 S 的半连接 R ⋉ S = π_R(R ⋈ S)，即 R 中能和 S 连上的那些元组。它的用途是：先只把 S 的连接列传过去，在对方场地筛掉连不上的元组，再把剩下的少量元组传回来，从而减少传输量。半连接不满足交换律：R ⋉ S 和 S ⋉ R 的结果不同。

完整走一遍（计算例）。 场地 S1 存员工表 EMP，10000 行，每个元组 28 字节（eno 4、ename 20、dno 4）。场地 S2 存部门表 DEPT，查询在 S2 发起：求"位于北京的部门的所有员工"。S2 上选出北京的部门共 10 个；这 10 个部门共有 500 名员工。设 C₀ = 1000，C₁ = 1（每字节）。

策略传输内容传输量通信代价
直接连接把整个 EMP 传到 S210000 × 28 = 280,000 字节1000 + 280,000 = 281,000
半连接① 把 10 个 dno 传到 S1：10 × 4 = 40 字节；② S1 算 EMP ⋉ 北京部门，把 500 个元组传回 S2：500 × 28 = 14,000 字节14,040 字节(1000 + 40) + (1000 + 14,000) = 16,040

半连接多了一次启动代价，但传输量从 28 万字节降到 1.4 万字节，总代价约为直接连接的 5.7%。选择度越低（能连上的元组比例 ρ 越小，本例 ρ = 500 / 10000 = 0.05），半连接越划算。

分布式事务。 一个全局事务在多个场地上各有一个子事务，由协调者统一决定全部提交或全部回滚，最常用的协议是两阶段提交（2PC）。2PC、3PC 和分布式事务的详细流程见第 28 章。[12]

规律与考场结论。

  • 标准答案：分布式数据库是物理上分散、逻辑上集中的数据库系统，具有分布透明性和场地自治性。分布透明性包括分片透明性、位置透明性和局部数据模型透明性，其中分片透明性层次最高。
  • 分片原则：完备性、可重构性、不相交性。水平分片用选择、用并重构；垂直分片用投影、必须保留主键、用连接重构。
  • 分布式查询优化的主要目标是减少场地间的数据传输量，半连接是常用手段。

10.15 Redis：内存数据库、持久化、淘汰与高可用

为什么需要它。 热门商品页每秒被访问 10 万次，全查 MySQL 扛不住。把读多写少的数据放进内存数据库 Redis，响应降到亚毫秒级；它还常用作计数器、排行榜、分布式锁。

它是什么。 Redis 是开源的、基于内存的键值型数据结构存储：每个键对应的值可以是多种数据结构，客户端直接操作这些结构。[34] 五种基本类型：

类型是什么常用命令底层结构（简述）典型场景
String字符串（二进制安全，最大 512MB）SET GET INCR SETEX简单动态字符串 SDS；整数直接编码缓存对象、计数器、分布式锁
Hash字段 → 值 的映射HSET HGET HGETALL小时用 listpack，大了转哈希表存对象，可只改一个字段
List按插入顺序的字符串列表LPUSH RPOP LRANGEquicklist（listpack 组成的双向链表）消息队列、最新动态

小集合用 listpack、intset 这类紧凑编码，元素数或长度超过阈值（如 Hash 默认 512 个字段、ZSet 默认 128 个成员）时自动转成普通编码，对用户透明。[35] ZSet 用跳表维持顺序、用哈希表按成员查分数，插入是 O(log N)。[36]

String 还是 Hash？ 对象整体存成 JSON 用 String；要单独改某个属性用 Hash（HSET user:1 age 30）。过期时间一般设在整个键上，Redis 7.4 起才能用 HEXPIRE 给单个字段设过期。[37]

Redis 为什么快

  1. 数据在内存，读写不碰磁盘；
  2. 单线程执行命令，没有线程切换和加锁开销，每条命令天然原子；
  3. I/O 多路复用：用 epoll（第 07 章）让一个线程监听成千上万个连接；
  4. 数据结构高效：SDS、跳表、listpack 等。

Redis 的瓶颈通常在内存和网络，很少在 CPU。[38] Redis 6.0 起可以开启多线程处理网络读写，但执行命令仍是单线程。

一个线程用多路复用同时服务大量连接，命令在内存中串行执行

持久化：RDB 与 AOF

内存断电即失，Redis 提供两种方式把数据存到磁盘：[39]

RDB（快照）AOF（追加日志）
存什么某一时刻全部数据的二进制快照每条写命令，按顺序追加
怎么做fork 子进程写快照，主进程继续服务；save 60 1000 表示 60 秒内至少 1000 次修改就快照每条写命令追加到文件；appendfsync 决定多久刷盘一次
丢多少数据上次快照之后的全部修改（可能几分钟）always 几乎不丢；everysec（默认）最多丢 1 秒；no 由操作系统决定
文件大小 / 恢复速度紧凑；恢复快较大；恢复要重放命令，较慢
文件变大怎么办—AOF 重写：后台生成能重建当前数据的最短命令序列

两者可以同时开启，重启时优先用 AOF 恢复，因为它的数据最完整。[39] 和 10.11 对照：AOF 相当于数据库的日志，RDB 相当于后备副本。

RDB 定期拍快照，AOF 逐条记录写命令，两者可同时开启

过期删除与内存淘汰

过期删除用两种方式结合：惰性删除（访问时发现过期就删）和定期删除（周期性随机抽查一批带过期时间的键，删掉已过期的）。[40] 前者漏掉没人访问的键，后者漏掉没抽到的键，所以要结合。

内存淘汰处理"内存用到 maxmemory 上限了"，按 maxmemory-policy 选择牺牲哪些键：[41]

策略范围淘汰谁
noeviction—不淘汰，写命令直接报错
allkeys-lru / allkeys-lfu / allkeys-random所有键最近最少使用 / 使用频率最低 / 随机
volatile-lru / volatile-lfu / volatile-random设了过期时间的键同上
volatile-ttl设了过期时间的键剩余寿命最短的

做纯缓存时常用 allkeys-lru。Redis 的 LRU 是近似 LRU：随机采样几个键，淘汰其中最久未用的，省去维护全局链表的开销。

主从复制与哨兵

主从复制：主节点负责写，从节点复制数据并分担读。首次连接做全量同步（主节点发 RDB，再补发期间的写命令）；短暂断线后按复制 ID 和偏移量部分重同步。复制默认异步。[42]

哨兵（Sentinel）监控主从节点，多个哨兵都认为主节点不可达时，把一个从节点提升为新主并通知客户端；至少部署 3 个，才能凑成多数票。[43] 数据量超过一台机器时，用 Redis Cluster 按哈希槽分片。

主从复制分担读压力；哨兵监控主节点，主节点故障时把一个从节点提升为新主

Redis 的事务与消息

MULTI 后的命令进入队列，EXEC 一次性按顺序执行、不被插队；WATCH key 是乐观锁，EXEC 前键被改过则整个事务放弃。Redis 事务不支持回滚：某条命令运行时出错，其他命令照样执行。[44] 发布订阅（PUBLISH/SUBSCRIBE）不保存消息，订阅者离线就收不到；List 队列（LPUSH + BRPOP）把消息存在列表里，消费者上线后还能取到。

规律与考场结论。

  • 标准答案：Redis 快的原因：① 基于内存；② 单线程执行命令，避免线程切换和锁竞争；③ 使用 I/O 多路复用（epoll）处理大量连接；④ 数据结构高效。
  • RDB 是定时快照，文件小、恢复快，但可能丢失最近一段数据；AOF 记录每条写命令，数据更完整（默认每秒刷盘，最多丢 1 秒），文件大、恢复慢。两者可同时使用，重启时优先加载 AOF。
  • 过期键删除采用惰性删除 + 定期删除；内存满时按 maxmemory-policy 淘汰，常用 allkeys-lru。
  • 主从复制实现读写分离和数据备份；哨兵实现自动故障转移；Cluster 实现分片。

10.16 缓存三问题：穿透、击穿、雪崩

为什么需要它。 Redis 做缓存的常见流程叫旁路缓存（Cache Aside）：先读缓存，未命中再查库并写回缓存；更新时先改数据库，再删缓存。有三种情况会让大量请求越过缓存打到数据库。

旁路缓存：未命中才查库；穿透、击穿、雪崩都是第②步的流量突然变大

它是什么。

问题现象原因解决方案
缓存穿透大量请求查根本不存在的数据数据库里没有，缓存里也就永远没有，每次都查库；常见于恶意请求 id = −1① 缓存空值（设较短过期时间）；② 布隆过滤器：先判断键是否可能存在，一定不存在的直接拒绝；③ 参数校验
缓存击穿一个热点键过期的瞬间，大量并发请求同时查库热点数据过期，成千上万个请求同时未命中① 互斥锁：只让一个请求查库重建缓存，其他请求等待或重试；② 热点数据逻辑过期或不设过期，后台异步刷新
缓存雪崩大量键同时失效，或 Redis 整体宕机，请求全部涌向数据库一批键设了相同的过期时间；缓存服务故障① 过期时间加随机值，错开失效；② 缓存高可用（主从 + 哨兵、集群）；③ 限流、熔断、降级；④ 多级缓存

穿透：查不存在的数据；击穿：一个热点键失效；雪崩：一大片键失效

完整走一遍：击穿的互斥锁方案。 商品 7 的缓存在 10:00:00 过期，同一毫秒来了 1000 个请求：

  1. 1000 个请求都发现缓存未命中；
  2. 每个请求执行 SET lock:7 1 NX EX 10 尝试加锁，NX 保证只有一个请求成功；
  3. 拿到锁的请求查数据库、写回缓存、删除锁；
  4. 其余 999 个请求加锁失败，短暂休眠（例如 50 毫秒）后重新读缓存，此时已命中。

数据库只被查了 1 次。代价是这 999 个请求多等了几十毫秒。

布隆过滤器：位数组加 k 个哈希函数，插入时把 k 个位置置 1；查询时只要有一位是 0 就一定不存在，全是 1 则可能存在。占空间极小。

规律与考场结论。

  • 标准答案：缓存穿透是查询不存在的数据，缓存和数据库都没有，解决方法是缓存空对象或使用布隆过滤器；缓存击穿是某个热点 key 过期瞬间大量请求打到数据库，解决方法是互斥锁或热点数据不过期；缓存雪崩是大量 key 同时过期或缓存服务宕机，解决方法是过期时间加随机值、搭建高可用缓存集群、限流降级。
  • 区分口诀：穿透是"不存在"，击穿是"一个热点"，雪崩是"一大片"。
  • 旁路缓存更新时先改数据库、再删缓存；删除而不是更新缓存，避免并发写把旧值写进缓存。

单选 · 理解检查 16　某系统每天 0 点批量加载 100 万个商品缓存，过期时间统一设为 24 小时。第二天 0 点数据库 CPU 飙升。最可能的问题和最直接的修复是？

10.17 OLTP、OLAP 与数据仓库

为什么需要它。 转账每笔只读写几行；风控统计"三年来每省每月违约率"要扫几亿行。两种负载放在一起互相拖累，于是分成业务库和分析库。

它是什么。

对比项OLTP（联机事务处理）OLAP（联机分析处理）
典型业务转账、下单、开户报表、风控分析、经营决策
一次操作按主键读写少量行，短事务扫描、聚合大量历史数据
关注并发、响应时间、事务一致性查询吞吐、复杂分析
数据当前数据，规范化设计（第 09 章三范式）历史数据，常为反规范化设计
存储行存（MySQL、PostgreSQL）常用列存（ClickHouse、Hive 等）

数据仓库是面向主题的、集成的、相对稳定的、反映历史变化的数据集合，用于支持管理决策。数据从各业务库进入数据仓库，要经过 ETL：

  1. 抽取（Extract）：从业务库、日志、文件中取出数据；
  2. 转换（Transform）：清洗脏数据、统一编码和格式、关联多个来源、计算派生字段；
  3. 加载（Load）：写入数据仓库。

先加载到仓库再在仓库里转换，叫 ELT。抽取时常用 CDC（Change Data Capture，变更数据捕获）：不反复全量扫描业务表，而是读业务库的变更日志（例如 MySQL 的 binlog，10.11 节），只取新增、修改、删除的部分。

业务库负责交易，数据经 ETL 进入数据仓库供分析

星型模型与雪花模型。 数据仓库常用维度建模：

  • 事实表：记录业务事件和度量值，行数巨大，例如"贷款发放事实表（日期键、客户键、产品键、网点键、金额）"。
  • 维度表：描述事实的角度，例如日期、客户、产品、网点。
  • 星型模型：事实表在中心，每个维度一张表直接连在事实表上；维度表不规范化（网点表里直接存城市名、省名）。查询只需一次连接，简单快速。
  • 雪花模型：把维度表进一步规范化，例如网点表只存城市键，城市表再连省份表，形如雪花。冗余少，但查询要多做几次连接。[45]

实线部分是星型模型；把网点维度再拆出城市、省份（虚线）就成了雪花模型

完整走一遍。 求"2025 年每省贷款总额"：星型模型连日期维度和网点维度，两次连接后按省分组求和；雪花模型还要再连城市表、省份表，共四次连接。

规律与考场结论。

  • 标准答案：OLTP 面向日常事务处理，操作少量数据、要求实时响应和事务一致性；OLAP 面向分析决策，对大量历史数据做复杂查询和聚合。数据仓库是面向主题的、集成的、相对稳定的、反映历史变化的数据集合。
  • ETL 指抽取、转换、加载。星型模型的维度表直接连接事实表、不规范化，查询快；雪花模型对维度表规范化，冗余少但连接多。

多选 · 理解检查 17　关于数据仓库建模，哪些说法正确？

A. 事实表存度量值和指向各维度的外键，行数通常远多于维度表

B. 雪花模型比星型模型查询时需要的连接更少

C. 星型模型的维度表通常是反规范化的

D. ETL 中的 T 指数据传输（Transfer）

查看答案与每个选项的解析

A · 正确：每个业务事件一行，维度表只描述有限的对象。

B · 错误：雪花模型把维度拆成多张表，连接更多。

C · 正确：把层级信息放在同一张维度表里，换取查询简单。

D · 错误：T 是转换（Transform），包括清洗、统一格式、关联等。

易错点：

  • OLTP 和 OLAP 描述的是负载类型；同一个数据库产品可以兼顾两者（HTAP），但大规模场景通常分开部署。

速记： OLTP 交易短而多，OLAP 分析大而少；ETL = 抽取、转换、加载，CDC 读变更日志增量抽取；星型维度直连事实表，雪花维度再规范化。

10.18 本章小结

索引管"快"，事务、并发控制和恢复管"对"，缓存和分布式管"扛得住"

页与 B+ 树InnoDB 页 16KB；扇出上千，三层存约两千万行扇出 = 页 ÷ (键 + 指针)；容量 = f^(h−1) × 每页行数
聚簇与二级索引聚簇叶子存整行，二级叶子存主键判断是否回表、是否覆盖、ICP 省了几次回表

封锁协议一级防丢失修改，二级防脏读，三级防不可重复读相容矩阵：S-S 相容，X 全冲突，意向锁互相相容

备份静态/动态、海量/增量；介质故障 = 副本 + 日志设计时间点恢复步骤

单选 · 理解检查 18　InnoDB、可重复读级别。事务 T 先执行普通 SELECT 读到余额 100，随后另一个事务把余额改成 80 并提交；T 再执行 SELECT … FOR UPDATE。T 第二次读到多少？为什么？

A. 80，因为 FOR UPDATE 是当前读，读最新已提交版本并加锁

B. 100，因为可重复读整个事务都用同一个快照

C. T 被阻塞，直到另一个事务提交

D. 报错，可重复读下不允许 FOR UPDATE

查看答案与每个选项的解析

A · 正确：当前读绕过 ReadView，读最新版本；普通 SELECT 才复用快照。

B · 错误：复用快照的只是快照读（普通 SELECT），FOR UPDATE 是当前读。

C · 错误：另一个事务已经提交并释放了锁，T 不会等待。

D · 错误：任何隔离级别下都可以在事务中使用锁定读。
