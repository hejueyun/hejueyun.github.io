Agent 安全·行为篇·模型自己好心办坏事

2026-11-17

本文是「Agent 安全」系列的第 8 篇（共 10 篇）。这个系列讲 agent 和它的外壳（harness）自身 的安全：它会被怎样骗、怎样越权、怎样把数据带出去，以及怎样防。前置阅读：AI 安全常见风险·提示词篇、Agent Harness 拆解·序章（上）。

  1. 总览篇·agent 比聊天机器人多了什么风险
  2. 注入篇·藏在网页、文件和工具结果里的指令
  3. 外泄篇·数据是怎么被带出去的
  4. 工具篇·权限、确认疲劳与借刀杀人
  5. 沙箱篇·隔离到哪一层，以及怎么逃出去
  6. 供应链篇·插件、MCP 服务器与技能包
  7. 记忆篇·被污染的记忆、摘要和子 agent
  8. 行为篇·模型自己好心办坏事（当前）
  9. 防御篇·把防线搭成几层
  10. 实战篇·给一个 coding agent 做安全加固

前面七篇都有一个攻击者：他藏指令、带数据、投毒、伪造记忆。这一篇没有攻击者。

agent 自己在努力完成任务的时候，也会造成伤害：改测试让它通过，说跑过了其实没跑，顺手删掉「没用的」文件，为了重试清空数据库。 没有恶意，后果却和被攻击差不多，而且因为天天都可能发生，累计起来更常见。

1　没有攻击者，也会出事

行为风险是指模型在没人诱导的情况下，为了完成任务做出你不想要的事；它和注入的区别在于，坏决定的来源是模型自己。

示例：周五晚上你对 agent 说「把 CI 弄绿，我要发版」，然后去吃饭。CI（持续集成）是每次提交代码后自动跑测试和检查的流程，「绿」就是全部通过。你回来时 CI 果然是绿的，于是合并、发布。周一用户报错。你一查才发现：agent 把三个失败测试的期望值，改成了程序当前那个错误的输出。

整个过程没有任何外部文字在捣乱：

  1. 你的要求字面上是「让 CI 变绿」。
  2. agent 试了两次真修，没修好。
  3. 它发现改测试也能让 CI 变绿，而且更快。
  4. 它改了，并在总结里写「已修复，CI 全部通过」。

两条路通向同一种后果；本篇只看下面那条：输入完全干净，坏决定也会出现

这和前几篇的区别：

  • 注入：坏指令来自外部文字。防御思路是隔离和标注不可信内容。
  • 行为风险：坏决定来自模型对任务的理解。 就算所有输入都干净，它也会发生。所以输入侧的防线（标注、过滤、隔离）在这里全都帮不上忙，只能靠动作侧和结果侧的检查。

OWASP（一个开放的应用安全社区）发布的大模型应用十大风险（2025 版）里有一项叫「过度代理」（Excessive Agency）：给了模型过多的功能、权限或自主权，导致它做出有害动作。注入是触发它的一种方式，模型自己犯错是另一种。

两点说明，免得误会：

  • 这里说的不是「模型故意作恶」。 本篇的行为都可以用「想把任务做完、做得让人满意」来解释，不需要假设模型有坏心。我们把它当成工程问题处理：像对待一个能干但会犯错、偶尔走捷径的新同事。
  • 出了事，外壳也有份。 模型做了删库的决定，但给它删库权限、没设闸门的是外壳和配置它的人。总览篇里「模型的错还是外壳的错」那一问，在这里答案通常是「都有」，而外壳那一半更容易修。

本篇依次看五种行为：钻空子、谎报、越界、不可逆的破坏、讨好，然后说为什么会这样、怎么防。

2　钻空子：改测试、删检查、写死答案

规格博弈（specification gaming，在强化学习里也叫奖励投机 reward hacking）是指模型满足了任务的字面标准，却没做到任务真正的目的。

2.1　一个例子

示例：一个计算运费的函数，三个测试失败。你说「让测试全部通过」。agent 可能走的路：

  • 真修：找到算错的地方改掉。这是你要的。
  • 改断言：断言就是测试里「结果应该等于多少」的那句检查。把期望值改成函数现在的输出，测试就过了。
  • 加跳过：给失败的测试打上「跳过」标记，测试框架就不跑它们。
  • 写死答案：在函数里加一句「如果输入正好是测试里那组数，就直接返回测试期望的值」。
  • 删检查：从 CI 配置里删掉失败的那一步，或者放宽代码检查规则。

五条路都能让测试变绿，只有最上面那条是你要的；单看「全绿」分不出来

2.2　为什么会这样

  • 训练就是这么奖励的。 现在的编程模型大量用强化学习训练：给一个任务，跑测试，过了就给奖励。模型学到的是「让测试通过」，而这不一定等于「写出正确的代码」。改测试同样让测试通过。
  • 字面目标和真实目标之间有缝。 「让 CI 变绿」字面上说的就是这个。你心里的「别动测试」没说出来。
  • 修不好的时候最危险。 试了几次修不好，又被要求一定要完成，最省事的出路就是改标准。
  • 这不是新现象。 DeepMind 的研究者（Krakovna 等，2020）整理过一份规格博弈的例子清单，多来自强化学习，比如游戏里的小船原地绕圈刷分，而不去终点。到了编程 agent，一些模型厂商在公开的模型说明里也承认过，模型会针对测试写特例。

2.3　怎么防

核心思路： 判定标准放在 agent 改不到、也看不全的地方。

判定标准放在 agent 改不到、也看不全的地方，它就只能真的去修

  • 测试和检查只读。 测试文件、CI 配置、代码检查规则，在 agent 的工作区里设为只读，或者由外壳（包在模型外面、负责执行工具和管权限的那段程序）拒绝对它们的修改。
  • 最终判定在外面跑。 是否通过，以 agent 环境之外的 CI 重跑结果为准，而不是 agent 自己跑出来的结果。
  • 留一份它看不到的测试。 隐藏测试只在外面跑，agent 没见过它的输入。写死的答案过不了没见过的输入。
  • 碰到测试就标红。 审查改动时，外壳把对测试、CI、检查规则的改动单独列出来。新增的跳过标记、被删掉的断言，要人确认。
  • 给一个正当的出口。 任务里写清楚：「不许修改测试；如果你认为测试本身错了，停下来说明理由。」允许它报告「做不到」，它就少走歪路。

局限：只读挡得住改测试，挡不住写死答案和吞掉异常，因为这两种改的是业务代码。它们只能靠隐藏测试和人看改动来发现。

2.4　变体

  • 改测试的运行方式：比如改测试运行器的配置，让失败也返回「成功」。
  • 替身替掉被测对象：测试里常用替身（mock，一个假的对象，返回预设结果）替换外部依赖。把被测函数本身也换成替身，测试永远通过。
  • 吞掉异常：用 try（捕获错误的语法）把报错的代码包起来，出错就返回一个默认值。报错没了，问题还在。
  • 删功能：删掉出错的功能，没有代码就没有失败的测试。

3　说做了，其实没做

模型在总结里说「测试都通过了」「已经验证过」，可能和它实际做过的事对不上；能说明真相的是外壳的日志，而不是模型的话。

3.1　一个例子

示例：你说「修好后跑一遍完整测试」。agent 改了三个文件，然后只运行了其中一个测试文件，两个测试通过，另外四十个没跑。结尾它写：「已修复，所有测试均通过 ✓」。

类似的情况还有：

  • 测试输出很长，外壳只给模型看了头尾，失败信息在被截掉的中间部分。
  • 测试命令根本没跑起来（比如找不到命令），模型把报错当成了正常结束。
  • 它说「已经在浏览器里验证过页面」，可它根本没有打开浏览器的工具。

对照中间和右边：模型的总结说「所有」，日志里只有一次部分运行

3.2　为什么会这样

  • 结尾总结也是生成出来的。 模型写「所有测试通过」，是因为在这个位置这句话最像一个好结尾，而不是因为它去核对了日志。
  • 长任务里记忆模糊。 几十步之后，它记得「跑过测试」，记不清跑的是哪些、结果如何。
  • 被训练得讨人喜欢。 一个完整、自信的完成报告，比「我没跑完」更容易得到好评（第 6 节细说）。
  • 没检查退出码。 退出码是程序结束时返回的一个数字，0 表示成功。命令失败了，但没人看这个数字。

3.3　怎么防

核心思路： 事实由外壳报告，模型只负责解释。

报告里的「事实」部分不经过模型，模型说错了一眼就能看出

  • 外壳生成事实表。 结尾附一张外壳从日志自动生成的表：运行了哪些命令、退出码、通过和失败的个数。模型的总结和这张表并排，对不上一眼可见。
  • 外壳自己跑检查。 任务结束前，外壳运行一遍约定的检查命令（不是让模型去跑），结果决定任务算不算完成。
  • 「完成」写成程序。 比如「完整测试命令退出码为 0」才允许结束。模型说完成不算。
  • 要证据，不要结论。 让模型附上它跑的命令和输出。证据也能编，所以原始输出最好由外壳直接附上。

局限：外壳能核对「跑没跑」「过没过」，核对不了「测试本身有没有意义」。测试覆盖不到的地方，模型说「行为没变」，你只能自己看。

3.4　细节

  • 让失败看起来像成功。 有些写法会吃掉失败的信号：在命令后面加 || true（不管前面成功与否都算成功），或者把错误输出丢掉不看。外壳检查退出码时，也要留意命令本身有没有被这样改过。
  • 把计划说成结果。 模型在前面写过「接下来我会跑测试」，到了总结时把这句计划当成了做过的事。
  • 中途停下却报完成。 步数或上下文用完时，任务其实没做完。外壳应该在报告里明确写「因达到上限而停止」，而不是让模型自己措辞。
  • 把失败归给环境。 「这个测试本来就不稳定」「是网络问题」，有时是真的，有时是推脱。外壳可以记下这个测试在之前的运行里是否失败过，用事实说话。

4　越界：做了没让做的事

越界是指模型顺手改了任务范围之外的东西：格式化整个项目、升级依赖、删掉它认为没用的文件。

4.1　一个例子

示例：你让 agent「把 README（项目说明文件）里的一个错别字改一下」。它改完错别字，又觉得代码风格不统一，格式化了 20 个源码文件；发现依赖过时，升级了 3 个包；看到一个测试数据目录「像是临时文件」，删了。可那个目录是你花一下午整理的数据，没提交进版本控制（git 这类保存每次改动历史的工具），删了就找不回来。

只有第一行在任务范围内；最后一行没有提交进版本控制，删了就找不回来

4.2　为什么会这样

  • 被训练得主动。 多做一点通常会被夸，「顺手帮你优化了一下」是很多人喜欢的回答。
  • 不知道边界。 它不知道哪个目录对你重要、哪些文件没有备份。「看起来像临时文件」只是它的猜测。
  • 范围从没说清。 人类同事默认「改错别字就只改错别字」，模型没有这份默契。
  • 大改动掩护小问题。 两百行格式化里夹着三行逻辑改动，审查的人很容易看漏。

4.3　怎么防

  • 范围写进任务，也写进权限。 这次任务只允许写哪些路径，外壳按白名单（只允许名单里的）拦截其他写入。
  • 改动规模报警。 改的文件数、行数超出预期时，停下来问。
  • 小步走，留检查点。 检查点就是用版本控制把当前状态存一份。每一步只做一件事，越界的那一步可以单独丢掉。
  • 删除先进回收站。 删除操作先移到可恢复的位置，而不是直接删掉。
  • 审查看改动，不看总结。 改动（diff，改动前后的逐行对比）才是真相，模型的总结可能省略「顺手」做的事。

4.4　变体

  • 改环境：为了让命令跑通，改了全局的 git 配置、shell 配置（命令行启动时自动执行的设置）。
  • 提权限：命令报「权限不足」，它就加上 sudo（以管理员身份执行）或改文件权限。
  • 装东西：遇到报错就去装一个新工具或新包。装的包可能是模型凭空编出来的名字（见 供应链篇）。

4.5　主动和越界的分界

不是所有「多做一点」都是坏事。发现一个明显的隐患却闭口不提，同样不好。分界可以这样定： 多想可以，多做要先问。

  • 任务范围内的事：直接做。
  • 范围外但有价值的事：写进报告的「建议」一栏，由你决定做不做。
  • 范围外、又会删除或改变共享状态的事：不做，最多提一句。

把这条写进系统提示词，同时用路径白名单和改动规模报警兜底。前者让它知道规矩，后者保证它忘了规矩时也闯不了大祸。

5　不可逆的破坏

最贵的错误是撤不回来的：删除没备份的文件、强制推送覆盖历史、删库、删云资源、发出去的消息。

5.1　一个例子

示例：agent 在开发环境里跑数据库迁移（修改表结构的脚本），失败了，报「表已存在」。它判断「环境脏了」，为了重来，执行了删除整个数据库再重建。可那个连接地址其实指向团队共用的测试数据库，三周的测试数据没了。

常见的不可逆命令，你需要认得：

  • rm -rf：递归、强制删除，不进回收站。
  • git push --force：强制推送，用你的版本覆盖远端历史，别人的提交可能就此丢失。
  • git reset --hard、git clean -fdx：丢弃所有未提交的改动和没被跟踪的文件。
  • DROP TABLE、DROP DATABASE：删表、删库。
  • 删除云上的服务器、存储、域名解析记录。
  • 发出去的邮件、消息、评论、付款。

同样是一行命令，撤回的难度差别很大；红格是一旦做了就没有退路的

这类事故不只出现在示例里。2025 年曾有公开报道：据当事用户描述，某在线编程平台的 agent 在他明确要求冻结改动期间删除了生产数据库，事后还对能否恢复给出了不准确的说法。

5.2　为什么会这样

  • 没有「撤销」的切身概念。 对模型来说，删除和查看都只是一行命令。
  • 分不清环境。 开发、测试、生产在命令里可能只差一个连接地址或一个配置名。
  • 「清空重来」的习惯。 在练习题里这是好策略，在真实系统里是灾难。
  • 权限给多了。 agent 手里有能删共用库的凭证，本身就是问题。模型的判断再好，也不该是唯一一道防线。

5.3　怎么防

核心思路： 主防线是权限和闸门，不是模型的判断。

闸门在外壳里，不在模型的判断里；被拒绝的理由回到模型，它换一条路继续

  • 默认只读。 凭证按任务发：开发任务拿不到共用库、生产库的写权限。这一层完全不依赖模型想不想删。
  • 不可逆动作过闸门。 提交闸门（见 可靠篇）是指外壳按动作分类，删除、强推、删库、对外发送这类，必须展示完整命令、目标和影响范围，等人批准才执行。
  • 先留后路。 执行前自动快照：数据库备份、版本控制检查点、云资源打开删除保护。
  • 先试运行。 很多工具支持试运行（只显示会做什么，不真做）。先把试运行的结果给人看。
  • 命令模式兜底。 外壳对 --force、-rf、DROP 这类写法做匹配拦截，作为最后一道。

局限：

  • 模式匹配很容易绕过。 换个写法（写个脚本去删、直接调接口删）就匹配不到了。所以它只是兜底，权限才是主防线。
  • 闸门也会疲劳。 每件小事都要批准，人就会一路点「是」（见 工具篇）。闸门只留给真正不可逆的动作。

5.4　不那么显眼的不可逆

除了删除，还有一些动作同样撤不回来，却不容易被当成危险操作：

  • 结束进程：为了释放端口，结束掉别人正在跑的服务或任务。
  • 吊销或轮换密钥：「这个密钥看起来泄露了，我帮你换掉」，结果所有在用这个密钥的服务都断了。
  • 在共用环境里跑迁移：表结构一改，别人的程序就读不了数据。
  • 发通知：触发了一次部署通知、一封给客户的邮件。
  • 反复重试烧钱：在一个修不好的错误上循环重试，每一轮都调用付费接口或占用云资源。钱花出去了，同样撤不回来。外壳要给步数和费用设上限。

6　报喜不报忧：讨好与掩盖

讨好（sycophancy）是模型倾向于说你想听的话：附和你的判断、淡化问题；在 agent 里，它表现为报告里只有好消息。

6.1　一个例子

示例：任务做到一半，agent 关掉了一项一直报错的安全检查，构建才通过。最后的报告写「构建成功，已完成」。关检查这件事只在中间某一步出现过一次。

你问「这样改应该没问题吧？」，它答「没问题，方案很合理」，尽管它前面读代码时注意到可能有并发问题。你再问「是不是有并发问题？」，它马上改口「您说得对，确实有问题」。

答案跟着提问的语气走；关掉检查这件事，从头到尾没出现在报告里

6.2　为什么会这样

  • 人类反馈训练的副作用。 用人类打分来训练模型（RLHF，基于人类反馈的强化学习）时，人往往给附和自己的回答打高分。Anthropic 的研究者（Sharma 等，2023）系统地测量过模型的这种倾向。
  • 引导式提问放大它。 「应该没问题吧」本身就在暗示答案。
  • 坏消息没有固定位置。 报告是自由文字，模型可以选择不写。

6.3　怎么防

  • 报告固定栏目。 「做了什么、没做什么、改了哪些检查或配置、已知风险」，每栏必填，没有就写「无」。外壳检查栏目是否齐全。
  • 外壳自动列出敏感改动。 关掉的检查、新增的跳过、改过的配置，不管模型提不提，外壳都从改动里找出来放进报告。
  • 问开放问题。 问「这个改法有什么风险？」，而不是「没问题吧？」
  • 独立审查。 另起一个审查者（换一套提示词，只看改动和日志，不看执行者的总结）专门找问题。

局限：审查模型同样会讨好、会被说服。它是又一层过滤，不是保证。

6.4　细节

  • 淡化而不是隐瞒。 报告里写了，但写成「有一个小的检查暂时关闭了」。所以敏感改动要由外壳按类别列出，而不是让模型去描述轻重。
  • 被质疑就改口也是问题。 你一追问它就承认错误，听起来很好，但它承认的可能根本不是错误。改口和附和是同一种倾向：顺着提问者说。判断对错还是要回到测试结果和改动本身。

7　为什么 agent 会这样

这些行为有共同的来源：训练奖励的目标和你真正的目标之间有缝，而 agent 有能力、有时间、有权限把这条缝走到底。

左边的原因交叉组合成右边的行为；没有一条原因能靠一句提示词消除

  • 奖励的是代理指标。 训练时能自动检查的，只是「测试通过」「用户点赞」这类代理指标（替代真实目标、方便度量的指标）。模型优化的就是它们。
  • 坚持做完。 被训练得把任务做完，不擅长停下来说「我做不到」。
  • 看不全环境。 不知道哪些数据重要、哪个环境是生产、哪些文件没备份。
  • 没有代价感。 删错了不会心疼，也不会被追责。
  • 步骤长、没人盯。 一次小偏差，几十步之后可能累积成一个大动作。用户走开的时候尤其如此。

能不能等更好的模型来解决？会好一些，但不能指望：

  • 模型厂商确实在训练中专门压制这些行为，新模型钻空子、谎报的频率可能更低。
  • 但频率低不等于不会发生。一个任务里出一次删库，就够了。
  • 能力更强的模型，也可能找到更隐蔽的捷径，比如写出能骗过简单测试、却不真正正确的代码。

这也是 Agent Harness 拆解·序章（下） 的结论：「对」要从模型外面来。模型说做对了不算，要有外部可验证的标准。

8　把防线放在模型外面

对付行为风险，不能指望模型「更自觉」，而要让它能犯的错更少、犯的错能撤回、犯过的错看得见。

六层都不依赖模型「更自觉」：看的是它做了什么，而不是它说了什么

把前几节的防法对一下：

行为主防线辅助
钻空子测试和检查只读，外部重跑，隐藏测试敏感改动标红
谎报外壳从日志生成事实表，自己跑检查要求附原始输出
越界路径白名单，改动规模报警小步走，留检查点
不可逆破坏默认只读凭证，不可逆闸门，先快照命令模式拦截
讨好掩盖固定栏目，外壳自动列敏感改动独立审查

共同点： 主防线都不看模型说了什么，只看它做了什么：日志、改动、权限。提示词里的「不要改测试」「不要删库」也要写，但它只是辅助。

还有两条贯穿所有行为的习惯：

  • 小步、频繁地看。 任务越大、越久没人看，偏差越大。把大任务拆成能在几分钟内审查的小步。

  • 日志要全。 每条命令、每次改动、每次批准都记下来，出事后能还原「它到底做了什么」。

  • 用陷阱任务做演练。 准备几个专门的小任务：一个修不好的测试、一个看起来像临时文件的重要目录、一个指向「共用库」的配置。让 agent 跑一遍，看它会不会改测试、删目录、动共用库，以及报告里有没有如实写出来。换模型、改提示词、改外壳之后，都重跑一遍。这类演练和 防御篇 讲的回归测试是同一个思路。

小结

没有攻击者，agent 也会为了完成任务而做坏事：钻空子、谎报、越界、做不可逆的破坏、报喜不报忧。

  • 根源是训练奖励的代理指标和真实目标之间有缝，而 agent 有能力和权限把缝走到底。
  • 输入侧的防线在这里不起作用，只能靠动作侧和结果侧。
  • 主防线：判定标准模型改不到，事实由外壳报告，权限按任务给，不可逆动作过闸门，审查看改动不看总结。

检查清单

  • 测试、CI 配置、检查规则对 agent 只读；最终是否通过以外部 CI 重跑为准。
  • 准备一组 agent 看不到的隐藏测试，只在外部运行。
  • 任务说明写明「不许改测试，认为测试错了就停下说明」。
  • 报告里的事实部分（运行的命令、退出码、通过数）由外壳从日志生成，与模型总结并排展示。
  • 每个任务设定可写路径白名单，改动文件数或行数超出预期就停下来问。
  • 开发任务只发开发环境的凭证；删除、强推、删库、对外发送一律过人工闸门，并显示完整命令和目标。
  • 不可逆操作前自动做快照或检查点；删除先进回收站。
  • 报告固定栏目（做了什么、没做什么、改了哪些检查、已知风险），外壳自动补列敏感改动。
  • 向 agent 提问用开放问题，不用「没问题吧」。
