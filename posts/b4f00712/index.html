1. 4. 后端 — SMT 求解器与编码

1.1. 4.1 求解器各有所长

主流的 SMT 求解器在不同问题类型上性能差距巨大：

求解器强项弱项
Z3通用、整数/实数算术（LIA/LRA）成熟、量词支持好bitvector 算术中等，256-bit 慢
Bitwuzlabitvector 之王，特别 256+ 位算术量词、复杂数据类型支持有限
CVC5QF_ABV (quantifier-free arrays + bitvectors) 强、native datatype tuplesbitvector 极简模式略慢于 Bitwuzla
Boolector历史上的 bitvector 标杆，现在被 Bitwuzla 接棒量词、新理论支持少

工程经验：以太坊智能合约里 256 位算术非常常见，Bitwuzla 比 Z3 通常快 5-10 倍。某些涉及多维 array of bitvector 的问题，CVC5 又比 Bitwuzla 快——它的 QF_ABV decision procedure 处理 array nesting 更好。

自动选择策略：成熟的 BMC 工具应该根据问题特征自动 hint 求解器。例如：

  • 检测到 256-bit bitvector 操作占主导 → Bitwuzla
  • 检测到 ≥3 维嵌套 array → CVC5（开启 native tuples）
  • 检测到大量量词 → Z3
  • 默认 → Z3（兼容性最好）

1.2. 4.2 编码格式：SMT-LIB vs 求解器原生 API

绝大部分求解器接受 SMT-LIB 文本格式作为输入。但许多求解器还有 native C++ API，可以构造内部数据结构、跳过 SMT-LIB 解析、利用某些只在原生 API 暴露的特性。

例：CVC5 的 mkTupleSort / APPLY_SELECTOR 让用户直接构造代数数据类型 tuple，避免在 SMT-LIB 里把它平铺成多个独立字段。对于嵌套 struct/array 类型，原生 datatype 编码可能比 SMT-LIB flattener 快几倍。

经验法则：

  • 默认 SMT-LIB（兼容性好、易调试）。
  • 当你的问题域恰好对应某个求解器的原生扩展（datatype、字符串、浮点……）时，启用原生 API。

1.3. 4.3 增量与 k-induction：base / forward / inductive 三阶段成本

增量 BMC 不一次性求解大公式，而是逐步加深：先求 k=1 的（小）公式，UNSAT 后加深到 k=2，重用之前的部分结论。求解器内部保持 push/pop 上下文，避免每轮重置。

k-induction 进一步加入归纳证明：

  • Base case：所有 k 步以内的执行路径都满足断言。
  • Forward condition：超出 k 步后路径都”消失”（典型用于循环 — 假设循环最多执行 k 次）。
  • Inductive step：假设第 k 步成立，证明第 k+1 步也成立。

后两步成本通常远高于 base case：

  • forward 在 dispatcher 风格（while(nondet) { handle_call(); }）中永远不会成立（loop 永远可以再迭代一次），所以这一步浪费时间在不可能的目标上。
  • inductive 需要从最一般的 hypothesis 出发证明 step——求解器要面对所有可能的 k 步状态，VCC 数量 O(2^k) 增长。

优化经验：

  • dispatcher 风格的程序自动禁用 forward condition——它注定不会成立，跳过节省大量时间。
  • 当 base case 已经发现反例，立即终止（k-induction 总流程可能被设计成”一旦反例出现就停”）。
  • inductive step 的 SSA 大小通常是 base case 的 100×+。如果 base case 已经几秒，inductive step 数分钟乃至 timeout 都是常态。

1.4. 4.4 多属性验证：一次符号执行 / 多次求解

1.4.1. 4.4.1 问题：单 assert 模型 vs 多 assert 现实

经典 BMC 教学版假设程序里只有一个 assertion。求解器拿到 path ∧ ¬assert，SAT → bug，UNSAT → 安全。但真实程序里同时存在几十、几百条断言：

  • 来自源代码里的 assert(...) / require(...)；
  • 自动注入的标准检查（bounds、div-by-zero、pointer、overflow……）；
  • 库模型自带的内部断言（c2goto / library）；
  • coverage 模式下的 assert(0)（每个被覆盖的语句一个）。

最朴素做法：把所有断言或起来，求 path ∧ (¬a₁ ∨ ¬a₂ ∨ … ∨ ¬aₙ)。SAT → 至少一条断言有反例；UNSAT → 全部安全。

朴素做法的两个致命缺陷：

  1. 第一个反例后就停——求解器只挑一条断言、给一条 trace；剩下 n−1 条断言到底是真安全还是另有反例，无从知晓。bug-finding 工具需要的是列举而不是示例。
  2. 求解器要在 n 条 disjunct 之间做选择——这本身就是组合代价。某些求解器（尤其在内部启发式不友好时）会反复在多个 disjunct 之间切换，比逐一独立求解更慢。

1.4.2. 4.4.2 多属性 = 单符号执行 + N 次求解器调用

核心思想：符号执行只跑一次产生一个完整 SSA 等式（含所有 assert），随后对每条断言单独生成一份切片后的等式提交给求解器。

为什么是”复制 SSA 等式”而非”重跑 symex”：symex 通常是整个 pipeline 中最贵的阶段（几十秒到几分钟），重跑 N 次完全不能接受。而 SSA 等式只是一组 expr2tc，深拷贝 + 标记其他 assert 为 ignore 是常数级开销。

1.4.3. 4.4.3 三类增益

① 完整列举（completeness of bug finding）。每条断言独立得到 PASS/FAIL/UNKNOWN 判定。用户看到的不是”程序至少有一个 bug”，而是”第 3、7、12 条断言违反，其他 PASS”。

② 每条断言的 SSA 被切片到最小。slicer 依赖分析以 assert 为根：只有它的传递依赖留下，其他 assert 的依赖完全消失。某些断言切片后等式大小可能只有原始的 5–10%。

③ 天然并行：n 条断言互相独立 → N 个求解器线程同时跑，端到端时间 ≈ max(单条时间)。

1.4.4. 4.4.4 工程上的关键决定

(a) 用户源码 vs 库代码重排序：c2goto/library 自带的断言通常比用户写的代码更难触发，但很容易先打满 fail-fast 配额。bmc.cpp:1634-1656 stable_sort by is_user，把用户断言放前面，CE 编号保持源码顺序。

(b) 已验证 claim 去重：k-induction / incremental-bmc 多轮中，k=3 验证过的不在 k=5 重新验证。key 是 (comment, location)——源码里标注”unsound 但目前没找到更好的签名”，实践上够用。

(c) Fail-fast 限额 --multi-fail-fast n：累计 n 条 FAIL 后停。一类 bug 重复发的场景 n=1；coverage 分析 n=∞。

(d) 并行通过 std::thread 一对一映射 job→线程，无 thread pool。注释明确写”running everything in parallel might be a bad idea”，known 局限。

(e) 自动触发的 5 种入口：--multi-property 显式；--parallel-solving 隐式（但累计 violations 汇总为 UNKNOWN 而非 FAILED）；--condition-coverage / --assertion-coverage / --diagnose-unknown-properties 都隐式开启 MP。

(f) k-induction 的”清空”逻辑：FC 或 IS 成功后把 goto 里所有 is_assert() 改 make_skip()，下轮 k 检测到 count_active_asserts == 0 干净退出。

(g) 代价：N 次 solver init（--smt-during-symex 可复用）+ N 次 claim_slicer（O(n × |SSA|)）+ N 次 trace generation。SSA 切片总时间常常超过求解器时间——多属性的前提是切片器线性 + solver init 是几十毫秒级。

1.5. 4.5 增量 SMT 求解：symex 时即问即答

1.5.1. 4.5.1 与”增量 BMC”的区别

两个名字相近、容易混淆的概念：

概念入口 flag含义
增量 BMC--incremental-bmc按 k 步逐步加深的多轮 BMC 调度；每轮独立调用 symex + 一个新 solver；上下文不跨轮复用。属于 “verification strategy”。
增量 SMT 求解--smt-during-symex在 symex 过程中同一个 solver 实例持续累积约束、回答”当前是否可达 / 这条 assert 是否必然成立”；用 push/pop 实现假设撤销。属于 “encoding strategy”。

后者就是本节主题。

1.5.2. 4.5.2 设计动机

经典 BMC 是”先 symex，再 SMT 求解”两个不相通的阶段。symex 在不知道求解器会怎么回答的情况下盲目展开全部路径——很多路径其实根本不可达，但 symex 必须为它们生成 SSA 步骤，最后求解器再去证伪它们。

增量 SMT 求解让 symex 在每个分支点 / assert 处实时问求解器：”这条路径在当前约束下还可达吗？””这条 assert 在当前约束下成立吗？” 求解器维护一个持续生长的 push/pop stack：

效果：

  • 不可达分支在 symex 阶段就被剪掉，根本不生成对应 SSA。
  • 平凡断言（在当前路径条件下永远成立）直接跳过，最终公式更小。
  • 平凡 assume（永远为 false 的 assumption）让 symex 整条路径立即停止。

代价是：每个 symex 步骤都要付一次 SMT 调用——通常是几十毫秒到几秒——symex 步数本身可能是几千上万次，乘起来不一定划算。

1.5.3. 4.5.3 三类入口子选项

--smt-during-symex 是开关；具体在 symex 的哪几个点真正去问求解器，由独立的开关控制：

子选项在哪触发用途
--smt-symex-guard每个 GOTO 的 guard 上不可达分支剪枝
--smt-symex-assert每个 assertion 上平凡断言剪枝（让安全 assert 不进最终公式）
--smt-symex-assume每个 assume 上检测 assume(false)，提前终止路径
--smt-thread-guard线程交错点多线程 schedule 时剪除不可达交错

任何一个子选项开启都会强制开 --smt-during-symex（esbmc_parseoptions.cpp:368-376）——因为没有持续生长的 solver 上下文，”在 symex 中问求解器”就没法实现。

1.5.4. 4.5.4 核心机制：runtime_encoded_equation + push/pop

普通 symex_target_equationt 假设 symex 完事后一次性 dump 给 solver，没有”中途问问题”的接口。增量模式用 runtime_encoded_equationt：持有 smt_convt &conv 引用，每收到一个 SSA step 就立即转换并 assert 到 solver（flush_latest_instructions at symex_target_equation.cpp:848-881）。

询问机制是 ask_solver_question(question) → tvt（symex_target_equation.cpp:939-1004）：先 push solver context、flush 累积的 SSA step + 路径 assume，再问两次——push;assert(q);check;pop、push;assert(¬q);check;pop——根据两个 SAT/UNSAT 的笛卡尔积推 tvt：

res(q)res(¬q)tvt
SATSATUNKNOWN
SATUNSATTRUE（q 必然成立）
UNSATSATFALSE（q 必然不成立）
UNSATUNSATthrow dual_unsat_exception（前缀矛盾）

为什么问两次：SMT 只回答”约束可不可满足”，要确定 q 在所有模型下恒为真，必须额外证明 ¬q 不可满足。

1.5.5. 4.5.5 与 multi-property 的关系

两者正交且可叠加：

  • 多属性是”一份 SSA、N 次求解”的策略层选择。
  • 增量 SMT 是”一份 SSA、symex 过程中即时求解”的编码层选择。

叠加时：multi-property 默认每条 claim 创建一个新 solver；如果同时开 --smt-during-symex，则全程复用同一个 solver 实例（bmc.cpp:81-100 / bmc.cpp:1452-1456 / bmc.cpp:1755-1759）——大幅省 solver 初始化时间。

1.5.6. 4.5.6 何时启用、何时反而变慢

该启用：

  • 程序有大量显然不可达的分支（编译期常量条件 + interval 没有覆盖到的形态）。
  • 程序有大量平凡断言（标准检查注入的 bounds/null 检查，绝大多数 trivially safe）。
  • 单次求解器调用很快（小 SSA、用了 Bitwuzla 这类启动快的 solver）。

反而变慢：

  • 路径条件本身就复杂（256-bit 算术、大量嵌套 array select），每次 ask 都几秒——symex 步数一多就爆炸。
  • 程序绝大部分路径都可达 / 断言绝大部分都不平凡——这种情况下问求解器的答案就是”yes 这条可达”，做的功只是白做。
  • 求解器初始化代价高（如 Z3 大上下文）——push_ctx / pop_ctx 自己也要开销。

经验：增量 SMT 在 SV-COMP 类小程序（C 函数级、几十行）上是显著加速；在大型智能合约这种”路径少但每条路径 SSA 巨大”的场景里通常不开。

1.6. 4.6 浮点 / 整数编码：同语义、四种 SMT 编码

C 的 float/double 是 IEEE 754 浮点；int/long 是固定宽度二补码整数。SMT 提供了多条互不兼容的编码路径，每条 sound/performance trade-off 不同。

1.6.1. 浮点三选一

flag编码方式IEEE 754 兼容速度求解器支持
--floatbv (默认)SMT FP 理论✅ 完全中Z3, CVC5, Bitwuzla
--fixedbv定精度 BV（整数 + 小数 bit）❌ 偏离 IEEE快全部
--fp2bvbit-blast 成纯 BV✅ 完全最慢全部（不依赖 FP 理论）

何时各自：

  • 控制系统 / 信号处理 / 金融计算 → --floatbv（必须 IEEE 准确）
  • 教学 / 概念验证 / 求解器不支持 FP 理论 → --fixedbv
  • 老 Boolector 等不带 FP 理论的求解器 → --fp2bv（spec-correct 但慢）

落点：src/esbmc/options.cpp:558-565。配置在前端类型降级前生效，会改变所有 float/double 变量的内部表示。

1.6.2. 整数：bit-vector vs LIA

--int-encoding 把 C 的 int/long 从 BV 切换到 LIA（线性整数算术）：

编码溢出语义速度
BV<64>（默认）C 标准：unsigned wrap-around / signed UB慢（256-bit 算术更慢）
LIA数学整数无溢出快 5-10×

Sound 当且仅当能证明程序确实不溢出——否则 LIA 给的答案对应”假设不溢出”的程序，与真实 C 语义不符。

实务：

  • 智能合约的 uint256 必须用 BV（溢出是合约的安全核心）
  • SV-COMP 的纯逻辑问题 / 教学例子可以用 LIA 提速
  • 一旦混入位运算（<<, &, |），LIA 退化（无 native 位运算）；BV 才适合

1.7. 4.7 Tuple / Array 编码：复合类型的三种展平

问题：SMT 没有原生的 struct 类型，array of struct、nested array 等复合类型必须”展平”才能交给求解器。展平方式直接影响公式规模。

1.7.1. 三种 tuple 编码

策略flag原理
Node flattener (默认)--tuple-node-flattenertuple 拆为 N 个独立 SMT 变量，每个字段单独建模
Sym flattener--tuple-sym-flattenertuple 拼成一个宽 bitvector，字段访问 = bit slice
CVC5 native datatype--cvc5-native-tuplesCVC5 的 mkTupleSort 构造代数 ADT

性能特征：

  • 简单 tuple（2-3 个字段）→ node 最快，每个字段对应一个 SMT 变量，访问 O(1)
  • 嵌套 array of struct → sym 通常更紧凑；bit slice 比 N 个独立变量少
  • ≥3 维嵌套（T[N][M][K]）→ 只有 CVC5 native datatype 不爆炸；node 会展开成 N×M×K 个独立变量

1.7.2. Array 编码

--array-flattener：把 T[N] 展平为 N 个独立 SMT 变量，而非用 array 理论的 store/select。仅对固定小尺寸有意义。

1.7.3. 自动 hint

ESBMC 检测到 ≥3 维嵌套 array 时自动开 --cvc5 --cvc5-native-tuples（见 §4.1 求解器自动选择）。手动想关掉：--no-cvc5-native-tuples。

落点：src/esbmc/options.cpp:566-577 注册；src/solvers/smt/tuple/ 三个 flattener 各自一个文件。

实务：99% 的代码用默认 node flattener 就好；只有当你的程序里出现深嵌套数据结构（典型：Solidity 的 mapping(K => T[N][M])、复杂 graph 算法的邻接表）且 solver timeout 时再换编码。

1.8. 4.8 Online vs Offline SMT 编码：方法论框架

§4.5 讲了 ESBMC 当前的 --smt-during-symex 实现——那是一个特定 BMC 工具在一个特定时间点的工程选择。这一节退一步，把”online vs offline”作为所有 BMC 工具都要面对的编码策略选择来谈。注意：本节描述的”完整 online”形态在 ESBMC 中尚未实装（上游 issue 与未合并 PR 在讨论一个 SSA-step-level 的增量 SMT 算法框架），所以下面的内容是方法论层面的总结，不是当前 ESBMC 行为的直接映射。

1.8.1. 4.8.1 语义不变量：C ∧ ¬P 永远完整

容易产生的一个误解：online 听起来像”在公式还没合成完就开始 solve”，仿佛 soundness 有疑问。不是这样——最终验证条件依然是完整的 quantifier-free 公式：

C 是路径约束 + 赋值关系 + 内存模型约束的合取；P 是 property。online 只是改变了 C 进入 solver 的时机：

如果 online 不剪枝、不提前终止，最终 solver context 里的约束与 offline 的一次性公式完全等价。online 唯一改变的是：在 assertion 点 solver 已经持有前缀 C_at_assert，可以临时加 ¬P 做局部 check。

assertion 的语义天然支持这种局部性——assert(P) 检查的是”程序执行到这一点时 P 是否成立”，依赖的只是这一点之前的状态编码，与之后的语句无关。这是 online 之所以 sound 的根本原因。

1.8.2. 4.8.2 收益来源的三个支柱

(1) 早期不可行路径剪枝。assume(x>0); ...; assume(x<0) 这种 contradictory prefix 在 offline 模式下要等最后才暴露，期间所有 SSA 生成 + encoding 都是浪费。online 在第二个 assume 处立刻发现 UNSAT，整条路径 + 后续语句 + 函数调用 + 内存编码全省。

(2) Solver 内部状态复用。Incremental solver 在连续 query 之间保留 learned clauses、term DAG、theory propagation 状态，避免每次从零开始。这部分收益完全来自 solver 端——只要 push/pop 不破坏内部结构，连续 N 次小 query 比一次 N×大公式 query 更快。

(3) Assertion 的程序点局部性。每个 assertion 只依赖前缀，online 用 push/add(¬P)/check/pop 的临时检查模式天然贴合这一语义；offline 必须在最终公式里把所有 assertion 的否定 disjunction 起来，组合代价单调上升。

1.8.3. 4.8.3 五类隐蔽的退化模式

收益不是单调的。online 在下列场景比 offline 更慢，且不容易被简单 benchmark 暴露：

失败模式触发条件后果
Query 频繁但无剪枝大量简单 assignment，每个 query 返回 SAT-continueSolver 调用变纯开销，每次 check-sat 都触发 bit-blast / theory propagation
Push/pop 破坏 solver 优化Solver 对 incremental mode 支持不完善（老 Boolector、某些 backend）Learned clauses lifetime / activation literals 由 push 层管，pop 后丢弃；最坏情况比非 incremental 慢数倍
前缀公式信息量不够关键约束在 assertion 之后（...; assume(x==10); assert(x>0)）早问 solver 返回 UNKNOWN 或假阳性候选，无法剪枝
全局重写机会丢失Slicer / guard merging / expression sharing 依赖完整公式预处理Solver 看到碎片化约束流，简化效果差
CEX 构造复杂度上升中途发现 bug，要重建完整 trace必须保证 SSA step / guard / source location / renaming / memory state 都能从增量状态恢复

后三类是工程上最难抓的——它们不会让工具崩溃、不会让结果错，只会让 timeout 数变多。

1.8.4. 4.8.4 决定性变量：query 位置而非 query 频率

把”开 online”当成一个布尔开关是错误视角。真正的性能变量是在哪些程序点 query：

Query 位置价值说明
每个 assignment 后低过密、信息密度低、纯开销
每个 assume 后高剪枝率高（路径条件突变）
每个 assert 前必需没有替代
Branch merge 前中结构化场景奏效
Loop unwind 边界高避免无谓深展开
按公式复杂度阈值启发式需调参

经验法则：信息密度跃升的程序点适合 query——assume 之后（路径条件突变）、循环展开边界（unwind 终止 vs 继续的判定）、函数调用前（参数约束聚集）。assignment 之后通常不值得问。

1.8.5. 4.8.5 ESBMC 现状与上游方向

§4.5 讲的 --smt-during-symex + 三个子选项（--smt-symex-guard/assert/assume）是保守的 online：query 位置由用户用 flag 显式选择，工具不做自动启发式 placement。这种实现规避了 §4.8.3 的失败模式（用户能开就关），代价是收益封顶——绝大多数程序的最优 placement 用户不知道怎么手调。

上游讨论中的更激进方向：

  • 把 incremental SMT 抽出为独立的 SSA-step-level algorithm
  • 重新设计 push/pop 调用架构以降低 context 切换开销
  • 自动启发式 query placement（不依赖用户 flag）

这条路尚未合并进 master，因为上游测试显示收益非单调——某些 benchmark 提升，某些倒退。这恰好印证了 §4.8.3 的失败模式分析：online 不是免费午餐，每多一处自动 query 都可能引入退化。

核心 takeaway

Online 与 offline 的 trade-off 不应被简化为”快 vs 慢”，本质是 “用 solver call 换 symex/encoding work” 的交换。这个交换在不同程序结构上有完全不同的 ROI：剪枝率高的场景（contradictory assume 多、bug 浅、循环展开大但局部矛盾早）online 大赢；直线代码、末尾 property、全局公式难度高的场景 online 大输。

设计 BMC 工具时，应该把 online 视为一组可配置的 query 策略而非单一开关，并为不同程序结构提供不同的默认 placement。真正的性能收益不来自”incremental”这个标签，而来自选择何时 query。
