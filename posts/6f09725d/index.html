第 8 章　LTL 检查 —— 把时序性质归约成监视器线程上的断言

前面七章里，ESBMC 检查的所有性质都落在某一个程序点上。本章讲 --ltl 这条路径：它检查的是整条执行轨迹上的时序性质。线程调度相关的内容建立在 Symex 篇 的 reachability_treet 与上下文切换之上。源码引用基于 commit adb54abefe（8.5.0）。

8.1 背景：LTL 是什么

8.1.1 assert 说不出来的那类性质

ESBMC 日常检查的东西，无论是用户写的 assert、数组越界还是空指针解引用，形式上都是同一种性质：程序执行到某一点时，某个条件成立。这类性质叫 安全性 (safety)，口号是“坏事永远不发生”。它有一个很好的特点：违反它只需要一条 有限 的执行前缀，走到出错的那一步就够了，这正是 BMC 擅长的。

但有些需求不长这样：

  • 按下按钮之后，电量 最终 会超过下限；
  • 每个请求 迟早 得到响应；
  • 互斥锁被拿走之后 终究 会被释放。

这类性质叫 活性 (liveness)，口号是“好事终将发生”。它谈论的是 整条执行轨迹上状态之间的先后关系，而不是某一个程序点。你没法在源码里找到一个位置插 assert 来表达“以后某个时刻会怎样”。

线性时序逻辑 (Linear Temporal Logic, LTL) 就是用来写这类性质的语言，由 Pnueli 在 1977 年引入程序验证。

8.1.2 语法和直觉

LTL 的公式解释在 一条 无限的状态序列 s0 s1 s2 ... 上，这样一条序列叫 轨迹，可以想成程序一次运行的录像，每个状态是一帧。下表里的 p、q 是 原子命题：在某一帧上看一眼就能判断真假的条件，比如“按钮被按下”“电量超过下限”。在命题逻辑（!、&&、||、->）之外，LTL 加了几个时序算子：

算子常见写法读法含义（在位置 i 处）
G p[] p、□pglobally / always从 i 起每个位置 p 都成立
F p<> p、◇pfinally / eventually从 i 起存在某个位置 p 成立
X p○pnext位置 i+1 处 p 成立
p U quntilq 终将成立，且在那之前 p 一直成立
p R qp V qreleaseq 一直成立，直到（含）p 成立的那一刻；p 永不成立则 q 永远成立

公式总是在轨迹的某个位置上求值；说“一条轨迹满足公式”，指的是在位置 0 满足。所以外层有没有 G 差别很大：p -> F q 只在开头检查一次，开头 p 为假就算通过，之后发生什么都不管；G(p -> F q) 在每个位置都检查一次。

G 的“所有”指的是 一条轨迹上的所有时刻，不是“所有情况”。一个程序有很多条轨迹（输入不同、线程调度不同），“每一条轨迹都要满足公式”这层要求不写在公式里，由检查工具负责。于是验证 G(p -> F q) 时实际有两层“所有”：

LTL (Linear Temporal Logic) 名字里的“线性”就是指公式只描述一条轨迹。与之相对的 CTL (Computation Tree Logic) 把“所有轨迹 / 存在一条轨迹”也写进公式（A、E，称为路径量词），本文不涉及。

从一句需求到一条公式。 翻译分两步：先找出句子里的原子命题，在 ESBMC 里它就是花括号中的一个 C 布尔表达式；再把句子里的时间词换成算子，“永远、绝不”是 G，“最终、迟早”是 F，“一直……直到……”是 U。

下面是七句需求和它们的翻译，公式用 ESBMC 的写法。句子里的条件和公式里对应的原子命题用同一种颜色标出：

需求原子命题公式怎么对上的
计数器永远不超过 100（The counter is always at most 100）count <= 100G {count <= 100}“永远”是 G，后面直接跟条件
绝不出现线程 1 在临界区且线程 2 也在临界区（It never happens that thread 1 is in the critical section while thread 2 is too）cs1、cs2G !({cs1} && {cs2})“且”是两个命题的合取，“绝不”是 G !
最终会初始化完成（Eventually, initialization is done）init_doneF {init_done}“最终”是 F
每次发出请求，之后都会收到应答（Whenever a request is sent, eventually a reply is received）req、ackG({req} -> F {ack})“每次”是外层的 G，“如果发出请求”是 -> 的左边，“之后会收到”是 F
拿到锁之前不会进入临界区（The program does not enter the critical section until the lock is held）in_cs、locked!{in_cs} U {locked}“在……之前一直不”是 U：左边是这段时间里保持的条件，右边是结束这段时间的事件
一旦报警在响，就一直响，直到被复位（Once the alarm is on, it stays on until it is reset）alarm、resetG({alarm} -> ({alarm} U {reset}))“一旦”是 G(… -> …)，“一直响直到复位”是 U
系统最终会稳定处于空闲状态（Eventually the system stays idle forever）state == IDLEF G {state == IDLE}“最终”是 F，“稳定”是此后“一直”，即 G

两点补充。算子的嵌套顺序有含义：F G {state == IDLE} 要求从某一刻起不再离开空闲状态，对调成 G F 则只要求空闲状态反复出现。p U q 自带“q 终将发生”的承诺；不需要这层意思时用 R（ltl2ba 语法里写作 V），例如 {locked} V !{in_cs}。

8.1.3 轨迹从哪里来：程序、状态转移系统与 Kripke 结构

LTL 只规定了公式在一条轨迹上怎么求值，没有规定轨迹从哪里来。讨论“ESBMC 怎么检查 LTL”时，有几件不同层次的事容易混在一起，先分开：

层次回答的问题在 ESBMC --ltl 里本文位置
被验证对象验证什么C 程序§8.4
系统模型程序怎么执行、产生哪些轨迹程序的状态转移系统，通过原子命题看成一个 Kripke 结构本节
规约要求轨迹满足什么LTL 公式；只看到有限前缀时按四值语义判决§8.1.2、§8.3
验证算法怎么检查BMC 展开程序，Büchi 自动机做监视器§8.2、§8.5
求解生成的约束怎么解SMT 求解器前几篇

这只是帮助理解的划分，不是软件架构。本节讲第二层。

状态转移系统 由三样东西组成：状态集合、初始状态、转移关系。对 C 程序，一个状态是全部变量的取值加上程序计数器，一次转移是执行一条语句。前几篇里 symex 展开的就是它。

Kripke 结构 是 LTL、CTL 教科书里用的系统模型，记作 (S, I, R, L)。它在状态转移系统之上只多要求两件事：

  1. 标注函数 L：给每个状态标上哪些原子命题为真。LTL 看不到状态本身（堆、栈、程序计数器），只看得到这层标注，轨迹就是沿一条路径读出来的标注序列 L(s0) L(s1) L(s2) …；
  2. 转移关系是全的：每个状态至少有一个后继，于是每条路径都无限长，正好对上 LTL 的无限轨迹。

所以 Kripke 结构不是另一类系统，而是“状态转移系统 + 原子命题 + 不许停下来”。有的教材（如 Baier 与 Katoen 的 Principles of Model Checking）直接把带标注的状态转移系统叫 transition system，说的是同一个东西。任何状态转移系统补上这两样就能检查 LTL，ESBMC 也不例外。它并不显式构造 Kripke 结构（C 程序的状态多到构造不出来），而是逐项隐式地给出：

Kripke 结构需要ESBMC 给的
状态C 程序的状态，在 symex 里是 SSA 形式的符号值
标注 L公式花括号里的 C 表达式，在当前状态上求值
一步一次对受监视变量的赋值
转移关系是全的main 返回后，最后一个状态无限重复（§8.3.1 的 stutter 扩展）

“一步”这一行需要解释。两次受监视赋值之间的语句不改变任何原子命题的真假，在轨迹上只是把同一帧重复几遍。不含 X 的 LTL 公式对这种重复不敏感，算不算作一步结论都一样，所以 ESBMC 只在赋值之后采样。代价是 X 的含义变成了“下一次相关赋值之后”（§8.6）。这也意味着时间是事件驱动的：没有时钟，两次赋值之间过了多久监视器看不到，“100 毫秒内响应”这类实时性质不在 LTL 的表达范围内。

8.1.4 安全性与活性在反例形状上的区别

前缀 指一条轨迹从开头起连续的一段，在它后面接上的状态叫 延续。安全性和活性的区别可以用它说清楚，这一点决定了后面所有的设计：

  • 安全性的反例是一条 有限前缀。G !bad 被违反，只要给出走到 bad 的那一段。
  • 活性的反例必须是一条 无限轨迹。F done 被违反，意味着 done 永远不成立，任何有限前缀都不足以证明这一点，因为总可以说“下一步也许就成立了”。在有限状态系统里，这种无限轨迹表现为 lasso（套索）：先走一段前缀，然后进入状态图（即 Kripke 结构，§8.1.3）里的一个 环 (cycle)，即一串首尾相接、能回到起点的状态转移，沿着它可以无限绕下去。这里的环是状态图上的回路，不是源码里的 for / while 循环。

8.1.5 测试能检查活性吗

严格地说不能。一次测试是一段有限的执行，跑了十分钟没等到响应，逻辑上只能说“还没等到”。工程上的做法是把活性改写成安全性再测，最常见的是加超时：“请求最终得到响应”变成“请求在 5 秒内得到响应”，后者一段有限执行就能违反。

真正的活性结论要对所有无限行为做论证，这是验证工具的领地。ESBMC 的 --ltl 处在中间：它对活性给出的仍是基于有限前缀的推定（§8.3），不是无界证明；它比测试强在覆盖面，一次运行覆盖了界内的所有输入和所有线程交错，而一次测试只是其中一条。

8.2 经典做法：把公式变成自动机

8.2.1 自动机理论方法

显式状态模型检查器（Spin 是代表）检查 LTL 的标准流程，由 Vardi 与 Wolper 在 1986 年提出：

  1. 把性质取反，得到 !φ；
  2. 把 !φ 翻译成一个 Büchi 自动机。它是读无限字的有限自动机，接受条件是“无限次经过接受状态”。这个自动机恰好接受所有 违反 φ 的轨迹；
  3. 让自动机和被测系统同步运行（求乘积）；
  4. 在乘积的状态图里找一个可达的、经过接受状态的环，称为 接受环 (accepting cycle)。能无限次绕这个环，就是无限次经过接受状态，所以找到它就找到了一条违反 φ 的无限轨迹；找不到则 φ 成立。

以 φ = G({pressed} -> F {charge > min}) 为例，记 p 为 pressed、q 为 charge > min。!φ 的意思是“某次按下之后，电量再也没上来”，它的自动机只有两个状态（下图 ①）。q0 是等待：什么都可以发生。某一步看到“按下且没电”时，自动机可以选择跳到 q1，相当于猜测“就是这一次按下之后再也不会充电”。q1 是验证这个猜测：只要 q 一直为假就能留在这里。q1 是接受状态，所以能在 q1 里永远待下去的轨迹就是被接受的轨迹，也就是违反 φ 的轨迹。

图 ② 和 ③ 是第 3、4 步的样子。系统每走一步，自动机读入当前的 p、q 并跟着走一步，两者的状态配成一对。② 里系统停在“没充电”的状态不动，自动机停在 q1，这一对状态构成一个经过接受状态的环，反例就是“前缀 + 这个环无限重复”。③ 里系统后来充电了，q 变为真，q1 没有对应的出边，猜错的这次运行被丢弃；系统的每条轨迹都是这个结局时，φ 成立。

Spin 里那个 !φ 的自动机叫 never claim：它描述“绝不应该出现的行为”。记住这个方向，后面 ESBMC 的用法里有一个一模一样的取反。

8.2.2 这条路在 BMC 上走不通的地方

难点在上面的第 4 步：要找接受环，就得能判断“系统又回到了一个之前到过的状态”。显式状态检查器可以存下访问过的状态再比较，硬件 BMC 则可以在展开 k 步之后加一组“第 k 步的状态等于第 l 步的状态”的约束来编码 lasso（Biere 等人 1999 年提出 BMC 时就是这么处理 LTL 的）。

对 C 程序做这件事要难得多，两层都有障碍。系统模型这一层，C 程序的状态里有堆、指针、调用栈，不是一组固定宽度的位向量，“两个状态相等”写不成一条简单的约束。验证算法这一层，symex 只把循环展开到给定的界，手里只有 有限前缀，并不知道“这个状态以前是否出现过”。

于是问题变成：只看到一段有限前缀，能对一个定义在无限轨迹上的公式说些什么？

8.3 ESBMC 的答案：有界轨迹语义与四值格

ESBMC 的 LTL 支持来自 Morse、Cordeiro、Nicole、Fischer 的工作（SEFM 2011，扩展版发表于 SoSyM 2015）。思路借自 运行时验证 (runtime verification)：那个领域的做法是在程序真实运行时旁边放一个监视器，边跑边判断性质。监视器只能看到“到目前为止”的一段前缀，所以它给的结论不止“对 / 错”两种，还有“目前看是对的，但以后可能被推翻”这样的中间值。BMC 的处境相同，于是把这套多值结论搬了过来。

8.3.1 四个判决值

设 u 是探索到的有限前缀：

ESBMC 输出记号含义例子
LTL_BAD⊥确定违反：u 后面无论接什么都违反 φ性质 G {s == 0}，程序 s = 0; s = 1; s = 0;。出现过 1，无可挽回
LTL_FAILING⊥ᵖ推定为假：程序就此停住的话违反 φ，但接着跑下去还有可能满足按钮性质，程序 min = 10; charge = 5; pressed = 1;。按下了，电还没充上
LTL_SUCCEEDING⊤ᵖ推定为真：程序就此停住的话满足 φ，但接着跑下去还有可能违反按钮性质，程序 min = 10; pressed = 1; charge = 11;。充上了，但以后可能再按一次
LTL_GOOD⊤确定成立：u 后面无论接什么都满足 φ性质 F {done}，已经看到过 done 为真

“按钮性质”指 G({pressed} -> F {charge > min})。四个值从低到高排成 ⊥ ⊑ ⊥ᵖ ⊑ ⊤ᵖ ⊑ ⊤。

中间两个值里的“程序就此停住”是一个明确的规则，叫 stutter 扩展：程序结束后，认为最后一个状态永远保持不变，这样有限前缀就被补成了一条无限轨迹，可以按 LTL 原本的定义判断。main 返回之后全局变量确实不再变化，所以这个补法是合理的。

对活性性质，任何有限前缀都排除不了“以后又按一次而不再充电”，所以 ⊤ 够不着，最好的结果就是 ⊤ᵖ：

对活性性质，LTL_SUCCEEDING 就是预期中的“通过”，不是差一点通过。

8.3.2 程序有很多条路径时

ESBMC 不是挑一条路径来查。输入的不同取值、线程的不同交错，它全部探索，每条路径各得一个判决，最后报告其中 最低 的那个，日志里那一行因此叫 Final lowest outcome。这就是 §8.1.2 里“对所有轨迹”那一层：只要有一条路径是 ⊥，整体就是 ⊥。

8.4 上手：一个最小用例

8.4.1 准备 libltl2ba

公式到自动机的翻译不在 ESBMC 里，而在一个外部工具 libltl2ba 中。它是 Gastin 与 Oddoux 的 ltl2ba 的分支，多了一个把自动机输出成 C 代码的后端（-O c）。

注意两点：

  • ESBMC 的构建脚本不会替你下载它，需要自己编译；
  • 必须用 master（b810033 之后）。打了 tag 的 v2.1 生成的监视器缺少一次关键的上下文切换调用，配上新版 ESBMC 得不到任何判决。

每一次对这三个变量的赋值就是轨迹上的一个时刻（§8.1.3），p、q 两列就是 Kripke 结构的标注。时刻 4 是关键：按钮已经按下，电还没充上，p 真而 q 假。φ 在这里没有被违反，因为它要求的是 q “最终”为真，而时刻 5 兑现了这一点。程序在时刻 5 之后结束，状态停在 p 真、q 真，往后无限重复也满足 φ。

这个中间时刻也说明了公式里为什么要有 F。如果把性质写成 G({pressed} -> {charge > min})，即“按下的同时电量就必须够”，时刻 4 就是一个违反，而且无法挽回：ESBMC 对这个版本的回答是 LTL_BAD。

8.5.1 先看结果：ESBMC 实际检查的是一段普通程序

这段代码里有整个机制的四个要素：

  1. 自动机变成了一个变量。 !φ 的 Büchi 自动机（§8.2.1）有两个状态：Q0 表示“还没见过 s != 0”，Q1 表示“见过了”。state 记着它当前在哪。

  4. 三条断言从低到高问一遍。 哪一条最先能被违反，判决就是哪一个。这里三条都能被违反，最低的是 LTL_BAD。

8.5.2 真实实现和上面那段程序的四处对应

监视器代码和三张表由 ltl2ba 生成。 你不用手写 monitor_step 和那些表，ltl2ba -O c 根据公式生成一个 C 文件，里面有命题函数、自动机的转移代码、三条断言和三张表：

表表项为真的含义对应断言
_ltl2ba_bad_prefix_states自动机停在这个状态，以后无论程序怎么走都会被接受LTL_BAD
_ltl2ba_stutter_accept_table命题保持现在的取值不变，自动机会接受LTL_FAILING
_ltl2ba_good_prefix_excluded_states自动机停在这个状态，以后还有可能被接受LTL_SUCCEEDING

“被接受”就是违反 φ（§8.2.1）。三张表是 ltl2ba 在翻译公式时对自动机做离线分析得到的，找环这件事在那时、在只有几个状态的自动机上就做完了。这正是 §8.2.2 那个难题的解法。

monitor_step() 的调用由 ESBMC 自动插入。 add_property_monitors（src/esbmc/parseoptions/property_monitors.cpp:55）先从监视器文件里找出命题读了哪些全局变量，然后把程序里对这些变量的每一次赋值改写成：

同时在 main 的开头插入启动监视器的调用，在每个 return 之前插入查表的调用。只有直接对具名变量的赋值会被识别，通过指针、数组元素、结构体成员的写入不会触发监视器。

监视器实际上是一个线程，但被当作协程用。 生成的自动机代码是一个 for 循环，每转一圈走一步，走完要暂停、把控制权还给程序，下次接着转。能在循环中间暂停的东西需要自己的调用栈，所以它被做成了一个 pthread。但它不参与普通的线程调度：ESBMC 用四个内建函数显式地切过去（__ESBMC_switch_to_monitor）、切回来（__ESBMC_switch_from_monitor）、登记（__ESBMC_register_monitor）和结束（__ESBMC_kill_monitor）它，调度器永远不会自己选中它，它走一步的过程中也不允许别的线程插入（src/goto-symex/scheduler/execution_state.cpp:1566）。这样保证了监视器恰好在命题变化的那一刻采样，上图中 s = 1 那一列才不会被漏掉。

三条断言一次只查一条。 bmct::ltl_run_thread（src/esbmc/bmc.cpp:2631）先确认监视器完整跑完了（循环展开断言等没有被违反），否则不给结论；然后依次只保留 LTL_BAD、LTL_FAILING、LTL_SUCCEEDING 中的一条去求解，第一个可满足的就是这条路径的判决，三条都不可满足则是 LTL_GOOD。所有路径跑完后取最低值：

最低值进程判决
LTL_BAD / LTL_FAILINGVERIFICATION FAILED，附反例
LTL_SUCCEEDING / LTL_GOODVERIFICATION SUCCESSFUL
没有任何判决VERIFICATION UNKNOWN

8.6 局限与踩坑

  • 判决是有界的。 LTL_SUCCEEDING 说的是“在探索到的前缀上性质推定成立”，不是无界证明。
  • 程序必须从 main 返回。 查表的调用只插在 return 之前。while (1) 的主循环、exit()、abort() 都走不到那里，结果是 VERIFICATION UNKNOWN。
  • LTL_PREFIX_BOUND 要给够。 它是监视器最多走多少步，至少要等于最长路径上受监视的赋值次数加一。给小了同样是 VERIFICATION UNKNOWN。--unwind 也作用于监视器的循环，同样要留够。
  • 只能用朴素 BMC。 和 --k-induction、--incremental-bmc、--termination 混用都得不到判决。
  • 其他性质被屏蔽。 --ltl 运行时不报告越界、空指针、溢出和用户的 assert，内存安全要另跑一遍。
  • 监视器看得到中间状态。 它在每次赋值后采样，所以一条语句改了一半的状态也算一个时刻（§8.4.2 的时刻 4）。X 的含义是“下一次相关赋值之后”，建议避开。
  • 多线程代价高，也没有公平性。 判决是所有交错的最小值，交错数量增长很快：主线程加一个工作线程要探索 36 种调度，再加一个是 382 种。
  • 只支持 C 前端。
  • 日志里的 ERROR: Switching to ended monitor 在结果正常的运行里也会出现，不影响判决；以有没有 Final lowest outcome 这一行为准。

8.7.1 和 TLA+ 的区别

用两个例子并排比较：一个两边都能检查，一个只有一边能检查。系统都是 §8.4 的按钮充电，性质都是“按下之后电量最终超过下限”。

例一：两边都能检查。

结论的含义模型的全部 4 个可达状态都查过了，性质成立按两次按钮以内的所有输入都查过了，性质推定成立（⊤ᵖ）

两边都通过了，但过程里有三处不同。

TLA+ 那边的输入是另写的一份模型。 TLC 不读 C 代码。Press 和 Charge 是两个 动作，各自描述一步之内变量怎么变（带撇号的是下一个状态的值）。这份模型和 C 代码是否一致，没有工具负责检查。ESBMC 的输入就是代码本身。

TLA+ 那边多了一行 WF_vars(Charge)。 去掉它，TLC 会报性质不成立：

[][Next]_vars 的含义是“每一步要么执行 Next，要么变量不变”，所以按下之后从此原地不动（Stuttering）是模型允许的行为，电量也就再没上去。WF_vars(Charge) 是 弱公平性 (weak fairness)，意思是 Charge 如果一直可以执行，就终将被执行。叫“公平”是因为它约束的是调度：一个随时可以执行的动作不能被永远晾在一边。在 TLA+ 里，“该发生的事不会被无限期搁置”必须由你明确写出来。C 代码不需要这一行，因为 if (pressed) 的下一条语句一定会执行，这是语言语义保证的。

结论的强度不同。 左边的模型描述的是按钮被按任意多次，TLC 的结论覆盖了全部行为，是确定的。右边的循环只转两圈，ESBMC 的结论只覆盖这两圈，而且带“推定”二字。

例二：只有 TLA+ 能检查。 真正的固件不会只处理两次按键，主循环是 while (1)。把 C 代码改成它本来的样子：

TLA+ / TLCESBMC --ltl
输入和例一完全相同，一个字不用改

int main()
{
  charge = nondet_int();
  min = nondet_int() % 1024;

    pressed = nondet_int();
    if (pressed)
      charge = min + 1;
  }
}
性质同上同上
结果Model checking completed. No error has been found.WARNING: LTL monitor preconditions violated, the automaton did not run to completion; prefix outcome is inconclusive
VERIFICATION UNKNOWN
结论的含义同上，本来描述的就是一个永远运行的系统没有结论

对 TLA+ 来说什么都没变，因为它的模型从一开始描述的就是无限行为，检查方法是在状态图里找环（§8.2.1），程序停不停都一样。

ESBMC 这边得不到结论，原因有两层。给了 --unwind 时，while (1) 在任何展开界下都没走完，展开断言必然被违反，ESBMC 据此判定监视器没有完整运行（§8.5.2）。更根本的一层是：三条前缀断言放在 ltl2ba_finish_monitor 里，而它只插在 main 的 return 之前（§8.5.2），一个永不返回的程序根本走不到那里。stutter 扩展需要一个“最后的状态”，而这个程序没有。

能做的只有把循环改回有界，也就是退回例一，然后接受结论只对前 N 圈负责。

反过来的差异也存在。 把例一的 % 1024 去掉，min + 1 就可能溢出，charge > min 不再有保证。ESBMC 按 32 位 int 的真实语义处理，能看到这个问题：同样的命令，结果从 LTL_SUCCEEDING 变成了 LTL_FAILING。TLA+ 模型里的 Min + 1 是数学整数运算，永远大于 Min，这类错误在模型里不存在，也就无从发现。指针、数组越界、内存布局同理。

所以两类工具用在不同阶段：TLA+ 在写代码之前检查协议和算法的设计，擅长永不终止的系统和需要公平性的活性；ESBMC 在代码写出来之后检查这份实现，擅长位精确的语义，时序方面只对有界前缀负责。

8.7.2 其他几个工具

  • Spin：思路上最接近，ESBMC 的监视器就是 Spin never claim 的翻版，ltl2ba 也来自 Spin 生态。区别是 Spin 存储显式状态，能真正找到接受环，给出无限的反例。
  • NuSMV 一类的硬件 BMC：同样是 BMC，但状态是固定宽度的位向量，可以直接把“第 k 步回到第 l 步”写成约束来编码环。C 程序有堆和调用栈，做不到这一点。
  • Ultimate LTL Automizer：同样直接检查 C 源码，借助终止性分析可以给出无界证明，代价是自动化难度高得多。
  • SV-COMP 的性质文件里写着 LTL(G ! call(reach_error()))、LTL(F end)，语法上是 LTL，但只有固定几条，ESBMC 用各自的专门模式处理，不经过 --ltl。

8.8 小结

  • LTL 让你写出 assert 写不出的性质，尤其是活性：“好事终将发生”。
  • LTL 只需要系统产生一串命题取值。C 程序的状态转移系统加上原子命题作标注、以受监视的赋值为一步、用 stutter 补成无限，就是 LTL 要的 Kripke 结构。
  • 经典检查方法是把 !φ 变成 Büchi 自动机，在乘积里找接受环。BMC 只有有限前缀，找不了环。
  • ESBMC 的办法是有界轨迹语义：判决取自四值格 ⊥ ⊑ ⊥ᵖ ⊑ ⊤ᵖ ⊑ ⊤，中间两个值靠 stutter 扩展定义。活性性质的“通过”是 ⊤ᵖ。
  • 实现上，ESBMC 核心并不认识 LTL。libltl2ba 把自动机编译成一个 C 监视器线程和三张预计算的表；ESBMC 负责给相关赋值插桩、把监视器当协程定向调度、最后按层屏蔽断言各求解一次。
  • 和 TLA+ 相比：一个验证代码、有界、四值、无公平性；一个验证设计模型、对有限模型完备、公平性是一等公民。
  • 用之前请确认：ESBMC 8.4.0 以上、libltl2ba 取 master、显式给 LTL_PREFIX_BOUND、不要和 k-induction 等策略混用、内存安全另跑一遍。
