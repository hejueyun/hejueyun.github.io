ESBMC 前端盘点

2026-05-13

调研基准：本仓库 master 分支，截至 2026-05-13。
评估对象：src/ 下除 solidity-frontend 之外的全部前端。
评估维度：① 语法/语言特性覆盖 ② 标准库/运行时模型 ③ ESBMC 核心验证能力 ④ 已知缺陷与未来计划 ⑤ Scale（能验多大/多复杂） ⑥ Soundness/Completeness 备注。

注意：文档可能滞后于代码，本文以 regression/ 测试首行类别（CORE / THOROUGH / KNOWNBUG / FUTURE）、源码 TODO/FIXME 数、近 6 个月 commit 数为主要”硬证据”，文档作为辅助参考。

2. 1. C 前端（src/clang-c-frontend，12.5 K SLOC）

2.1. 原理

  • 走 Clang AST，clang_c_convert.cpp/clang_c_adjust_*.cpp 把 ClangAST → ESBMC IRep2 → GOTO。
  • 入口 clang_c_language.cpp:286+ 注册支持的标准：-std=c89 / c99 / c11 / c17 / c23 / c26。
  • libc/POSIX 通过 src/c2goto/library/ 的操作模型注入（19 个顶层文件，覆盖 stdlib/string/io/pthread/setjmp/locale/fenv/time/inet/getopt/complex 等），编译成 GOTO 二进制后链接。

2.2. 语法/语言特性覆盖

  • C 标准：C89 → C23（C26 已枚举但实际依赖 LLVM 版本）。
  • GCC 扩展：嵌套函数（nested_func_transform.cpp 专门走 lambda-lifting）、__attribute__((...))、__builtin_*（regression/clang_builtins/ 17 个子目录覆盖原子/位运算/常量预测）、VLA（github_1533_*）、复合字面量、designated initializer。
  • C11/C23：_Atomic（部分，clang_c_convert.cpp 中有 FIXME 标注表示原子类型表示尚未完整）、_Generic、_BitInt。
  • 浮点：regression/floats 共 83 个测试，覆盖 NaN/Inf/亚正规数等 IEEE754 corner cases。
  • 未支持/弱项：inline assembly（无 fallback，多半直接报错）。

2.3. 标准库 / 运行时模型

  • libc：见 src/c2goto/library/，包含 pthread/semaphore/setjmp/fenv/locale/complex/libintl/inet/getopt/time。
  • POSIX 覆盖：regression/esbmc-unix（298 测试）+ regression/esbmc-unix2（186 测试），合计 ~484 个 POSIX 用例。
  • Linux 内核驱动：regression/esbmc/31_cdaudio/main.c（8 822 SLOC，光驱驱动）、32_floppy/main.c（8 281 SLOC，软驱驱动）—— 能咬下真实 Linux driver 代码。

2.4. ESBMC 核心验证能力（在 C 前端下全部可用）

  • 指针/内存安全：--pointer-check --bounds-check --memory-leak-check
  • k-induction：~52 个 test.desc 显式启用
  • 函数契约（function-contract）、循环不变量（loop-invariant）
  • 并发：pthread 模型、--multi-property、--deadlock-check、--lock-order-check
  • 浮点验证（83 个测试）
  • Witness 生成与验证：regression/witnesses/ 与 regression/witnesses_validate/

2.5. 已知缺陷与未来计划

  • regression/esbmc 类别分布：CORE 1 113 / THOROUGH 123 / KNOWNBUG 19 / FUTURE 1 —— 已知缺陷率 ~1.6%，非常低。
  • 源码 TODO/FIXME/XXX 共 28 处。
  • 近 6 月 61 次 commit，方向偏向 C++17/20 配套设施（结构化绑定、CTAD、__builtin_bit_cast），纯 C 扩展的增量较少。

2.6. Scale（可验证规模）

  • 最大测试源：8 822 SLOC（Linux cdaudio 驱动）。Top 5 全部超过 5 000 SLOC（驱动、算法库、GitHub issue 还原）。
  • 没有 SV-COMP 完整 benchmark 套件，但有 regression/csmith、regression/cbmc 等借鉴外部测试集。

2.7. Soundness/Completeness 备注

  • 未识别构造倾向于 abort 而非过近似 —— 严格但偶尔会拒绝合法输入。
  • _Atomic、offsetof 基类成员、部分 C++ union 特性 TODO 中。

2.8. 结论

Industrial 偏成熟（约 60–70% 工业完备度）。指针/并发/浮点/k-induction/contract 一应俱全；能消化数千行真实 Linux 驱动代码。短板在 inline asm 与部分 C23 新构造。适用范围：POSIX 程序、多线程系统软件、驱动验证；规避：inline-asm 密集场景。

3. 2. CHERI-C 前端（C 前端扩展）

3.1. 原理

  • 不是独立前端，是 C 前端的能力延伸。命令行入口：--cheri {hybrid|purecap}（src/util/config.cpp 中注册）。
  • 数据模型在 src/util/config.h 定义 cheri_flavor {OFF, HYBRID, PURECAP}；capability 宽度 = address_width × 2（默认压缩）或 × 4（--cheri-uncompressed）。
  • 标准库存根：src/c2goto/cprover_library.cpp 预编译 hybrid/purecap 两套 libc（clib32/64_cherih/p）。
  • SMT 端：src/solvers/smt/smt_casts.cpp 处理 provenance 跟踪与强制转换。

3.2. 支持范围

  • 架构：MIPS64-EL、RISC-V64、ARM Morello (aarch64c)。
  • 变体：CHERI-128（默认）+ CHERI-256（未压缩模式）。
  • 模式：Hybrid（指针/能力混用）+ Purecap（仅 64 位）。
  • 属性：bounds、tag、permissions、sub-object bounds（-cheri-bounds=subobject-safe）。

3.3. Regression

  • regression/cheri-c：15 CORE + 1 KNOWNBUG（混合模式，典型用例 01_cheri_ptr1_failed、01_cheri_clear_tag_leak_failed）
  • regression/cheri-128：10 CORE + 1 KNOWNBUG（RISC-V64 big-endian，覆盖 hybrid/purecap）
  • regression/cheri-cpp：6 CORE（C++ hybrid）
  • 最大测试仅 46 SLOC —— 全是断言驱动的 toy 例子，没有真实 CHERI 项目（CheriBSD、cheri-libc 等）的 case study。

3.4. 已知缺陷

  • 1 个 KNOWNBUG（cheri-c/01_cheri_ptr5_failed）。
  • src/util/config.cpp 中有 CHERI-TODO：架构推导仍需手工 -target。
  • 不支持 capability revocation（无对应测试）。

3.5. 发布与定位

  • 论文：Brauße et al., “ESBMC-CHERI: towards verification of C programs for CHERI platforms”, ISSTA 2022 Tool Demo（3 页工具论文）。
  • 学术原型：演示性目的明确，未集成进 SV-COMP 等主流 benchmark。

3.6. 结论

Research prototype。框架完整、模式选项齐全（128/256 × hybrid/purecap × 多目标），但所有测试都是 ≤50 行的断言例子，缺乏真实项目验证经验。适合：CHERI 语义实验、教学；不适合：替代真实 CHERI 工具链做生产分析。

4. 3. CUDA 前端（C 前端扩展）

4.1. 原理

  • 同样复用 clang-c-frontend 解析，无 CUDA-specific AST 路径。
  • 核心是 src/cpp/library/CUDA/（18 个头文件 stub，8 374 行）提供 operational model：
    • call_kernel.h（600+ 行）：用 pthread 模拟 grid/block，宏 ESBMC_verify_kernel() 触发验证。
    • device_launch_parameters.h：把 threadIdx/blockIdx/gridDim 实现为查表，默认硬编码 2×2×2 grid 以压缩状态空间。
    • cuda_runtime_api.h：cudaMalloc/cudaMemcpy 包在 __ESBMC_atomic_begin/end 内做内存检查。
    • sm_atomic_functions.h（737 行）：atomicAdd 等原子原语模型。
    • 还包含 cublas.h、cudnn.h、curand.h 头存根（仅签名，验证不深入）。

4.2. Regression（132 个 .cu）

  • 类别：CORE 8 / THOROUGH 123 / KNOWNBUG 1 —— 几乎全靠 THOROUGH（Linux-only deep tests）。
  • 子目录：COM_sanity_checks (11)、Supported_long_time (43)、benchmarks (78)。
  • 代表测试：002_add_one_fail（atomicAdd race）、011_value_causing_race（跨线程数据竞争）、114_cudnn_conv（cuDNN 卷积建模，81 行）、113_curand_race_fail。
  • 最大源文件仅 113 SLOC —— CUDA 测试规模与真实 GPU kernel 完全不在一个量级。

4.3. 并发建模

  • 复用 pthread 模型，GPU 线程 = pthread。
  • 支持 --data-races-check，可检测跨 threadIdx.x 的别名冲突。
  • 缺 __syncthreads() 等 warp/block 级同步原语；线程交织受 ESBMC context-bound 限制。

4.4. 已知缺陷

  • 1 个 KNOWNBUG：benchmarks/099_test8，别名分析在设备代码中失效。
  • 无 cuBLAS/cuDNN 函数体验证（仅签名 stub）。

4.5. 结论

Research prototype。Operational model 设计较完整（CUDA 8.0 时代），但线程上限固定（默认 2 线程 × 2 block × 2 grid）、race detection 部分失效、无真实 kernel benchmark。适用：小规模 kernel 的内存安全/race 检测；不可用于大规模 GPU workload。

5. 4. C++ 前端（src/clang-cpp-frontend，5.9 K SLOC）

5.1. 原理

  • 复用 C 前端基础设施，叠加 C++ 专属 AST/typecheck（clang_cpp_convert.cpp + clang_cpp_adjust_* + clang_cpp_convert_vft.cpp + clang_cpp_convert_bind.cpp）。
  • STL/标准库通过 src/c2goto/library/（abstract_includes 目录与 cpp 子树）提供自有 OM 模型，不混用宿主 libstdc++/libc++（典型做法：-nostdinc++ + 注入自家头）。

5.4. Scale

  • 源码 TODO/FIXME 仅 14 处（质量较高）。
  • 近 6 月 32 次 commit，方向：VFT 合成、跨 TU 类视图、继承构造函数、noexcept 值依赖、deducing this。

5.6. 结论

Industrial（C++03 → C++20 的核心子集已就绪）。虚函数、多重继承、异常、STL 建模都到位，更新积极、KNOWNBUG 率 ~2%。短板：测试规模偏小（最大 454 行），C++23/26 尚处早期。与 CBMC 的 C++ 支持相比，STL OM 更深，最新标准更新更快。

6. 5. Python 前端（src/python-frontend，64.9 K SLOC，最大也最活跃）

6.1. 原理

  • Pipeline：.py → CPython ast 模块 + ast2json → JSON AST → 类型标注（python_typechecking.cpp、python_annotation.h）→ ESBMC IRep2 → GOTO。
  • parser.py 由 ESBMC 在 PATH 中调用 python3 执行，因此 regression 需要 ast2json 可用（venv 或系统 Python）。
  • Operational model 双层：
    • Python 侧：src/python-frontend/models/ 25 个 .py（builtins/math/cmath/re/random/collections/datetime/decimal/heapq/time/os/numpy/typing/enum/dataclasses…）总 16 K 行。
    • C 侧：src/c2goto/library/python/ —— list/dict/str/math 的 C 操作模型供 SSA/SMT 直接消费。
  • python_consteval.cpp 做编译期部分求值（包括循环展开/常量折叠），是 Python 前端独有的优化层。

6.2. 语言特性覆盖（参考 website/content/docs/python/supported-features.md + 实测）

已支持：

  • 控制流：if/elif/else、while、for + range()
  • 函数：定义/调用/*args/递归/lambda（单表达式）/闭包/global
  • OOP：单+多继承、__init__、实例/类属性、super()
  • 字符串：f-string（含 :d/:i/:.Nf 等格式说明符）、32 种方法、切片
  • 集合：list（append/pop/extend/sort 含 key=/sorted/reverse）、dict（完整 CRUD）、tuple（字面值/常量索引/切片/拼接/重复）、set（add/discard/issubset 等）
  • 异常：try/except/raise/9 个内建异常、exception binding
  • 类型提示：Union（宽化为单一类型，损失分支语义）、Any（朴素推理）、dataclass（基础）
  • with：支持但 __exit__ 返回 True 不会抑制异常（与 CPython 不一致）

部分/未支持：

  • generator/yield：只支持纯 generator expression 的 for x in gen:
  • 装饰器 @decorator：文档未明言（实际较弱）
  • async/await：仅 async with 反糖支持
  • match/case、frozenset、set comprehension、变量索引元组 t[i]：未支持

6.3. 泛型与类型注解处理

核心结论：ESBMC 接受所有泛型注解语法，但执行擦除式处理 —— 泛型参数和 TypeVar 完全不参与类型推导；类型分发由 PyObject tagged union 在运行时承担。注解非必须，但写具体非泛型注解能显著提升验证精度。

机制：

  • type_handler.cpp:376-383：遇到 list[T]、dict[K,V]、List[int] 等带 [...] 的注解，字符串截断 [ 之前的部分递归处理 list / dict 基类型；元素类型参数被完全丢弃 —— List[int]、List[str]、List[Foo] 在 IRep2 中完全无区别，都落到同一个 tag-struct __ESBMC_PyListObj（type_handler.cpp:929-936）。
  • type_handler.cpp:574-579：T = TypeVar("T") 被识别为”无具体类型”，直接返回 any_type()。约束 TypeVar("T", int, str)、bound=Foo、covariant=True 等高阶配置均被丢弃。
  • Generic[T] 基类被当成普通类处理；继承自 Generic 没有任何额外语义。

写法 → 实际编码：

写法实际编码验证精度
x: int = 5signedbv64（原生 BV 算术）最高
nums: list = []tag-struct __ESBMC_PyListObj，元素 PyObject*中：靠 type_id 标签分发
nums: list[int] = []同上（int 被丢弃）中：与 list 等价
T = TypeVar("T"); def f(x: T) -> TT 退化为 any_type()，等同 def f(x): return x低：跨调用点无类型绑定
class Stack(Generic[T])Generic 被忽略，Stack 当普通类低

关键代价：T 被擦成 Any 后，identity("hello") + identity(1) 这类类型上明显错误的代码不会在前端被拦 —— 能否验证取决于后续 + 在 tagged union 上的分发结果，而非泛型类型检查。

真实 regression：

  • typing_typevar/main.py：def identity(x: T) -> T: return x; assert identity(1) == 1 通过，本质是 T 已被擦为 Any，靠 1 自带的 type_id = PYTHON_INT 标签传递。
  • type-annotation-generics-pass/main.py：numbers: List[int] = [1, 2, 3] 通过，List[int] 被切成 List，int 信息从未被用上。

与 Java/Kotlin 的相似性：JVM 字节码层面 List<Integer> 和 List<String> 也是同一个 List（type erasure，见 §6）。Python 前端在这一点上和 JBMC 处理 Java 泛型思路完全一致 —— 擦除 + 运行时 dispatch；区别是 Python 的分发由 PyObject.type_id 在 SMT 层做，Java 是 JVM checkcast 字节码。

根本原因：IRep2 类型系统只有 16 个类（§7.1），无 template/generic 概念，所有高阶类型构造必须在前端擦除或在 OM 阶段用 tagged union 模拟。

实操建议：

  • 追求验证精度 → 写具体非泛型注解（int / float / bool / str）
  • 仅为可读性 → List[int] / Dict[str, int] 可写，但不要指望 ESBMC 据此报类型错
  • 真要泛型类型检查 → 交给 ESBMC 前先跑 mypy / pyright

关键文件：src/python-frontend/type_handler.cpp:376-383, 574-579, 929-936、src/c2goto/library/python/python_types.h:33-58

6.4. 标准库覆盖（OM 完整度从高到低）

  • 完全：math/cmath（32+ 函数 + IEEE-754 边界）、decimal、re（基础正则 .*、\d+、[a-z]+、(x|y)、字面量）
  • 良好：random（randint/random/uniform/getrandbits/randrange/seed/choice/shuffle/sample）、collections（defaultdict/Counter/deque/OrderedDict）、heapq、os.path、numpy（array/zeros/ones、elementwise add/subtract、部分 stub）
  • 极简：datetime（仅 datetime(y,m,d)）、time（time() 每次 +1.0 单调递增）、os（路径与目录基础操作，nondet 异常）

6.5. ESBMC 核心验证能力

  • assert：原生支持
  • nondet：__ESBMC_nondet_int()、random.* 模型
  • __ESBMC_assume()、__ESBMC_cover() 一应俱全（参考 docs/python/random-operational-model.md）
  • 异常路径验证
  • 缺：高阶模块间数据流/符号约束推理（无独立静态分析层）

6.6. Regression

  • regression/python：2 945 CORE + 248 THOROUGH + 9 KNOWNBUG（总 3 202）—— 是所有前端中 CORE 数最大的套件。
  • regression/python-coverage：13（coverage 用例）
  • regression/python-intensive：77 THOROUGH + 12 CORE + 1 KNOWNBUG（cmath 重负载）
  • 9 个 KNOWNBUG：dict65、concurrency_fail、shedskin、rover、mixed-types、github_4117*、cast —— 集中在并发、复杂类型混用、edge case 类型转换。
  • 最大测试：object_passing_comprehensive/main.py（457 SLOC，跨函数对象传递综合用例）。

6.7. 活跃度

  • 近 6 个月 463 次 commit —— 比 C/C++ 加起来还多 5 倍。
  • 近期方向：list.sort(key=)、set.add/discard/issubset、random.{seed,choice,shuffle,sample}、tuple slicing/concat/repeat、sorted(key=, reverse=)、models/ 整理。
  • 源码 TODO/FIXME 仅 14 处（活跃维护下数量保持低位）。

6.8. Soundness/Completeness 备注

  • python_consteval 的编译期部分求值可能”提前折叠”导致路径覆盖率下降 —— --goto-functions-only 可见已被求值的字面量。
  • Union 类型宽化（int|float → float）会丢失类型分支语义。
  • 不支持的构造：行为混合（有些 abort，有些静默 skip），需要 case-by-case 关注。

6.9. 结论

接近 Industrial（功能上比 Java/Kotlin 高一个数量级，比 CUDA/CHERI 高一个数量级；但还远未到 C/C++ 的”能咬下数千行 driver”水平）。强项：单文件序列程序、数学验证、异常路径、nondet+assume 组合；弱项：复杂 OOP（多态、metaclass、装饰器）、跨模块数据流、async、match/case、大整数。当前实际能力 ≈ Python 3.10 一个能用的”安全子集”。

8. 7. 数据结构与 Operational Model 设计 —— soundness/completeness 的真正瓶颈

这一章是前述前端评估的”地基”。IRep2 起源于 C，没有 dict/map/set/list/string 这些高阶类型；SMT-LIB 标准只规定 array、bitvector、float 三类核心理论。各前端要支持高阶数据结构，只能用 IRep2 已有的 struct/array/pointer/bv 把它们”降级”建模。建模选择直接决定 soundness（是否会漏报）与 completeness（是否会误报或拒绝合法输入）。

8.1. 7.1 IRep2 提供的类型原语

src/irep2/irep2_type.h 中所有可用的类型类只有以下 16 个（全部用 C 语义思考）：

类别类说明
基础bool_type2t, empty_type2t, symbol_type2t标量基元
整数unsignedbv_type2t, signedbv_type2t（基类 bv_data）定宽 bitvector
浮点floatbv_type2t, fixedbv_type2t, complex_type2tIEEE-754 / 定点
复合struct_type2t, union_type2t同 C 的 struct/union
序列array_type2t, vector_type2t定长 / 可变长数组
引用pointer_type2t指针 + provenance
函数code_type2t仅描述签名
C++ 元cpp_name_type2t名字解析占位

没有：dict/map、set、string、list、tuple、generator、ADT、sum type。所有这些都必须用上面 16 个原语拼出来。

8.2. 7.2 SMT 后端能给到什么

ESBMC 把 IRep2 进一步降到 SMT 理论 + bitblasting。在 src/solvers/smt/ 中：

  • array_iface（smt_array.h）：标准 (Array Index Element) 理论 + 一个 ESBMC 独有的开关 can_init_infinite_arrays（不是所有 solver 后端都支持）。
  • “Infinite array”（smt_conv.cpp:1469-1479, 2829, 3607-3629）：当 array_type2t::size_is_infinite=true 时，跳过具体长度约束，等价于”键域是机器字宽的可寻址 SMT 数组”。这是 ESBMC 用来表达 Solidity mapping(K=>V) 这类无界关联容器的核心机制。
  • smt_tuple_*：把 struct 投影成多个并行的 SMT 数组（用于 array-of-struct 等）。
  • 没有原生 string 理论：即便 Z3/CVC5 都有 string 理论，ESBMC SMT 层不使用它，所有字符串都走”字符数组 + 长度”路线。

关键事实：SMT-LIB 的 array 理论是足够强的（理论上能编码任何 map），但实际”infinite array”在 ESBMC 里只被 Solidity 前端深度利用。C/C++/Python/Java 前端都选择了”定长 C 数组 + 元数据”的工程化路线 —— 性能更可控，但带来了 7.4 节列举的 soundness 隐患。

8.8. 7.3.5 Python str

字符串字面值 → array_type2t(unsignedbv_type2t(8), n+1) 含 '\0'；动态字符串 → pointer_type2t(unsignedbv_type2t(8))。

有界长度由 __python_strnlen_bounded(s, ESBMC_PY_STRNLEN_BOUND) 强制（src/c2goto/library/python/python_types.h:8-9、string.c:1094）。ESBMC_PY_STRNLEN_BOUND = 256。超界触发 __ESBMC_assert(0, "string not null-terminated") —— 验证 abort，不会给出虚假 SUCCESS。所有 string method（split/replace/format/strip 等 32 种）都建立在这个 256 上限之上。

关键澄清（与初稿不同）：在 IRep2 阶段，char* __capability cap_ptr 依然落为普通 pointer_type2t(unsignedbv_type2t(8))，没有专门的 capability 类型类。capability 的解构发生在 SMT 层 (src/solvers/smt/smt_casts.cpp:349-396)。根据 config.ansi_c.cheri 的 flavor（OFF/HYBRID/PURECAP，src/util/config.h:122-129）和 --cheri-uncompressed 标志，SMT 后端把单个指针展开成等价的：

8.12. 7.3.9 Solidity mapping 与 Java/Kotlin 容器

Solidity mapping(K=>V)：通过 src/c2goto/library/solidity/solidity_mapping.c 直接生成一个 array_type2t 且 size_is_infinite=true，SMT 层走 (declare-fun m (Array K V)) 路径（smt_conv.cpp:2829）。这是所有前端中唯一真正用 SMT array 理论建模无界关联容器的实现。Solidity mapping 语义天然契合 —— 不可迭代、不能查 size，所以 SMT array 的”无 cardinality”刚好够用。

Java / Kotlin：src/c2goto/library/ 下没有 java/ 子目录，HashMap、ArrayList、String.format、Optional 等 JDK 容器完全没有 OM。Jimple frontend 遇到这些会发出未解析符号或 nondet 返回；要验证真实 Java/Kotlin 程序中超过纯算法/数组操作的代码基本不可能。
