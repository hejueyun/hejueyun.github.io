ProverB深度导读·第五章PV3-模型检验与CBMC谱系

2026-05-11

1. 第五章 · PV3：属性检查器——模型检验的黄金时代

终于到了你熟悉的世界。

PV3 的定义是”用户给一条属性，工具检查这条属性在程序/模型上是否成立”。
这正是教科书里”Model Checking”一章的定义，也是整个形式化验证社区
在 1981 到 2010 年代最闪亮的三十年。

1.1. 5.1 起点：Clarke–Emerson–Sifakis (1981) 与时序逻辑

1977 年，Amir Pnueli 在 FOCS 上发表了一篇题为
《The Temporal Logic of Programs》的论文——这是第一次有人把
时序逻辑 (Temporal Logic) 引入到程序验证里。之前人们用 Hoare Logic 描述
程序的输入-输出关系，但并发、反应式系统的核心性质不是”终态是什么”
而是”什么时候永远不会发生 X”或”从任何状态出发最终都能到达 Y”——
这些是时间上的量词，不是 Hoare Logic 能轻易表达的。
这篇论文让 Pnueli 后来拿了 1996 年的图灵奖。

插播：时序逻辑和命题逻辑是什么关系？

不是独立的两套东西,而是包含关系——时序逻辑是在命题逻辑之上加了一层时间算子。

  • 命题逻辑 只有原子命题 p, q, r 和连接词 ¬ ∧ ∨ →,描述的是
    “一个静态时刻的真假关系”。没有时间,没有状态迁移。
  • 时序逻辑 在此之上加了 □ ◇ ○ U(CTL 再加路径量词 A/E),描述的是
    “一条(或一棵)执行轨迹上,命题的真假如何随时间演化”。

你写 □(request → ◇response),最里层的 request、response 仍然是命题逻辑的原子;
去掉所有 □◇○U,时序逻辑就塌成普通命题逻辑。反过来,时序逻辑是命题逻辑的真扩展——
□p(“p 永远为真”)没法用任何有限的命题公式等价表达,因为命题逻辑里根本没有”时刻”这个概念。

这也解释了为什么本书里不同工具选的逻辑不一样——完全是”表达力 ↔ 自动化“的权衡:

工具类别代表底层逻辑为什么
SAT 求解器MiniSAT、Kissat纯命题逻辑决定性问题最小单元,NP-complete 但启发式极快,是一切上层工具的”汇编语言”
SMT 求解器Z3、CVC5命题 + 无量词一阶理论(整数、数组、位向量…)程序里要谈整数和数组,纯命题太底层;限制在 quantifier-free 片段保证可判定
BMCCBMC、ESBMC展开成命题/QF-SMT把循环展 $k$ 次后就退化成一段直线代码,天然是无时间的命题问题——BMC 的本质就是”用命题逻辑近似时序性质”,这也是它只能说”$k$ 步内安全”的原因
显式/符号模型检验SPIN(LTL)、SMV/nuXmv(CTL+LTL)时序逻辑要谈”请求最终被响应”、”永远不死锁”,命题逻辑根本写不出”最终”和”永远”,必须上时序算子
交互式证明助手Coq、Lean(依赖类型论);Isabelle/HOL(高阶逻辑);ACL2(一阶逻辑)高阶 / 依赖类型要证”对所有自然数 $n$…”这类带量词和归纳的定理,一阶都不够

两条值得记住的观察:

  1. BMC 是一座桥:顶层用时序逻辑描述问题,底层把 $k$ 步内的 LTL 语义
    编译成一条命题公式交给 SAT。正是 $k$ 这个界限把时序塌回了命题——
    所以 BMC 只能回答”$k$ 步内安全”,不能回答”永远安全”。
  2. SMT 扩展的是命题逻辑的”数据维度”,不是”时间维度”。
    SMT = SAT + 理论,加的是整数/数组/位向量,没有加时间。所以
    CBMC/Dafny/Why3 能查 assert x > 0 却不能直接查 □(lock → ◇unlock)——
    后者要么手工把时序语义展开成 SMT 约束,要么交给专门的模型检验器。

一句话总结:命题逻辑管”一瞬间”,时序逻辑管”一段时间”,一阶/高阶逻辑管”所有情况”。
每个工具选哪层,取决于它要回答的问题天生属于哪一层——下层快但表达力弱,
上层强但要么放弃自动化(证明助手),要么付 PSPACE 的代价(模型检验)。

先插入两个你后面会反复碰到的概念——Safety 和 Liveness：

  • Safety（安全性）：”坏事永远不会发生。”
    比如”程序永远不会访问数组越界”、”两个进程永远不会同时在临界区”、
    “账户余额永远不会变成负数”。Safety 的特征是：
    如果它被违反了，你可以在有限步内发现（一个反例就是一条有限的执行轨迹）。
  • Liveness（活性）：”好事最终一定会发生。”
    比如”每个请求最终都会收到响应”、”被阻塞的进程最终都会被调度”、
    “协议最终都会达成一致”。Liveness 的特征是：
    如果它被违反了，你需要看无穷长的执行才能确认（有限前缀永远不够判定）。

这个区分非常重要，因为不同工具能查的性质类型不同：
CBMC/ESBMC 只能查 safety（有界展开能发现的有限反例）；
SPIN 既能查 safety 也能查 liveness（通过检测无穷执行中的接受环）。
这是选择工具时的一个关键判断标准。

Pnueli 提出的时序逻辑就是用来精确表达这类性质的数学语言。
他提出的是 LTL (Linear Temporal Logic，线性时序逻辑)——
它把程序的执行看成一条无穷长的状态序列（”线性”的意思），
然后用四个时间操作符来量化”什么时候发生什么”：

操作符读法含义例子
□ p (always)“永远 p”在此刻以及此后的所有时刻，p 成立□(balance ≥ 0)：”余额永远非负”
◇ p (eventually)“最终 p”在此后的某个时刻，p 会成立◇(response)：”请求最终会被响应”
p U q (until)“p 直到 q”p 持续成立直到 q 变成立(waiting) U (served)：”等待直到被服务”
○ p (next)“下一步 p”在下一个状态，p 成立○(ready)：”下一步就绪”

Safety 性质在 LTL 里通常长成 □ ¬bad（”坏状态永远不发生”）；
Liveness 性质通常长成 □(request → ◇ response)（”每次请求最终都有响应”）。

1981 年 Edmund Clarke 和他的博士生 Allen Emerson 在美国，Joseph Sifakis 在法国，
几乎同时且独立地提出了”模型检验”这个词：
给一个有限状态系统 M 和一条时序逻辑公式 φ，自动判定 M ⊨ φ。
这项工作让他们三个分享了 2007 年的图灵奖。

Clarke 和 Emerson 用的逻辑不是 LTL，而是 CTL (Computation Tree Logic，计算树逻辑)。
LTL 把执行看成一条线；CTL 把执行看成一棵分叉的树——
在每个状态你可能走向不同的后继，所以 CTL 多了”路径量词”：
A（所有路径都满足）和 E（存在某条路径满足）。
比如 AG ¬deadlock 表示”沿所有路径、在所有时刻都没有死锁”——
这里 A = “所有路径”，G = “所有时刻”（相当于 LTL 的 □）。

LTL vs CTL 的快速区分：LTL 更适合描述单条行为轨迹上的性质
（”这个请求最终会被响应”），SPIN 用 LTL；
CTL 更适合描述状态上的全局性质（”从任意状态出发都能回到初态”），
SMV/nuXmv 用 CTL。大部分安全性质两者都能表达；区别主要在活性和分支性质上。

还有一种更强大的逻辑叫 ATL (Alternating-time Temporal Logic)，
它额外引入了”玩家”概念——“联盟 A 的玩家有没有一个策略，
无论对手怎么走，都能保证 φ 成立？“这在多智体系统（博弈、协议、多方交互）
里非常有用，但 ATL 的模型检验复杂度更高，目前在 ProVerB 收录的工具里还不多见。

最早的 CTL 模型检验器运行在几千个状态上——对真实程序完全没用。
转折点是 1986 年 Ken McMillan 在博士论文里提出的 符号模型检验 (Symbolic Model Checking)：
用 BDD 表示状态集合而不是枚举状态。他把这个思路做成了 SMV，
一举让可处理的状态数从 $10^5$ 推到 $10^{20}$。
BDD 的底层数据结构实现就是 ProVerB PV0 里那个 CUDD——地基又回来找你了。

ProVerB 里 SMV 的现代后代是 nuXmv（ProVerB 归 PV4）——
FBK 的 Alessandro Cimatti 团队在 NuSMV 基础上做的，加入了无限状态和 SMT 后端。
你用 nuXmv 写 SMV 语言的模型，它帮你检查 CTL/LTL 属性。

1.2. 5.2 显式状态一派：SPIN 与它的 Promela 语言

和 SMV 走符号路线不同，Bell Labs 的 Gerard Holzmann 从 1980 年代开始做另一条路线——
显式状态模型检验。工具叫 SPIN，模型语言叫 Promela。

SPIN 的气质是”我不装聪明，我老老实实枚举全部可达状态”——
但它有一系列非常聪明的工程手段（偏序归约、状态压缩、位状态哈希）
让显式枚举能到达 $10^{10}$ 级别的状态空间。
SPIN 被用来验证过 Mars Pathfinder 的调度器、Curiosity 的文件系统、
以及一堆通信协议。它现在在 ProVerB 里被归到 PV5，
因为用户需要用 Promela 写一个系统模型——你不是在验证 C 代码，
你是在验证你对 C 代码行为的一份”抽象表述”。

这是一个重要的思维转换：

模型检验有两种用法——
一种是”我把真实代码转成可检验的形式”，这属于 PV3；
一种是”我用一门专门的语言重写了系统的关键部分”，这属于 PV5。

UPPAAL、TAPAAL、PRISM、Storm 都属于后者——它们检查的是你用它们自己的建模语言写的模型，
所以 ProVerB 把 UPPAAL 归到 PV5，把 PRISM 归到 PV3（PRISM 的语言能直接吃 MDP 描述）。
边界不是一刀切的，ProVerB 自己也承认这点。

1.3. 5.3 一次倒戈：Bounded Model Checking (1999)

讲到这里你会问：那 CBMC 怎么还没出场？

1999 年，当时在 Carnegie Mellon 跟着 Clarke 做博士的 Armin Biere
（是的，后面搞 Lingeling/CaDiCaL/Kissat 那个 Biere）写了一篇叫
《Symbolic Model Checking without BDDs》的论文。
它提出了一个大胆的想法：不用 BDD，直接用 SAT。

思路是这样的：

  1. 给一个系统 M 和一条 LTL 属性 φ，问”M 在 k 步内是否存在反例”。
  2. 把 M 的 k 步展开（unroll）拼成一个大逻辑公式。
  3. 把 ¬φ 在 k 步内的表达也拼进这个公式。
  4. 整个公式送给 SAT 求解器。如果 SAT ⇒ 找到反例；UNSAT ⇒ k 步内无错。

这就是 Bounded Model Checking (BMC)。

BMC 的”倒戈”之处在于：它主动放弃了完备性——它不证明”永远不出错”，
只证明”在 k 步内不出错”。但换来的是完全不用写不变量，
而且可以直接吃非常复杂的系统（因为 SAT 求解器 2001 年以后已经不是瓶颈）。

这个取舍值得停下来讲一下。传统模型检验像是给你一只广角镜头——
它试图一次看完所有可达状态；而 BMC 像是换成了一只显微镜——
它只看接下来 k 步里会发生什么，但看得极其清晰，bit 级精确。
1999 年之前硬件验证社区一直嫌 SAT 太慢、搞不定广角镜头这种大活，
但 Biere 的那篇论文本质上在说：”那就别搞广角镜头了，换个显微镜也挺好——
反正你真实的 bug 大部分在前几十步内就会显形，为什么非要枚举到无穷远？”
这个心态上的翻转比算法本身更重要。它等于告诉后面一代人：
“不完备”不是羞耻——不完备但能跑的工具比完备但跑不动的工具有用一百倍。
CBMC/ESBMC/JBMC 整个家族的商业成功都是建立在这句话上的。

CBMC 就是 Biere、Clarke、Kroening 他们把这套思路从硬件搬到 C 代码的产物。
CMU 团队 2003–2004 年第一次发 CBMC 的论文（你在 ProVerB 的 CBMC 页面能看到
那条《A Tool for Checking ANSI-C Programs》，2004 年的 TACAS）。
它做的事情很简单但很划时代：

  1. 把 C 代码”展开”成一个无循环、无递归、无别名歧义的”平坦”中间表示（GOTO 程序）。
  2. 把所有的 C 语义（位运算、有符号/无符号、指针、数组）bit-precisely 编码成公式。
  3. 把这个公式送给 SAT 或 SMT 求解器。
  4. 返回 counterexample trace 或”k 步内无错”。

ProVerB 的 CBMC 页面一句话抓住了它的核心内部：

“Loop unwinding / Bounded model checking / SAT solving”

ProVerB 把 CBMC 归到 PV3，因为它的核心工作模式是用户控制要查什么性质——
你用 assert(...) 在代码里写下你关心的断言，CBMC 就查这个断言。

但必须说明：现代 CBMC（5.x）实际上自带了大量内置检查开关，无需用户写任何 assert：
--signed-overflow-check、--unsigned-overflow-check、--bounds-check、
--pointer-check、--div-by-zero-check、--memory-leak-check、
--float-overflow-check、--nan-check、--undefined-shift-check、
--conversion-check、--enum-range-check 等等——
打开这些开关后，CBMC 的行为其实很像 PV4：”我有一套内置的检查清单，我替你跑”。

那为什么 ProVerB 仍然把 CBMC 归到 PV3 而不是 PV4？区别不在”有没有内置检查”，
而在有界 vs 归纳：CBMC 做的是有界模型检验，展开 k 步之内穷搜，
它能说”在 k 步内找到了 bug”或”在 k 步内没找到 bug”，
但它不能说”证毕——对所有 k 都成立“。
用户始终需要自己选择 --unwind k，并对 k 够不够大做出判断——
这份判断责任留在用户手里，是 PV3 的标志。
相比之下，ESBMC 的 k-induction 能自动递增 k 并最终输出 proof，
不再需要用户猜 bound，这才是它滑向 PV4 的真正原因。

1.4. 5.3.5 从代码到逻辑：两条翻译路线

现在我们知道了 CBMC 在做”把 C 代码变成 SAT 公式”这件事。但具体怎么变？

这个问题比看起来重要。从 C 到逻辑的翻译方式不是唯一的——你选什么样的翻译管线，
决定了你整个工具的气质：能查什么 bug、看不见什么、需要用户提供多少配合、
给用户多强的承诺。PV3 和 PV4 里几乎所有的设计分歧，追到根上都可以追到翻译策略。

我们先把 CBMC 这一条路走一遍，然后对比 Dafny/Why3 走的另一条完全相反的路。

1.4.1. 问题本身：验证器的眼睛是逻辑，不是代码

所有 PV3/PV4 工具最终都要和 SAT/SMT 求解器对话——而求解器的输入是逻辑公式（CNF 或 SMT-LIB），
不是 C 代码、不是 Java 字节码、不是 Rust。所以每一个”吃代码”的验证器内部都必须藏一个
翻译器，负责把”人类写的带 if/while/指针/struct 的代码”变成”求解器认识的一组公式”。

这个翻译器的架构会暴露工具的整个世界观。它要回答一连串不中立的问题：

  • int 翻译成无限精度的数学整数，还是精确的 32 位位向量？
  • 用户要写断言（assert），还是写契约（pre/post/invariant，即 Design by Contract 里的”契约式设计”——和前文 PV 层级里的”约定”是同一回事，只不过这里它落到了函数签名层）？
  • 一次性把整个程序展开成一个大公式，还是分模块各证各的？
  • 循环怎么办——展开？归纳？不变量？

这些选择中的每一个都不是中立的工程决定，而是一种立场。
CBMC 选了一组非常极端的立场，我们称之为”低空翻译“——紧贴 ISA 语义，
不做任何哲学上的抽象，相信硬件是唯一的真相。

是对这个难题的工程式回避：”我不要你写不变量，你告诉我展开多少次就行。”
这是一个经典的”用蛮力换自动化”取舍：它让普通工程师用得起 CBMC，代价是永远不能声称”证毕”。

回到我们的无循环例子，继续第三步。

1.4.2.3. 第三步：SSA（赋值变方程）——整个管线的灵魂

这是 CBMC 内部最精妙、也最违反直觉的一步。

在命令式代码里，y = 1 和 y = x + 1 是两个不同时间的赋值，
同一个变量名 y 在不同时间代表不同的值。可是逻辑公式里没有”时间”——
如果把它们直译成 y = 1 ∧ y = x + 1，会立刻被求解器判成 x = 0，这显然不是代码的本意。

SSA（Static Single Assignment） 的做法简单得令人发笑：
给每一次赋值一个新名字。 y 变成 y₁、y₂、y₃……每个版本只赋值一次。
这样一来命令式代码就变成了一组没有时间概念的数学等式。

汇合之后的 y。SSA 把这三件事分开命名之后，整段代码就变成了四条同时成立的等式。

这一步是整个翻译管线的魔法核心。
变量有了版本之后，命令式程序突然丢掉了”先执行再执行”的时间序，
变成了一个纯数学对象——一组约束。从这一刻起，”程序”和”逻辑公式”的边界消失了。

顺带说一句：GCC、LLVM 在做编译器优化时用的也是 SSA——那是 1988 年 Rosen/Wegman/Zadeck
那篇论文引入的。验证和优化在 SSA 上是同一件事的两面：
优化问的是”这组等式能被怎么简化”，验证问的是”这组等式再加上断言的否定，能不能同时满足”。
一个 IR 服务两个目的不是巧合——是因为 SSA 已经把程序变成数学对象了，
接下来你想干什么随你。

工程注解：symex = unwind + SSA。
我上面为了讲清楚把”循环展开”和”SSA 重命名”拆成了第二步和第三步，
但在真实的 CBMC 源码里它们是同一个阶段，叫 goto-symex，也就是符号执行
（symbolic execution）。symex 从 GOTO program 的入口开始静态地走一遍每一条语句：
遇到循环就按 --unwind k 展开，遇到赋值就分配一个新的 SSA 版本，遇到分支就 fork
出一条带 guard 的路径，最后吐出一组带 guard 的 SSA 等式交给后端。

注意这里的”符号执行”和 KLEE 那种”动态符号执行”不是一回事——
KLEE 是真的在解释器里跑程序、遇到分支时调 SMT 求解器决定走哪边；
而 CBMC 的 symex 是静态的路径编码，不跑程序，直接把所有可能路径一起塞进一个大公式。

这也解释了一个常见的混淆：ESBMC、JBMC、SolCMC 并不是”比 CBMC 多了一步 symex”——
它们都有 symex，goto-symex 最早就是从 CBMC fork 出来的。
ESBMC 真正的差异在 symex 之后那一步：它从一开始就是 SMT-first
（名字里的 “S” 就是 SMT），内置检查开得更激进，而且叠了 k-induction
把”k 够不够大”这件事自动闭合掉——这才是它从 PV3 滑到 PV4 的根本原因。

这在数学上对，但在 C 上错。CBMC 抓到这个 bug 不是因为它比你聪明，
而是因为它拒绝做任何数学抽象——它只相信 bit。

这一刻你就完全理解了 CBMC 的哲学内核：

程序的”真相”不是程序员想要它做什么，而是编译器和 CPU 把它解释成什么。
形式化验证要对齐的是后者，不是前者。

如果你接受这个立场，那 CBMC 的每一个设计决定——GOTO 扁平化、unwinding、SSA、bit 级编码——
都是从这一条根长出来的。

如果 CBMC 是”低空贴地飞行、盯着每一个 bit”，那 Dafny 和 Why3 走的就是完全相反的路——
“高空飞行、信任程序员的契约、用数学对象建模“。

1.4.4. Boogie 和 Why3：高空管线的”LLVM”

Dafny 并不直接生成 VC。中间有一层叫 Boogie——微软在 2005 年前后由
Rustan Leino 抽出来的一个专用中间语言。Boogie 看起来像一种极简的命令式语言，
但所有的命令式构造都有对应的 wp 规则。Dafny 先把自己翻译成 Boogie，
再由 Boogie 负责 VCGen，最后把 VC 送给 SMT 求解器。

法国的 INRIA 有一个平行的东西叫 Why3（以及它的子语言 WhyML），功能几乎一样，
但生态不同：SPARK（Ada 的可验证子集）和 Frama-C 的 WP 插件背后跑的都是 Why3；
而 Dafny、VCC（微软的 C 验证器）、F* 背后跑的是 Boogie。
它们是”高空翻译管线”世界里两个竞争的中间层标准。

用一个类比：

如果 SAT/SMT 求解器是 CPU，那么 Boogie 和 Why3 就是 LLVM IR。

它们让多种前端语言（Dafny、SPARK、Frama-C、F*……）共享同一套 VCGen 后端。
没有这一层中间语言，每一个验证器都要自己实现一遍 wp 演算，工作量会爆炸。
正如没有 LLVM，每一个编译器都要自己实现一遍寄存器分配和指令选择。

这也解释了 ProVerB 为什么把 Why3 归到 PV2 而不是 PV4——它页面上的关键句是
“can generate correct OCaml programs”。Why3 不仅仅是 VC 生成器，它还能把验证过的
WhyML 程序提取成可执行的 OCaml 代码。它的定位更像一个带证明的编译器，
所以才落到了 PV2（合成器）那一栏。
Boogie 则没被单独列进 ProVerB，因为它是 Dafny/VCC 的内部组件，普通用户不直接用。

1.4.5. 两条路线的并排对照

现在把两条翻译管线并排放一起，差异就全显出来了：

维度CBMC 路线（低空）Dafny/Why3 路线（高空）
输入真实 C / C++ / Java 代码带契约的程序（Dafny/SPARK/Frama-C…）
中间语言GOTO programBoogie / WhyML
关键变换Unwinding + SSAVCGen（最弱前条件）
整数语义32/64 位 BitVec，会溢出数学整数，不溢出
数组语义连续内存 + 指针算术映射函数 int → T
用户写什么assert(...)requires / ensures / invariant
循环怎么办展开 k 次，k 用户给用户写不变量，工具用归纳
能发现 x+1 溢出吗？天生就查只有你显式声明 bv32 才查
能证链表反转的逆是原链表吗？几乎做不到（递归数据结构对 BMC 不友好）这正是它擅长的
输出强度“k 步之内没找到反例”“证毕，对所有合法输入成立”
背后 SMT 逻辑QF_BV + QF_AQF_LIA + 量词 + 未解释函数
擅长的 bug 类型内存安全、溢出、指针、并发功能正确性、数据结构不变量、算法等价性
典型失败模式k 不够大，漏 bug不变量写不出来，证不出来
PV 层次CBMC = PV3；ESBMC = PV4Dafny = PV4；Why3 = PV2（气质偏 PV5）

两条路线最深的分歧可以用一句话讲清楚：

CBMC 相信：”程序 = ISA 上的 bit 行为”——真相在硬件里，工具要做的是忠实地复刻硬件。

Dafny/Why3 相信：”程序 = 程序员契约的一份实现”——真相在契约里，工具要做的是证明代码兑现了契约。

一条路线把 bit 当真相，一条路线把契约当真相。这不是技术偏好的差异，
是认知立场的差异。

1.4.6. 为什么两条路线都不能被对方取代

你可能会想：”高空路线看起来更’数学’，是不是’更对’的那条路？”不是的。

两条路线面对的是两种不同的问题：

  • CBMC 擅长的场景：你手头有一段已经写好、跑了很多年的 C 代码——
    Linux 内核的某个子系统、一个路由器固件、一个车载 ECU。
    你不想也不可能让开发者回去补上 pre/postcondition。
    你想要的是”这段代码有没有 memory bug、有没有溢出、有没有指针悬挂”。
    你要的是贴着真实代码、bit-precise、不需要用户写契约的 bug finder。
    CBMC 家族就是为此而生的。

  • Dafny 擅长的场景：你正在从头写一个关键算法——分布式共识协议、密码学原语、
    一个数据结构库。你愿意花时间写契约，因为你要的不是”没找到 bug”这种弱保证，
    而是”对所有合法输入永远成立“的数学证明。
    你要的是和程序员一起建立契约层、证明功能正确性的伙伴。
    Dafny 就是为此而生的。

两者在工业界常被组合使用：

  • Amazon 的 s2n-tls（TLS 实现）用 SAW / Cryptol 做密码层的全功能证明，
    而周边的 C 代码用 CBMC 做持续 memory-safety 审计。
  • 微软 Hyper-V 的关键组件 2008 年前后用 VCC（Boogie 后端）做过全功能证明，
    而同期整个 Windows 内核也一直用 SLAM/SDV（CBMC 家族思路的早期工具）做驱动审计。
  • Mozilla SpiderMonkey 用 CBMC 家族做 JIT 代码的溢出审计；
    一些关键的密码学模块则用 hacl* / F*（Boogie 家族）做全功能证明。

它们在同一个系统里分工，而不是互相替代。

1.4.7. 回到 PV 层次

这套翻译管线的差异恰好解释了 ProVerB 为什么把这些工具放在不同的 PV 等级：

  • CBMC（PV3）：用户用 assert 直接指定要查什么——用户掌握菜单，经典 PV3。
  • ESBMC（PV4）：在 CBMC 基础上加了内置检查清单（--overflow-check 等）
    和 k-induction（自动递增 k 直到证明）——
    用户不再掌握菜单，工具有固定范式，滑进 PV4。
  • Dafny（PV4）：契约是用户写的，但翻译到 Boogie 再到 VC 的全流程是固定的——
    用户不能更换”证明策略”，只能调整契约。这符合 PV4 的”内置范式 + 自动兜底”定义。
  • Why3（PV2）：因为它能从验证过的 WhyML 提取 OCaml 代码——是一个合成器的气质。
    但如果你只看 VC 生成能力，它其实非常 PV5（用户写自己的规约语言 WhyML）。
    ProVerB 这里的分类有点勉强——真实的 Why3 横跨 PV2/PV4/PV5 三层。

这也回答了本章开头埋下的问题：”PV3 和 PV4 的分界究竟在哪里？”

分界不在”能不能找到 bug”，而在”翻译管线的结尾是否自动 close 掉用户判断”。

CBMC 把 k 留给用户决定 ⇒ PV3。
ESBMC 的 k-induction 把 k 自动闭合 ⇒ PV4。
Dafny 的 VCGen 对用户完全不可见、不可调 ⇒ PV4。

这不是一条清晰的分界线——它是一条灰度边界，由工具”向用户借了多少判断”决定。
越往 PV4 走，工具向用户借的判断越少、代价是灵活性越小；
越往 PV3 走，灵活性越大、代价是用户要扛更多。

理解了这一层，后面看到 SPARK、Frama-C、VeriFast、KeY 的时候，你就可以自己问一个问题：
“这个工具走的是低空路线还是高空路线？它的翻译管线结尾把哪些判断留给了用户？”
答案几乎总能告诉你它在 PV 里的位置。

1.5. 5.4 CBMC 的孩子们：ESBMC、JBMC、SolCMC

ESBMC 是 CBMC 的一个 fork——更准确地说，是一个以 CBMC 的 GOTO 前端为起点
重新实现了后端的独立工具。它的名字里 “E” 是 SMT 的”S”倒过来……其实是
“Efficient SMT-based”。ESBMC 最初由 Federal University of Amazonas 的 Lucas Cordeiro 团队做，
后来 Manchester 也加入了。

为什么 ProVerB 把 ESBMC 归到 PV4 而 CBMC 归到 PV3？这是一个值得注意的判断。
看 ESBMC 页面的关键句：

“ESBMC v6.0 employs a k-induction algorithm to both falsify and prove safety properties”

“--interval-analysis enables invariant generation”

“--memory-leak-check、--overflow-check“

也就是说，ESBMC 不再单纯依赖用户写 assertion——它内置了一组”你不写我也要查的性质”
（内存泄漏、溢出、空指针），并且会自动生成不变量**。
（公平地说，现代 CBMC 也有类似的内置检查开关如 --signed-overflow-check、--memory-leak-check 等，
在这一点上两者的差距比 ProVerB 2022 年的分类暗示的要小。）

但真正把 ESBMC 推向 PV4 的是 k-induction：它不只是在有限步内找反例，
而是能自动递增 k 并尝试归纳证明——如果成功，输出的是”证毕“，
而不是 CBMC 的”在 k 步内没找到 bug（但 k+1 步呢？你自己判断）”。
按 ProVerB 的约定定义，这份”用户不需要判断 k 够不够大”的保证就从 PV3 滑到了 PV4。

PV3 和 PV4 的分界线，不仅是”谁来决定查什么”，更是”工具能不能在不依赖用户判断的情况下给出完备的回答”。

JBMC 是 CBMC 的 Java 版，同样 PV3。Pinaka 也是 CBMC 家族但走不一样的并发建模。
至于你熟悉的 SolCMC（旧称 SMTChecker）——它在 ProVerB 里有自己的页面（proverb/solcmc.html），
但它的定位大致对应”PV3 的智能合约版本”：用户在 Solidity 里写 assert / require，
SolCMC 把函数体翻译成 Horn Clauses 或 BMC 公式送给 Z3/CVC5/Eldarica。
血统上它是 CBMC 思想 + Horn 求解器（见 PV4 的 Spacer/GSpacer）的混合。

1.5.2. SolCMC vs Certora：同一条赛道上的两种约定

SolCMC 和 Certora Prover 都用来验证 Solidity 智能合约，但它们站在 ProVerB 分级的不同位置。

SolCMC 是 PV3 风格——你在合约代码里写 assert，编译器帮你查。
规约和代码混在一起，学习门槛几乎为零（加一行 assert 就行），
但你能表达的性质有限——基本上只有”这个函数在任何调用序列下不会违反这条断言”。

Certora 是 PV5 风格——你用一门独立的规约语言 CVL (Certora Verification Language)
写一个单独的 .spec 文件，和合约代码分开。CVL 支持量词、ghost 变量、参数化规则、
跨函数不变量这些 assert 表达不了的东西。Certora Prover 把 CVL 和 Solidity 字节码
一起编译成 SMT 公式送 Z3。

  • SolCMC 的 assert 写在合约里面，只能表达”这个函数此刻此地此条件”
  • CVL 的 rule 写在合约外面，能跨函数、带量词、引用 ghost 状态

Certora 由 Tel Aviv 大学的 Mooly Sagiv 联合创办（2018），
Sagiv 在静态分析和抽象解释领域有深厚积累（TVLA、形状分析），
CVL 的设计受 JML (Java Modeling Language) 和 Design by Contract (Eiffel) 影响。
后端用 Z3，和 SolCMC 一样——但 CVL 给了用户远超 assert 的表达能力。

在 ProVerB 的地图上：SolCMC ≈ PV3（用户写断言），Certora ≈ PV5（用户写规约语言）。
它们验证的是同一种程序（Solidity 合约），但约定等级不同——
Certora 要求你学 CVL，代价更高，但能保证的东西也更多。

1.6. 5.5 PV3 的其它方向

模型检验在过去十年长出了三条新的分支，ProVerB 都记在了 PV3 里：

  • 符号执行 (Symbolic Execution) 一派：KLEE (Stanford，Cristian Cadar 2008)、
    SPF (Java PathFinder 的符号模式)、JDart、COASTAL、JPF、JavaRanger。
    符号执行不 unfold 整条路径，而是沿着具体执行路径收集约束再送 SMT。
    它和 BMC 是两种不同的路径探索策略，但后端都是 SMT。
  • 概率模型检验：PRISM (Birmingham)、Storm (RWTH Aachen)、STAMINA、Modest。
    这一派检查的不是”会不会出错”而是”出错的概率是多少”。
    数学对象是 Markov 链 / MDP / CTMC。
  • 神经网络验证：Marabou (Stanford)、DNNV、nnenum、Verisig、ERAN。
    2017 年 Reluplex 是这个方向的奠基之作——它是一个专门为 ReLU 激活函数
    改造的 Simplex 算法，能在 SMT 框架下判定”给定输入扰动，网络输出是否保持类别”。
    Reluplex 后来被 Marabou 吸收。你可以把这个方向看成”CBMC 的 NN 版本”，
    但它的数学更接近线性规划。
  • CEGAR 驱动的模型检验：BLAST (Berkeley)、SLAM (Microsoft)、CPAchecker (LMU Munich)。
    这是 PV3 里最重要的一条算法主线，值得单独展开。

CEGAR（CounterExample-Guided Abstraction Refinement，反例驱动的抽象精化）
是 Clarke 团队 2000 年前后提出的元算法，专门为了解决 PV3 的核心矛盾：

真实程序太大，无法直接模型检验；但粗糙的抽象又会产生假警报（spurious counterexamples）。

CEGAR 的解法是把精化过程本身自动化：

形象地说：先做便宜的初筛，初筛报警了再用这个警报决定下一步精查哪里。
不是一上来就做全精度检查，而是让反例来”指路”，每轮只在有意义的地方加精度。

这条线的工业化代表是微软的 SLAM 项目（Tom Ball、Sriram Rajamani，2001）：
他们把 CEGAR 用于 Windows 驱动验证，检查”API 使用顺序是否正确”（比如 Lock 必须配对 Unlock）。
SLAM 后来演变成微软内部的 SDV（Static Driver Verifier），
写 Windows 驱动的程序员每次提交代码时编译器顺手跑的那个静态检查就是它。

注意 CEGAR 在 PV3 和 PV4 里都有身影，但语境不同：

  • PV3（这里）：BLAST/SLAM 用 CEGAR 检查用户指定的属性（API 顺序、指定的断言）
  • PV4（第六章）：CPAchecker/Ultimate 用 CEGAR 做内置范式的全自动验证，用户不需要指定属性

CEGIS（PV2）和 CEGAR（PV3/PV4）共享同一个”反例驱动”的直觉，但方向相反：
CEGIS 用反例来收紧综合搜索空间（我要找一个没有反例的程序）；
CEGAR 用反例来收紧抽象的精度（我要找一个足够精细的模型）。
