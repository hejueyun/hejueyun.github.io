1. 第 6 章　SMT 后端 —— 把 SSA 方程编码为可判定公式

到这一步我们手里有一个 symex_target_equationt，里面是几千条形如
“x@1#3 := ite(cond, x@1#2, x@1#1)“或”ASSERT cond@1#7“的 SSA 步骤。
要让 SMT 求解器吃下去，必须把这些 expr2tc 树翻译成 SMT 求解器能理解的 AST。

本章把这道翻译流水拆成十节：从总入口、连接方式，到具体 theory 的实现，再到求解、模型读回与反例。
读完本章可以回答两个看似简单却经常被低估的问题：

  • “无界数组、嵌套结构体、字节级访问这些 C 习语，在 SMT 层是怎么变成可判定公式的？”
  • “ESBMC 究竟是怎么接上 solver 的？是 fork 出一个进程喂 SMT-LIB2 文本，还是直接调 solver 的 C/C++ API？两种都有，本章会回答 哪一种、在什么时机、为什么。”

1.1. 6.1 章前知识：SMT 求解器、SMT-LIB 标准与库/二进制双形态

第 2 章已经粗略介绍过 SMT 的概念（”带量词的一阶逻辑里挑出来的可判定片段”）。
但要看懂本章下面 lowering 的细节，还有几个工程层面的基础事实绕不开。
这一节就是把这些”业内默认知识”集中讲一次。

1.1.1. 6.1.1 SMT 求解器是什么样一个东西？

把 SMT 求解器（如 Z3、Bitwuzla、CVC5）想成一个**”会做位向量 / 数组 / 浮点判定的代数引擎”**：
你扔给它一份”变量 + 公式”的描述，它告诉你这份描述是否有解（sat / unsat），
有解时还能告诉你每个变量取什么值（model）。

从工程角度看，每个主流 SMT 求解器都是一个 中等规模的 C/C++ 项目——比如 Z3 大概几十万行 C++，
内部包含：

  • SAT 内核（CDCL）
  • 各 theory 的求解模块（位向量、数组、UF、FP……）
  • 简化器、tactic 系统（Z3 特有）
  • 一份 SMT-LIB2 标准的解析器
  • 一份对外的 C/C++/Python/Java/.NET API

关键事实：当你 apt install z3 或在 ESBMC 的 CMake 里看到 Z3 found，得到的从来不是单一文件。
你装下来的至少有这么几个东西：

文件用途
z3 (binary)命令行可执行程序：从 stdin 读 SMT-LIB2 文本，向 stdout 输出 sat/unsat/(model …)
libz3.so / libz3.a共享库 / 静态库：把 Z3 的全部功能以 C ABI 暴露出来
z3.hC 头文件：声明 Z3_mk_bv_sort、Z3_solver_check 等几百个函数
z3++.hC++ 封装：把 C API 包成 z3::context、z3::expr、z3::solver 等 RAII 类
z3.dll + z3.libWindows 版本
Python / Java / .NET 绑定跨语言用

换句话说，Z3 既是一个程序（binary），又是一个库（library）。
Bitwuzla、CVC5、Boolector、MathSAT、Yices 也是同样的形态——
它们的项目都同时构建出一个 CLI 二进制和一个共享/静态库。

用户在命令行手敲 SMT-LIB2 时用的是前者：

而 ESBMC、Boogie、Dafny、CBMC 这类”用 SMT 当后端的工具”则绕开 binary 路径，直接链接库。
两条路最终调到的是 同一份算法代码，但接合面完全不同。

1.1.2. 6.1.2 SMT-LIB 标准：求解器的”通用字节码”

SMT-LIB 是由 SMT 社区于 2003 起维护的一套文本格式 + 语义标准（当前版本 v2.6）。
它有两个层次：

  1. 语法：用 S-表达式写的命令序列，类似 Lisp。
  2. theory + logic：标准化的 sort（类型）名、函数名、量词约定。
    一份具体公式的 logic 写在文件第一行的 (set-logic ...) 里，
    告诉求解器”这份公式属于哪个可判定片段”。

常见 logic 名（前缀 QF_ 表示无量词）：

Logic含义
QF_UF等式 + 未解释函数
QF_LIA线性整数算术
QF_BV位向量（机器整数运算）
QF_ABV位向量 + 数组（下标也是 BV）
QF_AUFBV上面再加 未解释函数
QF_FPBV浮点 + 位向量（IEEE-754）
QF_AUFBVFP全活：BV + Array + UF + FP，ESBMC 默认用这个
AUFBV去掉 QF_ 前缀 = 带量词版本（不可判定）

1.1.3. 6.1.3 一份公式从 ESBMC 走到求解器：两条路

到这里 6.1.1 的”binary vs library”和 6.1.2 的”SMT-LIB 文本格式”就拼起来了：
求解器既然有两副面孔，工具调用它就也有两种连法。

路径 A — 链接库（in-process）：ESBMC 在编译时通过 -lz3 把 libz3.so 链到自己的 binary 里。
运行 ESBMC 时，求解器作为共享库的一部分和 ESBMC 活在同一个进程里、用同一份堆。
“提交一个公式”是普通的 C++ 函数调用：

没有任何文本！x + x 这个表达式直接是 Z3 内部 AST 节点的 C++ 包装，
solver.check() 调用进入 libz3.so 后执行 Z3 的算法。
全程没有进程间通信，没有字符串序列化，所以速度比文本快得多。

路径 B — fork 出 binary（subprocess）：ESBMC fork() 出一个子进程，
通过 execlp 让它跑 z3 -in 之类的 CLI 工具，
然后用两根管道（pipe）做双向通信：父进程往子进程的 stdin 写 SMT-LIB2 文本，
从 stdout 读 sat/unsat/(model …)，再用 Flex/Bison 解析回来。

这条路是 smtlib_convt（solvers/smtlib/）走的，仅当你显式加 --smtlib 才启用。
它的好处：

  • 求解器没装库、只有 binary也能用（如某些研究原型）；
  • 兼容任何遵守 SMT-LIB2 的求解器；
  • 可以把完整的 SMT-LIB2 dump 出来，方便人工调试与跨求解器复现。

代价：序列化开销 + 解析开销 + 进程通信，通常慢一个数量级。
6.3 节会把这两条路对应的代码细节摊开。

1.1.4. 6.1.4 库从哪来：CMake 怎么把求解器拉进来

CLAUDE.md 里那行神秘的 -DDOWNLOAD_DEPENDENCIES=On 此刻可以解释了：

  • 打开（默认 On）：CMake 通过 scripts/cmake/SolverZ3.cmake 等模块，
    用 FetchContent / ExternalProject 从 GitHub Release 抓预编译的 Z3、Bitwuzla 等，
    解压到 build/_deps/ 下，再把头文件路径与 .a / .so 喂给链接器。
    这是 ESBMC 推荐的方式——版本固定，避免系统包不同步带来的奇怪 bug。
  • 关闭：CMake 改用 find_package(Z3) / find_library，去系统的 /usr/lib、/usr/include 找 libz3-dev。
    如果系统包版本太老（Z3 < 4.8 之类的），会编译失败。

链接发生在 ESBMC 最终可执行文件 esbmc 生成阶段。
跑 ldd build/src/esbmc/esbmc 你会看到：

——libz3.so 就在那里。ESBMC binary 启动时由动态链接器加载它，从此 z3::context ctx; 这一行
就能合法构造。ESBMC 不需要单独的 z3 二进制，除非用户加了 --smtlib --smtlib-solver-prog z3。

所有这些”具体怎么找 / 怎么编 / 怎么链”的 CMake 模块在 scripts/cmake/ 下：

1.1.5. 6.1.5 接下来几节的阅读地图

带着上面四个事实再回到本章后面，每一节就更容易定位：

6.3与求解器的接合面把 6.1.3 的”两条路”展开成代码

6.5元组接口SMT-LIB 没有 struct——ESBMC 怎么把它造出来

6.8内存模型pointer_struct + addr_space_arr 在 SMT 里的形态

无论走哪条路，对求解器讲的”语言”都是同一套 SMT 概念：sort、term、assert、check-sat。
区别只在于这套概念是以文本字符串还是 C++ 对象的形式传递。

小结：本节灌进来的几个事实——

  1. SMT 求解器是带 SAT 内核与多个 theory 的引擎；
  2. 它有 binary 和 library 两副面孔；
  3. SMT-LIB 是文本通用语；logic 名（如 QF_AUFBV）声明片段类别；
  4. ESBMC 默认链接库走 in-process，仅 --smtlib 用 binary + pipe；
  5. 这些库由 CMake 在 -DDOWNLOAD_DEPENDENCIES=On 时自动拉取并链入 ESBMC binary。

后面 6.2 之后每一节都会用到这五件事中的某一件，记不住可以回来对照。

它是所有具体 solver 适配类（Z3、Bitwuzla、Boolector、CVC5、MathSAT、Yices、SMTLIB）的抽象基类。
最重要的入口是 convert_ast（同文件 188 行）：

smt_astt 是 const smt_ast * 的别名（src/solvers/smt/smt_ast.h:29），
它是一个 handle——抽象意义上的”SMT 节点的引用”，具体内部装着什么由每个 solver 自己决定。
convert_ast 递归地把任何 expr2tc 表达式转化成一个 smt_astt，主体逻辑在 src/solvers/smt/smt_conv.cpp:1336：

逐行解读：

  • 缓存（第 1 步）：smt_cache 用 expr2tc 的指针/哈希做键。
    因为 SSA 方程里同一个子表达式（特别是常量、地址符号）会被引用上千次，缓存能砍掉一个数量级的工作量。
    缓存条目还记录”是在哪一层 push_ctx 时插入的”，pop_ctx 时会按层级清理（见 6.10.1）。
  • 白名单跳过自动 lowering（第 2 步）：有些节点的语义不是”先算 operand 再合成”。
    例如 address_of(x) 不应该先把 x 转成 SMT 值——x 是一个 左值，
    我们要的是它的”对象 ID + 偏移”，不是它当前的数值。这些节点在第 3 步里走另一条专门的处理路径。
  • 派发（第 3 步）：剩下的就是按 expr_id 调虚函数。
    mk_add / mk_bvadd / mk_select 等几十个虚函数都在 smt_convt 的抽象接口里声明，
    各 solver 子类提供具体实现。这是经典的 模板方法 模式：
    一份 lowering 框架，七个 solver 共用。

smt_convt 的构造函数（src/solvers/smt/smt_conv.cpp:69）在求解器还没接好的时候就先建立了内存模型骨架：

注意这里就在构造时就建立了两个关键结构：

  1. pointer_struct：一个 { pointer_object, pointer_offset } 的元组类型，
    用来在 SMT 层表示 C 指针。每个 C 指针都是一个 对象 ID + 字节偏移 的元组。
  2. addr_space_type / addr_space_arr_type：每个对象在地址空间里有 start 和 end，

这两个结构本身只是 type2tc 描述——它们对应的 SMT sort 要等到 6.5 节的 tuple / array 接口决定怎么落地。
这也是为什么构造函数无法立刻把它们注册进 solver：tuple/array 接口的选择要发生在 create_solver 中。

入口函数 create_solver（src/solvers/solve.cpp:135）的逻辑非常直白：

  1. factory 工厂：每个 solver 一份。create_new_z3_solver 在 z3_conv.cpp:12 里

这种”接口可插拔”的设计让 ESBMC 同一份 lowering 代码能对接七种 solver，每种又有几种降级模式。

SMT-LIB2 后端：唯一一个 不 走原生 API 的，是 smtlib_convt。
它的工作方式是 fork 一个子进程，把 SMT-LIB2 文本通过 pipe 喂进去，再从另一根 pipe 读取响应。
看 src/solvers/smtlib/smtlib_conv.cpp:200~266：

之后 ESBMC 把每个 mk_* 调用都格式化成一行 SMT-LIB2 文本（emit_terminal_ast 等函数），
最后发 (check-sat) 并 flush()。子进程的输出用 Flex/Bison 生成的扫描器 + 解析器（smtlib.ypp / smtlib_tok.lpp）读回。

这种方式的两个好处：

  • 任何兼容 SMT-LIB2 的 solver 都能用（包括没有 C 头文件的）；
  • 可以把整个生成的 SMT-LIB2 公式 dump 到文件用于调试 / 复现。

代价是显而易见的：文本序列化、进程通信、解析开销，通常比原生 API 慢一个数量级。
所以 SMT-LIB2 后端在 pick_default_solver 的优先级排序里被特意跳过（solve.cpp:68），
默认不会选它。

题外话：这正是为什么 ESBMC 默认 不 推荐 --smtlib——除非要把公式喂给 ESBMC 没适配的 solver
（或者就想用文本格式调试）。
也是为什么 pick_default_solver 会在 all_solvers 数组里把 smtlib 跳过。

1.4. 6.4 数组接口：有界数组 vs 无界数组的 lazy 化身

数组是 SMT 编码中开销最大、最容易”爆炸”的那一块。
ESBMC 在 src/solvers/smt/array_conv.{h,cpp} 里实现了一个完整的 array flattener，
可以在 solver 没有数组 theory（如某些只支持 QF_BV 的小 solver）时把数组展开成一组个体变量；
即使 solver 原生支持数组，ESBMC 也会用它来处理”很大或无界”的数组，避免一次性给 solver 制造天量约束。

入口函数是 array_convt::mk_select 和 mk_store（array_conv.cpp:135 / 177）：

1.4.1. 6.4.1 有界数组（bounded）

is_unbounded_array 的判定标准非常朴素（array_conv.h:23）：domain 宽度 ≤ 10 位就算有界。
这是因为 2^10 = 1024 个元素以内，”把数组直接展开成 1024 个独立 SMT 变量”在性能上还划得来，
而且能让 solver 用上简单高效的位向量推理。

1.4.2. 6.4.2 无界数组（unbounded）—— 真正的 lazy axiomatization

当 domain 宽度 > 10（典型如 bv32、bv64，对应 int / size_t 索引的真实大数组，或符号大小的堆数组），
“一次性生成 2³² 个变量”是疯狂的做法。这时进入 mk_unbounded_select（array_conv.cpp:223）：

逐步解读：

  • 第 1 步：记账。每个 base 数组都维护一份 它被访问过的所有下标集合 array_indexes[base_id]。
    这是后续 Ackermann 化 的依据：等到把所有约束发给 solver 时，ESBMC 会对每两个不同的下标加入
    “若 i = j 则 a[i] = a[j]”的等式，让数组的函数性（functional consistency）只在”实际被访问过的下标”之间成立。
  • 第 2 / 3 步：本地缓存。这两步是简单优化，能让 *p 紧跟 *p = v 的情况短路出去。
  • 第 4 步：发放 fresh 变量。对一个全新的 (array_snapshot, idx) 对，
    ESBMC 不知道它的值是多少——可能等于某次 store 的值，也可能是数组原始的初值——
    所以分配一个 fresh BV 让 solver 去赌。add_new_indexes 与 apply_new_selects
    会在合适的时机把这些 fresh 变量与历史 store 串起来。

mk_unbounded_store（array_conv.cpp:283）则更复杂一点：每次 store 都产生一个”新版本”
（array_update_num 递增），并不修改源数组——这与 SSA “每次赋值都是新版本”的精神一致。
array_updates[base_id] 是一条 更新链表：每条记录或者是一次普通 with（{idx, val}），
或者是一次 array-ite（合并两条不同的更新历史，对应 phi）。

1.4.3. 6.4.3 等待结算：add_array_constraints_for_solving

无界数组的所有 select / store 都只是先记账，并没有立刻生成约束。
真正的约束生成发生在 pre_solve（也就是 dec_solve 即将调用时）：
add_array_constraints_for_solving 把记下的更新链与 select 集合编织成
“对每个 select：它的值 = 沿着更新链一直追溯到 base array，找到第一个匹配下标的 store 的值，否则 = 初值” 的约束。

这种 lazy 风格的好处：

  • 不预先承诺数组大小——对真正大或大小未知的数组（堆分配、int[N] with N nondet）唯一可行的做法；
  • 稀疏地展开——只为程序里 实际访问过 的下标生成约束，避免无意义的 2³² 个公式；
  • 支持 SSA 版本演化——多个数组版本并存时各自维护更新链，phi 合并就是另一个 update 记录。

与 CBMC 不同：CBMC 历史上更倾向 eager bitblast；ESBMC 选择 lazy 化方式，让 solver 可以利用增量地选择性展开。

1.6. 6.6 量词消除：为什么 ESBMC 发给求解器的公式是 QF_…

到这里我们已经看了三件事：位向量是怎么编出来的（6.2）、数组是怎么编出来的（6.4）、struct 是怎么拆平的（6.5）。
但如果你打开任何一个 SMT-LIB 输出文件（用 --smtlib --output some.smt2 试试），
你会发现文件顶部的 logic 声明长这样：

——QF_ 是 Quantifier-Free 的缩写，意为”这份公式里没有 ∀ 和 ∃”。
事实上 ESBMC 几乎所有内部产物都属于这种”无量词片段”，
具体可能是 QF_BV / QF_ABV / QF_AUFBV / QF_FPBV / QF_FPABV 等等，
但前缀都是 QF_。

为什么非要无量词？
在位向量理论里，带量词 的版本（BV）是不可判定的（带量词的位向量可以编码 Diophantine 方程）；
而 QF_BV 是 NP-完全但可判定的。求解器对 QF 片段有一整套高度优化的判定算法
（SAT-style 的 CDCL、bit-blasting、preprocessing），速度远超量词版。
ESBMC 想”几秒钟出结果”，就只能在 QF 上玩。

但 C 程序里”看起来需要量词”的地方比比皆是：

语义层面”原本需要”的量词含义
for (int i=0;i<N;i++) a[i]=0; 之后的循环不变式∀k ∈ [0,N). a[k] == 0
int f(int x) { return x*x; } 的语义∀x. f(x) == x*x
数组的 select/store 公理∀a ∀i ∀j ∀v. select(store(a,j,v), i) = ite(i=j, v, select(a,i))
别名分析的潜在结论∀p. (p == &x ∨ p == &y) → ...
用户写的契约 __ESBMC_forall(&i, P(i))∀i. P(i)

ESBMC 的”消除量词”绝不是某个集中的”量词消去算法（QE）”调用，
而是把这件事分散到整个管线的关键设计选择里。下面把这五种来源逐个拆掉。

1.6.1. 6.6.1 循环：把 ∀k 展成有限合取（BMC 的根本承诺）

最经典的来源——也是 BMC 名字 Bounded 的来由。考虑：

完整地刻画循环语义需要量化：

但 ESBMC 不去构造这个公理；它选择走 bounded unwinding 路线：

每次复制 PC、guard、value-set 完整推进一遍。

这正是 BMC “sound for bounded depth, incomplete in general” 的本质——
量词被消掉的代价是覆盖范围被截断了。

你可以把 BMC 的全部哲学概括成一句话：
以”丢失对超过 k 步的覆盖”为代价，把∀换成有限的∧。

1.6.2. 6.6.2 函数：内联 + 递归展开

函数语义同样自然带 ∀：
“对任意输入 x，f(x) 返回 x*x“。但只要函数 被调用，

要么 emit unwinding assertion，要么直接 ASSUME false 终止该路径——

总结：消除量词的五种工具

  1. 循环展开（symex 主循环）—— ∀ 迭代 → 有限 ∧
  2. 函数内联（symex_function_call）—— ∀ 输入 → 调用点特化的 SSA
  3. 数组 Ackermann 化（array_convt）—— ∀ 下标 → 出现过的下标对实例化
  4. value-set 静态枚举（pointer-analysis）—— ∀ 对象 → 有限 ite 链
  5. 求解器原生 ∀（mk_quantifier）—— 仅给 __ESBMC_forall 等用户契约用，退路

前四件事在 symex 与 SMT 编码阶段 就被吃掉了——
你在最终送给求解器的公式里看不到任何量词痕迹，
所以那行 (set-logic QF_AUFBV) 不是骗你的。

1.8. 6.8 内存模型在 SMT 层的体现

第 5 章我们看到 dereference 怎么把 *p 展开成对每个候选对象的 guarded 读写。

src/solvers/smt/smt_memspace.cpp 实现了与内存模型相关的所有谓词：

  • convert_ptr_cmp（32 行）：指针比较。
    两个指针先比较 pointer_object：相同则比较 pointer_offset；
    不同则按”两个 object 的 start 地址”比较——这要查 addr_space_arr_type 数组。
  • convert_pointer_arith：指针算术。
    p + i 不改 pointer_object，但 pointer_offset 加 i * sizeof(*p)。
  • convert_address_of：取地址。
    返回一个 (obj_id, 0) 元组，其中 obj_id 是该对象在 pointer_logic 表里的编号。
  • init_addr_space_array / bump_addrspace_array：每出现一个新对象，
    就在 addr_space_arr 这个 SMT 数组里 store 一个 (start, end) 条目。
    finalize_pointer_chain 同时 emit “新对象不与任何已有对象重叠” 的约束，
    保证 SMT solver 选出的对象地址在语义上是合理的。

每个静态对象在 SMT 里被建模成一个独立的 SMT 数组（flat_array_api 视角下），
按字节索引：obj_k : Array(bv32, bv8)。
写入 *p = 1 实际上是为每个 candidate 对象生成
obj_x_new = ite(p == &x, store(obj_x, off, 1), obj_x)。

1.9. 6.9 浮点：原生 FP theory vs 软件 bit-blast

ESBMC 对浮点（float、double、long double）的处理有两种模式，由 6.3 节描述的 fp_api 是否非空决定：

  1. Native FP：Z3、Bitwuzla、CVC5、MathSAT 都支持 SMT-LIB 的 FloatingPoint theory，
    它们直接 implement fp_convt，mk_smt_fpbv_add 就是一行调 solver 的 mk_term(FP_ADD, ...)。
  2. 软件 bit-blast (fallback)：Boolector、Yices 没有 FP theory，或用户加了 --fp2bv，
    则使用 fp_convt 基类（src/solvers/smt/fp/fp_conv.cpp）的默认实现，
    它把 IEEE-754 加减乘除全部 手写 成位向量级别的电路——
    解包符号 / 指数 / 尾数 → 对齐 → 算 → 规格化 → 舍入 → 重新打包。

来感受一下 bit-blast 路径有多麻烦——这是 mk_smt_fpbv_add 的开头（fp_conv.cpp:1231）：

unpack、round、mk_rounding_decision、mk_leading_zeros……
全部是 fp_convt 的 private 帮手。整个 fp_conv.cpp 1700+ 行的代码全是这种”手工搭建 IEEE-754 电路”，
本质上就是 ESBMC 自己用位向量 再实现一遍 SMT-LIB 的 FloatingPoint theory，
免得 Boolector 之类的轻量 solver 没办法处理浮点程序。

ESBMC 还有更激进的 --use-fixed-for-float：直接用 fixed-point 数近似 IEEE-754，
精度有损但公式小很多——适合需要快速跑通的场景。

  • ASSERT step → 收集到一个”待否定”列表里。

若结果是 UNSAT，则所有 assert 都不可被违反，VERIFICATION SUCCESSFUL。
若是 SAT，求解器返回的模型给出了那条让 assert 失败的具体执行；

  2. 该函数遍历 target 上所有 SSA step：
    • 对 ASSIGNMENT：从 solver 读 rhs_ast 的具体值（smt_convt::get，内部按类型分派到 get_bv / tuple_get / get_array_elem）；
    • 对 ASSERT：检查 cond_ast，若为 false 标记为”违反点”；
    • 对 ASSUME：若条件假则忽略此 step（路径不可达）；
  3. 输出可读的 trace（按 GOTO 程序的 location 反向定位到源代码行）。

1.10.1. 6.10.1 push/pop 与增量求解

很多策略（incremental BMC、k-induction 的三路验证）需要多次 dec_solve，
每次只增量地添加几条约束。smt_convt::push_ctx / pop_ctx（smt_conv.cpp:175 / 231）做的就是：

子类（如 z3_convt::push_ctx）会在调完基类之后再调 solver.push() / solver.pop()，
把 push 命令同步给 native solver——这样 solver 内部也按”层”管理自己的 asserts。
增量求解的好处：保留 solver 已经学到的 lemma，下一轮只需要 增量 推理新加的约束，避免重头算。

小结：SMT 后端不只是一个递归翻译器。它在 smt_convt 这一层提供了 lowering 框架与缓存；
在 tuple_iface / array_iface / fp_convt 三个可替换接口上覆盖了 SMT 没有原生提供、
或 solver 没有支持的 theory；并通过 create_solver 的 接口可插拔 机制
把同一份 lowering 代码接到七种 solver、两种连接方式上。
push/pop 让多轮增量求解高效；最后通过 get 把 SAT 模型解码成人能读的反例 trace。

2. 第 7 章　BMC 与 k-induction 主驱动

前面六章拼起来已经是一条完整的”程序 → SMT → 结果”管线。
但 ESBMC 真正灵活之处，在于它能用不同的验证策略反复跑这条管线：
增量 BMC、k-induction、Falsification、Termination ……
本章看这一切的总调度。

2.1. 7.1 总入口：esbmc_parseoptionst → bmct

打开 src/esbmc/main.cpp:8，整个 ESBMC 的 main 只有几行：

真正干活的是 esbmc_parseoptionst（src/esbmc/esbmc_parseoptions.h:26）。
它负责：

  1. 解析命令行参数（--unwind、--z3、--k-induction 等）；
  2. 解析源文件，构建 GOTO 程序，跑完 transformation 流水线；
  3. 按选定的策略反复创建 bmct 实例，驱动 symex → SMT；
  4. 汇总结果，打印 trace。

bmct（src/esbmc/bmc.h:22）一次只做一轮：固定 unwind 次数、做一遍 symex、跑一次 SMT。
反复创建 bmct 让多 k 步策略变得简单——每个 k 一个 bmct。

三个核心函数的语义：

    本质就是普通 BMC。找到了 → SAT → 报反例。

    如果不可能（UNSAT），归纳完成——证毕。

2.4. 7.4 incremental-bmc 与并行模式

Incremental BMC 是最朴素的策略：
固定 k 从小到大地试，每次都跑一次 base case。
找到反例就停；找不到（UNSAT）继续增大 k——
直到 max_k 或超时。
这种模式找 bug 速度快但永远证不了程序正确（除非 forward condition 已成立）。

k-induction parallel 模式（esbmc_parseoptions.cpp:852）则启动三个子进程，
让 base / forward / inductive 三路同时跑。
谁先得出确定性答案，就把其他两路 kill 掉。
这是工程上换取 wall-clock 时间的常见手法。

Termination 是 forward condition 的纯净版：
只关心循环是否必定终止，不关心是否安全。

Falsification 是 base case 的纯净版：
只关心找反例，不试图证程序正确。
适合做模糊测试样式的 bug hunting。

当 SAT 出现时，bmct::error_trace 调用 build_goto_trace 完成 trace 重建。
传统输出是带源行号、变量值演变的可读文本：

对接 SV-COMP / GraphML 工具链时，

小结：BMC 主驱动是 ESBMC 的”指挥官”。
它根据策略反复创建 bmct 实例，每个 bmct 都是一次”症 → SSA → SMT → 判定”。
k-induction 三路裁决让 BMC 不再只是 bug finder，而是可以证程序正确的形式化方法。
反例打印则把 SMT 模型反向解码成可读的 trace，完成 程序员 ↔ 求解器 之间的翻译。
