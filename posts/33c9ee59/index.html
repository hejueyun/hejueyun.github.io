Agent 安全·沙箱篇·隔离到哪一层，以及怎么逃出去

2026-11-17

本文是「Agent 安全」系列的第 5 篇（共 10 篇）。这个系列讲 agent 和它的外壳（harness）自身 的安全：它会被怎样骗、怎样越权、怎样把数据带出去，以及怎样防。前置阅读：AI 安全常见风险·提示词篇、Agent Harness 拆解·序章（上）。

  1. 总览篇·agent 比聊天机器人多了什么风险
  2. 注入篇·藏在网页、文件和工具结果里的指令
  3. 外泄篇·数据是怎么被带出去的
  4. 工具篇·权限、确认疲劳与借刀杀人
  5. 沙箱篇·隔离到哪一层，以及怎么逃出去（当前）
  6. 供应链篇·插件、MCP 服务器与技能包
  7. 记忆篇·被污染的记忆、摘要和子 agent
  8. 行为篇·模型自己好心办坏事
  9. 防御篇·把防线搭成几层
  10. 实战篇·给一个 coding agent 做安全加固

工具篇 讲的是「一条命令该不该执行」。这一篇换一个问题： 命令已经执行了，它能碰到什么。 权限确认看的是命令写成什么样，沙箱管的是命令跑起来以后的后果。前者会被绕过，后者是兜底。

1　沙箱是什么：命令看着无害，后果才是问题

沙箱不管命令写成什么样，只管命令跑起来以后能碰到什么。

示例：一次普通的跑测试

示例：你让 coding agent（会自己读代码、改代码、跑命令的编程助手）修一个测试失败的问题。几天前，有人给这个仓库提交过一个合并请求（别人提交给项目、请求合并进去的一组代码改动），顺手改了测试脚本，在里面加了两行：读取你电脑上的云服务凭据文件，再把内容发到一个陌生网址。

接下来：

  • agent 想确认修复有没有效，请求运行 npm test（运行项目测试的常用命令）。
  • 你看了一眼，这是再正常不过的命令，点了允许。
  • npm test 去执行测试脚本，那两行跟着一起运行。
  • 凭据（证明「我是我」的东西，比如密码、密钥、令牌）被读出来，发到了攻击者的服务器上。这就是 外泄：数据被送到攻击者手里。

看你批准的那一行：你批准的是命令文本，干坏事的是命令背后的文件

为什么权限确认拦不住

问题不在你粗心。你批准的是 npm test 这几个字符，干坏事的代码藏在它调用的文件里。 一条命令能做什么，从命令文本上看不出来。 跑测试、构建、装依赖，这些最常用的命令恰恰都会执行仓库里的代码。

而 agent 默认以 你的身份 运行。进程就是一个正在运行的程序；agent 启动的每个子进程（由它启动的程序）都继承你的全部权限：

  • 能读你家目录（存放你个人文件的文件夹）里的一切；
  • 能用你保存在电脑上的各种登录凭据；
  • 能访问任何网站。

沙箱：一个只能碰到指定东西的小房间

沙箱 就是把程序关在一个只能碰到指定东西的小房间里。房间里的程序照常运行，墙决定它碰得到什么。对 agent 来说，墙主要管三件事：

  • 文件：能读哪些目录，能写哪些目录。
  • 网络：能不能联网，能连哪些地址。
  • 系统能力：能不能启动别的程序、改系统设置、使用危险的系统功能。

有了沙箱，上面那两行照样会运行，但它们读不到凭据文件，也连不上陌生网址。 沙箱不阻止坏代码运行，它让坏代码运行了也没用。

同一个进程：左边碰得到你能碰到的一切，右边只碰得到项目目录

补充

  • 沙箱不只防攻击者。模型自己也会犯错，比如误删一个目录（行为篇 会讲）。同一道墙对两种情况都有效。
  • 资源也可以算进墙里：限制内存、处理器和运行时间，防止一个死循环把机器拖垮。
  • 沙箱和权限确认是两道不同的防线。确认管「做不做」，沙箱管「做了能碰到什么」，要一起用。

2　隔离的几层：从换个用户到换台机器

各种沙箱的区别，在于房间里的程序和外面的系统还共用多少东西；共用得越多，墙越薄。

示例：同一段脚本，放进不同的房间

示例：还是那段恶意测试脚本。它想做三件事：读你的私钥，联网发出去，再借一个系统漏洞跳出房间。把它依次放进下面六种环境，每往下一层，它能做成的事就少一些，搭建和运行的成本也高一些。

先解释两个词：

  • 内核：操作系统最底层的部分，管文件、网络、进程和内存。
  • 系统调用：程序想读文件、想联网，都要请内核帮忙。系统调用就是程序递给内核的申请单。

由浅到深的六层

第一层：换一个操作系统用户。 给 agent 建一个单独的低权限账号。这个账号读不到你的私人文件。但网络完全不管，系统里人人可读的文件它也能读。

第二层：进程级策略。 不换账号，直接给进程加规则。常见的有三种：

  • seccomp：Linux 内核的一个功能，给进程一张系统调用白名单，名单外的申请单直接拒绝。
  • Landlock：Linux 较新的一个功能，让程序给自己和子进程划定能访问的目录，不需要管理员权限。
  • Seatbelt：macOS 自带的沙箱机制，用一份规则规定进程能读写哪些路径、能不能联网。

这一层很轻，不用装别的软件，启动几乎没有开销。一些编程助手在本机跑命令时就用这类机制。缺点是规则要写对， 漏写一条就是一个洞。

第三层：容器。 容器（比如 Docker）用 Linux 的 命名空间 让程序看到一个独立的小世界：自己的文件树、自己的进程列表、自己的网络。再用控制组（限制资源用量的内核功能）管住它能用多少内存和处理器。但是， 所有容器和宿主机共用同一个内核。宿主机就是容器所在的那台真实机器。

第四层：gVisor。 Google 开源的一个「用户态内核」，也就是一个用普通程序身份运行、自己实现了大部分系统调用的内核替身。容器里的程序以为在跟内核说话，其实在跟 gVisor 说话。真内核只需要应付 gVisor 发来的少量请求。

第五层：微虚拟机。 比如亚马逊开源的 Firecracker。每个沙箱是一台精简的虚拟机， 有自己独立的内核，靠处理器的硬件虚拟化功能和宿主机隔开。它启动很快，适合每个任务单开一台。

第六层：远程沙箱。 命令根本不在你的电脑上跑，而是在云端一台临时机器里。你电脑上的文件，它一个都看不到。

从上往下读右边一列：和宿主共用的东西越来越少，墙越来越厚，成本也越来越高

这六层各挡住了什么

回到那段脚本：

  • 第一层：挡住了读私钥（前提是私钥文件的权限设对了），挡不住联网。
  • 第二、三层：配置得当时，读私钥和联网都能挡住，挡不住内核漏洞。
  • 第四、五层：把内核漏洞这扇门缩小了，或者换成了另一个内核。
  • 第六层：你电脑上有什么，已经无关了。但 你放进云端的东西 照样在房间里，比如令牌（一串代表你身份的字符，拿着它就能以你的名义调用服务）。

套在哪里：整个 agent，还是每条命令

选好了层级，还要决定墙罩住谁。常见的有两种套法：

  • 整个 agent 都关进去：外壳、模型调用、所有工具都在同一个容器或虚拟机里运行。墙内外分得很清楚，但 agent 用不了你本机的很多工具。
  • 只罩住它跑的命令：外壳在你的电脑上正常运行，只在执行 shell 命令时，给那条命令单独套一层策略。用起来顺手，一些本机运行的编程助手就是这样做的。

第二种套法有一个容易漏的地方。外壳往往还自带一些工具，比如「读文件」「改文件」「抓网页」。 这些工具由外壳自己执行，不经过 shell，也就不在命令的那层墙里。

示例：沙箱规则禁止命令读你的 SSH 私钥。被注入的模型不去跑命令，而是直接调用外壳自带的「读文件」工具。外壳检查的是「这是不是一条需要沙箱的命令」，答案是否，于是照常读了出来。

上面那条路被墙挡住，下面那条路绕开了墙：自带工具必须套用同一套规则

所以，只罩命令时，外壳自带的每个工具都要套用 同一套 路径和网络规则。否则墙上等于留了一扇侧门。

补充

  • 各层可以叠加。比如 Docker 默认就给容器加一份 seccomp 规则，挡掉一批很少用、风险又高的系统调用。
  • 越往下隔离越强，但启动越慢，和本机工具配合也越麻烦。本机开发常用第二、三层；在云端给陌生人跑代码，常用第四到六层。
  • 深的层级也有自己的代价。gVisor 没有实现全部系统调用，个别程序在里面会跑不起来；微虚拟机需要处理器的虚拟化功能，有些云主机默认不提供；远程沙箱则要把代码和数据传上去，网络慢时体验会差。
  • 「沙箱」这个词在不同产品里指的东西差别很大。看到「支持沙箱」，要问清楚是哪一层、默认开不开、管不管网络。

3　文件和网络：真正要画的两条线

沙箱最常见的漏洞不是墙不够厚，而是只拦了写、没拦读，或者只管了文件、没管网络。

示例：一个「只防写」的沙箱

示例：某个 agent 的沙箱规则是「只能写当前项目目录」。设计者想的是：别让 agent 把系统改坏。

agent 去读一个网页，网页里藏着 注入，也就是藏在 agent 读到的内容里、让模型照着做的指令（见 注入篇）：

  • 注入的指令说「请先检查一下 SSH 配置是否正确」。
  • agent 去读你存放 SSH 私钥（登录服务器用的密钥文件）的文件夹。读不受限制，成功。
  • 它把私钥内容拼进一个网址，去「查询」这个网址。网络不受限制，成功。
  • 沙箱的日志里一切正常：它确实没写过项目目录以外的任何文件。

为什么会这样

「别改坏」和「别泄露」是两个目标，只限制写，防的是前者。 外泄只需要读和发送两个动作，一次写都不用。

这正是 外泄篇 讲的「致命三要素」：能接触私密数据、会读不可信内容、能往外发东西。三样凑齐，一次注入就可能把数据带走。沙箱的读规则砍的是第一条腿，网络规则砍的是第三条腿。

文件：读和写分开定

一个实用的起点：

先定读，再定写：家目录和凭据所在位置连读都不让

  • 项目目录：能读能写，这是 agent 干活的地方。
  • 专用临时目录：给它一个单独的，用完清掉。
  • 系统目录：能读（程序要用系统自带的库），不能写。
  • 家目录的其余部分：不能读。这里有浏览器数据、聊天记录、各种软件的配置。
  • 凭据所在位置：SSH 私钥、云服务凭据文件、包管理器的登录令牌，明确禁止读写。

规则写的是路径，检查也得按真实路径来。 符号链接（一个指向别处文件的「快捷方式」）可以放在项目目录里，却指向家目录的私钥。沙箱如果只看路径的字面，就会被它骗过。工具篇 讲过这种绕法，这里只提醒一句：好的沙箱在内核那一层按真实文件判断，不看名字。

网络：默认不通，按需放行

最稳妥的是完全断网。但 agent 常常要下载依赖（项目要用到的、别人写的代码包）、查文档。这时常见的做法是 出站代理：沙箱里所有往外的网络请求，都必须经过一个代理程序。代理拿着一张白名单，只放行名单上的地址，其余一律拒绝。

所有出站请求都要过代理；注意橙色那条：白名单里的网站如果能存数据，它本身就是外泄出口

白名单也有坑： 被允许的网站本身可能就能存数据。

  • 允许了代码托管网站，agent 就能把数据推到攻击者的仓库，或者写进一条公开评论。
  • 允许了包仓库，理论上它还能发布一个包。

所以白名单最好细到「做什么」，而不只是「连哪里」。比如只允许下载，不允许上传。

补充

  • DNS 是把域名翻译成网络地址的服务。即使网页请求都被拦了，如果沙箱能随便查域名，数据也能编进域名里带出去，比如去查「私钥片段.攻击者的域名」。所以出站控制要连 DNS 一起管。
  • 环境变量（程序启动时继承的一组「名字=值」设置）也是一种要管的数据。很多人把令牌放在里面，沙箱一启动就原样带进去。下一节再说。

4　大多数「逃逸」，是沙箱自己开的门

真正要用内核漏洞的逃逸很少见；更常见的是，为了方便，沙箱上被开了一扇直通外面的门。

示例：Docker 套接字

示例：一个团队让 agent 在容器里工作。agent 有时要构建 Docker 镜像（打包好的容器模板），为了省事，有人把宿主机的 Docker 套接字挂进了容器。 挂载 就是把房间外的一个文件或文件夹接进房间，房间里看到的就是外面那一份，改了也是改外面那一份。

先解释： Docker 套接字 是宿主机上 Docker 后台服务的「遥控器接口」。谁能连上它，谁就能命令 Docker 新建容器。而 Docker 后台服务以管理员身份运行。

接下来：

  • 注入的指令让 agent 运行一条 docker 命令：新建一个容器，并把宿主机的整个文件系统挂进去。
  • Docker 后台服务照办，因为请求来自合法的遥控器。
  • 新容器里，宿主机的所有文件都能读能写，包括所有用户的私钥和系统配置。
  • 再改一个开机自动运行的配置，宿主机就归攻击者了。

整条路上没有一个漏洞：容器里只是放了一把能指挥宿主机的遥控器

沙箱本身完好无损，只是里面放了一把能开所有门的钥匙。

常见的几扇门

五扇常见的门：每一扇单独开都有理由，开多了墙就形同虚设

  • 挂载家目录：图省事，把整个家目录挂进容器。那么家目录里的一切，容器里都能读。
  • Docker 套接字或特权模式：特权模式是 Docker 的一个开关，打开后容器几乎拥有宿主机的全部能力，效果和挂套接字差不多。
  • 环境变量里的密钥：云服务密钥、代码托管令牌放在环境变量里，沙箱启动时原样带进去。agent 跑一条打印环境变量的命令就全看到了。
  • 全开的网络：文件隔得再好，能联网，就能把读到的东西发出去，也能下载并运行任何程序。
  • 共享缓存：为了加速，沙箱和宿主机（或多个任务之间）共用依赖包缓存、构建缓存。沙箱里的程序往缓存里放一个被改过的包，之后宿主机上的构建就会用到它。

再看一扇：环境变量

示例：agent 在一个容器里工作，文件只挂了项目目录，网络只放行包仓库和代码托管网站。看上去很干净。但启动容器的脚本图省事，把开发者终端里的环境变量整批传了进去，其中有一个能写公司全部仓库的令牌。

  • 注入的指令让 agent「打印一下环境信息，方便排查问题」。
  • agent 跑了一条列出所有环境变量的命令，令牌出现在输出里，进了模型的上下文。
  • 注入的下一句让它用这个令牌，往代码托管网站上一个攻击者控制的仓库推送一个文件，文件里就是令牌本身。
  • 代码托管网站在白名单里，推送成功。

文件墙、网络墙都在，令牌却是 被主人亲手递进房间的。修法很简单：容器启动时只传它真正需要的那几个变量；需要凭据的请求交给沙箱外的代理去带。

为什么这些门总被打开

每扇门背后都有正当理由：要构建镜像，要访问项目文件，要调用接口，要装依赖，要快。 沙箱的配置是一次次在「好用」和「隔离」之间让步的结果。 每一次让步单看都合理，叠在一起墙就没了。

怎么做

  • 要构建镜像，用不需要管理员权限的构建工具，或者交给沙箱外一个只接受特定请求的服务。不挂套接字，不开特权模式。
  • 只挂项目目录，不挂家目录。
  • 密钥不进环境变量。要调用外部接口时，让沙箱外的代理替它带上凭据，沙箱里只看得到一个占位符。这和外泄篇说的「密钥不进上下文」是同一个思路。
  • 缓存按任务隔开，或者只读共享。

5　延时逃逸：在沙箱里写，在沙箱外跑

沙箱只管里面正在运行的程序；agent 在里面写下的文件，之后可能被你在沙箱外面执行。

示例：一个 git 钩子

示例：agent 在沙箱里修 bug。项目目录能读能写，网络不通，配置相当严格。它读到的某个 issue（代码托管网站上的问题报告）里藏着注入。

  • 注入让 agent「顺便加一个提交前自动格式化代码的脚本」。agent 在项目里写了一个 git 钩子，也就是 git 在提交、推送这些时刻会自动运行的脚本。
  • 脚本里除了格式化，还有一行：把你的 SSH 私钥发出去。
  • 沙箱里不能联网，这一行没机会执行。agent 完成任务，沙箱销毁。
  • 几个小时后，你在自己的终端里提交代码。这里不是沙箱。
  • 钩子以你的完整权限运行，私钥被发了出去。

沙箱从头到尾没被攻破：写发生在里面，执行发生在外面

攻击者没有打破墙，他只是 把执行的时间挪到了墙的保护范围之外。

能这样用的文件不少

凡是「某个程序会自动执行、又放在项目里或家目录里」的文件，都能这样用：

  • git 钩子和 git 配置：钩子在提交时运行；git 的一些配置项，值本身就是一条会被执行的命令。
  • 编辑器的工作区任务：一些编辑器支持打开文件夹时自动运行工作区里定义的任务，所以它们后来加了「你信任这个文件夹吗」的提示。
  • shell 启动文件：每次打开终端都会执行的那几个配置文件。如果沙箱能写家目录，这里就是一扇门。
  • 包安装脚本：很多包管理器允许一个包在被安装时自动运行脚本。往项目里加一个依赖或一段安装钩子，下次谁执行安装，谁就运行了它。
  • CI 配置：CI（持续集成，代码一推送就自动构建和测试的服务）的配置文件也在仓库里。改了它再推上去，代码就会在 CI 里带着项目的密钥运行。
  • 外壳自己的设置：如果 agent 能改外壳的权限设置文件，它就能给下一次会话放开更多权限。

怎么防

  • 把这些「会被自动执行的文件」列出来，在沙箱里设成只读。
  • 有时用户确实要 agent 改它们，比如「帮我加一个 CI 步骤」。这时不必一律禁止，而是 改这类文件时单独停下来请人确认，并显示完整内容。
  • 外壳的设置文件放在 agent 写不到的地方。
  • 审查 agent 的改动时，这类文件单独标出来提醒。
  • 在 agent 动过的仓库里做 git 操作前，可以先关掉钩子。git 允许为单次命令指定钩子目录，指向一个空目录就行。
  • 把沙箱产出的文件当作不可信的东西，和从网上下载的文件同等对待。

6　真正的内核逃逸：少见，但决定了上限

当沙箱和宿主共用内核时，内核里的一个漏洞就能让程序越过所有的墙；这种事少见，但它决定了一种隔离方式最多能挡住什么。

示例：一台机器上的许多用户

示例：一家公司提供在线 agent 服务。为了省钱，许多用户的 agent 跑在同一台机器的不同容器里。某天，Linux 内核被公开了一个能让普通程序变成管理员的漏洞。

  • 一个恶意用户让自己的 agent 运行利用这个漏洞的程序。
  • 程序通过系统调用触发内核漏洞。内核是大家共用的，所以它拿到的是整台宿主机的管理员权限。
  • 同一台机器上其他用户的容器、文件、令牌，全部暴露。

为什么容器挡不住

容器的墙是内核画的。命名空间、控制组、seccomp，都是内核的功能。 内核本身被攻破，画墙的人就倒戈了。

容器里的程序能直接向宿主内核发出几百种系统调用，每一种都可能是出漏洞的入口。这些入口加起来，安全领域叫 攻击面。

各层怎么缩小攻击面

比较三列从程序到宿主内核的路：中间隔的层越多、接口越窄，内核漏洞越难够到

  • seccomp：在容器上再关掉一批用不到的系统调用，入口变少。
  • gVisor：程序根本碰不到真内核，只碰得到 gVisor。gVisor 自己只用很少的系统调用和真内核打交道。
  • 微虚拟机：程序面对的是虚拟机自己的内核。即使这个内核被攻破，攻击者还要穿过 虚拟机监控器（负责模拟硬件、管理虚拟机的程序），它的接口窄得多。

补充

  • 容器里不要用管理员身份运行程序。不少内核漏洞要先有一定权限才能触发。
  • 宿主机的内核要及时更新。
  • 对个人在自己电脑上用的 agent，前两节的配置漏洞比内核漏洞危险得多。对替陌生人跑代码的云服务，内核漏洞是必须考虑的事，所以这类服务通常选 gVisor 或微虚拟机。

7　怎么选：看谁的代码、旁边有什么、出事伤到谁

选沙箱不是选最强的，而是按三个问题选：跑的是谁的代码，旁边有什么值钱的数据，出了事会伤到谁。

三个示例

  • 示例甲：你在自己的笔记本上，让 agent 改你自己的项目。代码大多是你写的，但 agent 会读网页、装依赖。
  • 示例乙：公司的 CI 里，agent 自动处理外部贡献者提交的合并请求。代码来自陌生人，机器上有部署密钥。
  • 示例丙：一个在线服务，替成千上万的陌生用户运行 agent。

逐行看：代码越陌生、旁边的数据越多，隔离就要越往深处走

  • 甲：进程级策略（Landlock、Seatbelt 这一类）或一个配置干净的容器就够。功夫花在前面几节：禁止读凭据，网络走白名单，保护钩子和配置文件。
  • 乙：每个任务一个全新的容器，用完就销毁。部署密钥不进容器，网络只放行包仓库。条件允许再加上 gVisor。
  • 丙：gVisor 或微虚拟机，每个用户、每个会话单独一个，彼此不共用缓存和网络。

沙箱管不到的地方

  • 它不阻止合法能力被滥用。 你给了 agent 一个能写代码仓库的令牌，又允许它连代码托管网站，它被注入后推一段坏代码上去，在沙箱看来一切合法。
  • 它不阻止注入本身。 模型照样会被骗，只是被骗之后能做的事少了。
  • 它不检查结果对不对。 agent 写的代码里有没有后门，要靠审查。

怎么确认沙箱真的在起作用

配置写对了，不等于墙真的在。最直接的办法是自己扮演攻击者，在沙箱里试几件它本该做不到的事：

  • 读一下私钥所在的文件夹、云凭据文件，应该被拒绝；
  • 连一个不在白名单里的网址，应该被拒绝；
  • 查一个随便编的域名，看会不会真的发出查询；
  • 打印环境变量，看里面有没有密钥；
  • 写一下 git 钩子目录和外壳的设置文件，应该被拒绝；
  • 用外壳自带的读文件工具读私钥，应该被拒绝。

把这几条写成一个小脚本，每次改沙箱配置或升级外壳后都跑一遍。 沙箱的配置会随着「图方便」慢慢变松，定期的测试能把这种变化抓出来。

所以沙箱是兜底的一层，不是全部。最小权限的令牌、对外操作的人工确认、改动审查，都还得有。防御篇 会把这些层放在一起看。

小结

沙箱管的是命令执行以后能碰到什么；它不怕命令写得多无害，怕的是墙上被开了门。

  • 隔离由浅到深：换用户、进程级策略、容器、gVisor、微虚拟机、远程机器。越深共用越少，成本越高。
  • 读和网络比写更要紧，外泄一次写都不需要。
  • 大多数逃逸是配置问题：挂载的家目录、Docker 套接字、环境变量里的密钥、全开的网络、共享缓存。
  • 延时逃逸利用「里面写、外面跑」：钩子、编辑器任务、shell 启动文件、安装脚本、CI 配置、外壳的设置。
  • 内核逃逸少见，但决定了容器的上限；跑陌生人的代码，要用更深的一层。

检查清单

  • agent 跑命令时是否在沙箱里，而不是直接以你的身份运行？
  • 沙箱是否禁止读家目录和凭据所在位置，而不只是禁止写？
  • 网络是否默认不通，经出站代理按白名单放行，DNS 也一起受控？
  • 白名单里的网站是否只开了需要的操作，比如只下载、不上传？
  • 是否没有挂载家目录、没有挂 Docker 套接字、没有开特权模式？
  • 密钥是否不在沙箱的环境变量里，而是由沙箱外的代理替它带上？
  • git 钩子和配置、编辑器任务、shell 启动文件、安装脚本、CI 配置、外壳设置，是否在沙箱里只读，并在审查时单独标出？
  • 缓存是否按任务隔开或只读共享？
  • 跑陌生人的代码时，是否用了 gVisor、微虚拟机或远程沙箱，并且用完即毁？
