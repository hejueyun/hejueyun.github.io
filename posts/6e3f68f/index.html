ProverB深度导读·穿插讨论与决策附录

2026-05-11

1. 第九章 · 穿插讨论：这张地图的关系、机制与边界

到这里 PV0–PV6 的”主线”已经讲完。但在沿着主线走的过程中，一些跨工具、跨层级
的问题反复浮现：model checker 和 verifier 是同一件事吗？工具为什么跑不动大程序？
“翻译成 SMT” 真的是 BMC 的全部吗？这些问题不属于任何单一 PV 层，但理解它们是把
ProVerB 这张约定图真正读懂的必要条件。本章把这些跨层级的疑问一一拆开。

1.1. 9.1 Model Checker 和 Verifier 是什么关系？

读到这里你可能会问：SolCMC 底下用的是 CHC（约束 Horn 子句）求解，
那它到底还算不算 model checker？”Model checker”和”verifier”是包含关系吗？

1.1.1. 先看 SolCMC 的两副面孔

SolCMC 内部其实跑了两个引擎：

引擎技术本质
BMC 引擎展开有界路径 → SAT/SMT经典 bounded model checking
CHC 引擎程序编码为约束 Horn 子句 → 求解归纳不变量更接近自动定理证明

CHC 求解的核心操作不是”遍历状态空间”，
而是”找到一个归纳不变量使所有 Horn 子句同时成立”——这本质上是在做归纳证明，不是穷举。
所以严格说，CHC 部分已经不是传统意义的 model checking 了。

但学术界习惯把它归入广义的”software model checking”，因为它仍然是全自动、按按钮就跑的。

1.1.2. 形式验证方法的完整分类

“Verifier”不等于”model checker + 什么”。正确的关系是：

  • Model Checking — 穷举 / 符号化遍历状态空间
  • 抽象解释 — 用抽象域近似所有执行
  • 演绎验证 — Hoare 逻辑 / 最弱前条件
  • 定理证明 — 人机交互构造证明
  • CHC 求解 — 横跨 MC 与演绎的灰色地带

所以：

Verifier ≈ 任何做形式验证的工具（大伞概念）

Model Checker ⊂ Verifier（是其中一种方法，不是唯一一种）

不是 verifier = model checker + …，
而是 verifier 按方法分成了好几个并列的流派。

1.1.3. 为什么现代工具让边界变模糊

现代工具经常混合多种方法，脚踏好几个圈：

工具方法 A方法 B你感受到的
ESBMCBMC（model checking）k-induction（归纳证明）全自动，但 k-induction 严格说不是在”遍历状态”
SolCMCBMCCHC 求解全自动，CHC 部分是在”求不变量”
SeaHornCHC 求解抽象解释全自动，两种非 MC 方法的混合
Dafny演绎验证后端调 Z3（和 BMC 用同一个求解器）半自动，但用的求解器你很熟

关键直觉：区分方法看的不是工具名字，而是核心操作——

  • 在遍历状态？→ Model Checking
  • 在求解不变量 / 做归纳？→ Deductive / CHC
  • 在近似抽象？→ Abstract Interpretation
  • 在构造证明项？→ Theorem Proving

所以当别人问你”ESBMC 是 model checker 还是 verifier”，
最准确的回答是：它是一个 verifier，主要方法是 model checking（BMC），但也用了归纳证明（k-induction）。
叫它 model checker 是约定俗成，不是精确分类。

1.2. 9.2 为什么验证器跑不动大程序？是图灵停机问题的锅吗？

读到这里你大概会有一个反复浮上来的疑问：这些工具看起来都很厉害,
为什么没人用 CBMC 跑整个 Linux 内核,没人用 Coq 直接证明 Chrome?
是不是图灵停机问题从根上就堵死了”大程序验证”这条路?

答案有点反直觉:主因不是停机问题,而是”状态/搜索空间爆炸”和”规约负担”——
停机问题只决定了”原则上有上限”,但真实工具远在那条上限之前就被现实击溃了。

1.2.1. 停机问题是”原则障碍”,不是”工程障碍”

Turing 1936 + Rice 1953 说的是:对图灵完备语言,任何非平凡的语义性质
(包括”会不会崩溃””会不会死锁”)在一般情形下都不可判定。这意味着:

不存在一个既 sound、又 complete、又 always-terminating 的算法,
能对任意程序判定任意性质。

但这是一句”存在某些病态程序没法被判定”的存在性陈述——它不解释为什么
1 万行的 Linux 驱动比 10 行的玩具难一百万倍,因为这两者都”原则上不可判定”,
难度上没有等级。换句话说,停机问题是天花板,不是斜坡。
真实工具沿着这条斜坡爬,触不到天花板就先撞墙了。

1.2.2. 撞的是哪几堵墙

1. 状态爆炸 (State Explosion) — 模型检验的”原罪”。
一个程序有 $n$ 个布尔变量 → 状态空间 $2^n$;两个并发进程交错 → 状态空间相乘。
32 个布尔变量就是 40 亿状态,加一个 64 位整数变量直接 $2^{96}$。
BDD/SAT 把常数压下去,但指数本身没消失——只是底数变小、可处理的 $n$ 变大而已。
SPIN/nuXmv 跑不动大并发系统的真正原因,不是图灵,是 $2^n$ 长得太快。

2. 路径爆炸 (Path Explosion) — BMC 与符号执行的痛点。
CBMC 要把循环展 $k$ 次。每个 if 把路径数翻倍,$m$ 个分支就是 $2^m$ 条路径,
全部塞进一条 SAT 公式。结果是:程序行数线性增长,SAT 公式规模指数爆炸,
而 SAT 本身又是 NP-complete。两个指数叠在一起,千行级就开始让 solver 喘不过气。

3. 抽象的代价 (Abstraction Cost) — 抽象解释/类型分析的反噬。
EVA/Astrée/Infer 用过近似回避状态爆炸——但代价是误报。
你越想跑大程序,就越要粗化抽象,越粗就越多 false positive。
它们不是”算不动”,而是”算得动但报告变成噪音”。

4. 规约负担 (Specification Burden) — Dafny/Coq 真正的瓶颈。
到了 PV5/PV6,机器其实没那么累——人累垮了。Dafny 验证一个 100 行算法
可能只要 30 行 invariant,但验证一个 10 万行的系统需要写多少 invariant?
seL4 微内核只有 8700 行 C,但 Coq 证明用了约 20 人·年、20 万行 Isar。
瓶颈从 SMT 时间变成了人类证明工程的 person-year——
这不是图灵问题,是社会学问题。

1.2.3. PV0–PV6 各自撞的是哪一堵墙

等级代表主要瓶颈大程序困难度
PV0CUDD、Spot没有验证语义天然就是库,跟”大小”无关
PV1Z3、MiniSATNP-complete + 量词理论上百万子句后启发式失效;但作为后端总能被上层切小
PV2Sketch、SyGuS洞数量的指数爆炸几十个洞已是极限——综合本质上比检查难
PV3CBMC、SPIN、nuXmv状态爆炸 + 路径爆炸千行级 C 或几百状态变量是日常上限;Linux 子系统量级要靠人工切片
PV4EVA、Infer、Astrée抽象太粗 → 误报反而最能跑大程序:Astrée 验过空客 A380 全套航电、Infer 跑过整个 Facebook 代码库
PV5Dafny、Why3、F*人写规约 + SMT 偶发超时AWS s2n、Azure RustBelt 这种规模需要团队级投入
PV6Coq、Isabelle、Lean纯人力——证明工程seL4 / CompCert / CakeML 都是十年级项目

注意一个反直觉的事:PV4 反而是最能跑大程序的一档。原因正是它主动放弃完备性——
Infer 跑过 Facebook 整个 monorepo,但它会漏报也会误报;
Astrée 跑过空客全套航电,但它锁死在”无浮点异常”这一种性质上。
它们用”放弃通用性”换”可扩展性”,这是图灵障碍的一个绕道而非突破。

1.2.4. 把这串现象抽象成一个三元悖论

所有这些工具都在同一张图上做权衡——你最多能同时拿两个:

  1. Soundness(说”对”就一定对,不漏报)
  2. Automation / Generality(对任意程序自动跑,不要人写 invariant)
  3. Scalability / Termination(在合理时间内出结果)
  • PV3 模型检验:要 1+2,放弃 3 → 状态爆炸
  • PV4 抽象解释:要 1+3,放弃 2 的一部分 → 误报、固定属性
  • PV6 证明助手:要 1+2 的”通用性”+ 3 的”原则上能终止”,放弃 2 的”自动” → 人累死
  • 测试 / fuzzing(本书外):要 2+3,放弃 1 → 不 sound,只找 bug

停机问题是这个悖论的”为什么”——它解释了为什么三个不能同时拿。
但它没规定”具体在哪一行 C 代码上撞墙”——那是 $2^n$、NP-complete、
和人类带宽决定的。所以严格说:大程序难,根源是 Rice 定理(任何想要
sound + automatic + general 的工具必败),形态是状态/路径/规约爆炸,
应对是各 PV 等级各自挑了不同的妥协方式。

一句话:图灵告诉你天花板在哪;指数函数告诉你你离天花板还很远就已经摔了。

1.3. 9.3 Verification 和 Symbolic Execution 是一回事吗?

不是一回事,但关系非常密切——symbolic execution 是一种技术,verification 是一类目标。
一个是”手段“,一个是”用途“。这两个词在文献里经常混用,值得单独澄清一下。

1.3.1. 定义层面的区别

Verification(验证) 是目标/目的:证明(或反驳)”程序满足某条性质”。
它不规定用什么方法——你可以用 model checking、deductive proof、abstract interpretation、
type system、甚至 fuzzing(只要你接受 unsoundness)。本书这张地图整本书讲的都是
verification 的不同路线。

Symbolic Execution(符号执行) 是一种具体的程序分析技术:不用具体输入值运行程序,
而是把输入当作符号变量 $x, y$,沿着程序路径维护一个路径条件(path condition):
“要到达这一行,必须 $x > 0 \wedge y = x + 1$”,然后把这个条件交给 SMT solver 问”可满足吗”。

1.3.2. 它们的关系:交叉但不等同

Symbolic execution 既可以用来 verify,也可以不用来 verify:

用法例子算 verification 吗
纯找 bug(不关心覆盖所有路径)KLEE、SAGE、Mayhem、angr✗ 只是高级的 fuzzing,sound 性打折
展开路径 + SMT 判否决CBMC、ESBMC(BMC 本质就是 bounded symbolic execution)✓ 在展开界内 sound
作为 deductive verifier 的内核Dafny、Why3 的 VC 生成 本质上就是 symbolic execution 的变体✓

Verification 也常常不用 symbolic execution:

  • Abstract Interpretation(Astrée、Infer、EVA)——完全不走符号路径,用抽象域做不动点迭代
  • Type Systems(Haskell、Rust borrow checker)——纯静态,不模拟执行
  • Proof Assistants(Coq、Lean)——人在构造证明项,根本不”执行”
  • 显式模型检验(SPIN)——枚举具体状态,不维护符号表达式

1.3.3. 本书里最容易混的两处

1. BMC vs Symbolic Execution。
CBMC/ESBMC 的工作流程(展开 → SSA → 合取程序语义 → 问 SMT)本质上就是 symbolic execution——
每个变量都是符号表达式,路径条件被编码进公式。所以有人直接说
“BMC is just bounded symbolic execution with a twist”。区别只在:

  • 经典 symbolic execution 一条路径一条路径地走,path-by-path 发给 solver;
  • BMC 把所有路径塞进一条大公式(用 $\phi$ 变量表示分支走向),一次性发给 solver。

这是策略差异(path-merging 的时机),不是本质差异。现代工具都在中间谱上。

2. KLEE 算不算 verifier?
按 ProVerB 的约定分层,KLEE 通常不被归到 PV3 及以上——它的目标是高覆盖率找 bug,
并不保证”找不到就没 bug”(路径爆炸时它会主动放弃一些路径)。
而 CBMC 在 $k$ 步展开界内是 sound 的,所以它能坐上 PV3。
同样是 symbolic execution,出口不同 → 一个算 bug-finder,一个算 verifier。

1.3.4. 一句话对照

概念是什么回答什么问题
Verification一类目标“这个程序满足性质 P 吗?”
Symbolic Execution一类技术“如果输入是符号变量,程序会走到哪些路径、每条路径的约束是什么?”

更准确的说法是:symbolic execution 是很多 verifier 的”引擎”,但一个 verifier
不一定用 symbolic execution,一个 symbolic executor 也不一定是 verifier
(它可能只是更聪明的 fuzzer)。

1.4. 9.4 BMC 工具到底在做什么优化——一条 pipeline 看完

读到这里很容易冒出一个尖锐的问题:既然 CBMC/ESBMC 本质上就是个翻译器,
把 C 程序加性质翻译成 SMT 公式,那它们除了”翻译”还做了什么?
如果没什么特别的,我自己写一个翻译器手动 BMC 展开,不也一样吗?

短答案:确实可以写一个,但你写出来的是 CBMC 2001 年的样子——
能跑,但 solver 永远跑不完。CBMC 这二十年几十万行 C++ 代码,
主要不在”加新语法支持”,而在把每个阶段的公式压小。
按流水线展开看,优化密集到不可思议。

1.4.1. CBMC 的内部流水线

每一个箭头都不是无脑透传,都做优化。逐一拆。

1.4.2. 阶段 ① 前端:从 C 到 GOTO IR

CBMC 不直接在 AST 上跑 BMC,先把代码降到一个叫 GOTO 的 IR——
类似带显式 goto、assume、assert 的简化 C。这一步的优化:

  • 函数内联 (function inlining):默认激进内联,因为 BMC 是路径式的,
    跨函数边界会让符号执行复杂得多。代价是代码膨胀,所以 CBMC 给你
    --no-inline 等开关。
  • 死代码消除 (DCE):基础但必要,减少后续展开规模。
  • 常量折叠:编译期能算的提前算掉。sizeof(int) → 4,1 << 10 → 1024。
  • switch lowering、复合表达式拆分、短路求值显式化:把 C 的高级结构
    降成 GOTO 的简单 if/goto 形式,便于后面 symex 一致处理。
  • 循环规范化:把 for / while / do-while 统一成”head + back-edge”
    的标准形式。

1.4.3. 阶段 ② 性质插桩

--bounds-check、--pointer-check、--signed-overflow-check 这些 flag
会让 CBMC 在 GOTO 程序里自动插入 assert。这里有个常被忽略的优化:

  • 静态可证则不插桩:如果 i 是个 for (i=0; i<10; i++) 的循环变量,
    CBMC 的简单值分析能证明 0 ≤ i < 10,那 arr[i](arr 长度 ≥ 10 时)
    的 bounds check 可以静态消除,不会进公式。
  • 冗余 check 合并:同一行上多个 *p 解引用,只插一次 p ≠ NULL 检查。

这一阶段做不做优化,直接决定 solver 要处理多少条 assert。

1.4.4. 阶段 ③ 符号执行 + 循环展开 (核心算法贡献)

这是 CBMC 真正的算法心脏。它把 GOTO 程序”跑一遍”,但用符号值跑,
展开循环 k 次。优化最密集:

优化作用典型例子
常量传播symex 时维护每个变量的”已知具体值”的格int x=5; if (x>0) A; else B; → x 是 literal 5,条件折叠成 true,B 直接砍掉
死分支剪枝guard 折叠成 false 的分支不展开配合常量传播,跨过整段代码
常量展开循环循环边界是常量时,完全具体展开for(i=0;i<10;i++) sum+=a[i]; 展成 10 条具体 SSA 赋值,索引是 literal 0..9,数组理论用不上
不可达赋值消除symex 路径不可达的赋值不进公式沿”已知不可达”路径走时跳过
简单别名分析用 points-to 信息缩小 store/load 影响集*p = v 只更新可能指向的对象,不是整个内存

效果:同一段代码,naive 路径枚举 vs CBMC symex 公式大小常常差
100×~10000×。

1.4.5. 阶段 ④ SSA + slicing (削公式)

把 symex trace 转成 SSA,然后做切片 (cone-of-influence slicing)
——这是 CBMC 最香的优化之一:

  • 从每条 assert 倒推,只保留能影响 assert 的 SSA 赋值,其它全删。
  • 一段 50000 行代码里,一条 assert 的影响锥可能只有几百行,
    95%+ 的 SSA 等式会被删。
  • CBMC 有 --slice-formula flag(默认开),不开的话性能直接崩。

类似地还有 dead variable elimination:某个 SSA 变量没有任何后续读取
也不在 assert 里,删。

1.4.6. 阶段 ⑤ 公式构造 + 简化 + theory 选择

构造公式时还有一层”局部代数简化”:

  • 代数恒等:x + 0 → x,x ∧ true → x,x ⊕ x → 0,ite(true,a,b) → a。
  • 位级简化:(x & 0xFF) | 0 → x & 0xFF,
    extract[7:0](concat(hi, lo)) → lo。
  • Tseitin 编码调优:布尔公式转 CNF 时引入辅助变量的策略。

Theory 选择也是个优化决策点:

选项适用代价
QF_BV (纯位向量,内存”flatten” 成大 BV)没数组、小内存模型数组操作膨胀
QF_ABV (位向量 + 数组理论)有 malloc、大数组数组公理慢
QF_AUFBV (+ 未解释函数)跨函数概要公式更抽象

CBMC 默认 QF_AUFBV,可通过 flag 切换。ESBMC 走得更远——solver portfolio:
同时跑 Z3、Boolector、MathSAT、Yices,哪个先出结果用哪个。

1.4.7. 阶段 ⑥ Solver 层面

到这里公式才送给 solver,但送的方式也有优化:

  • Incremental SMT:展开循环 k → k+1 时,不重发整个公式,
    只 push 新增的约束。
  • Assumption-based check-sat:用 SMT-LIB 的 (check-sat-assuming ...),
    不同 assert 复用同一个 solver state。
  • k-induction 三阶段:ESBMC --k-induction 在外层套一个
    base/forward/inductive 三段归纳,每段都是独立 BMC,但共享 IR。

1.4.8. 阶段 ⑦ 反例重构

solver 返回的 model 是一堆 SSA 变量的赋值。CBMC 维护
source-to-SSA 映射表,把它翻回”在第 17 步,变量 n 等于 5”,
并构造可执行的 input vector。这一步不削公式,但是把”翻译器”的语义闭环
关上的关键——否则 solver SAT 之后你只能盯着 hex 值发呆。

1.4.9. “为什么有些优化没做?”——这是问题真正有意思的部分

CBMC 故意不做的几类优化,理由都很硬:

  1. 不重复 solver 的 rewriting。Z3/Boolector 内部有几百条 rewrite rule,
    前端做太多代数简化会重复劳动,甚至破坏 solver 内部更聪明的简化路径。
    所以 CBMC 的简化集刻意保留在”显然削减规模”的那一档,深度推理留给 solver。
  2. 不做可能影响 soundness 的优化。比如”假设这两个指针不别名”——
    除非 alias analysis 能证明,否则不能假设。CBMC 在不确定时总是保守保留,
    把判断丢给 solver。
  3. 不做用户特定领域的优化(e.g., “我知道这段是矩阵运算,可以走
    polyhedral abstraction”)。这类信息没法从 C 通用语义里恢复,
    CBMC 是通用工具,不进这个坑。这恰恰是为什么 Astrée 这类领域专用
    抽象解释能在飞控里跑赢 CBMC:它放弃通用性,在一个垂直领域把抽象做精。
  4. 不做”启发式 unsound”优化。比如”循环超过 100 次就把循环变量当未知”
    ——这会让结果不可信,CBMC 不会偷偷做,只在你显式开
    --abstract-unwinding 这类 flag 时才启用。

1.4.10. 一句话总结

“CBMC = 翻译器 + solver” 这句话没错,但这个翻译器的工作量,
80% 在”把公式压小”,不是”把公式生成出来”。

打个比方,SMT solver 像 CPU,BMC 工具像 compiler。说”compiler 也只是个翻译器”
技术上没错,但写一个能正确编译 1 万行 C 程序的 compiler 和
写一个能正确 BMC 1 万行 C 程序的工具,都不是几百行 Python 翻译脚本能搞定的——
能跑出有意义结果的工具,优化在每个阶段都有,而且每个阶段都有研究论文级别的取舍。

挑战版回应:让你手动 BMC 翻译一段带指针、带循环、带有符号溢出、带 malloc
的 50 行 C 程序,你大概会在三天内做出一个 unsound 的、慢于 CBMC 一万倍的、
还漏报 80% bug 的翻译器——这就是为什么这个领域有 CBMC/ESBMC/SeaHorn/SMACK/EBF
等等几十个工具,而不是”每个研究生都自己写一个”。

1.5. 9.5 多语言前端怎么摊薄成本——Boogie / Why3 / Viper 的角色

上一节讲了”BMC 工具不只是翻译器,优化在每个阶段都密集存在”。
紧接着会冒出下一个问题:那如果每来一种新语言都要从头写这套流水线,会不会太贵?

答案是:非常贵。 一个工业级前端是 5–10 万行代码的工作量。
CBMC 的 C 前端、JBMC 的 Java 前端、EBMC 的 Verilog 前端,
各自独立维护。所以这 30 年里整个 verification 领域演化出了
三种”摊薄前端成本”的策略——理解它们能让你看清新工具的位置和取舍。

1.5.1. 策略 A:每种语言写一个专用工具(最贵,但保留高层语义)

CBMC (C/C++)、JBMC (Java)、EBMC (Verilog)、SolCMC (Solidity)、Pat (CSP#)
等等都走这条路。

  • 优点:可以利用语言特有的语义——C 的内存模型、Java 的对象、
    Solidity 的 gas/storage、Verilog 的时钟域。建模越精细,验证越精确。
  • 缺点:每个语言都从头来一遍。所以一个新语言要被这个家族”覆盖”,
    通常等于一个博士论文或工业团队多年投入。

这条路属于”工具开发者的苦力活”,但产出的工具往往是该语言事实上的金标准。

1.5.2. 策略 B:中间验证语言 (Intermediate Verification Language, IVL)——真正改变游戏

类比一下:LLVM 不替你写 C/Rust/Swift 编译器,但它让 C/Rust/Swift 都能复用
同一个优化器 + 后端。Verification 领域有同样的发明:

IVL谁开发的作用哪些前端把它当后端
BoogieMicrosoft Research“verification 界的 LLVM IR”Dafny、VCC、Spec#、Chalice、AutoProof
Why3Inria类似 Boogie,法系血统Frama-C、Krakatoa (Java)、SPARK (Ada)
ViperETH Zurich内置分离逻辑支持Prusti (Rust)、Nagini (Python)、Gobra (Go)、VerCors

写一个新语言的 verifier,现代标准做法是
“我的语言 → Boogie/Why3/Viper”,然后让 IVL 自动接到 Z3。
你只需要写 5000 行的前端,不用碰 SMT 编码,不用做 slicing,
不用处理 incremental SMT——这些 IVL 已经替你做好。

这就是为什么 Dafny、Prusti、Gobra 这些”新语言验证器”近十年井喷:
进入门槛从”写一个 CBMC”降到了”写一个 IVL 前端”。

这同时也回过头来解释了 ProVerB 里 PV5(规约编译器) 这一层为什么会存在——
Boogie/Why3/Viper 本身就是典型的 PV5 居民:用户写规约,IVL 把它编译成
SMT 求解器能消化的格式。Dafny 之所以也属于 PV5,正是因为它走的是
Dafny 源码 → Boogie → SMT 这条管道。

1.5.3. 策略 C:统一编译到 LLVM bitcode

LLVM 已经是工业级多语言前端基础设施。SeaHorn、SMACK、KLEE、angr
都接受 LLVM bitcode 而不是某种具体语言:

  • C 用 clang 编出 bitcode → SeaHorn
  • Rust 用 rustc 编出 bitcode → SeaHorn(理论上,实践上 panic 处理麻烦)
  • Swift、OCaml、Haskell 都能编到 LLVM bitcode

代价是:LLVM bitcode 丢失高层语义。Rust 的所有权、Java 的对象、
C++ 的析构,到了 bitcode 层都被擦平成”指针 + load/store”。
所以这条路对”求快速覆盖广”的研究项目很好,但很难做 Rust 专属的
borrow checking 那种深度推理。

1.5.4. 三条路的取舍图

1.5.5. 一句话总结

“每种语言都要写翻译器”这件事,确实麻烦,但已经被 Boogie/Why3/Viper
这层”verification 界的 LLVM IR”大幅缓解了。 新语言进场不再需要
重造 SMT 编码的轮子——而这正是 PV5 这一层在生态里真正承担的角色。

1.6. 9.6 ProVerB 的边界：形式化验证不只是程序验证

读到这里,敏锐的读者可能已经发现一件事:ProVerB 几乎所有的描述都是关于
“编程语言代码”的——C 内存安全、Java 死锁、Solidity 智能合约、Verilog
电路。那如果我要验证的不是程序,而是网络配置、数据库 schema、分布式协议、
加密协议、云权限策略呢?

这是一个值得直面的问题。短答案:ProVerB 的视角确实集中在”程序验证”上,
这是它的范围(scope),不是它的盲点。但形式化验证作为一个领域,
远远不只针对编程语言。

1.6.1. 为什么 ProVerB 聚焦”程序”

历史原因:ProVerB 源自 SLEBoK(Software Language Engineering Body of
Knowledge)——它的母项目本来就是”软件语言工程”。所以它的 PV0–PV6 分类是按
**”工具对程序的承诺”**来组织的:

  • PV0 解析操作程序、PV1 给程序提反例、PV3 检查程序属性、PV6 证明程序定理……

“程序”这个词在 ProVerB 里被默认成”图灵完备的可执行代码 + 性质”。
SolCMC (Solidity)、EBMC (Verilog)、JBMC (Java) 都还算”程序”,
因为它们都是 imperative/structural 代码,验证语义都基于 transition system。

1.6.2. ProVerB 范围之外的形式化验证版图

但同一套底层数学(SAT/SMT/model checking/proof assistants)在很多
非程序领域同样开花,而 ProVerB 都没收录:

领域代表工具验证对象性质举例
网络配置Batfish、Minesweeper、Veriflow、AnteaterBGP / OSPF / ACL 配置“客户子网到 DB 子网是否可达?”、”两个 ACL 是否等价?”
分布式协议TLA+、Ivy、Verdi (Coq)Raft、Paxos、Zookeeper一致性、活性、leader 唯一性
密码学协议ProVerif(注意名字撞车!)、Tamarin、CryptoVerif、EasyCryptSignal、TLS、Kerberossecrecy、authentication、forward secrecy
数据库 / SQLCosette、Qex、HoTTSQLSQL 查询查询等价、约束满足
云 / IAM 策略AWS Zelkova、Cedar AnalyzerIAM / S3 bucket policy“这个 bucket 是否会被公网访问到?”
混合系统 / CPSKeYmaera X、dReal、SpaceEx飞机、汽车、火车控制“ACC 永不追尾”、”无人机不进禁飞区”
文件系统FSCQ (Coq)、Yggdrasil文件系统的 crash safety任何 crash 序列后,recover 之后数据一致
编译器自身CompCert (Coq)、CakeML (HOL4)、Alive2编译器实现编译保持源程序语义

这些领域和”程序验证”有同样的数学骨架——都是把对象编码成逻辑公式,
丢给 SMT solver 或 proof assistant。但关注的性质不同、建模的抽象不同,
所以工具长得很不一样:

  • 网络验证的”程序”是几千条静态路由表项;不需要循环、不需要内存模型,
    但需要 BDD/SAT 高效处理大量分支条件。
  • 协议验证的对象是”消息交换序列”,时序逻辑 / 迹语义 (trace semantics)
    是主角,而不是 Hoare 三元组。
  • CPS 验证要处理连续微分方程,SMT solver 要支持
    非线性实数算术 (QF_NRA) + delta-decidability,这是 ProVerB 收录的工具几乎都不碰的方向。

1.6.3. 为什么 ProVerB 还是值得这样划定边界

强行把这些都塞进 PV0–PV6 不是不行,但会失焦。比如 TLA+ 你可以说是 PV5
(规约编译器):用户写 TLA+ 规约,TLC 模型检验器做 PV3 检查。但 TLA+ 的整个生态
——PlusCal、Apalache、TLAPS——讨论的是分布式协议而不是”C 代码会不会越界”。
把它们和 ESBMC、Coq 放在同一张表里反而让分类失去解释力。

更合理的视角是:PV0–PV6 是一套”工具承诺”的元分类 (meta-taxonomy),
可以应用到任何形式化验证子领域;但 ProVerB 这本书只展开了”程序”这一支。
同样的尺度可以拿去量网络验证、协议验证、CPS,你会发现:

子领域这个领域的 PV3这个领域的 PV5这个领域的 PV6
网络验证Batfish、Minesweeper(尚未成熟)(实验性)
分布式协议TLC (TLA+ 模型检验)TLA+、IvyTLAPS、Verdi (Coq)
密码学协议ProVerif、TamarinEasyCryptEasyCrypt 的 PRHL 模式
混合系统 / CPSSpaceEx、dRealKeYmaera X 的 dLKeYmaera X(交互式证明部分)
云 / IAMZelkovaCedar(尚未成熟)

1.6.4. 一句话总结

“ProVerB 只看程序” = 这本书的范围选择,不是这套分类的局限性。
PV0–PV6 是关于”工具和用户之间怎么约定分工”的分类法,它和验证对象是什么
(代码、配置、协议、硬件、连续动力学)正交。
真要扩展,完全可以做一个 NetVerB、ProtoVerB、CPSVerB——分类骨架不变,
只换工具表。

2. 第十章 · 回到 CBMC / ESBMC / SolCMC：你现在站在地图哪里

读到这里，你应该能把你已经熟悉的三个工具放在这张地图上：

  • CBMC（PV3，CMU/Diffblue 血统，2004）
    位置：模型检验家族里”BMC 分支”的奠基工具，C/C++，依赖 SAT/SMT 后端。
    它的直接祖先：Clarke-Biere 的 BMC 论文 (1999)。
    它的哥哥：hardware BMC 时代的产物。
    它的兄弟：JBMC (Java)、EBMC (Verilog)。
    它的孩子：ESBMC、Pinaka、2LS。

  • ESBMC（PV4，Manaus/Manchester 血统）
    位置：CBMC 的孩子，转向 SMT 后端 + k-induction + 内置 bug 类别。
    被 ProVerB 归到 PV4 是因为 k-induction 让它从”只能反驳”变成”能证明”，
    而内置的 memory-leak/overflow 检查让它的”性质集合”不完全由用户决定。

  • SolCMC (Solidity SMTChecker)（ProVerB 归 PV0，proverb/solcmc.html）
    血统很清楚：CBMC 的 BMC 思想 + Z3 Spacer (CHC) 的 Horn Clause 编码，专攻智能合约语义。
    功能上更接近 PV3（用户断言驱动）。

它们三个都属于 PV3/PV4 这个工业舒适区——用户投入少、自动化高、代价是
“只能在固定范式内工作”。如果哪一天你发现你需要验证的性质完全不在这些工具的范式内
（比如”这段 GC 算法的平均复杂度是 O(n log n)”或”这段协议满足某个 epistemic logic 下的知识性质”），
你就必须往 PV5 或 PV6 搬家——要么用 TLA+/SPIN 重写模型，要么用 Isabelle/Coq 写证明。

这不是”升级”，这是换一份约定。

如果你把它当海报读，你大致能一眼看完”形式化验证自动化”的六十年。

  4. Nqthm → ACL2：另一条 40 年不断香火的独立血脉。

4. 第十二章 · 接下来怎么读 ProVerB（三条路线）

ProVerB 有几百个条目，整本啃下来没有意义。我建议三条不同的路线，
按你当下的问题选一条。

4.1. 路线 A：扩展你已有的技能树

你已经在用 CBMC/ESBMC/SolCMC。下一步读：

  1. proverb/pv3.html 里的 KLEE、CPAchecker、SeaHorn 页面——
    看看”另一种 PV3 风格”（符号执行、CEGAR、Horn clause）长什么样。
  2. proverb/pv4.html 里的 Dafny、Boogie、Why3（其实在 PV2）——
    看看你为什么会想”从 BMC 往 auto verifier 搬家”。
  3. proverb/pv4.html 的 Spacer/GSpacer——SolCMC 内部用的 CHC 引擎。

4.2. 路线 B：跨过约定的边界

你想理解”当 PV3/PV4 不够用时你会跳到哪里”。读：

  1. proverb/pv5.html 的 SPIN 和 UPPAAL——学会”用一门专门语言重写问题”这种思维。
  2. proverb/pv6.html 的 Isabelle 和 Coq 页面。然后到外部读 CompCert
    和 seL4 这两个案例（它们都不在 ProVerB 里，但它们是 PV6 的工业答案）。

4.3. 路线 C：了解一个特殊领域

ProVerB 的 tags.html 按领域分类。几个热门标签：

  • Neural network → Marabou, Reluplex, nnenum, DNNV, ERAN, Verisig。
    这是过去五年最活跃的一块。
  • Smart contract → SolCMC (proverb/solcmc.html)、MoveProver 在。
    ProVerB 2022 未收录 Certora，但它是当前智能合约验证领域最重要的商业工具之一（见下文）。
  • Probabilistic → PRISM, Storm, STAMINA。
  • Hardware / HDL → EBMC, nuXmv, ABC, Yosys。
  • Termination → AProVE, TcT, iRankFinder, Loopus。

5. 附录 · 遇到什么问题该选什么工具？

读完前面的历史和概念，你可能最想知道的就是：
“我手上有一个具体问题，该用哪个工具？”
下面按问题类型列出推荐路径。这不是精确的采购指南，
而是一张”你该往哪个方向看”的指南针——找到方向之后再去 ProVerB 的对应页面读细节。

5.1. 场景 1：”我有一段 C/C++ 代码，想知道有没有内存安全 bug”

首选：CBMC（PV3）或 ESBMC（PV4）。

  • 如果你的代码有明确的循环边界（循环次数可预估）→ CBMC + --unwind N + --bounds-check --pointer-check
  • 如果你需要证明代码正确（不只是找 bug）→ ESBMC + --k-induction
  • 如果代码很大（>10k 行）且你只关心特定属性 → CPAchecker 或 Ultimate Automizer（CEGAR 驱动，能自适应精度）
  • 如果你想做更轻量的检查（不要求 bit-precise）→ Infer（Facebook 做的，基于 separation logic 的 sound 分析器）

5.2. 场景 2：”我有一段 Solidity 智能合约，想验证它不会被攻击”

首选取决于你愿意投入多少：

  • 零学习成本：SolCMC——在代码里加 assert，编译时加 --model-checker-engine chc。适合查溢出、断言违反。
  • 愿意学一门 spec 语言：Certora——用 CVL 写独立规约，能表达跨函数不变量、总供应量守恒等复杂性质。适合 DeFi 审计。
  • 更关注运行时行为和测试：Foundry 的 fuzz testing + symbolic testing。不是形式化验证，但在实践中和 SolCMC 互补。

5.3. 场景 3：”我有一个并发协议/分布式系统设计，想验证它没有死锁/活锁”

首选：SPIN / Promela（PV5）。

  • 你需要用 Promela 重写协议的核心并发结构。SPIN 能查 safety（无死锁）+ liveness（最终响应）+ LTL 属性。
  • 如果你的系统有时间约束（超时、截止期限）→ UPPAAL（timed automata）
  • 如果你的系统是分布式共识类型 → 考虑 TLA+（不在 ProVerB 里，但 Amazon 用它验证过 DynamoDB、S2N 等）
  • 如果你想直接在代码里验证而不是写模型 → Java PathFinder 或 DIVINE（直接吃 Java/C++ 多线程代码做穷举）

5.4. 场景 4：”我需要证明一个算法是正确的（不只是没有 bug，而是逻辑上正确）”

取决于”正确”的精度要求：

  • 函数级的前后置条件：Dafny（PV4/PV5）——用 requires/ensures/invariant 写 spec，全自动 SMT 验证。学习曲线中等。
  • 整个程序的完整功能正确性：Isabelle/HOL 或 Coq（PV6）——你需要写完整的证明脚本。适合核心算法、密码学原语、编译器正确性。投入巨大但保证最强。
  • Ada / SPARK 生态：如果代码是 Ada 写的 → SPARK，已经被用在航天（A380）和铁路信号系统。

5.5. 场景 5：”我想验证一个神经网络的鲁棒性”

首选：Marabou（PV3，Stanford）。

  • 它能验证”给定输入扰动 ε，网络输出是否保持同一类别”。
  • 如果网络较小且只有 ReLU 激活 → Marabou 或 nnenum（比 Marabou 快但限制多）
  • 如果需要更广的网络类型 → ERAN（ETH Zurich，基于抽象解释）或 DNNV（统一前端）

5.6. 场景 6：”我想验证一段密码学实现和它的规约一致”

首选：SAW (Software Analysis Workbench)（PV5，Galois 做的）。

  • AWS 用 SAW 验证过 s2n（TLS 实现）的关键函数。
  • 流程：用 Cryptol 写密码算法规约 → SAW 提取 C/LLVM 实现的语义 → 用 Z3/Yices 做等价性证明。

5.7. 场景 7：”我只是想让我的代码少一点低级错误，不需要完整验证”

首选：高质量的 linter / 静态分析器（PV1）。

  • C/C++：Clang Static Analyzer、Coverity、Infer
  • Java：SpotBugs、Error Prone
  • Rust：Clippy + Rust 的类型系统本身已经消除了大部分内存安全问题
  • 通用：Semgrep（规则驱动的代码搜索）

这些不做形式化验证，但投入产出比最高——零学习成本、秒级反馈、能在 CI 里跑。

5.8. 总结：一张快速决策表

你的问题推荐工具PV 层投入程度保证强度
C 代码有没有内存 bug？CBMC / ESBMCPV3–4低有界 / k-induction
Solidity 合约安全吗？SolCMC / CertoraPV3–5低–中CHC / CVL spec
并发协议有死锁吗？SPIN / UPPAALPV5中（要写模型）穷举
算法逻辑正确吗？Dafny / Isabelle / CoqPV4–6中–高数学证明
神经网络鲁棒吗？Marabou / ERANPV3中SMT-based
密码实现对吗？SAW / CryptolPV5高等价性证明
代码质量兜底？Linter / InferPV1极低Sound but incomplete

经验法则：越往右（PV 层越高），保证越强，但你需要投入的脑力和时间也越多。
大部分工业项目的最佳策略是混合使用——CI 里跑 linter + CBMC 做有界检查，
关键路径用 ESBMC k-induction 或 Dafny 证明，核心算法用 Isabelle/Coq 做一次性证明。

6. 附录 A · 术语速查

术语一句话
Halting Problem图灵 1936 年证明：不存在通用算法能判定任意程序是否会停止。形式化验证的所有”不完美”都源于此。
Sound工具说”没 bug”就真的没 bug——不漏报，但可能误报。
Complete工具报告的每条错误都是真的——不误报，但可能漏报。
Safety“坏事永远不发生”。违反时能在有限步内发现（一个反例就够）。
Liveness“好事最终一定发生”。违反时需要观察无穷长执行才能确认。
Consistency一个规约/公理集没有内部矛盾——不能同时推出 P 和 ¬P。证明助理的内核正确性保证的就是这个。
SAT / CNF判定一条布尔公式是否可满足；CNF 是它的”合取范式”标准形。
SMTSAT 加”背景理论”——整数、数组、位向量、未解释函数等。
QF_BVSMT 理论之一：量词无关的位向量，管 32/64 位整数的精确位运算。CBMC/ESBMC 的主要编码。
QF_LIA / QF_LRASMT 理论：线性整数/实数算术。Dafny 和 Boogie 常用。
QF_ASMT 理论：数组读写 (select/store)。
QF_UFSMT 理论：未解释函数，只管相等性推理。
DPLL(T)SAT 求解器（骨架）+ 理论求解器（顾问）的协作架构，SMT 的核心算法。
BMCBounded Model Checking，把 k 步展开成公式送 SAT/SMT。
k-inductionBMC 的扩展，能证明”永远成立”而不仅仅”k 步内成立”。
CEGAR反例驱动的抽象精化，让抽象解释自己学会加细节。
CDCL冲突驱动的子句学习，现代 SAT 求解器的主流算法。
BDD二叉决策图，符号模型检验的经典数据结构。
CHC约束 Horn 子句，把”程序是否正确”编码成”这组 Horn 子句可满足吗”。
Hoare triple{P} C {Q}，程序验证的最古老规约形式。
LTL线性时序逻辑：□ (always)、◇ (eventually)、U (until)、○ (next)。SPIN 用 LTL。
CTL计算树逻辑：在 LTL 基础上加了路径量词 A (所有路径) 和 E (存在路径)。SMV/nuXmv 用 CTL。
ATL交替时序逻辑：在 CTL 基础上加了”玩家联盟有没有策略保证 φ”。用于多智体/博弈系统。
Abstract InterpretationCousot 夫妇 1976 年提出的通用静态分析数学框架。
Craig Interpolation从两条不相容公式中提取”公共部分”的方法，用在 CEGAR 精化中。
LCF-style kernel把系统的可信基减到一个小内核的证明助理架构哲学。
Curry-Howard“证明 = 程序”对应。Coq/Lean 的哲学基础：类型检查就是证明检查。
VCVerification Condition，从程序+规约生成的逻辑公式。
SledgehammerIsabelle 把当前目标扔给外部 ATP/SMT 的自动化机制。
CVLCertora Verification Language，为 Solidity 合约写独立规约的 PV5 风格语言。

7. 附录 B · ProVerB 这本书自己的出身

最后值得一提：你正在读的这本”书”不是第一作者的论文，是一个副产品。
ProVerB 来自 University of Twente 的 Formal Methods and Tools 小组，
作者是 Sophie Lathouwers 和 Vadim Zaytsev（就是 @grammarware，
SLEBoK 的主编）。他们在 MoDELS’22 上发的那篇
《Modelling Program Verification Tools for Software Engineers》
才是这本”书”的方法论说明。那篇论文的核心诉求跟你开头的期望几乎一致：

形式化验证工具的数量已经超过了任何一个从业者能跟踪的上限，
我们需要一套**让软件工程师能”选对工具”**的分类法。

PV0–PV6 就是这个分类法的产物。ProVerB 自己承认，这张地图会错——
有些工具的描述是从论文摘要提取的，没经过原作者确认；
有些工具的边界很难清晰划分（比如 Alloy 既是语言又是 analyzer）。
但一本不完美的地图比没有地图好。你现在已经会用这张地图了，
下次看到一个新工具名，第一反应就不该是”这是什么”，而是
“这在 PV0–PV6 的哪一层，它的直接前辈是谁？“。

本导读基于 ProVerB 2022 年 12 月版本（proverb/ 目录内容），
CBMC/ESBMC 页面数据截至 2023 年 2 月。
所有未直接引用 ProVerB 原文的结论都标注了作者/年份，可以去原始论文核对。
