6.1 从一次模型调用到 Agent：谁来决定下一步

为什么需要分清这几个词。 面试官问"你做的是 Agent 吗"，其实在问：系统的下一步由写死的代码决定，还是由模型在运行时决定。

我们按"谁决定下一步"把四种形态排成一条线：

  • 单次调用：输入一段提示，模型输出一段文字，结束。下一步由调用方决定。
  • Prompt Chain（提示链）：把任务拆成固定几步，上一步的输出拼进下一步的提示，例如"先抽取字段 → 再生成摘要"。顺序写死在代码里。
  • Workflow（工作流）：在提示链上加分支、并行、路由，例如"先让模型分类，再按类别走不同的处理流程"。路径的集合仍由开发者预先画好，模型只在节点里做判断。
  • Agent（智能体）：模型在循环中自己决定调哪个工具、调几次、何时结束；代码只提供工具、约束和终止条件。Anthropic 的区分正是这一点：Workflow 走预先定义的代码路径，Agent 由模型动态主导流程。[1]

从左到右，控制权逐步从代码交给模型；灵活性上升，可预测性和成本控制下降

Agent 的组成部分。 通常拆成五块：** LLM**（理解与决策）、规划（拆步骤，6.3）、记忆（6.6）、工具（6.4）、执行环境 / 外壳（harness：拼请求、执行工具、管权限、记日志、决定何时停）。用户博客把它概括为 Agent = 模型 + 外壳：模型只会读一段文字、续写一段文字，读文件、执行命令、记账都由外壳完成，所以同一个模型换个外壳，表现可以差很远。[2]

模型只产出调用意图；执行、权限和记账都在外壳里

完整走一遍：三个"算不算 Agent"。

LLM 在 Agent 中的作用与局限。 作用：理解目标、选工具与参数、读结果、决定是否继续、生成回答。局限：输出随机；会幻觉（6.15）；窗口有限（6.6）；会被输入中的指令劫持（6.21）；无法自己保证副作用只执行一次（6.18）。能用代码确定处理的事，都交给外壳。

何时用 Workflow 就够。 步骤固定、能画成流程图、要求可审计（如开户审核）用 Workflow；步骤数事先未知、需按中间结果换策略（如排查故障、改代码）才用 Agent。标准答案句："能用 Workflow 解决的不用 Agent；Agent 用灵活性换来了成本、延迟和不可预测性。"

小结： 由代码决定执行路径的是工作流（Workflow），由模型决定下一步的是 Agent；Agent 由大模型、规划、记忆、工具和外壳程序组成。

6.2 Agentic Loop：一轮循环在消息层面怎样跑完

为什么要具体到消息层面。 面试中常要求画出 Agent 的执行循环。只画一个“思考、行动、观察”的圆圈是不够的，面试官会追问：工具结果以什么身份放回对话？并行的调用怎样区分？工具报错时怎么办？

消息的四种角色。 主流聊天接口把对话表示成一个消息列表，每条消息有一个角色：

角色谁写的内容
system开发者（外壳拼装）身份、规则、工具使用说明、项目约定
user用户问题或指令
assistant模型文字回答，或者若干个工具调用（每个带唯一 id、工具名、JSON 参数）
tool外壳某个工具调用的执行结果，带上对应的 tool_call_id

不同厂商字段名不同（OpenAI 用 tool_call_id / call_id，Anthropic 用 tool_use 块的 id 与 tool_result 的 tool_use_id），外壳用适配层统一成内部格式。[3] [4]

一轮（turn）里有两步（step）：每一步是一次模型调用加上它要求的全部工具调用

完整走一遍：消息列表怎样长出来。

查余额：消息列表的变化

1 / 4

第1步 · 用户提问：列表里有 system 和 user

2 / 4

第2步 · 模型第一次回复：一条 assistant 消息，里面是工具调用 c1，没有文字

外壳检查：工具存在、参数合法、当前用户有权查 A001
3 / 4

第3步 · 外壳执行工具，把结果以 tool 角色追加，tool_call_id 指回 c1

4 / 4

第4步 · 带着整个列表再请求一次；模型回复纯文字，没有工具调用，本轮结束

角色序列：system, user, assistant, tool, assistant

这一过程可以总结成三条规则：

  1. 没有工具调用即结束：模型回复里没有工具调用，这一轮结束，把文字交给用户。
  2. 每个调用恰好配一条结果：一次回复可含多个调用，每个结果带上对应 id；缺了结果，多数模型服务会拒绝下一个请求。被拒绝、取消或因崩溃没执行的调用，也要补"未执行"或"结果未知"。[5]
  3. 工具报错也是结果：参数非法、工具不存在、工具抛异常，都变成一条 Error: 开头的 tool 消息交还模型，循环继续；模型往往能据此改正参数，这是 ReAct 能"自我调试"的前提。

生产级执行循环的阶段。 一步之内依次经过以下阶段：

  1. 组装请求，必要时先压缩上下文（6.6）；
  2. 调用模型，遇到超时、429 或 5xx 时退避并限次重试，遇到 400 类错误直接结束；
  3. 解析输出并做 schema 校验；
  4. 检查权限，必要时请求审批（6.21）；
  5. 先写日志，再执行（6.18）；
  6. 执行工具调用，处理超时、取消，并在沙箱中运行；
  7. 回填结果，长输出写入磁盘；
  8. 判断是否终止（6.17）；
  9. 记录指标与追踪信息（6.20）。

代码。 变量表：messages 是消息列表；reply 是模型这一步的回复；tool_calls 是其中的调用列表；seen 记录每个调用指纹出现的次数；used 是累计 token。

def run_agent(llm, registry, user_text, max_steps=8, token_budget=10000, warn_at=3, stop_at=5):
    messages = [{"role": "system", "content": "你是银行内部助手。"},
                {"role": "user", "content": user_text}]
    seen = Counter()
    used = 0
    for step in range(1, max_steps + 1):
        reply = llm.chat(messages, registry.schemas())
        used += reply.pop("usage", 0)
        messages.append(reply)
        tool_calls = reply.get("tool_calls", [])
        if not tool_calls:                       # 没有工具调用：本轮正常结束
            return "completed", step, messages
        stuck = False
        for c in tool_calls:                     # 每个调用都必须配一条结果
            fp = fingerprint(c)
            seen[fp] += 1
            result = registry.dispatch(c)
            if seen[fp] >= warn_at:
                result += "\n[提醒] 同一工具与参数已调用 %d 次，请换思路或结束。" % seen[fp]
            stuck = stuck or seen[fp] >= stop_at
            messages.append({"role": "tool", "tool_call_id": c["id"], "content": result})
        if stuck:
            return "stopped_repeat", step, messages
        if used >= token_budget:
            return "stopped_budget", step, messages
    return "stopped_max_steps", max_steps, messages

测试时把 llm 换成按脚本回答的 FakeLLM（6.20）：先调用 get_balance、再答文字，两步结束；check_pairing 扫描消息列表，检查每个调用恰好有一条结果。

A. 3 条，c2 的那条内容是 Error: 参数不是合法 JSON

B. 2 条，跳过 c2

C. 0 条，整轮报错退出

D. 1 条，把三个结果合并成一条

查看答案与每个选项的解析

A · 正确：每个调用恰好一条结果；错误也作为结果交还模型。

B · 错误：c2 缺结果，多数模型服务会因为调用与结果不配对而拒绝请求。

C · 错误：参数错误属于可恢复的工具错误，应交给模型自行纠正。

D · 错误：每条结果要用各自的 tool_call_id 指回对应调用。

易错点：

  • 流式输出（SSE）只是边生成边显示；工具调用的参数要等这一步的流结束、拼完整后才能解析执行。
  • "一轮"（turn）从用户发言到最终回答，可以包含多"步"（step）；步数上限按 step 计。

小结： 消息有 system、user、assistant、tool 四种角色；模型不再发起工具调用时本轮结束，每个工具调用都要配一条带相同 id 的结果，报错也要作为结果回填。

6.3 规划：ReAct、Plan-and-Execute、Tree of Thoughts、Reflexion

为什么需要规划。 "核对上月三笔异常交易并给出建议"需要好几步，后一步依赖前一步的结果。规划回答两个问题：先拆成哪些步骤？每步做完怎样决定下一步？

ReAct：边想边做。 ReAct（Reasoning + Acting）让模型交替输出三种内容：** Thought**（推理，写出当前判断）、Action（调用一个工具）、Observation（工具返回的结果，由外壳填入）。观察结果会修正下一步的推理，推理又决定下一个动作。[6]

ReAct 轨迹：A001 本月有没有超过 5000 元的单笔支出

1 / 4

第1步 · Thought 1：要先拿到本月交易列表

2 / 4

第2步 · Observation 1：外壳执行工具，把结果填回

3 / 4

第3步 · Thought 2：-6800 超过 5000，再查它的商户信息

4 / 4

第4步 · Thought 3：信息够了，给出最终回答（不再有 Action）

共 2 次工具调用、3 次模型调用

Plan-and-Execute：先列计划再执行。 先让模型一次写出完整计划（步骤 1、2、3……），再由执行器逐步执行，必要时根据结果"重新规划"。Plan-and-Solve 提示法是这个思路在单次推理里的版本：先让模型"制定计划"，再"按计划逐步求解"。[7]

Tree of Thoughts（ToT）：在多条思路里搜索。 每一步生成多个候选思路，让模型给每个候选打分，保留得分高的若干个继续展开（广度优先或深度优先搜索），必要时回溯。[8]

完整走一遍：ToT 的调用次数。 3 层、每节点扩展 3 个、每层保留 2 个：第 1 层 3 个，第 2、3 层各 2×3 = 6 个，共 15 次生成，另有同样多的打分调用；不剪枝则 3+9+27 = 39 次。ReAct 通常只需几次。

图中 C 得分最低被剪掉；第 2 层保留 A1、B2 继续展开。

Reflexion：失败后写反思。 一次尝试失败后（例如测试没通过），让模型写一段"哪里错了、下次怎么改"的文字反思，存进记忆，下一次尝试时放进提示。它不更新权重，靠语言形式的经验改进下一次尝试。[9]

方法核心优点代价与风险适合
ReAct想一步、做一步、看结果灵活，能根据观察纠错步数不可预知，可能绕圈信息检索、排障、开放任务
Plan-and-Execute先出全计划，再执行，可重规划步骤可审阅，可并行，规划可用大模型、执行用小模型计划可能过时，重规划要设计多步骤、结构清楚的任务
Tree of Thoughts多候选 + 评估 + 搜索解空间大时更容易找到好解调用次数成倍增加，延迟高离线难题、需要探索的推理
Reflexion失败后写反思再试不改权重即可改进需要可靠的失败信号，多轮重试有自动判定（测试、校验器）的任务

要点：

  • ReAct 的标准答案句："推理指导行动，行动的观察结果反过来修正推理，二者交替进行。"
  • Plan-and-Execute 与 ReAct 的区别：前者先全局规划再执行，后者每一步局部决策。
  • ToT 能否线上使用：在线问答对延迟敏感、调用次数按分支数乘方增长，一般不直接用；可以用于离线任务、低并发的高价值决策，或者把束宽和深度压到很小（例如 2×2）并设预算。
  • Reflexion 需要外部可判定的反馈；没有判定器时，"自我反思"可能把错误说得更像真的。

A. 4 + 8 + 8 = 20 次

B. 4 + 16 + 64 = 84 次

C. 12 次

D. 3 次

查看答案与每个选项的解析

A · 正确：第 1 层根节点扩展 4 个；之后每层由保留的 2 个各扩展 4 个，即 8 个。

B · 错误：这是不剪枝的全展开数量。

C · 错误：只算了每层 4 个，漏掉了每个保留节点各自扩展。

D · 错误：这是层数，不是调用数；打分调用还要另算。

易错点：

  • ReAct 中的 Observation 由外壳填入，模型如果自己"编"出 Observation，说明格式控制出了问题。
  • 规划写得再好，也要配步数和预算上限（6.17）。

小结： ReAct 一边推理一边行动；Plan-and-Execute 先列出计划再执行；ToT 进行多路搜索，代价最高；Reflexion 在失败后写下反思再重试。

6.4 工具调用：Function Calling 原理与工具设计

模型只会输出文字。要让它"查余额"，需要一种约定：模型用固定格式说"调用哪个函数、参数是什么"，程序据此执行。这就是 Function Calling（也叫 Tool Use）。

请求里附上工具清单，每个工具三个要素：名字、描述（何时用）、参数的 JSON Schema（类型、必填、枚举）。模型经过训练会在需要时输出结构化的调用意图，宿主程序解析、执行、回填。模型只产出调用意图，执行在宿主侧。 严格模式（strict: true）可让参数必定符合 schema。[3] [4]

函数本身留在宿主程序；模型只看到 schema

完整走一遍：一个工具的定义与校验。 练习文件注册了 get_balance：

reg.register("get_balance", "查询账户余额。只读。参数 account 为账号，如 A001。",
             {"type": "object", "properties": {"account": {"type": "string"}}, "required": ["account"]},
             lambda account: balances[account], read_only=True)

dispatch 依次检查：工具是否存在、参数能否解析成 JSON 对象、必填参数是否齐全、是否有未知参数、类型是否正确，全部通过后才执行，执行时的异常也转换成 Error: 开头的结果。测试中五个故意写错的调用都得到了错误结果，循环照常结束。

输出精简只返回模型需要的字段，长输出落盘（6.6）返回整页 HTML
按场景裁剪不可信入口只开放只读工具；隐藏的工具连 schema 都不发所有渠道一套全量工具

规则写在机制里。 用户博客的例子：读文件工具给每行加了行号，模型编辑时把行号抄进了"要替换的原文"，匹配失败；在描述和报错里反复说明也没用，改成代码自动剥离行号前缀后才解决。[10] 结论：能用代码确定处理的约束，就别交给模型去"读懂"；提示负责理解，代码负责保证。

要点： Function Calling 原理的标准答案句："开发者用 JSON Schema 声明工具，模型根据描述决定是否调用并生成参数，宿主程序校验后执行，再把结果以 tool 消息回填给模型继续推理。"

6.5 MCP、A2A、ACP、Skills、Rules：各自连接哪两端

为什么需要协议。 5 个 Agent 产品各自给 20 个工具写适配，需要 5×20 = 100 份集成；有了统一协议，各方只实现一次，变成 5+20 = 25 份。

MCP（Model Context Protocol）。 连接 Agent 应用与工具或数据源。它采用三方架构：** Host**（宿主应用）、Host 中的 Client（每个连接一个）和外部的 Server（提供能力）。消息格式是 JSON-RPC 2.0。Server 暴露三类原语：** Tools**（可调用的函数）、Resources（可读取的数据）、Prompts（提示模板）。传输方式上，本地子进程用 stdio，远程用 Streamable HTTP（早期的 HTTP+SSE 传输已弃用）。截至本书写作时（2026 年 10 月），最新的修订版是 2026-07-28，它把协议改为无状态：去掉了初始化握手和会话头，每个请求自带协议版本和客户端能力。[11] [12]

MCP 管 Agent↔工具，A2A 管 Agent↔Agent，ACP 管编辑器↔Agent，Skills 是本地的说明书包

A2A（Agent2Agent）。 连接 Agent 与 Agent，让不同厂商的 Agent 互相委派任务，而不必共享内部的记忆和工具。核心概念有：** Agent Card**（JSON 格式的名片，写明能力、端点和认证方式，通常位于 /.well-known/agent-card.json）、Task（有生命周期的工作单元，状态包括进行中、需要输入、完成、失败、取消等），以及 Message、Part、Artifact。传输绑定有 JSON-RPC、gRPC、HTTP+JSON，流式更新使用 SSE。A2A 由 Google 提出，截至本书写作时由 Linux 基金会托管，2026 年发布的 1.0 是第一个稳定版本。[13]

ACP 与 Skills。 博客中的 ACP 指 Agent Client Protocol：连接编辑器与 Agent，本地时 Agent 作为编辑器子进程经 stdio 走 JSON-RPC，定位类似 LSP。[14] [2]（另有同缩写的 IBM Agent Communication Protocol，2025 年 8 月已并入 A2A。）Skills 是一个文件夹：SKILL.md（name、description 加操作说明）和可选脚本、资料。Agent 启动时只加载每个技能的名字和描述，任务匹配时才读入全文，执行时再按需运行脚本，即"渐进披露"。[15] Rules 是始终注入系统提示的项目约定（AGENTS.md、CLAUDE.md 等）。

名称连接的两端解决的问题加载方式
MCPAgent ↔ 工具 / 数据工具接入标准化连接 Server，工具 schema 进入请求
A2AAgent ↔ Agent跨系统委派与协作发现 Agent Card，按 Task 交互
ACP编辑器 ↔ Agent任意编辑器驱动任意 Agent编辑器启动 Agent 子进程
SkillsAgent ↔ 本地知识包程序性知识复用先索引、命中后全文载入
RulesAgent ↔ 项目约定统一风格与禁忌每次对话都注入

要点：

  • MCP 与 A2A 是互补关系：MCP 让一个 Agent 用上外部工具（纵向），A2A 让多个 Agent 彼此协作（横向）。一个 Agent 可以同时是 A2A 的服务方和 MCP 的客户端。
  • Skill、MCP、Rule 的区别：Rule 是"永远要遵守的约定"，常驻上下文；Skill 是"某类任务的做法"，按需载入，可附带脚本；MCP 是"可调用的外部能力"，以工具形式出现。
  • 协议只解决"怎么连"，授权和业务约束仍由外壳负责。第三方 MCP Server 和技能都属于不可信代码，安装前要审查（供应链风险，6.21）。

6.6 记忆与上下文：会话太长怎么办

一个排障会话跑了 40 步，每步工具返回几千 token 的日志，很快塞满窗口；用户下周回来，还希望 Agent 记得"我只看对公账户"。前者是上下文管理，后者是长期记忆。

短期与长期记忆。

类型存在哪里生命周期例子
短期（工作记忆）当前消息列表本次会话刚才查到的余额
长期 · 摘要式文件或数据库里的一段文字跨会话"用户偏好简短回答"
长期 · 结构化表、键值对、知识图谱跨会话，可精确查询用户 ID → 常用账户
长期 · 检索式向量库 + 关键词索引跨会话，按相关性取回历史工单、过往对话片段
程序性Skills、工作流长期"对账任务按这五步做"

会话过长的四种处理方法：

  • 截断：丢掉最早的消息，可能丢失关键的约定。
  • 滑动窗口：只保留最近 N 轮，系统提示固定保留。
  • 摘要压缩（compaction）：把较早的历史换成模型写的摘要。
  • 检索式记忆：把历史存入索引，需要时再取回。

前缀缓存与 KV cache。 KV cache（第 5 章 5.14）在一次生成之内避免重复计算；前缀缓存把这一点扩展到跨请求：开头完全相同的请求复用前缀的计算结果，首 token 延迟和输入费用都会下降。前缀按工具、系统提示、消息的顺序排列，任何一处改动都会使它之后的缓存失效。[16] 所以系统提示和工具清单要保持稳定，时间戳等容易变化的信息放到后面；会话中途写入的记忆，到下一个会话才放进系统提示。例如 4000 个 token 中有 3500 个不变，则 87.5% 可以命中缓存。

6.7 提示工程、RAG、微调：改的是哪一层

"模型答不好我们的产品问题，该加 RAG 还是微调？"这是选型题的第一问。回答前先看三种手段分别改了什么。

  • 提示工程：改输入的指令、格式和示例，模型参数不变。
  • RAG（检索增强生成）：回答前从外部知识库检索相关片段放进输入，参数不变，知识可随时更新、可追溯来源。[18]
  • 微调：用训练数据更新参数（全量或 LoRA 等低秩附加参数），适合改风格、格式、领域行为。原理见第 5 章。

提示工程和 RAG 都作用在输入上；只有微调改参数

6.9 切块：长度、重叠与结构

为什么需要切块。 整份文档太长，放不进上下文；一份文档讲多个主题，整体算一个向量会把主题混在一起。切块要同时满足：块足够小，检索时能精确定位；块足够完整，生成时不缺上下文。

策略怎样切主要风险
固定长度每 C 个 token 一块可能把定义和例外拆开
递归按结构先按标题、段落，超长再按句子拆文档解析出错时标题不准
语义切分相邻句子语义变化大处切开计算贵，边界不稳定
父子块小块用来检索，命中后把所在大节交给模型大节太长会引入噪声
表格专门处理每行连同表头、单位一起成块纯文本切法会让数字失去列名

滑动重叠。 长度 L、块长 C、重叠 O，每块起点比上一块后移 C − O（步长）。末块允许较短时，块数为 L ≤ C 时 1 块，否则 1 + ⌈(L − C)/(C − O)⌉。

L=1200、C=500、O=100：步长 400，三块，深色格是相邻块重复的 100 个 token

示例： L = 1200、C = 500、O = 100：步长 400。块 1 是 [0, 500)；500 < 1200，继续，块 2 是 [400, 900)；900 < 1200，继续，块 3 从 800 开始，800 + 500 ≥ 1200，截到 1200 后结束。公式验证：1 + ⌈700/400⌉ = 1 + 2 = 3 块，末块 [800, 1200) 长 400。再算一个：L = 1000、C = 300、O = 50，步长 250，块数 1 + ⌈700/250⌉ = 4，分别是 [0,300)、[250,550)、[500,800)、[750,1000)。练习文件的 chunk_spans 和 chunk_count 对这几组数据互相印证。

def chunk_spans(L, C, O):
    step = C - O
    spans, s = [], 0
    while True:
        spans.append((s, min(s + C, L)))
        if s + C >= L:
            return spans
        s += step

要点： 重叠让跨边界的信息至少完整出现在一块里；代价是存储约为 C/(C − O) 倍（O/C = 20% 时约 1.25 倍），重叠太大时 Top-k 可能全是同一段的副本。块大小是实验参数，用检索指标调。

6.10 嵌入模型与向量数据库：近似最近邻怎样做到快

嵌入模型把文字变成几百到几千维的向量，语义相近则夹角小。100 万块 768 维 float32 向量约 1,000,000 × 768 × 4 字节 ≈ 3.07 GB，每次逐一比较太慢，于是用近似最近邻（ANN）索引：牺牲一点召回率，换数量级的速度。

嵌入模型怎么选。 看语言与领域、最大输入长度、维度（影响存储和速度）、部署方式（开源私有部署如 BGE 系列，或云 API 如 OpenAI Embedding）、数据能否出境，最终以自建评测集上的 Recall@k 为准。换嵌入模型后新旧向量不在同一空间，整库要重建。

IVF：先分桶再找。 用聚类把所有向量分成 nlist 个桶（每桶一个中心）。查询时先找离查询最近的 nprobe 个中心，只在这些桶里逐个比较。[19]

HNSW：多层导航图。 每个向量是图中的一个节点，与若干近邻相连。上层节点少、边跨度大，像高速公路；底层包含全部节点、边短。查询从顶层入口出发，在每层贪心地走向更近的邻居，再下到下一层细找。[20]

查询从顶层 A 跳到 F，逐层下降，在底层找到最近的 E

完整走一遍：IVF 少算了多少。 100 万向量分成 nlist = 1000 个桶，平均每桶 1000 个；nprobe = 10。一次查询先和 1000 个中心比较，再比较 10 × 1000 = 10,000 个向量，合计约 11,000 次，约为暴力搜索 100 万次的 1/91。nprobe 调大，召回率上升、速度下降。

索引原理优点代价
Flat（暴力）逐个比较精确慢，适合小库或做基准
IVF聚类分桶，只搜 nprobe 个桶内存省，建索引快需要训练聚类，边界附近会漏
HNSW多层近邻图贪心搜索查询快、召回高内存占用大，删除和更新较麻烦
量化（PQ 等）压缩向量大幅省内存精度下降

向量数据库选型维度。 规模与增长、延迟与 QPS、索引类型、元数据过滤与混合检索、多租户隔离、更新频率、备份、部署方式（自建开源如 Milvus、托管如 Pinecone、现有数据库的向量扩展如 pgvector、Elasticsearch 向量检索）、运维与合规。几十万条且已有 PostgreSQL 时，向量扩展往往就够；上亿规模、高并发再上专门的分布式向量库。

6.11 混合检索、RRF 融合与 Rerank

为什么要两路召回。 向量检索擅长语义近似（"免年费"与"减免年费"），但对精确编号、罕见术语不敏感；BM25 关键词检索正好相反。两路各取前几名再融合，两类问题都能照顾到。[21]

BM25 与 RRF。 BM25 按词频打分，用 IDF 提高稀有词权重、按文档长度归一化。两路分数尺度不同，直接相加没有意义。RRF（倒数排名融合）只看名次：在某列表排第 r 名（从 1 起）得 1/(k + r)，各列表相加，常用 k = 60。[22]

先两路召回保证不漏，再融合、重排保证排得准

示例： 5 个文档（已分词）：D1"信用卡 年费 减免 条件……"、D2"信用卡 挂失 补卡 流程"、D3"白金卡 首年 免 年费 次年……免 年费"、D4"借记卡 账户 管理费 减免"、D5"白金卡 机场 贵宾厅 权益"。查询"白金卡 年费 免"。向量检索用词袋余弦模拟，并用同义词表让它认出"免≈减免、白金卡≈信用卡"。

def rrf(rankings, k=60):
    score = Counter()
    for lst in rankings:
        for r, doc in enumerate(lst, start=1):
            score[doc] += 1.0 / (k + r)
    return sorted(score, key=lambda d: (-score[d], d)), score

Rerank。 初筛用双塔模型（问题和文档分别编码，快）；重排用交叉编码器（问题和文档拼在一起逐对打分，准但慢），只对几十个候选做。重排只调整已有候选的顺序，没召回的证据找不回来。

检索结果冲突（虚构）。 A 写"2025 年阈值 200 万"，B 写"2026 年阈值 100 万"，用户只问"阈值是多少"：按生效日期、权威性和是否废止判断，必要时追问年份，证据不足就说明无法确认。

要点： 标准答案句："BM25 管精确词，向量管语义，RRF 按名次融合避免分数尺度不一致，Rerank 用交叉编码器精排少量候选。"

6.12 RAG 进阶：多查询、GraphRAG、结构化数据与多模态

为什么需要进阶做法。 真实问题会打破"一问一检索"：提问措辞和文档差很远；问题要综合全库；答案在数据库表里；证据是图或表。

多查询与 RAG-Fusion。 让模型把原问题改写成 3 到 5 个角度的查询，各自检索，再用 RRF 融合；代价是多一次改写调用和多路检索延迟。[23] 类似的还有 HyDE（用模型写的假想答案的向量去检索）和问题分解。

GraphRAG。 离线用模型抽取实体和关系建成知识图谱，用社区发现把图分成主题社区并预生成摘要；在线时全局问题汇总社区摘要，局部问题从相关实体沿边扩展。[24] 适合跨文档综合和多跳关系问题（"A 公司担保方的实际控制人是谁"）；代价是离线要对全库调模型，更新时维护复杂。

GraphRAG：离线建图和社区摘要，在线分局部与全局两种查询

结构化数据：Text-to-SQL。 "上季度华东区对公贷款余额"在数据库里，文本化后做向量检索既不准也算不了聚合。做法是让模型按表结构生成 SQL，程序执行，再用结果组织回答。

Text-to-SQL 的安全链路

1 / 4

第1步 · 检索相关表结构：只把可能用到的表和字段说明放进提示

2 / 4

第2步 · 模型生成 SQL

3 / 4

第3步 · 程序校验：只允许 SELECT、只读账号、行级权限、加 LIMIT 和超时

4 / 4

第4步 · 执行并回答：结果连同 SQL 一起展示，便于核对

多模态 RAG：图片和表格。 有三种做法：

  • 转成文字：用 OCR 识别图中的文字，用视觉模型写出图片描述，把表格转成“每行加表头”的文本，然后按文本的流程检索。
  • 多模态嵌入：用图文共享向量空间的模型（CLIP 一类，见第 5 章）直接对图片编码。
  • 混合：用文字描述检索，生成时把原图交给多模态模型。

表格要保留表头、单位和行列关系。

要点：

  • 措辞不匹配用多查询 / RAG-Fusion；需要全库综合或多跳关系用 GraphRAG；数值与聚合用 Text-to-SQL；图表用 OCR / 描述或多模态嵌入。
  • Text-to-SQL 的执行要只读、限表、限行、限时，SQL 本身也是要校验的不可信输入。

6.13 拼接上下文：Lost in the Middle 与多租户隔离

为什么要关心拼接。 检索选出了 8 段证据，按什么顺序放进提示？研究发现，当相关信息位于长上下文的中间时，模型的利用效果明显差于放在开头或结尾，准确率随位置呈 U 形。[25]

示意曲线（虚构数值）：证据放在两端时被利用得更好

对策：

  • 少而精：重排后只放入真正相关的几段，减少处于中间位置的内容。
  • 把最相关的放在开头和结尾：例如重排后的名次 1、2、3、4、5 按 1、3、5、4、2 的顺序摆放，使第 1、2 名分处两端。
  • 关键的约束（如“只依据证据回答”）在问题之前再重复一次。
  • 对长文档先分段摘要，再综合。

多租户隔离。 一个 RAG 平台服务多家分行或多个企业客户时，A 客户绝不能检索到 B 客户的文档。两种主要做法：

做法怎样隔离优点风险
元数据过滤每块带 tenant_id、权限标签，检索时强制加过滤条件一套索引，省资源过滤条件漏加就越权；先检索后过滤会让结果数不够
命名空间 / 独立集合每个租户一个分区或一个索引物理隔离清楚，删除方便租户多时管理成本高
独立实例大客户单独部署最强隔离，满足合规成本最高

租户条件由服务端根据身份附加，模型和用户输入都无法改写

要点： 标准答案句："租户与权限过滤在检索阶段由服务端强制执行（预过滤），依据是认证得到的身份，而不是模型或用户提供的参数。" 缓存也要按租户区分键，否则会把 A 的答案返回给 B。

6.14 RAG 评估与十大坑

为什么要分层评估。 答案错了，可能是没检索到、检索到了但排在后面、排在前面但模型没用上、或者用上了但编了额外内容。不分层就无从下手。

检索层看找没找到，生成层看有没有依据、有没有答到点上

检索指标。 Recall@k：相关文档中有多少比例出现在前 k 个结果里。** Precision@k**：前 k 个结果中相关的比例。** MRR（平均倒数排名）**：每个问题取第一个相关结果的名次 r，记 1/r，对所有问题求平均。

生成指标。 忠实度：答案中的陈述有多少能被检索到的上下文支持（RAGAS 的算法是把答案拆成陈述逐条判断）；答案相关性：是否回应了问题；上下文精确率 / 召回率：上下文中有用信息的占比、所需信息的覆盖率。[26]

示例： 三个问题，第一个相关结果分别排在第 2、第 1、第 3 名：MRR = (1/2 + 1 + 1/3)/3 ≈ 0.611。6.11 的例子中，BM25 的 Recall@2 = 1/2，向量与 RRF 都是 1。忠实度：答案拆出 5 条陈述，4 条有上下文支持，忠实度 = 0.8。

def mrr(list_of_ranked, list_of_relevant):
    total = 0.0
    for ranked, rel in zip(list_of_ranked, list_of_relevant):
        for r, d in enumerate(ranked, start=1):
            if d in rel:
                total += 1.0 / r
                break
    return total / len(list_of_ranked)

6.15 幻觉：成因、减少方法与结构化输出校验

为什么会产生幻觉。 幻觉是流畅但与事实或给定资料不符的输出，成因有四类：

  • 训练目标：模型学习的是下一个 token 最可能是什么，流畅与真实是两回事。
  • 知识缺失或过时。
  • 上下文问题：检索到了错误的资料，或者关键信息埋在中间。
  • 解码与提示：温度过高，或者提示暗示“必须给出答案”。

减少幻觉的五道措施：给依据、要引用、验结构、多采样、允许拒答

减少幻觉的方法。

  • 检索增强：让模型依据检索到的资料回答（6.8）。
  • 引用约束：要求每个结论标注证据编号，程序检查引用的编号确实存在、引用的原文确实包含相关数字。
  • 拒答：提示中明确"资料中没有就回答不知道"，并设检索相关度阈值，低于阈值直接走拒答或转人工。
  • 自洽性检验（self-consistency）：对同一问题采样多次，取多数答案；各次答案分歧大时说明模型不确定，可降级处理。[27]
  • 结构化输出校验：需要程序消费的输出，按三关校验（下面展开）。

结构化输出的三关。 提示里写"请输出 JSON"只是请求，程序要逐关检查：

检查检查什么失败例子
解析能否被标准 JSON 解析器解析外面包了 Markdown 代码围栏；对象末尾多一个逗号
Schema必填字段、类型、枚举amount 是字符串 "100"；decision 写成 approve 而枚举只允许 review / reject
业务权限、政策、证据两关都过，但用户无权执行这个操作

2 / 4

4 / 4

任何一关超过重试次数：拒绝并转人工

  "required":["decision","amount"],
  "properties":{

要点： 标准答案句："幻觉源于训练目标、知识缺失、上下文质量和解码方式；用检索增强、引用约束、结构化校验、自洽性检验和拒答机制组合降低，并用忠实度指标持续监测。"

6.16 多 Agent：什么时候值得拆，拆了要付什么代价

为什么会用多 Agent。 一个 Agent 的上下文窗口有限，工具多了容易选错；有些子任务可以并行；有些场景需要"一个做、一个查"。把任务分给多个各有专长、各有独立上下文的 Agent，可以缓解这些问题。

两种组织方式。

左：Supervisor 中心调度；右：Peer-to-Peer 彼此直接通信

方面Supervisor（中心化）Peer-to-Peer（去中心化）
控制流清楚，易追踪和审计灵活，可涌现协作
单点Supervisor 是瓶颈和单点无单点
一致性由中心维护全局状态各自状态，难以一致
调试容易难，消息可能循环
适合企业流程、客服、审批开放协作、模拟、跨组织（常借助 A2A）

多 Agent 新引入的复杂性。 通信、一致性（对同一事实的认识不同步）、成本（token 成倍增加）、延迟、责任归属、循环委派；Agent 之间的消息也是不可信输入，被注入的 Agent 会把恶意指令传下去。

依赖时序：把任务画成 DAG。 每个子任务有前置条件。读授权交易 A 与读最新政策 B 互不依赖；计算风险分 C 依赖 A 和 B；合规判断 D 依赖 C；生成报告 E 依赖 D。

A、B 并行；C 等两者都完成；关键路径长度决定总耗时

若每个任务耗时 1 秒，串行要 5 秒，按 DAG 调度只要 4 秒（A、B 并行占 1 秒）；练习文件的 dag_finish_time 按关键路径算出这个数。前置节点失败时要重试或停止，不能让模型"想象"出缺失的数据继续。

子 Agent 的上下文与权限。 子 Agent 有独立上下文，只把结论或失败诊断交回父 Agent，这是拆分的主要动机之一；委派可以从空白开始（任务描述必须自足），也可以复制父对话前缀（复用缓存）。权限规则：委派时固定权限，只降不升，子会话内无法扩大；限制委派深度和并发子 Agent 数，满了直接拒绝而不排队（父 Agent 可能在等自己占着的位置）；权限不足时向上报告。[5]

要点：

  • 何时用多 Agent：子任务可并行、需要不同工具集或不同专长、单个上下文装不下、需要独立复核。否则单 Agent 加好工具更简单、更便宜。
  • 多个 Agent 都同意，也只是多个模型的意见；授权和最终执行仍走统一的执行层。

6.17 终止条件与死循环：怎样让 Agent 一定会停

为什么会死循环。 模型可能反复用同样参数调同一个工具，在两个工具间来回切换，或一直"再查一下"不说完成。没有外部约束，就没有任何机制保证它会停。

终止机制分两类。 正常终止：模型回复中没有工具调用；或者达到任务完成条件（例如测试通过、表单字段全部填满）。** 强制终止**：

机制检测什么动作
步数上限一轮中模型调用次数达到上限强制停止，返回"未完成"及进展
token / 费用预算累计消耗用完即停
墙钟超时总运行时间超时即停，并取消正在执行的工具
重复调用检测相同"工具名 + 规范化参数"指纹出现次数先提醒，再达到更高阈值时停止
无进展检测连续若干步没有新信息（结果哈希不变、目标状态不变）提醒换策略或停止

完整走一遍：重复检测与预算（练习文件 run_agent）。 指纹由工具名加按键排序的参数组成，所以 {"a":1,"b":2} 和 {"b":2,"a":1} 算同一个调用。设提醒阈值 3、停止阈值 5：

1 / 5

第1步 · 第 1、2 次：正常返回 5200

2 / 5

第2步 · 第 3 次：结果后追加提醒“同一工具与参数已调用 3 次，请换思路或结束”

3 / 5

第3步 · 第 4 次：继续提醒

4 / 5

第4步 · 第 5 次：达到停止阈值，本步结果照常回填后结束，状态 stopped_repeat

5 / 5

第5步 · 预算例：每步 400 token，预算 1000：第 3 步后累计 1200，停止

无论哪种停止，已发出的调用都已配好结果，日志可继续恢复

提醒与停止的分工。 有些重复是正当的，例如轮询一个任务状态，所以重复检测通常先只提醒、把判断交给模型；步数上限、预算和超时才是硬保证，由外壳强制执行，不依赖模型配合。[5]

长程任务的一致性。 运行几十步的任务容易忘记目标，可以采取三项措施：

  • 计划锚点：把目标和计划写成结构化的待办列表，放在上下文的固定位置，每步更新，压缩时保留。
  • 检查点：在关键阶段持久化状态，崩溃后从检查点恢复。
  • 阶段验证：每个阶段运行可执行的验证，以工具的结果为准。

生产环境中出现无限循环时怎样止损：

  1. 用功能开关降级该 Agent 或工具，在全局收紧步数上限，取消异常的会话；
  2. 在网关上按用户和租户限速，并限制 token 预算；
  3. 按追踪 ID 找出循环的轨迹，确定是哪个结果或错误信息引发了重试；
  4. 修正错误信息，加入重复检测和无进展检测；
  5. 增加费用告警，并把这条轨迹加入回归测试集。

要点： 标准答案句："终止条件分正常终止（无工具调用 / 目标达成）和强制终止（步数、预算、超时）；重复调用用指纹检测，先提醒再停止；硬上限由外壳保证。"

6.18 崩溃、重复执行与取消：让副作用可控

付款接口已扣款，响应却超时没回来；或进程在执行中途被杀。重启后外壳不知道调用是否生效：重做可能扣两次，不做可能漏付。「计算机系统导论」第 13 章 13.6 讲过超时的三种可能，「计算机系统导论」第 10 章 10.11 讲过 WAL，这里把它们用到工具调用上。[17]

先持久化，再执行。 顺序是：先经过审批，再写入 tool_start 记录（带幂等键）并刷盘，然后执行，最后写入结果；写入 tool_start 失败就不执行。日志只追加，模型看到的每条消息都能从日志重建，所以恢复和排查都可以复现。

日志里有没有 tool_start，是恢复时唯一可靠的依据

崩溃恢复的三种分类。 重启时，外壳给缺结果的调用补结果：

日志状态判定恢复动作
没有 tool_startNOT_STARTED补"未执行"结果，模型可决定重新调用
有 tool_start，工具只读或幂等可安全重做用同一个幂等键重做
有 tool_start，工具有副作用且不幂等OUTCOME_UNKNOWN补"结果未知，可能已生效，先核实外部状态或问用户，不要直接重试"

"开始了还没生效"和"已经生效"在日志里一模一样，外壳只能按更坏的情况处理，并把"结果未知"如实告诉模型。

幂等键。 键 = 会话 ID + 调用 ID。两者都在执行前写进日志，重启后同一个调用拿到同一个键。服务端按键去重：见过这个键，就返回上次的回执，不再扣款。

def charge(self, to, amount, key):
    if self.idempotent:
        for e in self.ledger:
            if e["key"] == key:
                return e["receipt"]      # 同一个键：返回上次的回执
    receipt = "rcpt-%d" % (len(self.ledger) + 1)
    self.ledger.append({"to": to, "amount": amount, "key": key, "receipt": receipt})
    return receipt

练习文件中：幂等服务用同一个键调用两次，账本只有 1 笔、两次都返回 rcpt-1；对照组服务不认键，盲目重做后账本出现 2 笔。

恰好一次的边界。 结果未知时，外壳只有两种选择：不重试是最多一次（不会重复，可能漏），重试是至少一次（不会漏，可能重复）。只有服务端按幂等键去重，"至少一次"的重试才等于"恰好一次"。这条结论与「计算机系统导论」第 13 章 13.11 消息队列的结论相同。

取消：杀掉整个进程组。 只停止等待模型不够，工具起的子进程还在跑。命令放进新进程组，取消时对整组先发 SIGTERM，宽限后再发 SIGKILL（「计算机系统导论」第 7 章 7.9）；调用 setsid 逃出进程组的要靠 cgroup 或容器。进程恰好自己结束时按"完成"记；审批期间按了取消，批准后执行前要再查一次。取消不等于回滚：已写的文件、已发的请求收不回，回滚靠 git 工作区、独立 worktree 或业务补偿（Saga）。

提交闸门：验证绑定内容哈希。 规则"没验证通过不能提交"有个漏洞：先验证、再修改、再提交，提交的是没验证过的版本，这是典型的 TOCTOU（检查时与使用时不一致）。修正：验证记录里存被验证内容的哈希；提交时重算当前内容的哈希，日志里没有这个哈希的验证记录就拒绝。

提交闸门挡住“验证后又改”

1 / 4

第1步 · 写入 v1，直接提交：没有验证记录，拒绝

2 / 4

第2步 · 运行测试通过：记下 verified h1

3 / 4

第3步 · 提交 v1：当前哈希 h1 在验证集合里，通过

4 / 4

第4步 · 又改成 v2 再提交：哈希 h2 没验证过，拒绝

银行类比：审批要绑定具体的收款方和金额，改了任何一项都要重新审批

另外两条：验证器由用户配置，模型只能触发它，不能改它跑什么；而且约束要覆盖所有路径——闸门只管"提交"工具，模型却能在 shell 里直接执行 git commit 绕过，所以 shell 要在沙箱里运行并让 .git 只读（6.21）。

要点：

  • 标准答案句："先写日志再执行；用稳定的幂等键让重试可去重；崩溃恢复按未开始 / 可重做 / 结果未知三类处理；结果未知时如实上报，不盲目重试。"

6.19 性能与成本：延迟、流式、并发估算

为什么需要估算。 "日均 100 万次查询需要多少并发、多少 token 吞吐"是系统设计题的第一步；"Agent 回答太慢"是线上最常见的抱怨。两者都要先把时间和 token 拆开算。

一次 Agent 请求的延迟构成。 模型调用 4 次、每次 1.5 秒，工具调用 3 次、每次 0.8 秒，串行共 4 × 1.5 + 3 × 0.8 = 8.4 秒。下表是常见优化：

并行工具调用互不依赖的只读调用同时执行3 次 0.8 秒并行后约 0.8 秒

只有声明为并发安全（通常是只读）的调用才并行，写操作串行并作为屏障；结果总按模型给出的顺序回填。

SSE 流式与断线重连。 SSE 是一条长 HTTP 响应，服务端不断写入 data: 行，每个事件可带 id:。断线后浏览器的 EventSource 自动重连，在请求头 Last-Event-ID 带上最后收到的 id，服务端从下一个事件补发；retry: 设重连等待毫秒数。[28] 要能补发，服务端得按会话缓存已生成的事件（如 Redis），并让生成任务与连接解耦。

事件带 id，重连时带上最后的 id，服务端从缓冲区补发

MCP 此前的 Streamable HTTP 传输也支持按 Last-Event-ID 续传；截至本书写作时，2026-07-28 修订版连同会话头一起去掉了这一机制。[12] 续传因此成为应用层自己的设计选择。

成本控制。 小模型路由；前缀、语义与检索结果缓存；检索少而精、压缩历史、长输出落盘；每用户与每租户的 token 预算、速率限制和步数上限；离线任务走批量接口；按租户计量并设费用告警。

并发翻 10 倍、100 倍时的瓶颈。 10 倍：先卡模型服务的速率配额与推理 GPU，再是向量库与 Rerank；靠多供应商、排队分级、扩容、缓存、小模型分流。100 倍：GPU 供给与费用成为约束，KV cache 显存限制每卡并发，长连接与下游业务系统被放大的调用压垮；靠分级降级（只开 RAG、关多步 Agent）、异步化、租户配额、下游限流熔断。

要点： 标准答案句："并发 = QPS × 平均时长；延迟优化靠流式、并行、缓存、路由、减少往返；规模放大后瓶颈依次是模型配额与 GPU、检索服务、长连接、下游系统。"

6.20 评估、可观测性与测试：怎样知道 Agent 好不好

为什么 Agent 评估更难。 LLM 评估是"给输入、看输出"。Agent 的输出是一条轨迹：调了哪些工具、花了多少步、有没有越权，最后才是答案；同一任务可有多条正确轨迹，环境状态也会被改变，所以要在可重置的环境里跑，既查最终状态也查过程。

维度LLM 评估Agent 评估
对象单次输出多步轨迹 + 最终环境状态
正确性与参考答案比较任务是否完成（看环境状态，例如订单确实被改了）
过程一般不看工具选择、参数、步数、是否越权、是否重复
稳定性单次得分多次运行是否都成功
成本tokentoken、步数、墙钟时间、工具调用费用

任务完成率与轨迹质量的量化。 完成率 = 成功数 / 总数，成功由程序判定环境状态。稳定性看 pass^k：同一任务跑 k 次全部成功的比例。[29] 单次成功率 0.8 且各次独立时，pass^3 = 0.512，而"3 次至少成功 1 次"是 0.992，面向用户要看前者。轨迹质量：工具选择准确率、参数正确率、冗余步数、违规次数、平均 token 与时延。

LLM-as-judge 的偏差。 用模型打分便宜，但有位置偏差（偏向某个位置的候选）、冗长偏差（偏向更长的回答）、自我偏好。[30] 对策：交换顺序各评一次；给评分细则和参考答案；换一家模型当裁判；定期用人工标注校准。

A/B 测试。 按用户随机分流（同一用户始终在同一组），比较任务完成率、满意度、成本与延迟，同时监控越权率、费用等护栏指标。例：两组各 2000 个会话，完成率 70% 与 74%，差值的标准误约 0.0142，差值约为 2.8 个标准误，在 5% 显著性水平下显著。

用户反馈：信号还是噪声。 单条点赞点踩稀疏且有偏（不满意的人更愿意反馈），是噪声；聚合到足够样本、按问题类型分桶、与客观指标（工具报错、转人工、重复提问）交叉验证、再人工复核后，才是信号。用户是否复制答案、是否立刻改写重问这类隐式信号往往更可靠。

可观测性：日志、指标、追踪。

一次请求是一条 trace，每次模型调用、检索、工具调用是一个 span

日志要能回答"模型当时看到了什么"；指标看完成率、p95 延迟、每请求 token、工具错误率、重复调用率、转人工率；追踪把一次请求里所有调用串起来，常用 OpenTelemetry。

Agent 经常调错工具，怎样排查。 从追踪里收集调错样本并分类（选错工具、参数错、该调没调、不该调却调）；依次检查工具描述是否含糊或互相重叠、工具是否过多、参数是否缺少枚举、工具说明是否被压缩或挤到中间、报错能否指导改正；把样本做成回归评测集，改完对比工具选择准确率。

Agent 的测试方法。 真实模型每次回答都不一样，很难让它"恰好在第三步给出错误参数"，所以：

  • 假模型：外壳只依赖 chat(messages, tools) 接口，测试时换成按脚本回答的 FakeLLM；它按"已有几条 assistant 消息"决定答第几项，崩溃重启后能从断点接着答。
  • 故障注入：在指定位置（写 tool_start 前、执行后结果落盘前）让进程立刻退出，再重启检查恢复结果。
  • 对日志检查不变式：每个测试跑完，检查每个调用恰好一条结果（check_pairing）、每次执行都有批准记录、每次提交的哈希都验证过、步数不超上限；检查器本身也要用坏日志测一遍。
  • 变异测试（「计算机系统导论」第 11 章 11.14）：故意放进缺陷（闸门不查哈希、取消只杀主进程、恢复一律重做），确认至少一个测试失败。[17]

6.21 安全：提示注入、权限、沙箱与合规

为什么 Agent 的安全更难。 聊天机器人说错话是内容风险；Agent 能调工具，被操纵后会做错事：转账、删文件、外发数据。OWASP 的 LLM 风险榜把提示注入列第一，另列"过度代理"；2025 年 12 月发布的 Agentic 应用风险榜列出目标劫持、工具滥用、权限滥用、记忆与上下文投毒、Agent 间通信不安全、级联失败等。[31] [32]

提示注入。 直接注入：用户输入里写"忽略之前的规则……"。** 间接注入**：指令藏在 Agent 读取的网页、邮件、PDF、工具结果或另一个 Agent 的消息里，模型分不清"要处理的数据"和"要服从的指令"。写进长期记忆的注入更危险：网页里的指令被当作"用户偏好"存进记忆，之后每个会话开始时都被加载。[33]

上面几层降低成功率，下面两层决定最坏情况的损失

练习文件的 scan_untrusted 能拦下"忽略之前的所有指令"这类明显句式，换个说法（"请无视上文要求"）就漏过。所以真正的边界在执行层和隔离层：模型就算被说服，也没有权限和网络通路去完成危害动作。

权限落到执行层。

  • 权限档位：每次都问 → 只读放行、写操作问人 → 沙箱内随意 → 全部放行。档位越松越靠沙箱兜底；"要不要问人"与"能碰哪里"是两个独立维度。
  • 沙箱：用容器、namespace / Landlock、Seatbelt 等 OS 级隔离限制读写目录和联网，常见三档为只读、可写工作区、完全访问（原理见「计算机系统导论」第 12 章 12.14 访问控制）。
  • 失败即关闭（fail-closed）：沙箱不可用就拒绝执行；无审批服务或无人值守时，需审批的操作一律拒绝；审计写不进去，请求失败。
  • 多路径通往同一效果：只在读文件工具上查路径，模型可以在 shell 里 cat；闸门只管提交工具，模型可以在 shell 里 git commit。约束要覆盖所有路径，或用 OS 隔离堵死其他路径。
  • 底线不可覆盖：可调策略之间可互相覆盖；所有者底线一旦拒绝，后续规则不能改回允许。
  • 被拒绝即停：用户拒绝后结束本轮、交还控制权，同批剩余调用补"未执行"结果。
  • 子 Agent 权限只降不升（6.16）。

隐私、合规与过滤。 数据最小化（工具只返回必要字段）；身份证号、卡号在进入提示、日志前脱敏；客户数据能否发给境外模型服务按监管判断，敏感场景私有部署；审计记录谁让 Agent 做了什么、依据哪条授权；会话与记忆按期限保存、支持删除。输入侧做注入与敏感信息检测；输出侧做泄露与有害内容检测，渲染前转义防 XSS（「计算机系统导论」第 12 章 12.16）。

AI 红队。 有组织地模拟注入、越狱、诱导泄露系统提示、越权调用、记忆投毒、多轮渐进诱导，成功样本加入回归测试集。

Alignment 在 Agent 语境的含义。 对齐指模型行为符合人的意图和价值（RLHF 等原理见第 7 章）。在 Agent 中多三层：意图对齐（"让测试通过"不能靠删测试）、授权对齐（只在授权范围内行动）、可控（人能观察、打断、纠正）。** 能力与安全的权衡**：工具和自主性越多，出错时损失上限越高；按风险分级（只读自动、写操作确认、资金操作强审批），默认最小权限，临时提权单次有效。

要点： 提示注入防御的标准答案："注入无法在模型层根除；用来源标记和过滤降低成功率，用最小权限、执行层授权、人工确认和沙箱隔离限制最坏后果。"

6.22 框架与系统集成：LangChain、LangGraph、LLM Gateway

为什么需要框架。 自己写循环只要几十行（6.2），生产系统还需要模型适配、状态持久化、断点恢复、人工介入、流式输出，框架把这些做成部件。"Agent"一词指三个层次：产品（装好的车）、SDK / 运行时（发动机和底盘）、框架（零件和图纸，如 LangChain、LangGraph）。[2]

LangChain 与 LangGraph 的核心区别。 LangChain 为模型、提示、工具、检索器提供统一的抽象和预置的 Agent 循环，适合快速搭建。LangGraph 是更底层的编排运行时，把流程显式地建模为状态图：节点是函数（调用模型或执行确定性代码），边（包括条件边）决定下一个节点，所有节点读写同一个共享状态；它支持环、检查点持久化和人工介入。截至本书写作时，LangChain 1.x 的 create_agent 就运行在 LangGraph 之上。[34]

状态图：条件边做路由，可以有环，每个节点结束后状态写入检查点

模型与系统代码的职责边界。

交给模型交给代码
理解意图、抽取信息认证、授权、权限检查
选择工具与参数（提议）参数校验、执行、重试、幂等
阅读结果、组织语言金额计算、规则判断、状态机流转
生成摘要与解释终止条件、预算、日志、审计
处理开放、模糊的输入一切可以确定性实现的约束

一句话：模型负责"理解和提议"，代码负责"决定和执行"。

微服务怎样接入 Agent：

  • 服务作为工具：把接口包装成工具或 MCP Server，只暴露必要的接口，调用时携带用户本人的令牌，由下游按原有的权限判断。
  • Agent 作为服务：无状态部署，会话状态放在外部存储中，便于水平扩展，长任务采用异步加回调。
  • 治理：工具调用经过 API 网关做限流、熔断和追踪，写接口要求提供幂等键。

LLM Gateway 设计。 在应用和各家模型服务之间加一层网关，统一处理横切问题：

网关统一接口格式，业务方换模型只改路由配置

关键设计：统一请求与响应格式；按租户分配密钥、配额与预算；按任务类型、成本、数据敏感级别路由（敏感数据只走私有模型）；429、5xx 退避重试，超阈值切备用模型并熔断；请求组装照顾前缀缓存；脱敏、审计、token 计量、流式透传。

顺带会问的三个名词。 AI 应用开发工程师把模型接进业务（提示、RAG、工具、外壳、评估、上线），算法工程师改模型本身（数据、训练、微调、推理优化）。** AI Native** 指产品从设计起就围绕模型能力重构流程（"用户说目标、系统办完"），而非在旧界面上加个聊天框。端侧 AI 在手机或终端上跑小模型：延迟低、数据不出设备、可离线，但算力和内存有限，常让端侧处理简单与隐私敏感请求，复杂的回云端。

要点： LangChain 与 LangGraph 的区别标准答案："LangChain 偏组件和预置链，LangGraph 用显式状态图编排，支持循环、检查点持久化和人工介入，适合需要可控流程的生产级 Agent。"

6.23 系统设计题：企业级 RAG、多 Agent 客服、流式 RAG

为什么要有固定的答题结构。 系统设计题没有唯一的答案，面试官看的是思路是否完整。每道题都按五步回答：** 需求、估算、架构图、关键设计、瓶颈**。

题一：日均 100 万次查询的企业级 RAG

需求。 员工查询内部制度与产品文档；文档 50 万份、每天更新约 1%；回答带引用；按部门权限隔离；p95 延迟 3 秒内（流式首字 1 秒内）；可用性 99.9%。

估算。 平均 QPS ≈ 11.6，峰值按 3 倍约 35；每次请求平均 4 秒，在途约 139（6.19）。文档切块：50 万份 × 平均 40 块 = 2000 万块；768 维 float32 原始向量约 61 GB，加上 HNSW 图结构，需要分片部署。token：每请求输入 3000、输出 300，峰值输入约 10.4 万 token/s。

在线链路无状态可扩展；离线管道由文档变更事件驱动增量更新

关键设计：

  • 每个文本块带有部门和密级标签，服务端按用户身份预先过滤，缓存键包含权限组。
  • 文档变更时发送消息，离线管道只重新处理变更的文档，旧的文本块标记为失效。
  • BM25 和向量检索各召回 50 条，用 RRF 融合后再 Rerank，取前 5 条。
  • 只依据证据作答，标注引用，证据不足时拒绝回答。
  • 每天回归测试 Recall@k 和忠实度，线上抽检。
  • 多副本、多个模型供应商；Rerank 故障时降级为直接使用 RRF 的结果。

瓶颈。 生成模型配额与 GPU、Rerank 的 GPU、高过滤比例下的向量召回、换嵌入模型时的全量重建（需双写过渡）。

题二：多 Agent 智能客服

需求。 处理咨询、账单查询、挂失、投诉；能办理部分业务（冻结卡片）；高风险操作必须人工确认；可转人工；多渠道（App、网页、电话转写）。

估算。 日会话 20 万，平均每会话 6 轮，每轮平均 2 次模型调用，日模型调用约 240 万次。

Supervisor 模式：子 Agent 各有最小工具集，所有写操作经统一执行层

关键设计：

  • 采用 Supervisor 模式，便于审计；子 Agent 的工具按职责裁剪，咨询 Agent 没有写操作的工具。
  • 办理类操作只生成待确认的操作单（类型、卡号末四位、金额），用户确认后由执行层按用户身份执行，确认操作与操作单的哈希绑定。
  • 会话状态和计划锚点存放在外部存储中，转人工时附上结构化的摘要。
  • 每个会话设置步数和 token 上限，连续两次无法理解就转人工。
  • 按意图分桶统计完成率、转人工率和首次解决率。

瓶颈。 多 Agent 的 token 成本、路由错误的连锁影响、高峰期坐席容量、核心系统接口限流。

题三：支持流式输出的 RAG

需求。 回答逐字显示，首字延迟 1 秒内；网络抖动后能续传；引用在答案结束时可点击；用户可以中途停止。

先推送来源，再推送增量文字，最后推送结束事件与引用校验

关键设计：

  • 检索和重排先完成，可以先推送一条“来源”事件。
  • 生成阶段用 SSE 推送增量事件，每个事件带有递增的 id；生成任务与连接解耦，事件写入按请求分组、设有过期时间的缓冲区。
  • 重连时带上 Last-Event-ID，从缓冲区补发；缓冲已过期时返回完整的答案。
  • 用户停止时取消生成并释放资源。
  • 结束事件附上引用的校验结果。
  • 网关对 SSE 关闭响应缓冲，并调大空闲超时。

瓶颈。 长连接数量、事件缓冲内存；首字延迟主要取决于检索加重排，可缓存热门问题的检索结果。

要点： 系统设计题按以下顺序回答：需求（功能需求和非功能需求）、估算（QPS、并发、存储、token）、架构图、关键设计（权限、更新、检索、生成、评估、高可用），最后是瓶颈与扩展。

单选 · 理解检查 31　面试官问“MCP 和 A2A 是替代关系吗”，下列哪个回答最准确？

A. 互补：MCP 让 Agent 接入工具和数据，A2A 让不同 Agent 互相委派任务

B. A2A 是 MCP 的新版本

C. MCP 负责授权，A2A 负责执行

D. 二者只能选其一

查看答案与每个选项的解析

A · 正确：两者连接的两端不同，一个 Agent 可同时使用两者。

B · 错误：两者是不同组织提出、解决不同连接问题的协议。

C · 错误：两者都不替代外壳的授权与执行。

D · 错误：可以同时使用。

小结： 回答原理题时先说定义，再说机制，最后说取舍；每道题最终都要落到谁来决定、谁来执行、怎样停止、怎样验证。

6.25 附录：行为面准备框架

为什么需要准备框架。 题单前 18 题是行为面题。这类题没有标准答案，但有标准结构。本节只给结构，经历要用你自己真实做过的事来填。

STAR 法。 讲任何一段经历都分为四部分：** S**ituation，背景，即什么项目、有什么约束；Task，任务，即你负责什么、目标是什么，最好带有数字；Action，行动，即你做了哪些决定和动作，用“我”而不是“我们”，并讲清为什么这样选择；Result，结果，用数字说明，再加一句反思：如果重做会改变什么。

用 STAR 准备一个 Agent 项目的讲述（填你自己的内容）

1 / 4

第1步 · S：一句话讲背景与痛点

2 / 4

第2步 · T：你的职责与可量化目标

3 / 4

第3步 · A：两到三个关键决策，每个讲“考虑过什么、为什么选这个”

4 / 4

第4步 · R：结果数字 + 反思

项目讲述的结构（例如“分析你最核心的 Agent 项目”）。 准备 2 分钟和 10 分钟两个版本，依次讲：业务问题；能在白板上画出的架构图（参照 6.1 的五个组成部分和 6.2 的循环）；你负责的部分；一个难点（如死循环、调错工具、召回率低）的现象、定位与解决；评估方法与结果；还不完善的地方。图上的每个框都要能讲两层：它做什么，出错时怎么办。

单选 · 理解检查 32　用 STAR 讲项目时，下列哪一句最适合放在 R（Result）部分？

A. 上线后任务完成率从 72% 提到 85%，如果重做我会更早建评测集

B. 我们团队用了很多先进框架

C. 项目背景是客服压力大

D. 我负责检索模块

查看答案与每个选项的解析

A · 正确：结果有数字对比，并带一句反思。

B · 错误：既没有说明你的动作，也没有结果数字。

C · 错误：这是 Situation。

D · 错误：这是 Task。

易错点：

  • 用"我们"讲完全程，面试官分不清你个人做了什么；Action 部分多用"我"。

小结： 讲经历用 STAR 法的四部分，讲项目按六个步骤，观点题先表态再举例；所讲的经历必须真实。
